# fan-session-analytics

Расширение FAN для анализа истории сессий: читает JSONL-сессии (read-only), считает детерминированные метрики (13 детекторов D1–D13), опционально подключает LLM-судью (режим `full`), формирует markdown-отчёты и балл качества 0–100.

Спецификация: `docs/specs/spec_session-analytics_2026-08-02.md` (в монорепозитории FAN).

## Возможности (этап A)

- **Парсер сессий** — потоковое чтение JSONL через `parseSessionEntries()`, фильтрация мусорных сессий, толерантность к битым строкам
- **Нормализатор траекторий** — восстановление main branch по `id`/`parentId`, детекция скилов и воркеров оркестратора
- **13 детекторов**:
  - D1 ошибки инструментов · D2 петли · D3 длительность шагов · D4 эффективность пути
  - D5 флоу оркестратора (implement без verify и др.) · D6 использование скилов · D7 инструменты расширений
  - D8 уплотнения контекста · D9 токены/стоимость · D10 брошенные вызовы
  - D11 пропорциональность флоу (тяжёлый пайплайн на мелкой задаче)
  - D12 маршрутизация воркеров (эвристика соответствия типа воркера задаче)
  - D13 пустые ретраи
- **Отчёты** — markdown в `.fan/reports/session-analytics/`, балл 0–100, находки по severity с доказательствами
- **Интерфейсы** — инструмент `session_analyze` + slash-команда `/session-analytics`

## Установка

Скопировать в каталог расширений FAN и перезапустить:

```powershell
# Windows (глобально)
xcopy /E /I extensions\fan-session-analytics "%USERPROFILE%\.fan\agent\extensions\fan-session-analytics"
```

```bash
# Linux/macOS (глобально)
cp -r extensions/fan-session-analytics ~/.fan/agent/extensions/
```

Проектная установка: в `.fan/extensions/` внутри проекта.

## Использование

| Вызов | Что делает |
|-------|-----------|
| `/session-analytics init` | Мастер первоначальной настройки (интерактивный) |
| `/session-analytics config` | Просмотр эффективной конфигурации с источниками |
| `/session-analytics last` | Анализ последней сессии текущего каталога |
| `/session-analytics dir` | Пакетный анализ всех валидных сессий каталога |
| `/session-analytics <путь>` | Анализ конкретного JSONL-файла |
| `/session-analytics mark-golden [last\|<путь>] [метка...]` | Пометить сессию как эталонную (F12) |
| `/session-analytics golden` | Список эталонных сессий (F12) |
| `/session-analytics unmark-golden <sessionId>` | Удалить эталонную сессию (F12) |
| tool `session_analyze` | То же из промпта; параметры: `target`, `mode`, `since`, `batchSize` |

### Режим `full` и LLM-судья (этап B)

В режиме `full` после детерминированных детекторов подключается LLM-судья. Судья оценивает сессию по **6 рубрикам**:

| Рубрика | Что оценивает |
|---------|---------------|
| Уместность скилла | Правильно ли выбран инструмент/скилл для задачи |
| Полнота решения | Насколько полно выполнен запрос пользователя |
| Экономичность | Эффективность расхода токенов и вызовов |
| Соответствие правилам | Соблюдение конвенций и правил проекта |
| Качество декомпозиции | Правильность разбиения на подзадачи (только для оркестратора) |
| Качество оркестрации | Эффективность маршрутизации воркеров (только для оркестратора) |

**Combined score:** `deterministic × 0.6 + judgeScore × 0.4` (когда судья доступен).

**Расход:** типичный вызов — 1–3 батча × ~2k input + ~300 output токенов. Настраивается через `judge.batchMaxSteps`, `judge.batchMaxChars`, `judge.excerptLimit`.

**Деградация при недоступности модели:** если судья не может выбрать модель (ни сконфигурированная, ни cheapest из registry, ни currentModel), все рубрики получают `n/a`, combined score = deterministic score (без штрафа). В отчёте выводится пометка «Судья недоступен».

Если `config.json` не создан, расширение работает на встроенных дефолтах. Команды анализа и tool `session_analyze` выводят подсказку: `ℹ️ Расширение работает на дефолтах. Настройка: /session-analytics init`.

## Авто-режимы (этап C)

### F9. Авто-анализ при завершении сессии

При `autoAnalyze.enabled: true` расширение подписывается на событие `session_shutdown` и в фоне запускает детерминированный анализ текущей сессии (режим `metrics`, без LLM-судьи). Результат сохраняется в `state.json`.

При старте следующей сессии (`session_start`) выводится однострочная сводка (один раз):

```
Аналитика прошлой сессии: 87/100, петель: 0, ошибок: 2, overhead: 45% — отчёт: .fan/reports/session-analytics/…
```

**Фильтры:**
- Мусорные сессии (Temp, < minEntries) — пропуск.
- Сессии с вызовами `session_analyze` (самоссылание, BR3) — пропуск.
- Ошибки анализа не роняют FAN — все try/catch.

### F10. Еженедельный пакетный анализ

При `weeklyBatch.enabled: true` расширение при `session_start` проверяет `lastBatchRun` в `state.json`. Если прошло ≥ 7 дней — запускает пакетный анализ.

**Поведение:**
- Если `weeklyBatch.silent: false` — показывается подтверждение: «Запустить еженедельный анализ сессий? (~N файлов)».
- При отказе — анализ откладывается на 1 день (не спрашивает на каждом старте).
- Scope: все сессии каталога текущего cwd, изменённые за последние 7 дней, с фильтрами мусора и BR3.
- Режим: `metrics` (судья не вызывается — 0 токенов).
- Лимит: `batchSize` из конфига (дефолт 20).

**Сводный отчёт:** markdown в `.fan/reports/session-analytics/weekly_<дата>.md`:
- Таблица сессий (балл, находки по severity)
- Тренд-блок (↑/↓ против прошлого периода): средний балл, находки по severity, топ-3 детектора
- Уведомление о завершении через `notify` с путём к отчёту

**Защита от параллельного запуска:** флаг `weeklyRunning` в памяти.

## Золотые траектории (F12)

Эталонные сессии — «золотой стандарт» работы агента. Помеченная сессия сохраняется в `state.json` и используется для семантического сравнения с новыми сессиями того же каталога.

### Управление эталонами

| Команда | Действие |
|---------|----------|
| `/session-analytics mark-golden last [метка...]` | Пометить последнюю сессию эталонной |
| `/session-analytics mark-golden <путь> [метка...]` | Пометить конкретную сессию |
| `/session-analytics golden` | Список всех эталонов |
| `/session-analytics unmark-golden <sessionId>` | Удалить эталон |

Повторная пометка той же сессии (по sessionId) обновляет метку и путь.

### Сравнение с эталоном

В режиме `full` после обычного прогона судьи выполняется **один дополнительный вызов** LLM-судьи: компактные саммари текущей и эталонной траекторий (по 1 батчу каждая) сравниваются с промптом «сравни два прогона одной задачной области».

**Результат** — секция отчёта «Сравнение с эталоном (golden)»:
- `alignment` (0–3): насколько текущая сессия соответствует эталону
- Таблица отклонений по аспектам (аспект / текущая / эталонная / оценка)
- Текстовый verdict

При недоступности судьи или невалидном ответе — секция «n/a». В режиме `metrics` сравнение не выполняется (0 токенов).

### Хранение

Эталонные сессии хранятся в `state.json` в поле `golden`:
```json
{
  "golden": [
    {
      "sessionId": "...",
      "path": "/path/to/session.jsonl",
      "label": "эталонный багфикс",
      "markedAt": "2026-08-01T10:00:00.000Z",
      "firstRequest": "первые 300 символов запроса пользователя"
    }
  ]
}
```

## Майнинг паттернов (F13)

В пакетных режимах (`dir` и weekly batch) после анализа всех сессий выполняется **майнинг паттернов** — поиск повторяющихся последовательностей в наборе траекторий.

### Типы паттернов

| Тип | Что ищет | Предлагаемый артефакт |
|-----|---------|----------------------|
| `worker_chain` | Последовательности типов воркеров (длина 2–4), например `explore→implement→verify` | 👷 Воркер (новый тип или готовая цепочка) |
| `tool_sequence` | 3-граммы tool_call имён, например `read→edit→bash` | 🔧 Скилл |
| `prompt_template` | Схожие промпты воркеров (Jaccard ≥ 0.7 после нормализации) | 👷 Воркер или 🔧 Скилл |

### Пороги

- Минимум `orchestration.patternMinSessions` (дефолт 3) сессий с паттерном
- Для `tool_sequence`: дополнительно ≥ 3 суммарных вхождений

### Секция в сводном отчёте

«Рекомендации по синтезу» — таблица паттернов с частотой, примерами сессий и черновиком предложения. Пометка: **«Применение — только после подтверждения пользователем (BR4)»**.

Если паттернов нет — строка «Повторяющихся паттернов не найдено (порог: N сессий)».

### Отключение авто-режимов

Через `/session-analytics init` или вручную в `config.json`:

```json
{
  "autoAnalyze": { "enabled": false },
  "weeklyBatch": { "enabled": false }
}
```

### Файл состояния

`state.json` хранится рядом с `config.json` в каталоге расширения. Содержит:
- `lastBatchRun` — ISO-дата последнего еженедельного прогона
- `lastAutoSummary` — результат последнего авто-анализа (балл, метрики, путь к отчёту)
- `previousBatchStats` — статистика прошлого еженедельного прогона (для тренда)
- `analyzedMtimes` — mtime проанализированных файлов
- `weeklyDeferredUntil` — до когда отложен еженедельный анализ после отказа
- `golden` — массив эталонных сессий (F12, обратно-совместимо: отсутствие поля → `[]`)

При обновлении через FAN Store `state.json` сохраняется (preserve в DEPLOY.toml).

## Конфигурация

Необязательна — работает на дефолтах. Рекомендуемый способ настройки — команда `/session-analytics init`, которая проведёт через интерактивный мастер и сохранит `config.json` атомарно.

### Мастер `/session-analytics init`

Мастер проводит через следующие шаги:

1. **Автоанализ при завершении сессии** — вкл./выкл.
2. **Еженедельный пакетный анализ** — вкл./выкл.
3. **Порог coordination overhead** — число 0.1–1.0.
4. **Тяжёлые скилы** — мультиселект из списка установленных скилов (обнаруживаются из `~/.fan/agent/skills/*/SKILL.md` и `<cwd>/.fan/skills/*/SKILL.md`). Текущие значения из конфига предвыбраны. Если скилы не найдены — fallback на текстовый ввод.
5. **Каталог отчётов** — путь относительно cwd.
6. **Модель-судья** (этап B) — двухшаговый выбор: сначала провайдер (из `modelRegistry.getAvailable()`), затем модель этого провайдера. Пункт «Не настраивать» пропускает шаг. Если registry пуст — шаг пропускается автоматически.

Альтернативно: скопируйте `config.example.json` → `config.json` рядом с расширением и отредактируйте вручную.

### Приоритет источников (от низкого к высокому)

1. **defaults** — встроенные значения `DEFAULT_CONFIG` в `src/config.ts`
2. **config.json** — файл в каталоге расширения (`extensions/fan-session-analytics/config.json`)
3. **project override** — `<проект>/.fan/session-analytics.config.json` (наивысший приоритет)

Команда `/session-analytics config` показывает эффективную конфигурацию с пометкой источника каждой секции.

### Ключи конфигурации

| Секция | Ключ | Тип | Описание |
|--------|------|-----|----------|
| `judge` | `provider` | string | Провайдер LLM-судьи (этап B) |
| `judge` | `model` | string | Модель судьи (этап B) |
| `judge` | `batchMaxSteps` | number | Макс. шагов в сессии для пакетного анализа |
| `judge` | `batchMaxChars` | number | Макс. символов текста для анализа |
| `judge` | `excerptLimit` | number | Лимит символов в excerpt находки |
| `autoAnalyze` | `enabled` | boolean | Авто-анализ при завершении сессии (этап C) |
| `autoAnalyze` | `mode` | `"metrics"` \| `"full"` | Режим анализа |
| `weeklyBatch` | `enabled` | boolean | Еженедельный пакетный анализ |
| `weeklyBatch` | `silent` | boolean | Тихий режим (без уведомлений) |
| `filters` | `excludePathPatterns` | string[] | Паттерны исключения путей сессий |
| `filters` | `minEntries` | number | Мин. записей для анализа сессии |
| `orchestration` | `overheadRatioWarn` | number | Порог предупреждения о coordination overhead (0.1–1.0) |
| `orchestration` | `heavySkills` | string[] | Список тяжёлых скилов |
| `orchestration` | `smallChangeLines` | number | Порог «мелкого изменения» (строки) |
| `orchestration` | `smallChangeFiles` | number | Порог «мелкого изменения» (файлы) |
| `orchestration` | `retryPromptSimilarity` | number | Порог схожести промптов для D13 (0–1) |
| `orchestration` | `patternMinSessions` | number | Мин. сессий с паттерном для рекомендации синтеза (F13) |
| `reports` | `dir` | string | Каталог отчётов (относительно cwd) |
| `detectors` | `idleThresholdMin` | number | Порог простоя (минуты): интервалы > этого значения исключаются из метрик D3 как user-idle (дефолт 15) |
| `detectors` | `d12Enabled` | boolean | Включить детектор D12 (маршрутизация воркеров). Дефолт `true` |

При обновлении через FAN Store `config.json` сохраняется (preserve в DEPLOY.toml).

## Безопасность данных

- Файлы сессий **только читаются** (проверяется smoke-тестом по mtime/size)
- Запись — только отчёты, `config.json` и `state.json`
- Парсинг — только `parseSessionEntries()`; `SessionManager.open()` не используется (может перезаписать файл при миграции)
