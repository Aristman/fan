# Backlog: Развитие таск-листа FAN (персистентность и восстановление)

> Дата: 2026-08-10 · Статус: предложено · Приоритет: P1 · Источник: инцидент pipeline сверх-оркестратора (таск-лист из 18 задач теряется при перезапуске FAN)

## Цель

Сделать таск-лист оркестратора переживающим перезапуск процесса: длинные пайплайны (десятки задач, часы работы) должны восстанавливать доску задач после рестарта FAN, смены сессии или обрыва — без ручного пересоздания.

## Проблема (подтверждено кодом, 2026-08-10)

- `TaskManager` (`extensions/fan-orchestrator/task-manager.js:11`) хранит задачи в `new Map()` — только память процесса.
- Метод `serialize()` (строка ~273, «for session persistence») написан, но **нигде не вызывается** — мёртвый код.
- Нет записи ни в сессионный JSONL, ни в Prisma, ни в `.fan/`.
- Последствия: после перезапуска `list_tasks` пуст; все taskId недействительны; дашборд/виджет задач пустеют; координатор обязан восстанавливать доску из внешних артефактов (roadmap/pipeline-report).

## Что нужно сделать

### P1 — Минимум (персистентность)

1. **Сериализация в сессионный JSONL.** Подключить существующий `serialize()` к механизму custom messages сессии (паттерн: запись custom entry при каждом TaskCreate/TaskUpdate или snapshot при `session_shutdown`). Восстановление при `session_start` / `switchSession`: прочитать последний snapshot → `new Map(entries)`.
2. **Десериализация.** Сейчас её нет вообще — написать `deserialize(entries)` с валидацией статусов (`ALL_STATUSES`) и восстановлением двунаправленных связей blocks/blockedBy.
3. **Семантика in_progress при восстановлении.** Задача в `in_progress` после краша — не факт, что воркер жив. При restore переводить `in_progress` → `pending` с пометкой `recovered: true` (или failed — решить и задокументировать).
4. **Тесты:** roundtrip serialize/deserialize; restore после «краша»; blocks-связи восстановлены; TaskClear не затирает pending при записи snapshot.

### P2 — Удобство и наблюдаемость

5. **API для клиентов.** REST `GET /api/tasks` (+ WS-событие `task_update`) — дашборд и TUI-виджет смогут показывать доску после рестарта, не спрашивая LLM.
6. **Связь задача ↔ коммит.** Поле `commitSha` в задаче (заполняет координатор) — после восстановления видно, что реально закоммичено.
7. **Указатель на внешний источник истины.** Поле `externalRef` (путь к roadmap/pipeline-report) — протокол восстановления подсказывает, откуда пересоздать доску, если snapshot устарел.

### P3 — Стратегическое

8. **Реconciliaция при старте.** Опционально: сравнить восстановленную доску с git log/roadmap — задачи «completed», чьих коммитов нет, подсветить как подозрительные (полезно для миссий сверх-оркестратора).
9. **Привязка к mission-loop.** Когда появится fan-mission: доска задач миссии должна жить в `.fan/missions/<slug>/` (файловое состояние уже переживает всё) — единый принцип «диск = источник правды».

## Зависимости

- Сессионная персистентность FAN: JSONL custom entries (формат pi). Проверить, что custom messages переживают compaction.
- Не ломать существующие тесты оркестратора (158/158 в extensions/fan-orchestrator).

## Риски

- Snapshot-рассинхрон при частых TaskUpdate (писать snapshot на каждое изменение vs периодически — trade-off; начать с записи на каждое изменение, объёмы малы).
- Старые сессии без snapshot'ов — restore должен молча работать с пустой доской (backward compat).
- Не путать с `.fan/tracking/phase-status.json` из скилла feature-pipeline (v3.1.0) — тот механизм в текущем рантайме отсутствует; если оба появятся — унифицировать, не плодить два стора.

## Критерий готовности

`fan` → создать 3 задачи (pending/in_progress/completed) → перезапустить процесс → восстановить сессию → `list_tasks` показывает все 3 в корректных статусах, blocks-связи целы, `in_progress` обработан по п.3.
