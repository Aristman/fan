# План использования fan-session-analytics

> Дата: 2026-08-02 · Версия расширения: 1.3.x · Статус: принято в эксплуатацию

## Цель

Превратить историю сессий FAN из мёртвого архива в управляемый контур самоулучшения агента: каждая правка промптов, скилов и оркестратора должна быть **измеримой** через метрики и тренды, а не интуитивной.

## Принципы

1. **BR4 нерушимо.** Расширение рекомендует — человек применяет. Автоматических правок промптов/скилов по оценкам судьи не будет никогда.
2. **Метрики бесплатны, судья — по запросу.** Детерминированный слой (0 токенов) — повседневный инструмент; LLM-судья — для осмысленных разборов и калибровки.
3. **Одна находка = одна правка = одно измерение.** Не менять несколько вещей разом — иначе тренд не атрибутируется.
4. **Отчёты — единый архив.** Все отчёты централизованы (глобальный каталог), сессии анализируются один раз, дальше участвуют только в сравнительных недельных сводках.

## Ритуалы использования

### Ежедневно (пассивно, F9)
- Авто-анализ при завершении сессии → однострочник при следующем старте.
- Действие: если балл < 60 или есть 🔴 — открыть отчёт, понять причину. Если понятно, что пошло не так — сразу зафиксировать (правка промпта/скилла или заметка в backlog).

### Еженедельно (активно, F10 + ручной разбор, ~20 минут)
1. Принять еженедельный пакетный анализ (confirm при старте).
2. Открыть `weekly_<дата>.md`: тренд среднего балла и находок против прошлой недели.
3. Разобрать топ-3 повторяющихся находки: это кандидаты на правки (CLAUDE.md, SOUL.md, скиллы, описания воркеров оркестратора).
4. Применить ОДНУ правку (принцип 3). Записать гипотезу: «правка X снизит находки детектора Y».
5. Прочитать секцию «Рекомендации по синтезу» (F13): если паттерн ≥ 5 сессий — рассмотреть создание скилла/воркера через fan-forge.

### После изменения промптов/скилов (по событию, F12)
1. Прогнать 1–2 типовые задачи.
2. Full-анализ новых сессий → «Сравнение с эталоном»: alignment ≥ 2 — изменение не сломало флоу; < 2 — разобрать отклонения.
3. Помечать новые эталоны `mark-golden`, когда сессия прошла образцово.

### Ежемесячно (калибровка судьи, ~30 минут)
1. Взять 3–5 сессий, вручную оценить по рубрикам (0–3), сравнить с оценками судьи.
2. Расхождение > 1 балла систематически → уточнить критерии рубрик в `src/judge/rubrics.ts` или сменить модель судьи.
3. Пересмотреть пороги в конфиге (`overheadRatioWarn`, `patternMinSessions`) по накопленной статистике.

## Метрики успеха самого контура

| Метрика | Цель через 2 месяца | Источник |
|---------|--------------------:|----------|
| Средний недельный балл | ≥ 80 и растёт | weekly-отчёты |
| Сессии с 🔴 находками | < 15% | weekly-отчёты |
| D4 (перечитывания) | −50% к базовой неделе 2026-08-02 | тренд по детекторам |
| D11 (overhead оркестратора) | p95 < 40% | тренд по детекторам |
| Новые скиллы/воркеры из F13 | ≥ 1 принятый | лог синтеза ниже |

Базовая неделя (2026-08-02): средний балл ~70 (25 сессий), топ-нарушители D4 (9 сессий), D12 (8), D11 (до 82%).

## Правила эксплуатации

- Не анализировать сессии самого анализа всерьёз (self-reference шум) — они помечаются и пропускаются автоматически.
- Мусорные сессии (Temp, < 5 записей) исключены из статистики — не считать их отсутствие багом.
- Оценки судьи — индикатор, не истина: спорную рубрику проверять глазами по ссылкам на шаги.
- `state.json` и `config.json` — живут в каталоге расширения, переживают обновления (preserve), в git не попадают.
