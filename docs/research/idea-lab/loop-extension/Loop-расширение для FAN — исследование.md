# Loop-расширение для FAN — исследование

## Метаданные
- **Дата:** 2026-06-09
- **Тип идеи:** Техническая
- **Глубина:** Стандартный
- **Статус:** Исследовано

## 1. Ядро идеи

> В Claude Code внедрили фичу «петля» (loop): зацикленность работы над задачей, пока не будет достигнут результат. Нужно реализовать аналогичный функционал для FAN — либо внутри оркестратора, либо как отдельное расширение или скил.

### Цель
Создать механизм для FAN, позволяющий автономно выполнять задачу в цикле: задаётся промпт + критерии приёмки → агент работает → результат проверяется → если критерии не выполнены, запускается снова с контекстом предыдущих попыток.

### Дополнительные уточнения от пользователя
- **Формат:** отдельное расширение для FAN Store
- **Тип петли:** итеративная разработка (повторять задачу до выполнения критериев)
- **Интерфейс:** слэш-команда `/loop`, которая запрашивает промпт на разработку и критерии приёмки
- **Управление:** внешний контроль — расширение управляет циклом, запускает агента, проверяет результат и решает, продолжать или завершить

## 2. Исследование

### 2.1 Проблема

**Проблема:** Агент (LLM) пишет код, сообщает «готово», но в реальности код может не работать, не интегрироваться с остальной системой или не соответствовать критериям. Это фундаментальная проблема AI-кодинга: «код существует» ≠ «код работает».

**Для кого:** Разработчики, использующие FAN для автономного выполнения задач. Особенно ценно для:
- Ночных прогонов («запустил и пошёл спать»)
- Больших рефакторингов (миграция фреймворков, обновление зависимостей)
- Test coverage (генерация тестов для непокрытых функций)

**Насколько острая:** Высокая. Без верификации в цикле агент может «успешно выполнить» задачу, оставив неработающий код.

### 2.2 Что уже существует в Claude Code

Исследование показало три связанные, но разные фичи:

#### 2.2.1 Ralph Wiggum Plugin (оригинальная концепция)
🔗 https://paddo.dev/blog/ralph-wiggum-autonomous-loops/

Первый и самый известный подход. Плагин для Claude Code, перехватывающий попытку агента завершиться (Stop hook, exit code 2) и заново подающий исходный промпт. Механически это bash-цикл: `while :; do cat PROMPT.md | claude; done`.

**Ключевые элементы:**
- `--max-iterations N` — лимит итераций (защита от бесконечных циклов)
- `--completion-promise "text"` — стоп-слово: когда агент выводит этот текст, цикл останавливается
- Stop hook перехватывает завершение и перезапускает
- Каждая итерация видит изменённые файлы и git history от предыдущих запусков

**Результаты из сообщества:**
- Трёхмесячный цикл создал компилятор языка программирования Cursed
- YC hackathon: 6+ репозиториев за ночь за $297 API costs
- Миграция integration tests → unit tests: 4 минуты → 2 секунды

**Ограничения:**
- `--completion-promise` полагается на точное совпадение строки — ненадёжно
- Plugin использует один session, есть проблемы с session bleed между терминалами
- Требует jq на Windows

#### 2.2.2 Claude Code /loop (шедулинг)
🔗 https://www.mindstudio.ai/blog/what-is-claude-code-loop-scheduled-recurring-tasks

Запуск задачи по расписанию (cron) внутри активной terminal-сессии. Максимум 72 часа. Не сохраняется между перезапусками. Это **другая фича** — не итеративная разработка, а периодический запуск.

#### 2.2.3 Agent Loop в Claude Code Agent SDK
🔗 https://code.claude.com/docs/en/agent-sdk/agent-loop

Встроенный цикл Agent SDK: оценить → вызвать tools → получить результаты → повторить, пока не будет ответа без tool calls. Это **внутренний цикл** каждого агента, не внешняя петля.

**Ключевые механизмы управления:**
- `max_turns` / `maxTurns` — лимит tool-use раундов
- `max_budget_usd` / `maxBudgetUsd` — лимит стоимости
- `effort` — уровень reasoning (low → max)
- `permission_mode` — авто-аппрув, план, запрет
- `hooks` — PreToolUse, PostToolUse, Stop, SubagentStart/Stop
- `compaction` — авто-суммаризация при заполнении context window

### 2.3 Практический пример: Ralph Loop Testing

🔗 https://www.nathanonn.com/claude-code-testing-ralph-loop-verification/

Nathan Onn описал рабочий процесс с 38 тест-кейсами:
1. **test plan** — все кейсы определены заранее
2. **status.json** — отслеживает статус каждого кейса (pending, pass, fail, known_issue)
3. **results.md** — человекочитаемый лог итераций
4. **prompt.md** — инструкция на каждую итерацию: прочитай статус → выбери кейс → выполни → запиши результат → проверь completion
5. **completion-promise** — `ALL_TESTS_RESOLVED`

**Ключевой принцип:** «У тебя нет памяти предыдущих итераций. Файлы — твоя память». Каждая итерация начинается с чтения status.json и заканчивается его обновлением.

### 2.5 Архитектура FAN — что уже есть

Изучение кода и документации FAN показало:

**Оркестратор (fan-orchestrator extension) уже имеет:**
- `delegate_task` tool — запуск воркеров (explore, plan, implement, verify, bug-fix, code-research, tests-impl, docs-impl)
- `TaskManager` — создание задач, обновление статусов, зависимости (blocks[])
- Worker pool — слоты, параллельность, write slot (1 implement)
- `/plan` — команда планирования (explore → plan → user approval)
- Coordinator mode — агент как менеджер, делегирующий воркерам
- Retry/fallback — `maxRetries`, fallback cloud→local
- Task widget — визуализация задач в TUI
- Config с model routing, timeouts, dangerous commands

**Что НЕ хватает для петли:**
- Механизма, который запускал бы задачу → проверял → перезапускал → проверял
- Критериев приёмки (формальных, machine-checkable)
- Статус-файла для хранения состояния итераций
- Completion detection (не по строке, а по анализу результата)

## 3. SWOT-анализ

### Strengths (Сильные стороны) 🔵
- **В FAN уже есть 80% инфраструктуры:** TaskManager, worker pool, delegate_task, config, retry. Нужно только добавить loop-логику поверх.
- **Внешний контроль** — расширение управляет петлёй, что безопаснее внутреннего цикла (агент не может «зависнуть»).
- **Архитектура расширений FAN** позволяет опубликовать в FAN Store и распространять независимо от релизов ядра.
- **Проверенная концепция** — Ralph Loop доказал эффективность в Claude Code сообществе.

### Weaknesses (Слабые стороны) 🟠
- **Стоимость токенов** — каждая итерация сжигает полный контекст. На сложной задаче 10+ итераций могут стоить $50-100+ в API credits.
- **Зависимость от качества проверки** — если критерии приёмки размыты, петля может не сойтись (бесконечный цикл) или завершиться ложным успехом.
- **Нет встроенного верификатора** для code review / test run в цикле — нужно интегрироваться с воркером verify из оркестратора.

### Opportunities (Возможности) 🟢
- **Уникальная фича для FAN Store** — ни одно другое расширение для FAN не предоставляет loop-функционал.
- **Синергия с оркестратором**: `/plan` → реализация в цикле → verify → перезапуск при FAIL — полный конвейер.
- **Можно сделать multi-model**: loop-level модель (дёшево, local) для проверки, implement-level модель (дорого, cloud) для кода.
- **Рынок растёт**: Claude Code, Cursor, Windsurf — все движутся к autonomous loops.

### Threats (Угрозы) 🔴
- **Poisoning контекста** — после N итераций context window забивается, compaction может потерять важные детали.
- **Claude Code развивается** — Anthropic может поглотить loop в ядро Claude Code, что снизит интерес к FAN-реализации.
- **Model welfare вопросы** — сообщество Claude Code обсуждает этичность loop, блокирующих выход агента.

## 4. Альтернативы

### 4.1 Альтернатива A: Отдельное loop-расширение для FAN Store (рекомендуемая)

**Суть:** Создать новое расширение `fan-loop`, которое:
- Регистрирует слэш-команду `/loop`
- В интерактивном диалоге собирает: (1) промпт задачи, (2) критерии приёмки, (3) максимальное число итераций
- Запускает цикл: воркер → сбор результата → проверка критериев → перезапуск или завершение
- Использует статус-файл (JSON) для хранения состояния между итерациями
- Для выполнения задачи использует `delegate_task` из оркестратора или собственный запуск агента через `fan --mode rpc`

**Плюсы:**
- Независимое расширение — не требует изменений оркестратора
- Можно опубликовать в FAN Store отдельно
- Чистая архитектура: одна ответственность
- Просто тестировать изолированно

**Минусы:**
- Дублирует часть логики оркестратора (запуск воркеров)
- Пользователю нужно иметь и оркестратор, и loop-расширение

**Оценка:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя |
| Время реализации | 4-6 часов (TypeScript, ~400-600 строк) |
| Риски | Низкие — изолирован от ядра |

### 4.2 Альтернатива B: Loop-мод внутри существующего fan-orchestrator

**Суть:** Добавить в fan-orchestrator новый worker type `loop` и слэш-команду `/loop`, переиспользующую существующий TaskManager, worker pool и delegate_task.

**Плюсы:**
- Максимальное переиспользование кода (TaskManager, worker pool, config)
- Единая точка управления: оркестратор умеет всё
- Нет dependency hell между расширениями

**Минусы:**
- Модификация существующего, хорошо отлаженного расширения
- Усложнение и без того плотного кода (724 строки orchestrator-extension.js)
- Нельзя опубликовать/обновлять отдельно от оркестратора
- Риск сломать существующие фичи

**Оценка:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Высокая — требует глубокого понимания orchestrator internals |
| Время реализации | 6-8 часов |
| Риски | Средние — можно сломать существующие фичи |

### 4.3 Альтернатива C: Loop как SKILL.md

**Суть:** Создать скил в формате SKILL.md, который описывает промпт для loop-работы. При вызове `/skill:loop` агент получает инструкцию «работай в цикле, используй файлы как память, проверяй критерии».

**Плюсы:**
- Минимальная реализация — просто файл с промптом
- Не требует программирования
- Мгновенный деплой

**Минусы:**
- Полагается на то, что агент сам будет соблюдать цикл (самоконтроль)
- Нет внешнего safety net — агент может просто сказать «готово» и выйти
- Нет лимита итераций, нет управления извне
- Нельзя инструментировать (статус-файлы, completion-promise)
- Это «честный словесный скил», а не программный механизм

**Оценка:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Низкая (просто написать SKILL.md) |
| Время реализации | 30 минут |
| Риски | Высокие — ненадёжно, полностью на совести модели |

### 4.4 Альтернатива D: Гибрид — SKILL.md как пользовательский интерфейс + расширение как движок

**Суть:** Скил (`/skill:loop`) отвечает за UX — сбор промпта и критериев, красивый вывод. Расширение (`fan-loop-core`) предоставляет программный движок: запуск цикла, проверку completion, управление итерациями. Скил вызывает расширение.

**Плюсы:**
- Лучшее из обоих миров: пользовательский опыт скила + надёжность расширения
- Скил можно легко модифицировать без пересборки расширения
- Движок расширения можно переиспользовать из других скилов

**Минусы:**
- Сложнее архитектура (два компонента, связь между ними)
- Нужно определить контракт взаимодействия скила и расширения
- Избыточно для MVP

**Оценка:**

| Параметр | Оценка |
|----------|--------|
| Сложность | Высокая |
| Время реализации | 8-10 часов |
| Риски | Средние — сложная архитектура |

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Бесконечный цикл (не сходится) | Средняя | Критичное | `--max-iterations` (дефолт 10), тупиковое обнаружение (если 3 последних результата одинаковы — стоп) |
| Стоимость токенов выше ожиданий | Средняя | Среднее | Предупреждение перед запуском: «до X итераций ≈ $Y». Лимит бюджета. |
| Poсkson контекста | Высокая | Среднее | Каждая итерация — свежий вызов (clean context). Использовать статус-файл как единственную память. |
| Ложный PASS (критерии проверены плохо) | Средняя | Критичное | Использовать verify worker из оркестратора для объективной проверки |
| Конфликт с оркестратором (два extension управляют воркерами) | Низкая | Среднее | Loop-расширение использует свой WorkerManager, изолированный от оркестратора |

## 6. Рекомендация

### Что делать: Альтернатива A — отдельное loop-расширение для FAN Store

**Уверенность:** 0.9/1.0

**Обоснование:**
1. **Минимальный риск для существующей системы.** Расширение изолировано, не трогает ядро, оркестратор или другие компоненты. Если что-то пойдёт не так — просто удаляется.
2. **Оптимальная сложность.** 400-600 строк TypeScript, 4-6 часов работы. Для сравнения: модификация оркестратора (Альтернатива B) потребует 6-8 часов с риском поломок.
3. **Максимальная ценность.** Пользователь получает надёжный, управляемый извне loop с safety net. SKILL.md (Альтернатива C) не даёт гарантий — агент может просто проигнорировать инструкцию.
4. **Гибкость деплоя.** Можно публиковать независимо в FAN Store, обновлять без затрагивания оркестратора.

**Компромиссы:**
- Принимаем: небольшое дублирование логики запуска воркеров. Это оправдано изоляцией и независимостью.
- Отклоняем: максимальное переиспользование оркестратора (слишком высокий риск поломок для сомнительной выгоды).

**Предупреждения:**
- ⚠️ **Без лимита итераций — опасно.** Дефолт 10, max 50. Всегда выводить предупреждение о стоимости.
- ⚠️ **Не использовать completion-promise по тексту.** Вместо этого — проверка через verify worker или формальный разбор критериев.
- ⚠️ **Каждая итерация — свежий контекст.** Не накапливать историю в context window, только в status.json.

```
│  │    verdict = checkCriteria(result)         │   │
│  │    if verdict == PASS: break               │   │
│  │    if stalemate: break                     │   │
│  │    iteration++                             │   │
│  │                                            │   │
│  └────────────────────────────────────────────┘   │
│                                                    │
│  ┌─────────────────────────────────────────────┐   │
│  │ CriteriaChecker                             │   │
│  │  - сам проверяет формальные критерии         │   │
│  │    (tests pass, build success, git clean)    │   │
│  │  - или запускает verify worker для           │   │
│  │    семантической проверки                    │   │
│  └─────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### Стек технологий

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Язык | TypeScript | Стандарт для FAN extension |
| Extension API | pi.registerCommand, pi.on, pi.registerTool | Стандартный FAN extension lifecycle |
| Запуск агента | `fan --mode rpc` | Уже используется оркестратором. Каждая итерация — свежий RPC-воркер. |
| Верификация | Verify worker (через delegate_task) или CriteriaChecker | Переиспользование существующего verify из оркестратора |
| Память итераций | status.json на диске | Проверено Ralph Loop подходом. Не зависит от контекста. |
| Completion detection | Формальная проверка (тесты, билд) + LLM-оценка критериев | Комбинация machine-checkable + semantic check |

### Интеграция

- **С оркестратором:** опционально. Если оркестратор установлен, loop использует его `delegate_task` и Verify worker. Если нет — запускает агента напрямую через `fan --mode rpc`.
- **С TaskManager:** не использует — у loop-расширения свой лёгкий CycleManager.
- **С config:** свой config.json с настройками по умолчанию (maxIterations, модель, таймауты).

### API / Интерфейсы

```
/loop "<task_prompt>" [--criteria "<criteria>"] [--max-iterations N] [--model "<model>"]
```

**Интерактивный режим (без аргументов):**
1. Расширение спрашивает: «Опиши задачу»
2. «Какие критерии приёмки?»
3. «Максимум итераций?» (default: 10)
4. Запускает цикл

**Non-interactive (всё в команде):**
```
/loop "refactor auth module to use JWT" --criteria "all tests pass, build succeeds" --max-iterations 15
```

### Глоссарий

| Термин | Определение |
|--------|------------|
| Loop / Петля | Механизм, повторяющий задачу N раз до выполнения критериев |
| Итерация | Один проход цикла: запуск агента → сбор результата → проверка |
| Критерии приёмки | Формальные (тесты проходят) или семантические (LLM-оценка) условия успеха |
| Completion promise | Стоп-слово или условие, при котором цикл завершается |
| Stalemate / Тупик | Ситуация, когда N последних итераций дают одинаковый результат без прогресса |
| Внешний контроль | Расширение управляет циклом, а не агент сам себя перезапускает |
| status.json | Файл на диске, хранящий состояние всех итераций |
| Verify worker | Воркер оркестратора, проверяющий корректность результата (тесты, линтер, code review) |
