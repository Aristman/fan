## 1. Ядро идеи (v2)

> «Я хочу получить не столько средство работы с гитхабом, сколько сделать FAN сетевым инструментом. Чтобы он не был привязан к конкретной машине, работал на VPS и я мог бы, используя его, работать с кодом в репозиториях. С разными проектами. И не только с кодом, но и другими задачами.»

### Сдвиг рамки v1 → v2

| Аспект | v1 (FAN Remote) | v2 (FAN Network Agent) |
|--------|-----------------|------------------------|
| Категория | GitHub-автоматизация (cron → PR) | Персональный облачный агент |
| Главный сценарий | Автономные задачи по расписанию | Живая работа из любой точки с любого устройства |
| Проекты | Несколько репо на инстансе | Полноценные workspaces с переключением |
| Задачи | Код → ветки → PR | Код + исследования + документы + автоматизация — всё |
| Аналоги | code-automator, OpenHands | code-server, Coder, Gitpod, Replit Agent, Devin |

### Параметры, зафиксированные в интервью
| Параметр | Решение |
|----------|---------|
| Где код | Клоны репозиториев на VPS, локальные машины — только клиенты |

## 2. Исследование

### 2.1 Категория и аналоги

V2 перемещает идею в категорию **remote development environment + AI agent**:

- **code-server** — VS Code в браузере на своём сервере; «самый простой путь к удалённой среде: один контейнер, один порт» (selfhosting.sh)
- **Coder** — self-hosted cloud development environments; позиционируется прямо как «среды для разработчиков **и их агентов**» (coder.com/docs)
- **Gitpod / Codespaces** — эфемерные облачные среды
- **Devin / Replit Agent / OpenHands Cloud** — агентные облака

Отличие FAN: не IDE с агентом сбоку, а **агент как центр**, с мульти-модельностью, скиллами, оркестратором и FAN Store. Ниша «agent-native personal cloud» пустее, чем «cloud IDE».

### 2.2 Что показал аудит кода (code research)

Полный отчёт: `.fan/reports/research-fan-workspace-mode.md`.

**Хорошие новости:**
- Сессии **уже группируются по проектам** на диске: `~/.fan/agent/sessions/--encoded-cwd--/` (session-manager.ts)
- `SessionManager.listAll()` уже умеет сканировать все проекты; `SessionInfo` содержит `cwd`
- Все ресурсы (скиллы, extensions, MCP, контекстные файлы) уже имеют двухуровневую загрузку: глобально + `<проект>/.fan/`
- Инструменты резолвят пути через `resolveToCwd()` — cwd приходит замыканием, а не глобально

**Блокеры мультипроектности:**
1. `AgentSessionRuntime` — одна активная сессия; `switchSession()` делает полный teardown + `process.chdir()` (глобальное состояние процесса)
2. API project-agnostic: нет `project`/`cwd` ни в одном endpoint, нет `GET /api/projects`
3. Dashboard: плоский список сессий, нет переключателя проектов
4. Prisma `Session` не хранит `cwd`
5. Per-project settings/MCP не перезагружаются при смене проекта в рантайме

### 2.3 Что это значит для «не только кода»

Workspace в FAN — это просто директория + `.fan/`-конфиг. Git не обязателен. Значит, модель «проект = директория на VPS» естественно покрывает:
- кодовые репозитории (клоны на VPS)
- исследовательские workspaces (idea-lab, research-spec-generator пишут в `docs/research/` проекта)
- рабочие директории автоматизации (скрипты, данные, отчёты)

Отдельной архитектуры для не-код задач не нужно — нужен workspace-режим как таковой.

## 3. SWOT-анализ (v2)

### Strengths 🔵
- Workspace-модель заложена в фундамент: сессии уже группируются по cwd, ресурсы уже двухуровневые (глобальные + проектные) — это не редизайн, а «дорыть»
- Универсальность из коробки: скиллы (idea-lab, repo-explorer, research-spec-generator) уже делают не-код задачи; workspace = директория, git опционален
- Сетевая часть (REST+WS, dashboard, токены) готова и проверена аудитом v1

### Weaknesses 🟠
- Одна активная сессия на процесс + `process.chdir()` — главный архитектурный долг для мультипроектности
- Переключение проекта = полный пересоздание сервисов (settings, extensions, skills) — без кеша будет медленно
- Dashboard не знает о проектах — UI работа с нуля

### Opportunities 🟢
- Ниша «agent-native personal cloud» свободнее, чем cloud IDE: Coder/Gitpod — про IDE, Devin — проприетарное облако
- VPS как единая точка правды: сессии, БД, скиллы, память — доступны с любого устройства, включая телефон
- Естественная эволюция: workspace-режим полезен и локально (TUI), не только на VPS

### Threats 🔴
- Scope creep: «сетевой инструмент для всего» легко превращается в бесконечный проект — нужна жёсткая фазность
- Конкуренция за внимание: если делать и workspace-режим, и автономность, и продукт — можно не закончить ни одно
- Тот же класс угроз безопасности, что в v1: публичный агент с shell — мишень

## 4. Варианты мультипроектной архитектуры

### Вариант A: Workspace-режим в одном FAN (рекомендуется)
Один процесс FAN обслуживает N проектов. API становится workspace-aware (`?project=`, `GET /api/projects`, `cwd` в сессии), dashboard получает переключатель проектов, runtime — кеш сервисов по cwd.
- **Плюсы:** один инстанс, общая БД/токены/бюджет; естественная модель; полезно и локально
- **Минусы:** нужны правки ядра (14 точек); одна активная сессия сохраняется
- **Сложность:** Средняя · **Время:** ~2–3 недели

### Вариант B: Инстанс на проект
Отдельный процесс/контейнер FAN на каждый проект, nginx маршрутизирует по поддоменам/путям, тонкий launcher поднимает инстансы по требованию.
- **Плюсы:** ноль правок ядра; изоляция проектов; масштабирование
- **Минусы:** каждый инстанс — память и модели; нет единой картины сессий; launcher — новый сервис; сложнее с не-код задачами
- **Сложность:** Средняя · **Время:** ~1–2 недели, но больше операционной сложности

### Вариант C: Гибрид (B сейчас, A потом)
Начать с launcher'а инстансов (быстрый результат без правок ядра), workspace-режим в ядре — позже как продуктовая фича.
- **Плюсы:** быстрый доступ «из любой точки» уже на первой неделе
- **Минусы:** дважды платим за архитектуру; launcher выбросить будет жалко
- **Сложность:** Средняя · **Время:** суммарно больше

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Удаление `process.chdir()` сломает неочевидные места (сторонние extensions, MCP-серверы, читающие cwd процесса) | Средняя | Среднее | Регрессионные тесты; оставить chdir при switch как временную меру, убирать в фазе конкурентности |
| Scope creep «инструмент для всего» | Высокая | Критичное | Жёсткие фазы (ниже); фаза = рабочий результат |
| Публичный агент с shell скомпрометирован | Средняя | Критичное | Из v1: обязательная auth, nginx, bot-identity для git, budget caps |
| Медленное переключение проектов без кеша сервисов | Высокая без кеша | Низкое | ServiceRegistry (кеш по cwd) — в фазе 2 |
| Один VPS = единая точка отказа для всех проектов | Низкая | Среднее | Бэкапы `~/.fan/agent` + репозитории всегда на GitHub |

## 6. Рекомендация

### Что делать: Вариант A — workspace-режим в ядре FAN, поверх контура из v1

**Уверенность:** 0.87/1.0

**Обоснование:**
1. Аудит показал: workspace-модель уже наполовину заложена в код (группировка сессий по cwd, двухуровневые ресурсы) — достройка дешевле обходных путей
2. Вариант B решает только «доступ», но не «единый инструмент»: у каждого инстанса свои сессии, бюджеты, настройки — это фрагментация, а не сеть
3. Workspace-режим полезен и локально (TUI, dashboard) — улучшение ядра, а не VPS-only костыль

**Компромиссы:**
- Принимаем: одна активная сессия на инстанс в обозримом будущем (конкурентность — отдельная поздняя фаза)
- Принимаем: правки ядра — 14 точек, из них 2 крупные
- Отклоняем: инстанс-на-проект как основную модель (фрагментация), GitHub-автономность как первый приоритет (это v1-рамка)

**Предупреждения:**
- ⚠️ Контур безопасности из v1 (auth patch, nginx, TLS, Docker) — обязательная фаза 0, без него ничего наружу
- ⚠️ Сначала API, потом UI: workspace-aware API пригодится даже без dashboard (TUI, IDE-плагины, скрипты)

## 9. Решения по итогам рецензии (2026-07-24)

Рецензия проведена через lavish-артефакт. Итоги голосования: вариант A принят («в принципе согласен, но нужно продумать риски»), порядок фаз одобрен, одна активная сессия — допустимый сценарий, модель «workspace = директория» покрывает не-код задачи, скоуп достаточен для MVP.

### 9.1 Одна активная сессия vs «сессия на задачу» — анализ

Вопрос из рецензии: «может, не делать одну активную сессию? Одна сессия для каждой задачи?»

**Разделение понятий: конкурентность СОСТОЯНИЯ vs конкурентность ИСПОЛНЕНИЯ.**

- **Состояние** сессии — это JSONL-файл на диске. Держать «открытыми» сколько угодно сессий по всем проектам бесплатно уже сейчас — `SessionManager.listAll()` их видит.
- **Исполнение** — движок runtime один; `switchSession()` сейчас делает полный teardown + recreate сервисов, поэтому переключение дорогое. С кешем сервисов (точка изменений №8) переключение становится дешёвым.

**Вывод для MVP:** «одна сессия на задачу» — это и есть целевая UX-модель: у каждой задачи своя сессия в своём проекте, dashboard показывает их сгруппированными, но **одновременно исполняется одна**. Чтобы задачи не терялись, пока занят движок, в фазу 2 добавляется **FIFO-очередь сообщений** (мьютекс + буфер на sendMessage, точка №13 переносится из фазы 5 в фазу 2 в упрощённом виде): задача для проекта B встаёт в очередь, пока выполняется задача проекта A.

**Полноценное параллельное исполнение** (несколько runtime одновременно) остаётся в фазе 5: требует удаления `process.chdir()`, изоляции сервисов и разруливания конкурентных записей в SQLite/JSONL. Для личного инструмента овчинка выделки не стоит — один движок + очередь закрывает сценарий «кинул три задачи в три проекта и пошёл спать».

### 9.2 Обратная совместимость с локальной работой FAN — анализ

Вопрос из рецензии: «не поломают ли изменения ядра существующий локальный процесс?»

| # | Изменение | Влияние на локальный TUI/dashboard | Риск |
|---|-----------|-----------------------------------|------|
| 1 | Prisma `cwd` в Session | Аддитивно, nullable. Старые сессии → fallback на cwd из JSONL-header | 🟢 Низкий |
| 2 | Project-aware API | Аддитивно: новый query-параметр, поле, endpoint. Без параметра — поведение прежнее | 🟢 Низкий |
| 3 | SessionAdapter | Внутренний; без project-параметра путь исполнения не меняется | 🟢 Низкий |
| 4 | Per-session cwd | **Самое рискованное.** Митигация: в фазах 1–2 `process.chdir()` при switch СОХРАНЯЕТСЯ; удаление — только фаза 5. Локальный однопроектный flow не затрагивается вообще | 🟡 Средний (сглажен) |
| 5 | Реестр проектов | Новый файл, аддитивно | 🟢 Низкий |
| 6 | Стартовый cwd сервера | Только server mode; TUI стартует как раньше | 🟢 Низкий |
| 7 | `listAll()` → API | Аддитивно | 🟢 Низкий |
| 8 | Кеш сервисов | Поведение-сохраняющий рефакторинг. Риск устаревших настроек → инвалидация кеша при изменении `.fan/settings.json` проекта | 🟡 Средний |
| 9–10 | Dashboard | Новый UI, локально не ломает ничего | 🟢 Низкий |
| 11 | Settings reload при switch | Сейчас switchSession и так пересоздаёт сервисы — это формализация, а не ломка | 🟢 Низкий |
| 12 | MCP reconnect | Аналогично; риск дублей подключений → тесты на reconnect | 🟡 Средний |
| 13–14 | Очередь, per-project токены | Фаза 2/5, локальный flow опционален | 🟢 Низкий |

**Итог:** локальный однопроектный сценарий (TUI) не меняется — FAN по-прежнему стартует в cwd и работает там. Все точки с риском (№4, №8, №12) закрываются поэтапностью и регрессионными тестами. Критерий приёмки каждой фазы: `npm run build` — 0 ошибок, тесты orchestrator/api-gateway зелёные, ручной прогон TUI.

### 9.3 Полный список рисков варианта A (по запросу из рецензии)

| Риск | Категория | Митигация |
|------|-----------|-----------|
| `process.chdir()` — глобальное состояние процесса, неочевидные потребители (extensions, MCP-серверы) | Архитектурный | Сохранить chdir до фазы 5; регрессионные тесты; аудит потребителей `process.cwd()` перед удалением |
| Кеш сервисов: рост памяти и устаревшие данные | Архитектурный | LRU-лимит (3–5 проектов), инвалидация по mtime `.fan/settings.json` |
| **Path traversal через `cwd`-параметр API** — публичный endpoint, принимающий произвольный путь = чтение всей ФС VPS | 🔴 Безопасность | Валидация cwd против workspace root whitelist (`~/projects/*`), каноникализация путей, отказ на symlink-выход. **Обязательно в фазе 1, до публичного доступа** |
| Конкурентные записи в JSONL при очереди | Корректность | Мьютекс per-session; одна запись за раз |
| SQLite — единственный писатель; метаданные сессий из нескольких проектов | Корректность | Записи сериализуются одним runtime — конфликта нет, пока один движок |
| Глобальный бюджет: один проект-«прожора» съест всё | Ресурсный | Per-project бюджеты — позже (фаза 4+); пока — общий cap + алерты |
| Per-project MCP-серверы плодят процессы при каждом переключении | Ресурсный | Кеш сервисов держит MCP-подключения живыми; LRU-вытеснение их закрывает |
| Старые сессии без cwd в header | Данные | Fallback: cwd из имени директории (`--encoded-cwd--`) |
| Потеря задач из очереди при рестарте сервера | Надёжность | Фаза 2: очередь in-memory (потеря = уведомление клиенту); персистентная очередь — фаза 4 вместе с scheduler |

### 9.4 Изменения плана по итогам рецензии

1. **Точка №13 (мьютекс/очередь) переносится из фазы 5 в фазу 2** в упрощённом виде (in-memory FIFO + мьютекс на sendMessage) — без этого «сессия на задачу» в нескольких проектах будет терять сообщения.
2. **В фазу 1 добавлено требование безопасности:** whitelist-валидация `cwd` относительно workspace root — публичный API не должен принимать произвольные пути.
3. Критерий приёмки каждой фазы дополнен: регрессия локального TUI-сценария проверяется вручную.
