# FAN Remote — FAN на VPS с удалённым доступом и автономной работой — исследование идеи

## Метаданные
- **Дата:** 2026-07-24
- **Тип идеи:** Техническая
- **Глубина:** Стандартный
- **Статус:** Исследовано

## 1. Ядро идеи

> «Хочу сделать инструмент, который позволит запускать FAN на VPS и подключаться к нему из любой точки. Код должен лежать в общем репозитории (GitHub или ещё каком). FAN будет работать постоянно, будет делать код и коммитить в ветки.»

### Цель
Превратить FAN из локального инструмента в постоянно работающий удалённый агент: Web UI из браузера с любого устройства, автономные фоновые задачи по расписанию, результат — ветки и Pull Request'ы на GitHub.

### Контекст
FAN уже имеет серверный режим (Hono REST + WebSocket, dashboard SPA, токен-аутентификация), но проектировался как локальный однопользовательский runtime. Идея — построить контур развёртывания и автономности вокруг существующего ядра, а не переписывать его.

### Параметры, зафиксированные в интервью
| Параметр | Решение |
|----------|---------|
| Масштаб | Личный инструмент с заделом на продукт |
| Интерфейс | Web UI в браузере (существующий dashboard) |
| Автономность | Гибрид: чат по требованию + фоновые задачи |
| Триггеры MVP | Cron / расписание (не GitHub Issues) |
| Git flow | Ветки + Pull Requests |
| Репозитории | Несколько репозиториев на одном инстансе |
| Способ доступа | Свой домен + nginx |
| Упаковка | Docker / docker-compose |

## 2. Исследование

### 2.1 Проблема и аудитория

**Проблема:** FAN привязан к локальной машине. Нельзя поставить задачу с телефона, нельзя поручить агенту ночную работу, нет постоянного исполнителя, который сам пишет код и открывает Pull Request'ы.

**Для кого:** в первую очередь сам автор FAN (личный инструмент), во вторую — пользователи FAN, желающие self-hosted persistent-агента (задел на продукт).

**Насколько острая:** для автора — высокая (основной сценарий использования). Рыночная острота подтверждается популярностью аналогов: OpenHands набрал 76K звёзд на GitHub, появляются нишевые решения (code-automator, Hermes Agent).

### 2.2 Текущее состояние FAN (аудит кода)

Проведён полный аудит server mode (отчёт: `.fan/reports/explore-fan-server-vps-audit.md`).

**Уже готово:**
- REST API — 16 endpoint'ов (сессии, сообщения, модели, бюджет, токены), `packages/api-gateway/src/http-server.ts`
- WebSocket с broadcast нескольким клиентам одной сессии, авто-reconnect, keepalive
- Мульти-токенная аутентификация (ClientToken в Prisma/SQLite), `packages/api-gateway/src/auth.ts`
- Dashboard SPA раздаётся самим сервером (serve-static + SPA fallback)
- Background daemon (`fan server start/stop/status`, PID-файлы)
- Маршрутизация моделей, fallback-цепочки, бюджетный контроль
- Bash-инструмент — агент может выполнять любые git-команды

**Критические пробелы:**
- 🔴 Нет TLS/HTTPS в коде вообще — обязателен reverse proxy
- 🔴 В server mode аутентификация принудительно отключается (`main.ts` выставляет `FAN_NO_AUTH=1`) — выставить FAN в интернет сейчас значит подарить всем shell с API-ключами
- 🟡 `PORT`/`HOST` не читаются из переменных окружения — только CLI-флаги
- 🟡 Одна активная сессия на процесс, нет очереди сообщений — race condition при параллельных триггерах
- 🟡 Нет scheduler'а, webhook'ов, очереди задач — вся автономность отсутствует
- 🟢 Нет Dockerfile, systemd unit, deployment-руководства для runtime

### 2.3 Аналоги и альтернативы на рынке

- **OpenHands** (github.com/OpenHands/OpenHands) — самый зрелый open-source автономный coding-агент, 76K★, MIT, all-in-one Docker, решает GitHub issues end-to-end, есть GitHub resolver
- **code-automator** (github.com/SardineFish/code-automator) — лёгкий self-hosted сервис: GitHub App + webhook → запускает локальные агентские CLI (codex, claude) → PR. Архитектурный референс: агент как исполнитель, оркестрация снаружи
- **Hermes Agent** — webhook-триггеры, PR review, triage, cron-отчёты
- **GitHub Copilot coding agent / Jules / Codex cloud** — облачные проприетарные аналоги, не self-hosted

### 2.4 Способы безопасного доступа к сервисам на VPS

Исследованы варианты: nginx reverse proxy + Let's Encrypt, Cloudflare Tunnel, Tailscale Funnel, Pangolin. По выбору пользователя — **свой домен + nginx + Let's Encrypt** (полный контроль, стандартная схема, уже используется для FAN Store на fan.sea-agents.ru).

### 2.5 Источники исследования

| Источник | Релевантность | Ключевые выводы |
|----------|--------------|----------------|
| Аудит кода FAN (explore worker) | Высокая | 80% серверной части готово; критические пробелы — TLS, auth, scheduler |
| [OpenHands](https://github.com/OpenHands/OpenHands) | Высокая | Главный конкурент; модель «агент как сервис» подтверждена рынком |
| [code-automator](https://github.com/SardineFish/code-automator) | Высокая | Архитектурный паттерн: внешний оркестратор дёргает агента, ядро не трогаем |
| [Tailscale vs Cloudflare Tunnel vs nginx (Onidel)](https://onidel.com/blog/tailscale-cloudflare-nginx-vps-2025) | Средняя | Сравнение способов выставления сервиса; nginx + домен — полный контроль |
| [Pangolin vs Cloudflare Tunnels vs Tailscale (Contabo)](https://contabo.com/blog/pangolin-vs-cloudflare-tunnels-vs-tailscale/) | Средняя | Cloudflare Tunnel — нулевая конфигурация, но привязка к Cloudflare |
| [OpenHands Review 2026](https://aifoss.dev/blog/openhands-review-2026/) | Средняя | Рыночный контекст: ниша растёт, self-hosted востребован |

## 3. SWOT-анализ

### Strengths (Сильные стороны) 🔵
- Полный серверный фундамент уже существует: REST API, WebSocket, dashboard, токены, daemon. Это не разработка с нуля, а достройка ~20% контура (аудит кода)
- Маршрутизация моделей + fallback + бюджетный контроль из коробки — у конкурентов для этого нужны внешние router'ы (OpenHands + Lynkr)
- Bash-инструмент даёт весь git/gh CLI без нового кода — PR-флоу реализуется скиллами и промптами, а не правками ядра

### Weaknesses (Слабые стороны) 🟠
- Нет TLS, auth авто-отключается в server mode, `PORT`/`HOST` не из env — в текущем виде публичный деплой небезопасен (аудит кода)
- Одна активная сессия, нет очереди — cron-задача и живой чат могут столкнуться с race condition в JSONL-хранилище
- Нет scheduler'а, webhook'ов, git/PR-инструментов — автономность придётся строить полностью снаружи ядра

### Opportunities (Возможности) 🟢
- Ниша «self-hosted persistent coding agent» на подъёме: OpenHands 76K★, появляются нишевые обвязки; у FAN есть отличия (оркестратор, мульти-модельность, скиллы, FAN Store)
- Стек решения скучный и проверенный: Docker + nginx + cron — никакой экзотики
- Cron-триггеры для MVP проще webhook'ов: не нужен публичный endpoint для GitHub и верификация подписей

### Threats (Угрозы) 🔴
- Автономный агент с shell и git push при ошибке или промпт-инъекции может накоммитить мусор или утечь секреты — нужна изоляция и PR-only политика
- OpenHands и облачные агенты развиваются быстро — «задел на продукт» может устареть раньше реализации
- Постоянно работающий агент = постоянный расход токенов; без жёсткого бюджетного cap ночные cron-задачи сожгут лимиты

## 4. Альтернативы

### 4.1 Альтернатива: FAN Remote (своя обвязка поверх FAN)

**Суть:** Docker-compose стек: FAN server + nginx (TLS, Let's Encrypt) + scheduler-сервис (cron → FAN API). Минимальные патчи ядра (env vars, режим публичного сервера). Git/PR через bash + `gh` CLI.

**Плюсы:**
- Сохраняется вся экосистема FAN: оркестратор, скиллы, модели, dashboard
- Полный контроль, задел на продукт именно для FAN

**Минусы:**
- Нужно патчить ядро (auth-режим, env vars)
- Очередь задач и автономность писать самому

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя |
| Время | MVP ~2–3 недели вечерами |
| Риски | Конкурентный доступ к сессии; рост сложности scheduler'а |

### 4.2 Альтернатива: OpenHands как есть

**Суть:** развернуть готовый OpenHands (all-in-one Docker, GitHub resolver) и использовать его вместо FAN для удалённой работы.

**Плюсы:**
- Работает сегодня, проверен на практике, огромное сообщество
- Issue → PR из коробки

**Минусы:**
- Это не FAN: теряются скиллы, оркестратор, маршрутизация моделей
- Чужой большой Python-codebase, кастомизация дорогая
- Дублирование усилий: две агентные платформы вместо одной

| Параметр | Оценка |
|----------|--------|
| Сложность | Низкая |
| Время | 1 день |
| Риски | Зависимость от чужой экосистемы |

### 4.3 Альтернатива: Внешний оркестратор (паттерн code-automator)

**Суть:** ядро FAN не трогаем. Отдельный лёгкий сервис на VPS: cron/webhook → клонирование репо → вызов FAN API (`POST /api/sessions/:id/messages`) → FAN через bash делает ветку и PR.

**Плюсы:**
- Ноль изменений в ядре FAN
- Сервис крошечный (~300 строк), легко выкинуть или заменить

**Минусы:**
- Auth всё равно надо включать (патч авто-отключения неизбежен)
- Две системы вместо одной: scheduler живёт отдельно от FAN

| Параметр | Оценка |
|----------|--------|
| Сложность | Низкая-Средняя |
| Время | MVP ~1 неделя |
| Риски | Костыльность при росте числа триггеров |

### 4.4 Альтернатива: Ничего не делать (SSH + tmux)

**Суть:** запустить `fan server` на VPS в tmux, подключаться по SSH.

**Плюсы:** бесплатно, работает сегодня.
**Минусы:** нет Web UI «из любой точки», нет автономности, небезопасно, не решает исходную задачу.

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| FAN выставлен в интернет с отключённой auth (server mode сам её выключает) | Высокая без патча | Критичное | Патч: флаг `--public`/env `FAN_PUBLIC=1`, запрещающий авто-отключение auth; nginx basic auth как второй слой |
| Race condition при параллельных триггерах (cron + чат) | Средняя | Среднее | Mutex/очередь в scheduler-сервисе: одна задача за раз; чат имеет приоритет |
| Агент накоммитит мусор или удалит данные на VPS | Средняя | Критичное | Контейнерная изоляция, отдельный git identity (bot-аккаунт), push только в feature-ветки, branch protection на main, PR-only |
| Утечка API-ключей провайдеров с VPS | Низкая | Критичное | Секреты только в env контейнера, не в репозитории; отдельные ключи для VPS с лимитами; budget cap |
| Ночные cron-задачи сожгут бюджет токенов | Средняя | Среднее | Жёсткий лимит через существующий budget API (`PUT /api/budget`), алерты |
| «Задел на продукт» устареет из-за конкурентов | Средняя | Низкое | Сначала личная ценность; продуктовые решения отложить |

## 6. Рекомендация

### Что делать: FAN Remote — с поэтапным внедрением по модели внешнего оркестратора

**Уверенность:** 0.85/1.0

**Обоснование:**
1. Аудит показал: 80% серверной части готово — нужен контур (Docker, nginx, scheduler), а не новое ядро
2. Паттерн code-automator доказывает: автономность правильно строить снаружи execution engine — ядро FAN остаётся чистым
3. OpenHands отклонён: он заменяет FAN, а не усиливает его — теряется весь смысл затеи

**Компромиссы:**
- Принимаем: автономность живёт вне ядра (отдельный scheduler-сервис) — это нормально и обратимо
- Принимаем: одна активная сессия на инстанс для MVP — очередь задач решает это на уровне scheduler'а
- Отклоняем: OpenHands (замена экосистемы), Cloudflare Tunnel (выбран собственный домен)

**Предупреждения:**
- ⚠️ Никогда не выставлять FAN наружу без принудительно включённой auth — текущее поведение server mode опасно
- ⚠️ Отдельный git identity для агента, push только в feature-ветки, main под branch protection
- ⚠️ Cron-задачи только с бюджетным cap через budget API

## 7. План действий

### Приоритеты (MoSCoW)

**Must Have:**
- [ ] Патч ядра: env `PORT`/`HOST`, режим публичного сервера (не отключать auth)
- [ ] Dockerfile + docker-compose (FAN + nginx + certbot)
- [ ] nginx-конфиг: TLS, проксирование REST + WebSocket, optional basic auth
- [ ] Руководство по деплою (docs)
- [ ] Scheduler-сервис: cron-задачи → FAN API, очередь из одной задачи
- [ ] Git-политика агента: bot-identity, feature-ветки, PR через `gh` CLI

**Should Have:**
- [ ] Скилл/шаблон промпта для автономных задач (ветка → код → тесты → PR)
- [ ] Liveness/readiness endpoints для мониторинга
- [ ] Структурированное логирование в файл + ротация

**Could Have:**
- [ ] Очередь сообщений в api-gateway (несколько клиентов без race)
- [ ] Read-only токены (роли)
- [ ] GitHub webhook-триггеры (issue с лейблом → задача)
- [ ] Multi-repo конфигурация через YAML

**Won't Have (пока):**
- [ ] Multi-tenancy и роли пользователей — личный инструмент, один оператор
- [ ] Kubernetes — избыточно для одного VPS
- [ ] Встроенный TLS в ядре — решается nginx

## 8. Техническая архитектура

### Схема компонентов

```
Интернет (браузер, любое устройство)
        │ HTTPS (домен пользователя, Let's Encrypt)
        ▼
┌─────────────────────── VPS ───────────────────────┐
│  nginx (TLS termination, reverse proxy,           │
│         basic auth как второй слой)               │
│        │                                          │
│        ▼                                          │
│  fan server (контейнер)                           │
│    · REST API :3456  · WebSocket                  │
│    · dashboard SPA  · auth ОБЯЗАТЕЛЬНА            │
│        ▲                                          │
│        │ HTTP (внутренняя сеть docker-compose)    │
│  scheduler (контейнер)                            │
│    · cron-расписание задач (YAML-конфиг)          │
│    · очередь: одна задача за раз                  │
│    · клонирование/обновление репо в volume        │
│                                                   │
│  volumes: ~/.fan/agent (DB, сессии), repos/       │
└───────────────────────────────────────────────────┘
        │ git push (feature-ветки) + PR (gh CLI)
        ▼
   GitHub (bot-аккаунт / GitHub App, branch protection на main)
```

### Стек технологий

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Контейнеризация | Docker + docker-compose | Выбор пользователя; стандарт self-hosted |
| Reverse proxy / TLS | nginx + certbot (Let's Encrypt) | Свой домен; уже используется для FAN Store |
| Runtime | Существующий `fan server` (Bun) | Готов на 80% |
| Автономность | Отдельный scheduler-сервис (Node/Bun или Python) | Паттерн code-automator; ядро не трогаем |
| Git/PR | bash + `gh` CLI внутри контейнера FAN | Не нужен новый код в ядре |
| Секреты | env-файл на VPS, отдельные API-ключи с лимитами | Изоляция утечек |
| Git identity | Отдельный bot-аккаунт GitHub или GitHub App | Аудит действий агента, PR-only |

### Минимальные патчи ядра FAN

1. `main.ts`: чтение `process.env.PORT` / `process.env.HOST` как fallback для CLI-флагов
2. `main.ts`: режим публичного сервера — env `FAN_PUBLIC=1` запрещает авто-выставление `FAN_NO_AUTH=1`
3. (Опционально) readiness endpoint для healthcheck docker-compose

### Оценка трудозатрат

| Задача | Сложность | Оценка | Зависимости |
|--------|-----------|--------|-------------|
| Патчи ядра (env, auth-режим) | Низкая | 1 день | — |
| Dockerfile + compose + nginx | Средняя | 2–3 дня | Патчи ядра |
| Деплой и smoke-тесты | Низкая | 1 день | Docker |
| Git-настройка (bot, `gh`, защита веток) | Низкая | 1 день | VPS |
| Scheduler-сервис (cron + очередь + API-клиент) | Средняя | 3–5 дней | VPS |
| Скилл автономной задачи | Средняя | 2 дня | Scheduler, git |
| Документация | Низкая | 1–2 дня | Всё выше |

**Итого:** ~11–15 дней (при работе вечерами — 3–4 недели)
**MVP (патчи + Docker + nginx + деплой):** ~5 дней — уже даёт Web UI из любой точки
