🌐 FAN Network Agent

Исследование v2: FAN как сетевой инструмент — не привязанный к машине, работающий на VPS, с разными проектами и любыми задачами, а не только с кодом. Рецензируемый документ — аннотируй любой блок.
v2 · заменяет рамку v1 Тип: техническая Глубина: стандартная Дата: 2026-07-24 Уверенность рекомендации: 0.87

1Решение, которое рецензируем

В v1 идея была «робот для GitHub»: cron → ветки → PR. В v2 рамка шире — FAN как персональный облачный агент: единая точка доступа ко всем проектам и задачам с любого устройства. Это меняет категорию, архитектуру и приоритеты.

v1 — FAN Remote (робот для GitHub)

  • Главный сценарий: автономные задачи по cron → PR
  • Категория: GitHub-автоматизация (code-automator, OpenHands resolver)
  • Проекты: «несколько репо на инстансе» — без переключения
  • Задачи: код → ветки → PR
  • Пользователь — редкий гость, который ревьюит PR

v2 — FAN Network Agent (сетевой агент)

  • Главный сценарий: живая работа из любой точки, с любого устройства
  • Категория: agent-native personal cloud (code-server, Coder, Devin)
  • Проекты: полноценные workspaces с переключением в Web UI
  • Задачи: код + исследования + документы + автоматизация — всё
  • Пользователь — постоянный оператор; автономность — поздняя фаза
«Не столько средство работы с гитхабом, сколько сделать FAN сетевым инструментом… работал на VPS… с разными проектами. И не только с кодом, но и другими задачами.»

2Категория и место на рынке

V2 перемещает идею из ниши «ботов для PR» в нишу «удалённых сред разработки» — но с агентом в центре, а не IDE.

РешениеЧто этоЧем FAN отличается
code-server VS Code в браузере на своём сервере; «один контейнер, один порт» Это IDE, агент — сторонний. У FAN агент — центр системы
Coder Self-hosted cloud dev environments; «для разработчиков и их агентов» Про provisioning сред для команд. FAN — персональный, агентный, без k8s
Gitpod / Codespaces Эфемерные облачные среды Облако вендора; FAN — твой VPS, твои модели, твои данные
Devin / Replit Agent Проприетарные агентные облака Закрытые, подписочные. FAN — self-hosted, мульти-модельный
OpenHands Open-source автономный агент, 76K★ Заточен под issue→PR. FAN — универсальный runtime со скиллами и оркестратором

Вывод: ниша «agent-native personal cloud» заметно пустее, чем «cloud IDE». Отличия FAN — мульти-модельность с маршрутизацией и бюджетами, 8 скиллов, оркестратор, FAN Store.

3Целевая архитектура

Один процесс FAN на VPS обслуживает все проекты. Клиент — браузер (или телефон). Workspace = директория; git опционален — этим покрываются и не-код задачи.

Ключевой инсайт аудита: workspace-модель уже наполовину заложена в код
  • Сессии уже группируются по проектам: ~/.fan/agent/sessions/--encoded-cwd--/ — у каждого проекта своя директория сессий (session-manager.ts)
  • SessionManager.listAll() уже умеет сканировать все проекты; SessionInfo содержит cwd
  • Все ресурсы уже двухуровневые: глобальные ~/.fan/agent/ + проектные <проект>/.fan/ (скиллы, extensions, MCP, контекстные файлы)
  • Инструменты резолвят пути через resolveToCwd() — cwd приходит замыканием, не глобальным состоянием

Это не редизайн — это «дорыть» уже заложенную модель.

4Что готово vs блокеры

✅ Уже готово

  • есть REST API (16 endpoints) + WebSocket
  • есть Dashboard SPA, раздаётся сервером
  • есть Мульти-токенная auth, daemon, budget API
  • есть Группировка сессий по проектам на диске
  • есть Двухуровневые ресурсы (глобал + проект)
  • есть Универсальность: скиллы для не-код задач

⛔ Блокеры v2

  • нет TLS/auth-контур (из v1, фаза 0)
  • нет Одна активная сессия + process.chdir() — глобальное состояние
  • нет API не знает о проектах (нет ?project=, GET /api/projects)
  • нет Dashboard без переключателя проектов
  • нет Prisma Session не хранит cwd
  • нет Переключение проекта = полный пересоздание сервисов (медленно без кеша)

5Три варианта мультипроектности

Главное архитектурное решение v2. Рекомендуется вариант A — доказательства ниже.

РЕКОМЕНДУЕТСЯ

A. Workspace-режим в ядре

Один процесс FAN обслуживает N проектов. API workspace-aware, dashboard с переключателем, кеш сервисов по cwd.

  • ✅ Один инстанс: общие БД, токены, бюджет
  • ✅ Полезно и локально (TUI, dashboard)
  • ✅ Естественно покрывает не-код задачи
  • ❌ Правки ядра: 14 точек, 2 крупные
  • ❌ Одна активная сессия сохраняется

Срок: ~2–3 недели

B. Инстанс на проект

Отдельный процесс/контейнер FAN на проект, nginx маршрутизирует, launcher поднимает по требованию.

  • ✅ Ноль правок ядра
  • ✅ Изоляция проектов
  • ❌ Каждый инстанс — память/ресурсы VPS
  • ❌ Фрагментация: свои сессии, бюджеты, настройки у каждого
  • ❌ Launcher — новый сервис для поддержки

Срок: ~1–2 недели + операционная сложность

C. Гибрид: B сейчас, A потом

Быстрый старт на launcher'е, workspace-режим в ядре — позже.

  • ✅ Доступ «из любой точки» на первой неделе
  • ❌ Дважды платим за архитектуру
  • ❌ Launcher потом жалко выбрасывать
  • ❌ Откладывает правильное решение

6План фаз

Каждая фаза — самостоятельный рабочий результат. Автономность (v1) осознанно отодвинута в фазу 4.

0

Сетевой контур из v1

~5 дней · обязательный фундамент

Патч auth (публичный режим — сейчас server mode сам отключает auth!), env PORT/HOST, Docker + nginx + TLS, деплой на VPS.

→ FAN доступен из браузера откуда угодно, один проект
1

Workspace-aware API

~5 дней · 7 точек изменений (5 маленьких, 2 средние)

Prisma cwd, project-aware endpoints, GET /api/projects, SessionAdapter, реестр проектов, стартовый workspace root.

→ Скрипты и клиенты работают с любым проектом через API — даже без UI
2

Workspace UX

~5–7 дней · кеш сервисов + dashboard

Кеш сервисов Map<cwd, services>, переключатель проектов в dashboard, группировка сессий, per-project settings/MCP reload.

→ Полноценная работа с разными проектами из Web UI
3

Универсальные задачи

~3–5 дней · формализация не-код сценариев

Типы workspaces (код / ресёрч / автоматизация), шаблоны, не-код задачи как первоклассный сценарий в UI.

→ FAN как универсальный сетевой агент, не только кодинг
4

Автономность из v1

~5–8 дней · поверх workspace-режима

Scheduler-сервис (cron → FAN API), git/PR-политика (bot-identity, feature-ветки).

→ Фоновые задачи по расписанию в любом workspace
5

Конкурентность опционально

отдельный проект · пока не нужно

Очередь сообщений, удаление process.chdir(), per-project токены.

→ Несколько клиентов одновременно без гонок

7SWOT

Strengths — сильные стороны

  • Workspace-модель заложена в фундамент: сессии по cwd, двухуровневые ресурсы — «дорыть», не редизайн
  • Универсальность из коробки: скиллы уже делают не-код задачи
  • Сетевая часть (REST+WS, dashboard, токены) готова и проверена аудитом

Weaknesses — слабые стороны

  • Одна активная сессия + process.chdir() — главный архитектурный долг
  • Переключение проекта без кеша = полный reload сервисов
  • Dashboard не знает о проектах — UI с нуля

Opportunities — возможности

  • Ниша «agent-native personal cloud» пустее, чем cloud IDE
  • VPS как единая точка правды: сессии, скиллы, память — с любого устройства
  • Workspace-режим полезен и локально — улучшение ядра, не VPS-only костыль

Threats — угрозы

  • Scope creep: «инструмент для всего» легко стать бесконечным проектом
  • Публичный агент с shell — мишень (тот же класс угроз, что в v1)
  • Один VPS = единая точка отказа для всех проектов
