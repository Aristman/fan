# Сверх-оркестратор FAN — исследование идеи

## Метаданные
- **Дата:** 2026-08-09
- **Тип идеи:** Техническая
- **Глубина:** Глубокий
- **Статус:** Исследовано

## 1. Ядро идеи

> «У нас есть оркестратор. Он настроен достаточно неплохо и управляет флоу путём запуска сабагентов. Однако я хочу сделать сверх-оркестратор. Он будет запускать не только обрезанную версию фан в виде сабагентов, но и запускать отдельных агентов, полноценных агентов фан, которые сами могут строить свое флоу, и запускать сабагентов. То есть такую многоуровневую структуру. Ограничить её уровнем 12 в глубину и ширину. Идея — сделать запуск недетерминированного флоу. Чтобы под задачу была выстроена система агентов-исполнителей, воркеров и управленцев.»

### Цель
Система, способная долго (часы и дольше) и автономно работать над большими проектами: под глобальную задачу динамически выстраивается иерархия агентов — управленцы верхних уровней декомпозируют миссию, координаторы средних уровней ведут свои фронты работ, воркеры нижних уровней исполняют.

### Контекст
Текущий оркестратор FAN плоский: один координатор порождает воркеров (обрезанные инстансы `fan` в режиме RPC), глубина жёстко равна 1. На больших эпиках и долгих миссиях координатор упирается в собственный контекст и становится узким местом: вся декомпозиция, трекинг и синтез результатов проходят через одну точку. Пользователь выбрал модель исполнения «отдельные процессы `fan server`» для полноценных агентов нижних уровней.

## 2. Исследование

### 2.1 Проблема и аудитория

**Проблема:** плоский оркестратор не масштабируется на долгие автономные миссии над глобальными проектами. Контекст координатора — потолок сложности задачи; вся иерархия «менеджмент → исполнение» должна выстраиваться вручную через последовательные сессии.

**Для кого:** сам пользователь (ИИ-инженер, разработчик FAN) как оператор системы; в перспективе — пользователи FAN, запускающие многочасовые автономные задачи.

**Насколько острая:** средне-высокая. Плоская схема работает для типовых задач, но требует ручного управления на больших миссиях. Прямой денежной боли нет; это архитектурное ограничение роста.

### 2.2 Текущее состояние

Что уже существует в FAN (по исследованию кодовой базы, полный отчёт: `.fan/reports/code-research-orchestrator-architecture.md`):

- **Запуск воркеров** — `extensions/fan-orchestrator/subagent-runner.js`. Отдельный дочерний процесс (`child_process.spawn`), протокол JSONL RPC через stdin/stdout. Воркеры стартуют с флагами `--mode rpc --no-session --no-extensions --no-skills`, что лишает их оркестратора и делает глубину 1 архитектурным барьером.
- **Контроль параллелизма** — `workers.js`: эксклюзивный слот для пишущих воркеров, пул до `parallelWorkers` (по умолчанию 3) для читающих, FIFO-очередь. Лимиты `MAX_PARALLEL_TASKS=8`, `MAX_CONCURRENCY=4`.
- **Контроль зависания** — stall timer: сбрасывается при любом stdout-событии, по таймауту процесс убивается.
- **`fan server`** — `packages/coding-agent/src/cli/server-command.ts` и `main.ts`: полноценный headless-инстанс с полным runtime, расширениями, оркестратором, daemon-режимом и аутентификацией через ClientToken.
- **API Gateway** — `packages/api-gateway/src/http-server.ts`: 16+ REST-эндпоинтов (сессии, сообщения, модели, бюджет, токены, аналитика) + WebSocket `/api/ws/:sessionId` для стриминга событий. Синхронного эндпоинта «отправил — дождался ответа» нет: результат приходит асинхронно через WS.
- **Runtime** — `agent-session-runtime.ts`: ровно одна активная сессия на процесс; `switchSession()` разрушает текущую сессию и пересоздаёт runtime. Параллельные сессии внутри одного процесса невозможны.
- **Бюджет** — `packages/model-manager/src/budget.ts`: BudgetTracker глобален в рамках одного процесса (SQLite, ключи `provider + period`, периоды daily/monthly). Между процессами бюджеты независимы.
- **Протокол результатов** — `runSingleAgent()` возвращает структуру с текстом, статистикой использования (токены, стоимость, ходы), таймингом; вердикты проверки парсятся по маркеру `VERDICT: PASS|FAIL|PARTIAL`.

Внешние аналоги: LangGraph (графовая оркестрация, нативные чекпоинты и прерывания), CrewAI (ролевые экипажи, быстрое прототипирование), AutoGen (диалоговые мультиагенты), OpenAI Agents SDK. Во всех фреймворках контрольный слой (лимиты порождения, бюджеты, авторизация инструментов) нужно строить самостоятельно — фреймворк даёт точки подключения, но не принуждение.

## 3. SWOT-анализ

### Strengths (Сильные стороны) 🔵
- Процессная изоляция воркеров уже работает в проде FAN: запуск через `spawn` + JSONL RPC по stdin/stdout — паттерн проверен (`subagent-runner.js`).
- `fan server` — готовый headless-инстанс с REST+WS API, аутентификацией и daemon-режимом: полноценный агент нижнего уровня существует уже сегодня, без новой разработки ядра.
- Контрольные механизмы уже есть: слот-пул, stall timer, парсинг вердиктов, менеджер задач с зависимостями и блокировками.
- Лимит 12×12 задуман как осознанное ограничение, а не безграничная рекурсия — это соответствует главной рекомендации исследований (жёсткий предел на уровне инфраструктуры).

### Weaknesses (Слабые стороны) 🟠
- Глубина = 1 зашита жёстко: флаг `--no-extensions` физически лишает воркера инструмента `delegate_task`. Снятие барьера требует переработки запуска, а не конфигурации.
- Runtime держит одну активную сессию на процесс — параллельные сессии внутри инстанса невозможны, значит каждый узел дерева = отдельный процесс.
- Бюджет независим per-process: дерево из десятков инстансов = десятки разрозненных BudgetTracker'ов без общего потолка — прямой путь к убегающей стоимости (главная причина провала агентных проектов по Gartner).
- Нет контрольного слоя: лимиты порождения, атрибуция стоимости по дереву, авторизация инструментов — ничего из этого не централизовано.
- Нет синхронного вызова через API: родитель должен реализовывать клиент ожидания через WebSocket-события (`agent_end`) для каждого дочернего узла.

### Opportunities (Возможности) 🟢
- AdaptOrch (2026): топология оркестрации даёт 12–23% разницы в результате — правильно выстроенная иерархия это бесплатный прирост качества без смены моделей.
- Долгие автономные миссии — ниша, где плоские оркестраторы систематически проигрывают; у FAN есть все примитивы, чтобы занять её первым среди локальных рантаймов.
- Стандартизация MCP + A2A под Linux Foundation: каждый узел-`fan server` может стать A2A-совместимым агентом с карточкой возможностей — делегирование наружу и федерация с чужими системами.
- Федеративная оркестрация названа трендом 2026: суб-оркестраторы с общей политикой маршрутизации — ровно то, что задумано.

### Threats (Угрозы) 🔴
- Усиление ошибок до 17.2 раза в неструктурированных сетях (DeepMind): недетерминированный флоу без явной топологии — прямой путь в эту статистику.
- Плато координации после ~4 агентов на конвейер: ширина 12 на одного родителя экономически бессмысленна — накладные расходы съедят выигрыш.
- MAST: 36.9% отказов мультиагентных систем — сбои координации; без сквозной трассировки (correlation_id по дереву) система станет неотлаживаемой.
- Каскады внедрения промпт-инъекций между уровнями: каждое межагентное сообщение — вектор атаки; prompt injection присутствовал в 73% продакшн-развёртываний по аудитам 2026.
- Ресурсы хоста: 12×12 = до 144 одновременных процессов `fan server` — пределы по памяти, дескрипторам и портам наступят раньше лимита глубины.

## 4. Альтернативы

### 4.1 Альтернатива: Остаться на плоском оркестраторе (baseline)

**Суть:** ничего не строить; долгие миссии дробить вручную на этапы и гонять последовательными сессиями текущего оркестратора.

**Плюсы:**
- Нулевая стоимость разработки, система стабильна и предсказуема по счетам.
- Все существующие контроли (слот-пул, вердикты, stall timer) продолжают работать.

**Минусы:**
- Боль не закрыта: большие эпики требуют ручного управления, контекст координатора остаётся потолком сложности.
- Нет накопления архитектурного задела под автономные миссии.

| Параметр | Оценка |
|----------|--------|
| Сложность | Нулевая |
| Время | 0 |
| Риски | Отсутствуют (но и прогресса нет) |

### 4.2 Альтернатива: Рекурсия через снятие `--no-extensions` (точки A + E)

**Суть:** сделать загрузку оркестратора в воркерах опциональной, пробрасывать счётчик глубины через переменную окружения `FAN_ORCHESTRATOR_DEPTH`, ставить guard `depth < maxDepth`. Всё внутри существующего протокола stdin/stdout RPC.

**Плюсы:**
- Минимальный диф: десятки строк в `subagent-runner.js` + guard глубины.
- Полное переиспользование существующего протокола, слот-пула и stall timer.

**Минусы:**
- Нет изоляции сессий и наблюдаемости дерева: вложенные RPC-цепочки глубиной 12 хрупки и неотлаживаемы.
- Бюджет по-прежнему размазан по процессам; runaway-рекурсия давится только guard'ом глубины.
- Дочерний координатор — всё равно обрезанный инстанс (без сессий, без персистентности), а не «полноценный FAN» из задумки.

| Параметр | Оценка |
|----------|--------|
| Сложность | Низкая–средняя |
| Время | ~1–2 недели |
| Риски | Runaway-рекурсия, неотлаживаемость, несоответствие задумке «полноценных агентов» |

### 4.3 Альтернатива: HTTP-иерархия процессов `fan server` (точка B)

**Суть:** каждый суб-координатор — отдельный процесс `fan server start --port N`. Родитель управляет ребёнком через REST+WS: создать сессию → отправить задачу → слушать события до `agent_end` → забрать результат. Каждый узел — полноценный FAN со своими сессиями, расширениями и собственным плоским оркестратором внутри.

**Плюсы:**
- Полная изоляция процессов: kill-switch на любой узел, независимые жизненные циклы, health-check через `/api/health`.
- Наблюдаемость: каждый узел доступен по API, дерево можно опрашивать и визуализировать.
- Точно соответствует выбранной пользователем модели исполнения и задумке «полноценных агентов».

**Минусы:**
- Нужна новая инфраструктура: выделение портов, health-checks, синхронный клиент ожидания поверх WS.
- 144 процесса на одной машине — тяжело по памяти и дескрипторам; реальная ширина ограничена железом раньше, чем лимитом 12.
- Бюджет по-прежнему фрагментирован — без надстройки стоимость неконтролируема.

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя–высокая |
| Время | ~3–5 недель |
| Риски | Ресурсы хоста, стоимость токенов без глобального бюджета |

### 4.4 Альтернатива: HTTP-иерархия + контрольный слой (точки B + D, гибрид)

**Суть:** альтернатива 3 плюс обязательный контрольный слой с первой версии: глобальный координатор бюджета с моделью «родитель выделяет детям», бюджет порождения на запрос (максимум дочерних узлов — жёсткий потолок), лимиты глубины и ширины на уровне инфраструктуры (не промпта), сквозной correlation_id по дереву, санитизация межагентных сообщений, минимальные манифесты инструментов на узел.

**Плюсы:**
- Единственный вариант, проходящий продакшн-чеклист рекурсивных систем (все пять контролей из исследования Supergood).
- Структурированная топология обходит ловушку усиления ошибок 17.2× — контролируемая иерархия вместо свободного роения.
- Атрибуция стоимости по веткам дерева: видно, какая миссия сколько съела.

**Минусы:**
- Самая дорогая по времени разработка.
- «Недетерминированный флоу» придётся упаковать в рамки: свобода внутри уровня, жёсткие рамки между уровнями.
- Риск over-engineering, если строить всё сразу, а не этапами.

| Параметр | Оценка |
|----------|--------|
| Сложность | Высокая |
| Время | ~5–8 недель (полная версия; MVP — ~3 недели) |
| Риски | Over-engineering при старте с полной версии |

### 4.5 Альтернатива: Общее рабочее пространство (blackboard) вместо глубокой рекурсии

**Суть:** долгие миссии через разделяемое структурированное хранилище: агенты плоские, но читают/пишут общий workspace по precondition'ам; оркестрация динамическая без физической вложенности процессов.

**Плюсы:**
- Подходит для многочасовых асинхронных задач (паттерн прямо рекомендован для них).
- Дешевле дерева процессов, проще отлаживать: одно состояние вместо распределённого.

**Минусы:**
- Консистентность разделяемого состояния — отдельная сложная проблема.
- Не даёт «дерева управленцев» из исходной задумки: иерархия логическая, а не процессная.

| Параметр | Оценка |
|----------|--------|
| Сложность | Средняя |
| Время | ~3–4 недели |
| Риски | Гонки состояния, несоответствие задумке |

## 5. Риски

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Убегающая стоимость токенов при веерном порождении | Высокая | Критичное | Бюджет порождения на запрос + модель «родитель выделяет детям» + предел 30k токенов на прыжок; оценка токенов до вызова |
| Усиление ошибок по дереву (до 17.2×) | Средняя | Критичное | Структурированная топология с явными handoff-схемами; верификация на каждом уровне; порог уверенности > 0.7 на передачу результата вверх |
| Рекурсивные петли (ребёнок ретраит через порождение) | Средняя | Критичное | Предел глубины на уровне инфраструктуры (env-счётчик + guard), circuit breaker на ретраи, stall timer на каждом узле |
| Каскад prompt injection между уровнями | Средняя | Высокое | Санитизация всех межагентных сообщений как недоверенного ввода; минимальные манифесты инструментов на узел |
| Исчерпание ресурсов хоста (процессы, порты, память) | Высокая (при ширине 12) | Среднее | Реальная ширина 3–4 на узел; лимит 12 оставить предохранителем; пул портов с возвратом; kill-switch по idle-таймауту |
| Неотлаживаемость недетерминированного дерева | Высокая | Высокое | Сквозной correlation_id, трассировка каждого порождения с трассируемой темой задачи, дерево доступно через API, LLM-as-Judge по итогам веток |
| Over-engineering: построить систему, не нужную на реальных задачах | Средняя | Среднее | Поэтапный план (MVP глубины 2 → 3–4 уровня); валидация на 2–3 реальных эпиках до расширения |

## 6. Рекомендация

### Что делать: HTTP-иерархия `fan server` с контрольным слоем (альтернатива 4), поэтапно через альтернативу 3

**Уверенность:** 0.85/1.0

**Обоснование:**
1. Модель «полноценный агент = отдельный процесс `fan server`» выбрана пользователем и подтверждена исследованием кода: headless-инстанс с полным API существует сегодня, точки расширения локализованы (выделение портов, клиент ожидания, управление daemon'ами).
2. Исследования сходятся: рекурсия без инфраструктурных контролей — главный генератор провалов агентных проектов (Gartner: 40%+ закрытий к 2027). Контрольный слой — не опция, а условие жизнеспособности; строить его «потом» означает строить его после первого счёта за runaway-дерево.
3. Структурированная иерархия с явными handoff'ами — единственный способ получить выигрыш координации без усиления ошибок (DeepMind: неструктурированные сети хуже одиночного агента до 17.2 раза; AdaptOrch: правильная топология даёт +12–23%).

**Компромиссы:**
- Принимаем: «недетерминированность» ограничена рамками — свобода декомпозиции внутри уровня, жёсткие лимиты между уровнями. Это цена управляемости.
- Принимаем: рабочая глубина 3–4 уровня вместо 12. Лимит 12 остаётся в коде как предохранитель, но исследования (плато после ~4 агентов, усиление ошибок) показывают, что глубже лезть бессмысленно и вредно. Логическая глубина миссии достигается декомпозицией задач, а не вложенностью процессов.
- Отклоняем: RPC-рекурсию через снятие `--no-extensions` как основной путь — она не даёт ни полноценных агентов, ни наблюдаемости; годится разве что как однодневный эксперимент для проверки ощущений.
- Отклоняем: чистый blackboard — не соответствует задумке дерева управленцев, хотя разделяемое хранилище артефактов миссии полезно как дополнение.

**Предупреждения:**
- ⚠️ Без глобального бюджета с первой версии система опасна для кошелька. Минимум: бюджет порождения на запрос + выделение доли бюджета детям + отчёт о расходе вверх по дереву.
- ⚠️ 144 одновременных процесса на одной машине невозможны физически. Проектировать реальную ширину 3–4 дочерних узла на родителя, очередь — через существующий слот-пул.
- ⚠️ Первые две недели после MVP — только наблюдение: метрики расхода по веткам, частота отказов координации, доля преждевременных завершений. По данным MAST именно эти три категории дадут основные отказы.

## 7. План действий

### Приоритеты (MoSCoW)

**Must Have (обязательно):**
- [ ] Клиент управления дочерним узлом: запуск `fan server` на выделенном порту, health-check, создание сессии, отправка задачи, ожидание `agent_end` по WS, получение результата
- [ ] Предел глубины и ширины на уровне инфраструктуры: env-счётчик глубины + guard в коде запуска (не в промпте)
- [ ] Бюджет порождения на запрос: максимум дочерних узлов на родителя и на всю миссию, проверка до запуска
- [ ] Глобальный учёт расхода: каждый узел отчитывается о потреблении (токены, стоимость) вверх по дереву; потолок миссии
- [ ] Сквозной correlation_id и журнал дерева порождения (кто кого породил, с какой задачей, сколько потратил)

**Should Have (желательно):**
- [ ] Минимальные манифесты инструментов на узел (по аналогии с текущей обрезкой воркеров, но декларативно)
- [ ] Санитизация межагентных сообщений (валидация выхода ребёнка перед передачей родителю)
- [ ] Виджет/визуализация дерева миссии в дашборде FAN
- [ ] Верификация результата на каждом уровне перед передачей вверх (маркер вердикта уже есть — расширить на межпроцессный протокол)

**Could Have (возможно):**
- [ ] A2A-совместимость узлов (карточка возможностей, делегирование внешним системам)
- [ ] Разделяемое хранилище артефактов миссии (элемент blackboard-подхода)
- [ ] Адаптивный выбор топологии (в духе AdaptOrch: система сама решает, нужен ли ещё уровень)

**Won't Have (не входит):**
- [ ] Рабочая глубина 12 уровней — исследования показывают вред глубокой вложенности; лимит 12 остаётся только предохранителем
- [ ] Свободная рекурсия без бюджета порождения — прямой путь к runaway-стоимости
- [ ] Параллельные сессии внутри одного процесса (точка C) — ломает архитектуру runtime без необходимости: изоляция достигается процессами

## 8. Технические разделы

### Техническое решение

#### Архитектура

```
Миссия (задача пользователя)
  │
  ▼
┌─────────────────────────────────────┐
│ L0: Сверх-оркестратор (fan TUI/CLI) │
│  • декомпозиция миссии              │
│  • бюджет порождения, потолок расхода│
│  • correlation_id корня             │
└───────┬─────────┬─────────┬─────────┘
        │ REST+WS │ REST+WS │ REST+WS          (ширина 3–4, бюджет выделен)
        ▼         ▼         ▼
   ┌─────────┐┌─────────┐┌─────────┐
   │ L1: fan ││ L1: fan ││ L1: fan │      отдельные процессы fan server,
   │ server  ││ server  ││ server  │      уникальные порты, health-check,
   │ :7001   ││ :7002   ││ :7003   │      guard глубины (env)
   └────┬────┘└────┬────┘└────┬────┘
        │ внутри каждого — обычный плоский оркестратор
        ▼
   воркеры RPC (существующий механизм subagent-runner)
```

Контрольный слой (поперёк всех уровней): глобальный учёт расхода, бюджет порождения, журнал дерева (correlation_id), санитизация границ, circuit breaker на ретраи.

#### Стек технологий

| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Транспорт между уровнями | REST (Hono API Gateway) + WebSocket | Уже существует в `fan server`; 16+ эндпоинтов покрывают управление сессиями |
| Процессы узлов | `fan server start` (detached spawn, PID-файлы) | Готовый daemon-режим, graceful stop |
| Протокол результата | WS-события до `agent_end` + извлечение финального сообщения | Асинхронная природа API; синхронный клиент — новый модуль |
| Лимиты глубины/ширины | env-переменные + guard в коде запуска | Принуждение на уровне инфраструктуры, не промпта |
| Учёт расхода | BudgetTracker (существующий) + агрегатор дерева (новый модуль) | Per-process трекинг уже есть; нужна агрегация вверх |
| Журнал дерева | JSONL-приложение к сессии миссии + Prisma-метаданные | Соответствует принципу «диск — единственный источник правды» |

#### Интеграция

Новый модуль — расширение `fan-super-orchestrator` (по образцу `extensions/fan-orchestrator`, standalone через FAN Store). Не трогает ядро: использует публичные механизмы `fan server` и API Gateway. Существующий плоский оркестратор продолжает работать внутри каждого узла без изменений.

#### API / Интерфейсы

Ключевой новый контракт — «задача узлу»:

```json
{
  "task": "строка задачи с трассируемой темой",
  "correlationId": "mission-uuid/branch-path",
  "depth": 1,
  "spawnBudget": 4,
  "tokenBudget": 50000,
  "toolManifest": ["read", "bash", "..."],
  "deadline": "ISO-8601"
}
```

И «отчёт узла» (вверх по дереву): результат, вердикт, потребление (токены/стоимость/время), журнал порождённых детей, причина завершения.

### Оценка трудозатрат

| Задача | Сложность | Оценка | Зависимости |
|--------|-----------|--------|-------------|
| Спецификация протокола узлов | Низкая | 2–3 дня | — |
| Менеджер дочерних процессов (порты, health, kill) | Средняя | 3–4 дня | Спецификация |
| Клиент ожидания поверх WS | Средняя | 3–4 дня | Менеджер процессов |
| Инфраструктурные лимиты (глубина, ширина, бюджет порождения) | Низкая | 2 дня | Менеджер процессов |
| MVP глубины 2 | Средняя | 3–4 дня | Всё выше |
| Глобальный учёт расхода | Средняя | 3–4 дня | MVP |
| Валидация на реальных эпиках | — | 1–2 недели | MVP |
| Глубина 3–4 + манифесты + санитизация + визуализация | Высокая | 2–3 недели | Валидация |

**Итого:** ~7–9 недель полной версии; **MVP:** ~3 недели.

### Adoption

#### Шаги внедрения
1. [ ] Разработка MVP по шагам 1–5 плана действий на ветке `FAN/feature/super-orchestrator`
2. [ ] Прогон MVP на синтетической миссии (генерация документации по монорепо — достаточно большая задача с естественной декомпозицией)
3. [ ] Валидация на 2–3 реальных эпиках со сбором метрик расхода и отказов
4. [ ] Расширение до глубины 3–4 только после подтверждения экономики на шаге 3
5. [ ] Публикация расширения в FAN Store

#### Стратегия отката
Расширение standalone: удаление/отключение возвращает систему к текущему плоскому оркестратору без изменений в ядре. Дочерние процессы `fan server` останавливаются через `fan server stop` (SIGTERM → 5s → SIGKILL уже реализовано). Журнал дерева на диске позволяет разобрать любую миссию постфактум.
