## 1. Главный инсайт: бесконечность — это цикл, а не процесс

Индустрия к 2026 году пришла к консенсусу, который меняет саму постановку задачи:

> **Бесконечная автономная работа — это не один бесконечно живущий агентный процесс. Это детерминированный внешний цикл, порождающий короткие ограниченные сессии, с состоянием, вынесенным наружу — в файлы и git.**

Так устроены все рабочие реализации «вечных» агентов:

- **Ralph Loop** (Geoffrey Huntley): bash-цикл, который на каждой итерации поднимает агента со свежим контекстом. История диалога не суммаризируется — она выбрасывается. Память — только файловая система: `tasks.json`, `SUMMARY.md`, git-история. Человек может в любой момент записать коррекцию в `STEERING.md`, и агент подхватит её на следующей итерации.
- **GSD** (TÂCHES, на Pi SDK — предке FAN): волновая оркестрация с конечным автоматом DISCUSS → PLAN → EXECUTE → VERIFY → цикл. Оркестратор держит разрежённое состояние (30–40% контекста), исполнители амнезийны по построению — каждый получает ровно свой кусок задачи в свежем окне.
- **Autoresearch** (Andrej Karpathy): цикл-трещотка — гипотеза → эксперимент с жёстким бюджетом по wall-clock → измерение непробиваемой метрики → сохранить или откатить коммит → повтор. Сотни итераций без надзора (Shopify: 93 автономных коммита, +53% к скорости парсера).
- **Anthropic** (исследования harness-дизайна): разделение ответственности «состояние сессии» и «исполнение» — главный рычаг для многочасовых автономных прогонов без деградации связности.

Почему противоположный подход — «один долгоживущий процесс с накапливающимся контекстом» — проигрывает:

1. **Арифметика надёжности.** Шаг с успехом 85%: 10 шагов — 19.7% общего успеха, 20 шагов — 3.9%, 50 шагов — 0.03%. Наращивание длины цепочки без сброса вектора вероятностей на каждом шаге — гарантированный провал. Сброс даёт только детерминированная верификация на границе итерации.
2. **Контекстная гниль (context rot).** Даже миллионное окно не спасает: «lost in the middle», зацикливание на свежих ошибках, галлюцинированный прогресс. Деградация с длиной сессии — экспоненциальная, не линейная. Автокомпактификация FAN смягчает, но одноуровневая суммаризация теряет детали.
3. **Потеря незавершённого состояния.** JSONL-персистентность FAN восстанавливает историю, но in-flight состояние (текущая генерация, pending tool calls, очереди) при смерти процесса теряется. Чем длиннее неделимый блок работы, тем дороже его потеря — классическая проблема at-least-once доставки в очередях: перезапуск с шага 1 сжигает уже потраченные деньги повторно.

**Вывод для FAN:** мозг системы — не агент, а контур (harness) вокруг него. Модель — сменный безсостоятельный компонент; контур — детерминированная обвязка, владеющая состоянием, верификацией и прерываниями.

## 2. Система прерываний: да, и аналогия с ОС точна

Идея пользователя про прерывания — правильная и ложится на архитектуру идеально. Операционная система решает ровно эту задачу: бесконечно работающий планировщик, управляемый прерываниями разных приоритетов. Переносим модель на агентный контур.

### 2.1 Уровни прерываний (по аналогии с приоритетами ОС)

| Уровень | Название | Семантика | Аналог в ОС |
|---------|----------|-----------|-------------|
| I0 | **Стоп (немаскируемое)** | Немедленный abort: kill текущей генерации, состояние сохраняется как «aborted» | NMI / SIGKILL |
| I1 | **Осушение (drain)** | «Закончи текущий ход и встань»: graceful-пауза на границе итерации | SIGTERM с drain |
| I2 | **Коррекция курса (steer)** | Инъекция сообщения в работающий цикл между вызовами инструментов — агент учитывает её немедленно | IRQ, обрабатываемое в точке планирования |
| I3 | **Постановка в очередь (follow-up)** | Задача после завершения текущего цикла | Отложенный вызов (deferred call) |
| I4 | **Тик (heartbeat)** | Периодическое пробуждение контура: проверить состояние, решить — продолжать, спать или порождать работу | Таймер планировщика |

### 2.2 Источники прерываний

**Внешние:**
| Источник | Уровень | Механизм в FAN |
|----------|---------|----------------|
| Оператор (человек) | I0–I3 | API: сообщение в сессию (уже работает — очереди steer/followUp), будущий REST-эндпоинт abort |
| Таймеры/расписание | I4 | Расширение-планировщик (setInterval + `actions.sendMessage()`) — не требует изменений ядра |
| Вебхуки (CI, мониторинг, git-события) | I2–I3 | Расширение-слушатель вебхуков (микро-Hono внутри расширения, пример `file-trigger.ts` доказывает паттерн) |
| Файловая система | I2–I3 | `fs.watch` → `sendMessage()` — пример уже есть в `examples/extensions/file-trigger.ts` |
| Бюджетные сигналы | I0–I1 | WS-событие `budget_alert` (warning/critical/exceeded) — уже транслируется наружу |
| Родительский узел дерева | I0–I3 | REST+WS API `fan server` (см. первый документ: HTTP-иерархия) |

**Внутренние:**
| Источник | Уровень | Механизм |
|----------|---------|----------|
| Переполнение контекста | I2 (авто) | Уже есть: auto-compact → auto-retry при overflow |
| Детектор циклов | I1 | Отсутствует — нужен: семантическое сходство последовательных вызовов инструментов (тот же инструмент + те же параметры + та же ошибка дважды → стоп и запрет подхода) |
| Сторожевой таймер (watchdog) | I0–I1 | Отсутствует в runtime — нужен: таймер на `tool_execution_start` без `tool_execution_end` за N минут. В оркестраторе stall timer уже есть — перенести паттерн |
| Исчерпание бюджета итерации | I1 | Частично есть (BudgetTracker глобальный), нужен бюджет **на итерацию** с записью состояния и пометкой «не завершено» |
| Верификация провалена | I2–I3 | Маркер `VERDICT: PASS/FAIL/PARTIAL` уже парсится — расширить на контур: FAIL → новая итерация с диагностикой |
| Терминальные сигналы агента | I1 | Паттерн «теги обещаний» из Ralph Loop: `<promise>COMPLETE</promise>` / `BLOCKED:причина` / `DECIDE:вопрос` — структурированный протокол, по которому недетерминированный агент сообщает детерминированному контуру терминальное состояние |

### 2.3 Ключевая находка: почтовый ящик прерываний у FAN уже есть

В FAN уже существует транспорт прерываний уровней I2–I3 — это очереди сообщений агента:

- **Steering-очередь** впрыскивает сообщение между вызовами инструментов работающего цикла — это и есть маскируемое прерывание в реальном времени.
- **Follow-up очередь** ставит задачу после завершения текущего цикла — отложенные вызовы.
- API принимает сообщения в занятую сессию молча и без потерь (default — followUp).
- Событие `queue_update` позволяет наблюдателю видеть содержимое очередей.

Не хватает: приоритетов в очередях (сейчас FIFO), лимита размера (риск раздувания на бесконечной миссии, ~20 LOC), dead-letter очереди и — критично — **REST/WS-эндпоинта abort** (уровень I0 недоступен извне вообще: WS принимает только ping/subscribe, abort есть лишь в RPC-stdin; ~50 LOC).

## 3. Архитектура «миссионный контур» (mission loop)

Сборка: бесконечная работа с генерацией и реализацией идей — это внешний цикл поверх связки «миссионные файлы + короткие сессии + прерывания».

```
┌──────────────────────────────────────────────────────────────┐
│ КОНТУР МИССИИ (детерминированный, расширение fan-mission)     │
│                                                              │
│  while (миссия активна):                                     │
│    1. ПРОСНУТЬСЯ   ← тик I4, вебхук, команда оператора       │
│    2. ПРОЧИТАТЬ    MISSION.md ROADMAP.md STATE.md git log    │
│    3. РЕШИТЬ       что запускать: идея из бэклога /          │
│                    генерация новых идей / доработка / стоп   │
│    4. ЗАПУСТИТЬ    итерацию = сессия (или узел дерева)       │
│    5. ВЕРИФИЦИР.   лестница проверок + непробиваемая метрика │
│    6. ЗАФИКСИР.    git commit + STATE.md + чекпоинт (fork)   │
│    7. ОБНОВИТЬ     бэклог идей (новые из результатов)        │
│                                                              │
│  Прерывания: I0 стоп │ I1 осушение │ I2 steer │ I3 очередь   │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 Состояние миссии — снаружи, а не в контексте

Правило из исследования harness-инженерии: «контекст — это регистр процессора; файловая система и git — постоянная память». Набор файлов миссии (в репозитории проекта, `docs/missions/<slug>/`):

| Файл | Содержимое | Кто пишет |
|------|-----------|-----------|
| `MISSION.md` | Цель, рамки, непробиваемая метрика успеха, запреты | Оператор (контур не меняет) |
| `ROADMAP.md` | Декомпозиция на этапы с критериями приёмки (команда терминальной проверки у каждого пункта) | Контур по решению агента-планировщика |
| `STATE.md` | Текущая позиция: что сделано, блокеры, следующие шаги. Читается менее чем за 30 секунд | Контур после каждой итерации |
| `BACKLOG.md` | Идеи-кандидаты с оценками (из генерации идей) | Генератор идей + оператор |
| `DECISIONS.md` | Журнал архитектурных решений с обоснованием | Итерации записывают |
| git-история | Атомарный коммит на завершённую задачу — исполняемый журнал, time-travel отладка бесплатно | Контур (перед коммитом — вся лестница верификации) |

Дисциплина: информация, нужная новой сессии для продолжения, обязана помещаться в структурированный файл, читаемый за 30 секунд. Сырые логи инструментов и переписка — почти никогда не нужны; дистиллированные решения, блокеры и состояние — всегда.

### 3.2 Генерация идей внутри цикла

Петля «генерация → реализация» строится на уже существующих активах FAN:

1. **Генератор** — периодическая итерация (по тику I4 или по завершении этапа): анализ результатов, огрехов, новых возможностей → кандидаты в `BACKLOG.md`. Может использовать скилл idea-lab в режиме quick scan для оценки каждого кандидата.
2. **Оценщик** — детерминированная часть: скоринг по критериям (соответствие MISSION.md, стоимость, риск, ожидаемая ценность) + порог. Кандидаты выше порога — в ROADMAP; спорные — прерывание I3 оператору (`DECIDE:вопрос`).
3. **Исполнение** — итерации по приоритетам: один пункт дорожной карты = одна сессия (или ветка дерева сверх-оркестратора, если пункт крупный).
4. **Верификация** — лестница: статика → линтеры → сборка → тесты → приёмочная команда пункта → независимый аудитор в свежем контексте. План без терминальной проверки на пункт отклоняется ещё на стадии планирования (паттерн Nyquist-валидации из GSD).

### 3.3 Непробиваемая метрика

Главный урок Autoresearch: любая метрика, которую агент может накрутить, будет накручена — не со зла, а потому что модель оптимизирует наблюдаемый сигнал. Требования:
- метрика вычисляется кодом, который агент структурно не может изменить (аналог `prepare.py`);
- для инженерных задач — внешний интеграционный тест-сьют без прав записи у агента;
- «сделано» определяется до написания промптов: какая автоматическая проверка, метрика или артефакт должны существовать. Если «сделано» не формулируется проверяемо — задача открытая генерация, и контур обязан это пометить.

### 3.4 Чекпоинты и durable execution — облегчённая версия

Полный Temporal FAN не нужен; нужна дисциплина журнала:
- **Git-коммит после каждой задачи** = дurable-журнал исполнения. Новая сессия читает историю и знает, где остановка. (Совпадает с принципом FAN «диск — единственный источник правды».)
- **`fork()` как чекпоинт-снимок сессии** перед рискованными итерациями + паттерн `git-checkpoint.ts` (stash на начало хода, restore на fork). Провал → новая ветка от снимка с другой стратегией, без перепрогона завершённой работы.
- **Идемпотентность шагов**: повторный запуск итерации после сбоя не должен дублировать побочные эффекты. Правило контура: каждое внешнее действие (коммит, публикация, вызов API) помечается как обратимое (с компенсацией — паттерн саг) или необратимое (требует подтверждения оператора). Ключ идемпотентности — от детерминированного контекста (ID миссии + номер шага), не от аргументов, которые модель может переформулировать на повторе.

### 3.5 Трёхслойные автоматические выключатели (circuit breakers)

Обязательные параметры, определяемые ДО первого запуска:

1. **Бюджетный слой** — жёсткий потолок токенов/денег на итерацию и на миссию. При исчерпании контур не просто рубит: записывает состояние, помечает задачу незавершённой, эскалирует (I3 оператору).
2. **Детектор циклов** — семантическое сходство последовательных вызовов инструментов: тот же инструмент + те же параметры + та же ошибка дважды → останов, в следующий контекст впрыскивается явный запрет прежнего подхода. Тупой таймаут недостаточен — после перезапуска агент вернётся в ту же ловушку.
3. **Сторожевой таймер** — на каждый `tool_execution_start`; нет `tool_execution_end` за N минут → сигнал I1 + диагностика. В порождённых воркерах stall timer уже работает; нужен аналог на уровне runtime и дерева.

## 4. Связка со сверх-оркестратором (первый документ)

Контур миссии и HTTP-иерархия не конкурируют — это два измерения одной системы:

- **Контур миссии** — ось времени: бесконечная жизнь, прерывания, состояние, чекпоинты. Живёт в узле L0.
- **Иерархия узлов** — ось ширины: веерное исполнение крупных пунктов дорожной карты. Порождается контуром по мере нужды.

То есть: сверх-оркестратор L0 = контур миссии + дерево. Каждый узел L1 получает не «задачу на вечность», а ограниченный пакет работ с бюджетом и дедлайном; бесконечность существует только на вершине, в контуре, и выражена файлами миссии, а не бессмертными процессами. Это снимает и часть рисков из первого документа: неотлаживаемость дерева компенсируется журналом миссии и correlation_id, а «бесконечный расход» — бюджетами итераций.

**Обоснование:**
1. Боль «очень долгая работа» решается контуром, а не деревом: индустриальный консенсус (Ralph Loop, GSD, Autoresearch, Anthropic) — внешний детерминированный цикл + короткие сессии + внешнее состояние. FAN покрывает ~70% примитивов уже сегодня.
2. Система прерываний — правильная идея, и её транспорт на две трети готов: очереди steer/followUp = уровни I2–I3, `budget_alert` и WS-события = каналы сигналов, 27 хуков расширений = точки обработки. Недостающее — дёшево (P0: ~150 LOC ядра).
3. Контур даёт ценность немедленно и без рисков многоуровневости: на одном процессе, с существующим плоским оркестратором внутри. Дерево из первого документа подключается позже как расширение ширины, уже поверх зрелого контура.

**Компромиссы:**
- Принимаем: «бесконечность» логическая (цикл + файлы), а не физическая (бессмертные процессы). Процессы смертны по дизайну — это фича: смерть дёшева, восстановление бесплатно.
- Принимаем: graceful pause/resume (P3) откладываем — abort + чекпоинты покрывают сценарии дешевле.
- Отклоняем: внешние движки durable execution (Temporal и т.п.) — тянуть кластер ради локального рантайма непропорционально; git + JSONL + fork дают облегчённый вариант.

**Предупреждения:**
- ⚠️ Без непробиваемой метрики и детектора циклов «вечный» контур превратится в вечный счёт: зацикленный агент тратит деньги бесконечно, упавший — останавливается. Определять выключатели до первого прогона.
- ⚠️ Энтропия на длинной дистанции неизбежна даже с заборами: тысяча валидных коммитов всё равно размывает конвенции. Закладывать периодические итерации-«сборщики мусора» (рефакторинг по расписанию).
- ⚠️ Генератор идей без фильтра завалит бэклог мусором: скоринг и пороги обязательны, спорное — только оператору через `DECIDE`.
