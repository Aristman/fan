## Фаза A «Протокол результатов»

**Цель:** Реализовать протокол терминальных тегов обещаний, DECIDE-прерывание и лестницу верификации — три механизма, превращающих недетерминированный вывод агента в управляемый контуром процесс. Все 3 функции фазы — модули расширения `fan-mission`.
**Приоритет функций:** P1 (F-16, F-17, F-18)
**E2E-сценарий фазы:**
1. Контур запускает mock-итерацию → агент возвращает ответ с тегом `<promise>BLOCKED:нет доступа к БД</promise>` → парсер извлекает тег → контур записывает блокер в `STATE.md` → эскалация I3 оператору → контур продолжает следующую итерацию.
2. Контур запускает mock-итерацию → агент возвращает `<promise>DECIDE:Использовать JWT или session-cookie?</promise>` → статус миссии `awaiting_decision` → TUI-виджет показывает «Ожидает решения оператора» → оператор: `/mission:decide "JWT"` → контур возобновляет работу, ответ записан в `DECISIONS.md`.
3. Контур завершает итерацию → лестница верификации: линтеры (проходят) → сборка (проходит) → тесты (1 провал) → статус `FAILED` с диагнозом «test auth.test.ts:42 failed» → контур планирует повтор с другой стратегией.
**Smoke-критерий фазы:** Mock-итерация с каждым из 4 тегов (COMPLETE/BLOCKED/DECIDE/FAILED) обрабатывается корректно: парсер извлекает тег, маршрутизатор выполняет действие, лестница верификации запускает ступени в порядке.

#### ✅ F-16: Парсер тегов обещаний

- **Приоритет:** P1
- **Слой:** [BIZ]
- **Описание:** Реализовать модуль `extensions/fan-mission/promise-parser.ts` — парсер терминальных тегов обещаний из ответа агента. Regex: `/<promise>(COMPLETE|BLOCKED(?::[^\n<]+)?|DECIDE(?::[^\n<]+)?|FAILED(?::[^\n<]+)?)<\/promise>/` (из спеки §3.2.4). Правила: (1) теги внутри fenced code block игнорируются; (2) при нескольких тегах — последний валидный; (3) `BLOCKED` без причины → причина «не указана»; (4) отсутствие тега → статус `unknown` + эскалация I3. Возвращает `{ tag: "COMPLETE"|"BLOCKED"|"DECIDE"|"FAILED", reason?: string } | null`.
- **Пользовательская история:** «Как контур миссии, я хочу извлекать терминальное состояние из ответа агента, чтобы маршрутизировать дальнейшие действия»
- **Зависимости:** (none)
- **TDD-тесты:**
  - [ ] **TC-F16-1:** Парсер извлекает все 4 типа тегов
    - *Условие:* Ответ агента содержит `<promise>BLOCKED:нет доступа к БД</promise>`
    - *Шаги:* `parsePromise(response)` → извлечение тега
    - *Ожидаемый результат:* `{ tag: "BLOCKED", reason: "нет доступа к БД" }`
  - [ ] **TC-F16-2:** Теги в fenced code block игнорируются
    - *Условие:* Ответ содержит `` ```\n<promise>COMPLETE</promise>\n``` `` и вне блока `<promise>FAILED:ошибка</promise>`
    - *Шаги:* `parsePromise(response)`
    - *Ожидаемый результат:* `{ tag: "FAILED", reason: "ошибка" }` (код-блок проигнорирован)
  - [ ] **TC-F16-3:** Отсутствие тега → null + эскалация
    - *Условие:* Ответ агента не содержит тегов `<promise>`
    - *Шаги:* `parsePromise(response)`
    - *Ожидаемый результат:* `null`; вызывается callback эскалации `onUnknown()` (I3)
- **Red-тест:** TC-F16-1 — модуль не существует, `parsePromise()` не определена.
- **Refactor-цели:** Вынести фильтрацию fenced code blocks в утилиту `stripCodeBlocks(text)` для переиспользования в аудите.
- **Критерии приёмки:**
  1. Парсер корректно извлекает все 4 типа тегов с опциональной причиной
  2. Теги внутри fenced code block игнорируются
  3. При нескольких тегах возвращается последний валидный; при отсутствии — `null`
- **Ожидаемый результат:** Модуль `extensions/fan-mission/promise-parser.ts` (~80 LOC)
- **Оценка объёма:** S (≤ 4ч)

#### ✅ F-17: DECIDE-прерывание (блокировка контура)

- **Приоритет:** P1
- **Слой:** [BIZ]
- **Описание:** Реализовать обработку тега `DECIDE` в `extensions/fan-mission/mission-loop.ts` — при обнаружении тега `<promise>DECIDE:<вопрос></promise>` контур переходит в статус `awaiting_decision`, блокирует выполнение новых итераций и ожидает ответа оператора через `/mission:decide <answer>`. Ответ оператора записывается в `DECISIONS.md` (append-only, ADR-формат: дата, вопрос, ответ, результат). После записи — возобновление работы. - **Пользовательская история:** «Как оператор, я хочу чтобы контур остановился и задал вопрос при неопределённости, чтобы я принял решение до продолжения работы»
- **Зависимости:** F-16, F-09 (этап 0)
- **TDD-тесты:**
  - [ ] **TC-F17-1:** DECIDE блокирует контур до ответа оператора
    - *Условие:* Контур активен, mock-итерация вернула `<promise>DECIDE:JWT или session?</promise>`
    - *Шаги:* `missionLoop.tick()` → парсер возвращает `DECIDE` → проверка статуса
    - *Ожидаемый результат:* Статус миссии `awaiting_decision`, новые тики не запускают итерации, в `DECISIONS.md` записан вопрос
  - [ ] **TC-F17-2:** Ответ оператора возобновляет работу
    - *Условие:* Миссия в статусе `awaiting_decision`
    - *Шаги:* Вызвать `missionLoop.resolveDecision("JWT")` (эмуляция `/mission:decide`)
    - *Ожидаемый результат:* Статус → `active`, ответ записан в `DECISIONS.md`, следующий тик запускает итерацию
  - [ ] **TC-F17-3:** Таймаут DECIDE вызывает abort
    - *Условие:* `decideTimeoutMs = 1000` (тестовое значение), миссия в `awaiting_decision`
    - *Шаги:* Ожидание 1100 мс без ответа оператора
    - *Ожидаемый результат:* Статус → `aborted`, в `STATE.md` записана причина «decide_timeout»
- **Red-тест:** TC-F17-1 — обработка DECIDE не реализована, контур продолжает итерации без ожидания ответа.
- **Refactor-цели:** (none) — логика локализована в `mission-loop.ts`, связанность с F-16 через интерфейс `PromiseParseResult`.
- **Критерии приёмки:**
  1. Тег `DECIDE` блокирует контур (статус `awaiting_decision`), новые итерации не запускаются
  2. Ответ оператора через `resolveDecision()` возобновляет работу, записывает в `DECISIONS.md`
  3. Таймаут `decideTimeoutMs` вызывает abort с диагностикой
- **Ожидаемый результат:** Обработка DECIDE в `extensions/fan-mission/mission-loop.ts` + запись в `DECISIONS.md` (~100 LOC)
- **Оценка объёма:** S (≤ 4ч)

#### ☐ F-20: Скорер идей (гибридный LLM + арифметика)

- **Слой:** [BIZ]
- **Описание:** Реализовать модуль `extensions/fan-mission/idea-scorer.ts` — оценка идей-кандидатов по гибридной схеме (из спеки §3.1.3). Сырые оценки и score логируются в `BACKLOG.md` (воспроизводимость).
- **Пользовательская история:** «Как контур миссии, я хочу объективную оценку идей, чтобы приоритизировать лучшие и отсеивать слабые без субъективности»

- **TDD-тесты:**

    - *Шаги:* `ideaScorer.score({ relevance: 0.6, value: 0.5, risk: 0.5, cost: 0.6 })`
    - *Ожидаемый результат:* `score = 0.18 + 0.10 + 0.10 + 0.12 = 0.50` → статус `DECIDE`; вызывается `missionLoop.requestDecision()`

  2. Пороги: ≥0.7 → ROADMAP, 0.5–0.7 → DECIDE, <0.5 → REJECTED с записью в `DECISIONS.md`
  3. Сырые оценки и score логируются в `BACKLOG.md`

#### ☐ F-48: Персистентность таск-листа оркестратора

- **Приоритет:** P1
- **Слой:** [BIZ]
- **Описание:** Сделать `TaskManager` (`extensions/fan-orchestrator/task-manager.js:11`) переживающим рестарт FAN. Подключить уже написанный `serialize()` (~273) к механизму custom messages сессии: снапшот задач пишется в JSONL при каждом `TaskCreate` / `TaskUpdate` (или при `session_shutdown`); при `session_start` / `switchSession` — `deserialize(entries)` восстанавливает `new Map(entries)`, валидирует статусы по `ALL_STATUSES` и восстанавливает двунаправленные связи `blocks` / `blockedBy`. Задачи в `in_progress` после восстановления переводятся в `pending` с пометкой `recovered: true` (воркер после рестарта фактически мог умереть). Backward compat: сессии без snapshot дают пустую доску без ошибок. Источник — backlog `docs/backlogs/tasklist-persistence-backlog.md`. Реализация ~100 LOC (ядро: ~100 LOC на session JSONL custom messages + интеграцию) + ~50 LOC (расширение: deserialize, restore, доска) ≈ ~150 LOC.
- **Пользовательская история:** «Как координатор длинного пайплайна, я хочу, чтобы доска задач переживала перезапуск FAN, чтобы не пересоздавать её вручную после каждого краша»
- **Зависимости:** (none) — независима, использует существующие `serialize()` и custom messages JSONL
- **TDD-тесты:**
  - [ ] **TC-F48-1:** Roundtrip serialize/deserialize сохраняет задачи и связи
    - *Условие:* `TaskManager` содержит 3 задачи (pending / in_progress / completed), `blocks`/`blockedBy` связи между ними
    - *Шаги:* `taskManager.serialize()` → JSON → `new TaskManager().deserialize(json)` → `list_tasks()`
    - *Ожидаемый результат:* Все 3 задачи восстановлены с исходными статусами, поля `subject`/`activeForm`/`blocks`/`blockedBy` идентичны, двунаправленные связи целы
  - [ ] **TC-F48-2:** Restore после «краша» возвращает корректную доску из session JSONL
    - *Условие:* Mock-сессия содержит записанный snapshot с 3 задачами в статусах pending / in_progress / completed и связями между ними; процесс FAN «упал» и перезапущен
    - *Шаги:* Старт FAN → `continueRecent()` / `switchSession()` → восстановление доски → `list_tasks()`
    - *Ожидаемый результат:* Все 3 задачи в корректных статусах, связи целы; задача в `in_progress` помечена `recovered: true` и переведена в `pending`; `list_tasks` не пуст
  - [ ] **TC-F48-3:** `in_progress` после restore помечается `recovered: true` и становится `pending`
    - *Условие:* Snapshot содержит задачу в статусе `in_progress`
    - *Шаги:* `deserialize(snapshot)` → проверка задачи
    - *Ожидаемый результат:* Задача имеет `status: "pending"`, `recovered: true` в metadata; в `list_tasks` отображается как ожидающая перезапуска
- **Red-тест:** TC-F48-2 — `serialize()` не вызывается ни в одном хуке FAN; `deserialize()` отсутствует (метод не определён в `TaskManager`); после перезапуска `list_tasks` возвращает пустой массив, taskId из предыдущего процесса недействительны.
- **Refactor-цели:** Вынести валидацию статусов при десериализации в чистую функцию `validateStatus(status): ALL_STATUSES[number]` для переиспользования в CLI и дашборде; централизовать snapshot-логику в единый хук `onTaskBoardChange()` (если будет введён) вместо вызова `serialize()` из 6 разных мест.
- **Критерии приёмки:**
  1. Перезапуск процесса FAN → доска задач восстановлена из session JSONL; `list_tasks` возвращает все задачи с корректными статусами и связями
  2. Backward compat: сессии без snapshot работают без ошибок (пустая доска, не crash); существующие 158 тестов `extensions/fan-orchestrator` остаются зелёными
  3. `in_progress` после restore переводится в `pending` с пометкой `recovered: true`; `TaskClear` не затирает pending-задачи при записи snapshot
- **Ожидаемый результат:** Изменения в `extensions/fan-orchestrator/task-manager.js` + `extensions/fan-orchestrator/extension.js` (хук на session JSONL) + интеграция с custom messages `packages/coding-agent/src/core/agent-session-runtime.ts` (~150 LOC, из них ~100 ядро + ~50 расширение)
- **Оценка объёма:** M (≤ 1 день)
