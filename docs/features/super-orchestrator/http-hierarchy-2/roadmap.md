## Фаза A «Процессы и безопасность»

**Цель:** Реализовать менеджер дочерних процессов `fan server`, аутентификацию между узлами через `FAN_NODE_TOKEN`, ограничители глубины/ширины дерева и санитизацию межагентных сообщений. Все 4 функции фазы — модули расширения `fan-super-orchestrator` и изменения ядра для сидинга токена.
**Приоритет функций:** P0 (F-23, F-24, F-25), P1 (F-26)
**E2E-сценарий фазы:**
1. Менеджер процессов порождает дочерний `fan server` на порту 7001 → health-check `GET /api/health` зелёный за <10 секунд → запрос без токена возвращает 401 → запрос с `FAN_NODE_TOKEN` в `Authorization: Bearer` возвращает 200 → kill-switch останавливает узел за <10 секунд, порт освобождён в `child-ports.json`.
2. Depth/width guard: попытка породить узел при `FAN_DEPTH=12` → ошибка порождения + эскалация I3; ширина >4 → отказ в spawn.
**Smoke-критерий фазы:** Spawn одного дочернего `fan server` → health-check зелёный → запрос без токена → 401 → запрос с токеном → 200 → kill-switch останавливает за <10 сек → порт освобождён. `npm run build` зелёный.

#### ✅ F-23: Менеджер дочерних процессов

- **Приоритет:** P0
- **Слой:** [BIZ]
- **Описание:** Реализовать модуль `extensions/fan-super-orchestrator/process-manager.ts` — управление жизненным циклом дочерних `fan server`. Выделение портов из пула `7001–7099` (конфигурируется `portRangeStart`/`portRangeEnd`), блокировка в `~/.fan/agent/child-ports.json`. Запуск: `fan server start --port <N> --host 127.0.0.1` через `child_process.spawn` (detached), PID в `~/.fan/agent/child-<id>.pid`. Health-check: `GET /api/health` каждые 5 секунд, 3 провала подряд → маркировка «unhealthy» → рестарт (1 попытка) → при повторном провале эскалация родителю. Kill-switch: `fan server stop` (SIGTERM → 5s → SIGKILL, по образцу `packages/coding-agent/src/cli/server-command.ts:113`), принудительная остановка всех дочерних при abort миссии. Возврат порта при остановке. Передача `FAN_NO_AUTH=0` в env спавна (обязательно, т.к. `main.ts:1255-1256` по умолчанию `=1` в server mode).
- **Пользовательская история:** «Как L0-узел, я хочу управлять дочерними процессами fan server, чтобы порождать и останавливать узлы дерева»
- **Зависимости:** (none)
- **TDD-тесты:**
  - [x] **TC-F23-1:** Spawn узла и успешный health-check
    - *Условие:* Пул портов свободен, `fan server` доступен в PATH
    - *Шаги:* `processManager.spawn({ id: "L1/node-1" })` → ожидание health-check
    - *Ожидаемый результат:* Порт 7001 заблокирован в `child-ports.json`, PID записан в `child-L1-node-1.pid`, `GET /api/health` возвращает 200 за <10 секунд
  - [x] **TC-F23-2:** Kill-switch останавливает узел за <10 секунд
    - *Условие:* Дочерний `fan server` запущен на порту 7001
    - *Шаги:* `processManager.kill("L1/node-1")` → замер времени
    - *Ожидаемый результат:* Процесс остановлен за <10 секунд, порт 7001 освобождён в `child-ports.json`, PID-файл удалён
  - [x] **TC-F23-3:** Health-check обнаруживает crash за <15 секунд
    - *Условие:* Дочерний процесс запущен, health-check интервал 5 сек
    - *Шаги:* Убить дочерний процесс вручную (`process.kill(pid)`) → ожидание
    - *Ожидаемый результат:* Менеджер маркирует узел «unhealthy» после 3 провалов (15 сек), пытается рестарт (1 попытка), при повторном провале — эскалация
- **Red-тест:** TC-F23-1 — модуль не существует, `processManager.spawn()` не определена.
- **Refactor-цели:** Вынести пул портов в `port-pool.ts` для переиспользования; абстрагировать health-check в `HealthChecker` класс.
- **Критерии приёмки:**
  1. Узел стартует и проходит health-check за <10 секунд; порт не назначается дважды
  2. Kill-switch останавливает поддерево за <10 секунд
  3. Crash дочернего обнаруживается через health-check за <15 секунд; при исчерпании пула — явная ошибка + эскалация
- **Ожидаемый результат:** Модуль `extensions/fan-super-orchestrator/process-manager.ts` (~250 LOC)
- **Оценка объёма:** L (≤ 2 дня)

#### ✅ F-24: Аутентификация узлов (FAN_NODE_TOKEN)

Токен передаётся дочернему процессу через env `FAN_NODE_TOKEN`. Изменение ядра (~25 LOC): дочерний `fan server` при старте, если `FAN_NODE_TOKEN` задан — регистрирует его в ClientToken-хранилище (Prisma) **до** поднятия HTTP-сервера. Сидинг в `packages/coding-agent/src/main.ts` или `server-command.ts` перед вызовом `startServer()`. L0 использует токен для всех вызовов REST/WS дочернего (Bearer / `?token=`). При остановке узла L0 отзывает токен (`DELETE /api/tokens/:id`) перед SIGTERM. `FAN_NO_AUTH=0` передаётся в env спавна (обязательно, см. `main.ts:1255-1256`).
- **Пользовательская история:** «Как L0-узел, я хочу аутентифицироваться на дочерних узлах через токен, чтобы обеспечить безопасность межагентного взаимодействия»
- **Зависимости:** F-23
- **TDD-тесты:**
  - [x] **TC-F24-1:** Дочерний узел принимает запросы только с валидным токеном
    - *Условие:* L0 породил дочерний узел с `FAN_NODE_TOKEN=<token>`
    - *Шаги:* `GET /api/health` без заголовка → 401; `GET /api/health` с `Authorization: Bearer <token>` → 200
    - *Ожидаемый результат:* Запрос без токена отклонён (401), запрос с валидным токеном принят (200)
  - [x] **TC-F24-2:** Токен отзывается при остановке узла
    - *Условие:* Дочерний узел запущен с токеном
    - *Шаги:* `processManager.kill("L1/node-1")` → проверка ClientToken store дочернего
    - *Ожидаемый результат:* Токен отозван (`DELETE /api/tokens/:id` вызван перед SIGTERM); при перезапуске с тем же токеном → 401
  - [x] **TC-F24-3:** FAN_NO_AUTH не влияет на дочерние узлы

    - *Ожидаемый результат:* `FAN_NO_AUTH=0` в env дочернего; запрос без токена → 401 (auth включён)
- **Red-тест:** TC-F24-1 — сидинг токена из env не реализован, дочерний узел не знает о `FAN_NODE_TOKEN`, запрос с токеном → 401.

  1. Дочерний узел принимает запросы только от родителя с валидным `FAN_NODE_TOKEN`
  2. При остановке узла токен отзывается через `DELETE /api/tokens/:id`
  3. `FAN_NO_AUTH=0` в env спавна — auth включён для дочерних узлов
- **Ожидаемый результат:** Модуль `extensions/fan-super-orchestrator/node-auth.ts` (~100 LOC) + изменение ядра ~25 LOC (сидинг `FAN_NODE_TOKEN` в `packages/coding-agent/src/main.ts`)

## Фаза B «Протоколы и учёт»

**Цель:** Реализовать протоколы обмена данными между узлами (пакет работ, отчёт узла), клиент дочернего узла (REST+WS), агрегацию бюджета с глобальным координатором, журнал дерева и стартовую сверку. Все 7 функций фазы — модули расширения `fan-super-orchestrator`.
**Приоритет функций:** P0 (F-27, F-28, F-29, F-30, F-31, F-32), P1 (F-33)
**E2E-сценарий фазы:**
1. L0 отправляет пакет работ L1 через `POST /api/sessions/:id/messages` → L1 выполняет задачу (mock LLM) → L1 завершает → L0 подписан на WS `/api/ws/:sessionId` → получает `agent_end` → извлекает отчёт с `usage: { inputTokens: 15000, outputTokens: 8000, costUsd: 0.45 }` → агрегатор добавляет расход в `mission-budget.json` → tree-journal записывает `{ event: "complete", nodeId: "L1/node-3", usage: {...} }` → инвариант `Σallocated ≤ budget_total` не нарушен.
2. L0 порождает 3 дочерних узла с общим бюджетом 100000 токенов → каждому выделено `min(0.8 × 100000/3, 30000) = 26666` → узел 1 завершается, расход 10000 → остаток 16666 возвращается → узел 2 получает дополнительную долю → `mission-budget.json.by_branch` показывает расход по каждой ветке.
**Smoke-критерий фазы:** Roundtrip пакет работ → отчёт на mock-узле: L0 отправляет пакет → mock L1 возвращает отчёт → `usage` агрегируется → tree-journal содержит 2 записи (spawn + complete) → `Σallocated ≤ budget_total` в `mission-budget.json`.
