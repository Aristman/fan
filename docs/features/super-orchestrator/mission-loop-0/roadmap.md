## Фаза A «Ядро прерываний»

**Цель:** Реализовать минимальный набор механизмов прерываний в ядре FAN, чтобы внешний контур миссии мог безопасно останавливать, осушать и контролировать сессии агента. Все 7 функций фазы — изменения в пакетах `api-gateway`, `agent`, `coding-agent`.
**Приоритет функций:** P0 (F-01–F-07)
**E2E-сценарий фазы:**
1. Запустить `fan server` → отправить `POST /api/sessions/:id/abort` во время генерации → генерация остановлена за <1 секунду, WS-клиент получает событие `agent_end` с причиной `aborted`.
2. Запустить генерацию с зависшим tool call (mock, нет `tool_execution_end` за 12 мин) → watchdog прерывает сессию, генерирует событие прерывания с диагностикой.
**Smoke-критерий фазы:** `npm run build` зелёный + unit-тесты ядра (watchdog, детектор, abort, drain, лимиты) проходят.

#### ✅ F-01: REST abort эндпоинт

    - *Шаги:* `POST /api/sessions/:id/abort` с заголовком `Authorization: Bearer <token>`
    - *Ожидаемый результат:* Статус 202, тело `{ status: "aborted" }`, WS-клиент получает `agent_end` с причиной `aborted` за <1 сек

#### ✅ F-03: Watchdog (сторожевой таймер runtime)

- **Приоритет:** P0
- **Слой:** [BIZ]
- **Описание:** Добавить сторожевой таймер в `packages/coding-agent/src/core/agent-session.ts`. При событии `tool_execution_start` запускается таймер на `watchdogTimeoutMs` (дефолт 720000 мс = 12 мин). Таймер сбрасывается при любом `tool_execution_update` (длинные, но живые вызовы не убиваются). При истечении — генерация прерывается с диагностикой: имя инструмента, время начала, elapsed. При `tool_execution_end` таймер отменяется.
- **Пользовательская история:** «Как оператор миссии, я хочу чтобы зависший tool call был обнаружен и прерван автоматически, чтобы миссия не застряла навечно»
- **Зависимости:** (none)
- **TDD-тесты:**
  - [ ] **TC-F03-1:** Watchdog прерывает зависший tool call
    - *Условие:* `watchdogTimeoutMs = 1000` (тестовое значение), `tool_execution_start` отправлен, `tool_execution_end` не отправляется
    - *Шаги:* Запустить tool call → ждать 1100 мс
    - *Ожидаемый результат:* Генерация прервана, событие прерывания содержит `{ tool: "bash", elapsedMs: 1100, reason: "watchdog_timeout" }`
  - [ ] **TC-F03-2:** tool_execution_update сбрасывает таймер
    - *Условие:* `watchdogTimeoutMs = 1000`, tool call активен
    - *Шаги:* `tool_execution_start` → ждать 600 мс → `tool_execution_update` → ждать 600 мс → `tool_execution_update` → ждать 600 мс
    - *Ожидаемый результат:* Прерывания нет (таймер сбрасывался дважды, общее время 1800 мс > 1000 мс)
  - [ ] **TC-F03-3:** tool_execution_end отменяет таймер
    - *Условие:* `watchdogTimeoutMs = 1000`, tool call активен
    - *Шаги:* `tool_execution_start` → ждать 500 мс → `tool_execution_end` → ждать 1000 мс
    - *Ожидаемый результат:* Прерывания нет, таймер очищен
- **Red-тест:** TC-F03-1 — таймер не существует, зависший tool call работает бесконечно без прерывания.
- **Refactor-цели:** Использовать паттерн существующего stall timer из `extensions/fan-orchestrator/subagent-runner.js` как референс; вынести логику таймера в переиспользуемый `WatchdogTimer` класс.
- **Критерии приёмки:**
  1. Зависший tool call прерывается через `watchdogTimeoutMs` (дефолт 720000 мс) с диагностикой
  2. `tool_execution_update` сбрасывает таймер — живые длинные вызовы не убиваются
  3. `tool_execution_end` отменяет таймер — утечки таймеров нет
- **Ожидаемый результат:** Модуль `WatchdogTimer` + интеграция в хуки инструментов в `packages/coding-agent/src/core/agent-session.ts`
- **Оценка объёма:** M (≤ 1 день)

#### ✅ F-05: Drain-флаг в agent-session

- **Пользовательская история:** «Как оператор миссии, я хочу graceful-паузу, чтобы текущий ход завершился без потери результата»

- **TDD-тесты:**
  - [ ] **TC-F05-1:** Drain завершает текущий ход и останавливает
    - *Условие:* Активная генерация, tool call выполняется
    - *Шаги:* Установить `drainAfterCurrentTurn = true` → дождаться `tool_execution_end`
    - *Ожидаемый результат:* Текущий tool call завершён, новый ход не начат, сессия в состоянии `drained`
  - [ ] **TC-F05-2:** Drain запрещает новые ходы
    - *Условие:* `drainAfterCurrentTurn = true`, текущий ход завершён
    - *Шаги:* Попытка начать новый ход (followUp-сообщение в очереди)
    - *Ожидаемый результат:* Ход не начат, сообщение остаётся в очереди
  - [ ] **TC-F05-3:** Повторная установка drain идемпотентна
    - *Условие:* `drainAfterCurrentTurn = true` уже установлен
    - *Шаги:* Повторная установка `drainAfterCurrentTurn = true`
    - *Ожидаемый результат:* Состояние не меняется, ошибка не генерируется
- **Red-тест:** TC-F05-1 — флаг не существует, после drain сессия продолжает новые ходы.
- **Refactor-цели:** (none) — флаг локализован в `agent-session.ts`, связанность минимальна.
- **Критерии приёмки:**
  1. Drain позволяет текущему tool call завершиться, затем запрещает новые ходы
  2. Флаг идемпотентен — повторная установка безопасна
  3. Состояние `drained` наблюдается через статус сессии
- **Ожидаемый результат:** Поле `drainAfterCurrentTurn` + логика проверки в `packages/coding-agent/src/core/agent-session.ts`
