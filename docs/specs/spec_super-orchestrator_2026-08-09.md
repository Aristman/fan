## 1. Обзор

### 1.1 Цель

Сверх-оркестратор — система, способная длительно (часы и дольше) и автономно работать над большими проектами. Под глобальную задачу динамически выстраивается иерархия агентов: управленцы верхних уровней декомпозируют миссию, координаторы средних уровней ведут фронты работ, воркеры нижних уровней исполняют.

**Ключевые свойства:**
- Многоуровневая иерархия процессов `fan server` (рабочая глубина 3–4, предохранитель 12)
- Миссионный контур (mission loop) — детерминированный внешний цикл с файловым состоянием
- Система прерываний (I0–I4) по аналогии с приоритетами ОС
- Контрольный слой: глобальный бюджет, лимиты глубины/ширины, трассировка, санитизация границ
- Визуализация дерева узлов и статуса миссии в TUI и Dashboard

### 1.2 Контекст

Текущий оркестратор FAN плоский: один координатор порождает воркеров через `subagent-runner.js` (RPC, `--no-extensions`), глубина жёстко равна 1. На больших эпиках координатор упирается в контекст и становится узким местом.

**Что уже есть в FAN:**
- Процессная изоляция воркеров: `child_process.spawn` + JSONL RPC по stdin/stdout (`extensions/fan-orchestrator/subagent-runner.js:236-262`)
- `fan server` — полноценный headless-инстанс с REST+WS API, daemon-режимом, аутентификацией (`packages/coding-agent/src/cli/server-command.ts`)
- Контрольные механизмы: слот-пул (`extensions/fan-orchestrator/workers.js`), stall timer, парсинг вердиктов, менеджер задач
- Очереди steer/followUp — транспорт прерываний I2–I3 (`packages/agent/src/agent.ts:250-256`)
- 24 события расширений (`packages/coding-agent/src/core/extensions/types.ts:991-1026`), fork() с чекпоинтами (`packages/coding-agent/src/core/agent-session-runtime.ts:181`), автокомпактификация (`packages/coding-agent/src/core/compaction/compaction.ts:219`), восстановление из JSONL (`packages/coding-agent/src/core/session-manager.ts:1337`)
- API Gateway: 16+ REST-эндпоинтов + WebSocket (`packages/api-gateway/src/http-server.ts`, `packages/api-gateway/src/ws-handler.ts`)

**Чего не хватает:**
- Глубина = 1 зашита жёстко (`--no-extensions` в `extensions/fan-orchestrator/subagent-runner.js:262`)
- Бюджет независим per-process — нет общего потолка для дерева
- Нет REST/WS abort (~50 LOC)
- Нет сторожевого таймера runtime и детектора циклов
- Нет режима осушения (drain)
- Нет сквозной трассировки (correlation_id) по дереву

**Исследования:**
- DeepMind (дек 2025): неструктурированные агентные сети усиливают ошибки до 17.2×
- MAST (1642 трассы): 36.9% отказов — сбои координации, 41.8% — системный дизайн
- Gartner: >40% агентных проектов закроются к 2027 из-за убегающей стоимости
- Плато координации: выигрыш выходит на плато после ~4 агентов на конвейер
- Token Budget: предел на один прыжок — не более 30k токенов; избирательная передача экономит 30–50%
- AdaptOrch: топология оркестрации даёт 12–23% разницы в результате

### 1.3 Решения пользователя

| Решение | Выбор |
|---------|-------|
| Скоуп | Полный стек (этапы 0–3) |
| Формат миссии | CLI-инициализация + markdown-файлы |
| Управление | TUI slash-команды + виджет |
| Генерация идей | Гибрид (контур + DECIDE) |
| Дашборд | Базовая визуализация (Lit) |

### 1.4 Описание решения (высокоуровневое)

Система строится как два ортогональных измерения:

1. **Миссионный контур (ось времени)** — детерминированный внешний цикл, владеющий состоянием миссии через файлы (`MISSION.md`, `ROADMAP.md`, `STATE.md`, `BACKLOG.md`, `DECISIONS.md`). Короткие сессии сменяют друг друга; между сессиями состояние сохраняется в файлах и git. Контур управляется прерываниями I0–I4.

2. **HTTP-иерархия узлов (ось ширины)** — когда задача слишком велика для одного узла, контур порождает дочерние процессы `fan server` на выделенных портах. Каждый узел — полноценный FAN со своим плоским оркестратором. Родитель управляет ребёнком через REST+WS. Контрольный слой обеспечивает бюджет, лимиты и трассировку.

```
Миссия (задача пользователя)
  │
  ▼
┌─────────────────────────────────────────────┐
│ L0: Миссионный контур + Сверх-оркестратор   │
│  (fan TUI/CLI, расширение fan-mission)      │
│  • декомпозиция миссии, файлы состояния     │
│  • бюджет порождения, потолок расхода       │
│  • correlation_id корня, прерывания I0-I4   │
└───────┬──────────┬──────────┬───────────────┘
        │ REST+WS  │ REST+WS  │ REST+WS     (ширина 3–4)
        ▼          ▼          ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │ L1: fan │ │ L1: fan │ │ L1: fan │   отдельные процессы fan server,
   │ server  │ │ server  │ │ server  │   уникальные порты, health-check,
   │ :7001   │ │ :7002   │ │ :7003   │   guard глубины (env)
   └────┬────┘ └────┬────┘ └────┬────┘
        │ плоский оркестратор внутри каждого L1
        ▼
   RPC-воркеры (существующий subagent-runner)
```

## 2. Функциональные требования

### 2.1 Миссионный контур (этап 0)

#### 2.1.1 Внешний цикл (mission loop)

**Что делается:** Детерминированный цикл, работающий поверх связки «миссионные файлы + короткие сессии + прерывания». Реализуется как расширение `fan-mission`.

**Где в кодовой базе:** Новое расширение `extensions/fan-mission/` (FAN Store). Использует хуки `agent_end`, `session_start`, `session_shutdown`. Взаимодействует с ядром через `actions.sendMessage()`, `actions.abort()`, `actions.compact()`.

**Алгоритм цикла:**
```
while (миссия активна):
  1. ПРОСНУТЬСЯ   ← тик I4, вебхук, команда оператора
  2. ПРОЧИТАТЬ    MISSION.md, ROADMAP.md, STATE.md, git log
  3. РЕШИТЬ       что запускать: идея из бэклога / генерация / доработка / стоп
  4. ЗАПУСТИТЬ    итерацию = сессия (или узел дерева для крупных задач)
  5. ВЕРИФИЦИР.   лестница проверок + непробиваемая метрика
  6. ЗАФИКСИР.    git commit + STATE.md + чекпоинт
  7. ОБНОВИТЬ     бэклог идей (новые из результатов)
```

**Интерфейс:**
- CLI: `fan mission start [--dir <path>]` — запуск контура
- TUI: `/mission:start`, `/mission:stop`, `/mission:status`, `/mission:pause`
- События: расширение публикует `mission_tick`, `mission_iteration_start`, `mission_iteration_end`, `mission_complete`

**Критерии приёмки:**
- Контур выполняет ≥10 итераций без деградации качества (проверка на синтетической миссии)
- Состояние между итерациями полностью в файлах — новая сессия читает `STATE.md` за <30 секунд
- Каждая итерация завершается git-коммитом (если верификация пройдена)
- При abort контура состояние сохраняется, перезапуск продолжает с последней точки

#### 2.1.2 Файлы миссии: форматы и правила

**Где:** `docs/missions/<slug>/` в репозитории проекта.

| Файл | Содержимое | Кто пишет | Формат |
|------|-----------|-----------|--------|
| `MISSION.md` | Цель, рамки, непробиваемая метрика успеха, запреты | Оператор (контур не меняет) | Markdown с YAML frontmatter |
| `ROADMAP.md` | Декомпозиция на этапы с критериями приёмки | Контур по решению агента-планировщика | Markdown, checklist с `[ ]`/`[x]` |
| `STATE.md` | Текущая позиция: что сделано, блокеры, следующие шаги | Контур после каждой итерации | Markdown, читаемый за <30 сек |
| `BACKLOG.md` | Идеи-кандидаты с оценками (скор, источник, статус) | Генератор идей + оператор | Markdown-таблица |
| `DECISIONS.md` | Журнал архитектурных решений с обоснованием | Итерации записывают | Markdown, ADR-формат |

**Формат `MISSION.md`:**
```markdown
---
mission_id: mission-<uuid>
created: 2026-08-09T10:00:00Z
status: active | paused | completed | aborted | failed | budget_exhausted
metric_type: test_pass_rate | build_success | coverage | custom
metric_command: "npm run test:integration"
budget_tokens: 500000
budget_usd: 10.00
max_depth: 4
max_width: 4
---
# Миссия: <название>
## Цель
## Рамки
## Непробиваемая метрика
## Запреты
```

**Критерии приёмки:**
- Каждый файл имеет чёткий формат с валидацией схемы
- `STATE.md` читается и парсится автоматически (регулярные выражения для секций)
- `MISSION.md` frontmatter валидируется при старте; отсутствие обязательных полей → ошибка
- Контур не модифицирует `MISSION.md` после инициализации

#### 2.1.3 Инициализация миссии (`fan mission init`)

**Что делается:** CLI-команда генерирует шаблоны файлов миссии в `docs/missions/<slug>/`.

**Где:** Новый CLI-модуль `packages/coding-agent/src/cli/mission-command.ts` (по образцу `server-command.ts`).

**Интерфейс:**
```bash
fan mission init <slug> [--template default|research|refactor]
```

**Генерируемые файлы:**
- `MISSION.md` — шаблон с placeholder'ами (цель, метрика, бюджет)
- `ROADMAP.md` — пустой чеклист
- `STATE.md` — начальное состояние («миссия инициализирована, ожидает запуска»)
- `BACKLOG.md` — пустой бэклог
- `DECISIONS.md` — пустой журнал

**Критерии приёмки:**
- Команда создаёт директорию и 5 файлов-шаблонов
- Шаблоны различаются по `--template` (default, research, refactor)
- После генерации выводится инструкция: «Отредактируйте MISSION.md и запустите `fan mission start`»
- Повторный `init` на существующий slug → ошибка с предложением `--force`

#### 2.1.4 Управление жизненным циклом (TUI slash-команды)

**Что делается:** Slash-команды в TUI для контроля миссии + виджет статуса.

**Где:** Расширение `fan-mission` регистрирует slash-команды через ExtensionAPI.

**Команды:**
| Команда | Действие | Уровень прерывания |
|---------|----------|-------------------|
| `/mission:start` | Запуск контура из `docs/missions/<slug>/` | — |
| `/mission:stop` | Немедленная остановка (I0) | I0 — abort |
| `/mission:pause` | Осушение: закончить текущую итерацию и встать (I1) | I1 — drain |
| `/mission:resume` | Возобновление после паузы | — |
| `/mission:status` | Вывод текущего состояния (итерация, этап, расход) | — |
| `/mission:steer <msg>` | Инъекция сообщения в работающий цикл (I2) | I2 — steer |
| `/mission:decide <answer>` | Ответ на DECIDE-прерывание | I3 — followUp |

**Виджет миссии (TUI):**
- Коллапсируемый блок над редактором (по образцу task widget оркестратора, Alt+M)
- Показывает: название миссии, текущая итерация, этап ROADMAP, расход (токены/USD), статус
- Авто-скрытие при отсутствии активной миссии

**Критерии приёмки:**
- Все 7 slash-команд работают и выполняют соответствующее действие
- Виджет отображает статус в реальном времени
- `/mission:stop` останавливает контур в течение 1 секунды
- `/mission:pause` позволяет текущей итерации завершиться

#### 2.1.5 Генерация и оценка идей (гибридный режим)

**Что делается:** Контур генерирует идеи-кандидаты, оператор подтверждает спорные через DECIDE-прерывание.

**Алгоритм:**
1. **Генератор** — периодическая итерация (по тику I4 или завершении этапа): анализ результатов, огрехов, возможностей → кандидаты в `BACKLOG.md`. Опционально использует скилл `idea-lab` (quick scan).
2. **Оценщик** — детерминированный скоринг: соответствие `MISSION.md` (0.3), стоимость (0.2), риск (0.2), ожидаемая ценность (0.3). Кандидаты выше порога (0.7) → в ROADMAP. Спорные (0.5–0.7) → прерывание I3 оператору (`DECIDE:вопрос`). Ниже 0.5 → отклонение с записью в `DECISIONS.md`.
3. **Исполнение** — по приоритетам из ROADMAP: один пункт = одна сессия или ветка дерева.
4. **Верификация** — лестница: статика → линтеры → сборка → тесты → приёмочная команда пункта → независимый аудитор в свежем контексте.

**Интерфейс:**
- `BACKLOG.md` обновляется автоматически с полями: `| идея | источник | скор | статус |`
- DECIDE-прерывание: `STATE.md` помечается `blocker: DECIDE:<вопрос>`, контур встаёт на I3
- Оператор отвечает через `/mission:decide <answer>` или записью в `DECISIONS.md`

**Критерии приёмки:**
- Генератор создаёт ≥1 идеи на каждые 3 завершённых итерации
- Скоринг воспроизводим (одинаковые входные данные → одинаковый скор)
- DECIDE-прерывание блокирует контур до ответа оператора
- Все решения (принятые/отклонённые) записываются в `DECISIONS.md`

### 2.2 Система прерываний

#### 2.2.1 Уровни I0–I4

| Уровень | Название | Семантика | Аналог ОС | Механизм |
|---------|----------|-----------|-----------|----------|
| I0 | **Стоп** (немаскируемое) | Немедленный abort: kill генерации, сохранение «aborted» | NMI / SIGKILL | REST `POST /api/sessions/:id/abort` (~50 LOC) |
| I1 | **Осушение** (drain) | Закончить текущий ход и встать | SIGTERM + drain | Флаг `drainAfterCurrentTurn` в `agent-session.ts` (~30 LOC) |
| I2 | **Коррекция** (steer) | Инъекция сообщения между вызовами инструментов | IRQ | Очередь steering (уже есть, `agent.ts:251-270`) |
| I3 | **Постановка** (follow-up) | Задача после завершения цикла | Deferred call | Очередь followUp (уже есть) |
| I4 | **Тик** (heartbeat) | Периодическое пробуждение контура | Timer | Расширение `fan-scheduler` (setInterval + `actions.sendMessage()`) |

#### 2.2.2 Источники прерываний

**Внешние:**
| Источник | Уровень | Механизм в FAN |
|----------|---------|----------------|
| Оператор (TUI/CLI) | I0–I3 | Slash-команды `/mission:*`, REST abort |
| Таймеры/расписание | I4 | Расширение `fan-scheduler` |
| Вебхуки (CI, git) | I2–I3 | Расширение `fan-webhook` (микро-Hono) |
| Файловая система | I2–I3 | `fs.watch` → `sendMessage()` (пример: `packages/coding-agent/examples/extensions/file-trigger.ts`) |
| Бюджетные сигналы | I0–I1 | WS-событие `budget_alert` (warning/critical/exceeded) |
| Родительский узел дерева | I0–I3 | REST+WS API дочернего `fan server` |

**Внутренние:**
| Источник | Уровень | Механизм |
|----------|---------|----------|
| Переполнение контекста | I2 (авто) | Уже есть: auto-compact → auto-retry |
| Детектор циклов | I1 | Новый: семантическое сходство вызовов (~80 LOC) |
| Сторожевой таймер | I0–I1 | Новый: таймер на `tool_execution_start` без `end` (~80 LOC) |
| Исчерпание бюджета итерации | I1 | Бюджет на итерацию (model-manager) |
| Верификация провалена | I2–I3 | `VERDICT: FAIL` → новая итерация с диагностикой |
| Терминальные теги | I1 | `<promise>COMPLETE</promise>` / `BLOCKED:причина` / `DECIDE:вопрос` |

#### 2.2.3 Контроллер прерываний

**Где:** Модуль `extensions/fan-mission/interrupt-controller.ts`.

**Логика:**
1. Слушает все источники (REST, WS, fs.watch, таймеры, внутренние события)
2. Приоритизация: I0 > I1 > I2 > I3 > I4
3. Маршрутизация:
   - I0 → `actions.abort()` + запись `STATE.md` (status: aborted)
   - I1 → установка флага drain + запись `STATE.md` (status: draining)
   - I2 → `POST /api/sessions/:id/messages` с `{ message: msg, streamingBehavior: "steer" }`
   - I3 → `POST /api/sessions/:id/messages` с `{ message: msg, streamingBehavior: "followUp" }`
   - I4 → проверка условий продолжения + `POST /api/sessions/:id/messages` с `{ message: "tick", streamingBehavior: "followUp" }`
4. Дедупликация: повторяющиеся I2/I3 в течение 5 секунд схлопываются
5. Логирование: каждое прерывание записывается в `DECISIONS.md` с timestamp и источником

**Критерии приёмки:**
- I0 останавливает выполнение за <1 секунду
- I1 позволяет текущему tool call завершиться, затем останавливает
- I2 доставляется между tool calls без потери
- I3 не теряется при перезапуске сессии
- Каждое прерывание залогировано

#### 2.2.4 Протоколы (теги обещаний, steer/followUp)

**Теги обещаний** — структурированный протокол терминальных состояний агента:
```
<promise>COMPLETE</promise>          — задача выполнена
<promise>BLOCKED:<причина></promise> — блокер, нужна помощь
<promise>DECIDE:<вопрос></promise>   — требуется решение оператора
<promise>FAILED:<диагноз></promise>  — провал с диагностикой
```

**Обработка:** Контур парсит выход агента на теги (регулярные выражения). При обнаружении:
- `COMPLETE` → верификация → фиксация → следующая итерация
- `BLOCKED` → запись в `STATE.md` → эскалация (I3 оператору или I0 если таймаут)
- `DECIDE` → пауза контура, ожидание `/mission:decide`
- `FAILED` → анализ диагноза → повтор с другой стратегией (если бюджет позволяет) или эскалация

**Steer/FollowUp:** Используются существующие очереди FAN (`agent.ts:251-270`). Ограничения:
- Лимит очереди: 50 сообщений (новый, ~20 LOC в `agent.ts`)
- Dead-letter: сообщения старше 1 часа без доставки → `DECISIONS.md` как «пропущенное прерывание»

**Критерии приёмки:**
- Теги парсятся с точностью >99% (тесты на edge cases)
- `DECIDE` блокирует контур до ответа оператора
- Очереди не раздуваются сверх лимита
- Dead-letter сообщения записываются

### 2.3 HTTP-иерархия узлов (этап 2)

#### 2.3.1 Менеджер дочерних процессов

**Что делается:** Модуль запускает, контролирует и останавливает дочерние `fan server` на выделенных портах.

**Где:** `extensions/fan-super-orchestrator/process-manager.ts`

**Функции:**
- **Выделение портов:** Пул `7001–7099` (настраивается). Порт блокируется в `~/.fan/agent/child-ports.json` на время жизни узла. Проверка свободы: `netstat` / попытка bind.
- **Запуск:** `fan server start --port <N> --host 127.0.0.1` через `child_process.spawn` (detached). PID сохраняется в `~/.fan/agent/child-<id>.pid`.
- **Health-check:** `GET /api/health` каждые 5 секунд. 3 провала подряд → маркировка «unhealthy» → рестарт (1 попытка) → при повторном провале → эскалация родителю.
- **Kill-switch:** `fan server stop` (SIGTERM → 5s → SIGKILL, уже реализовано в `server-command.ts:113`). Принудительная остановка всех дочерних при abort миссии.
- **Возврат порта:** При остановке узла порт освобождается в `child-ports.json`.

**Критерии приёмки:**
- Узел стартует и проходит health-check за <10 секунд
- Порт не назначается дважды
- Kill-switch останавливает весь суб-дерево за <10 секунд
- При crash дочернего процесса parent обнаруживает это через health-check за <15 секунд

#### 2.3.2 Протокол «пакет работ» (L0 → L1)

**Что делается:** Контракт задачи, передаваемой от родителя к дочернему узлу.

**Формат (POST `/api/sessions/:id/messages`):**

Используется существующий `SendMessageRequest` (`packages/api-gateway/src/types.ts:82-85`):
```typescript
{ message: string; streamingBehavior?: "steer" | "followUp" }
```

Пакет работ передаётся как текстовое сообщение (`message`), содержащее JSON-структурированное описание задачи. Поле `streamingBehavior` управляет режимом доставки: `"steer"` — инъекция между вызовами инструментов (I2), `"followUp"` — задача после завершения цикла (I3).

```json
{
  "message": "{\"work_package\":{\"task\":\"Реализовать middleware авторизации\",\"correlationId\":\"mission-uuid/L1/node-3\",\"depth\":1,\"spawnBudget\":4,\"tokenBudget\":50000,\"costBudgetUsd\":2.00,\"toolManifest\":[\"read\",\"write\",\"edit\",\"bash\",\"grep\",\"find\",\"ls\"],\"deadline\":\"2026-08-09T14:00:00Z\",\"verificationCommand\":\"npm run test:unit\",\"context\":{\"parentSummary\":\"Миссия рефакторинга auth, этап 2 из 4\",\"relevantFiles\":[\"src/middleware/auth.ts\",\"tests/auth.test.ts\"],\"constraints\":[\"не менять public API\"]}}}",
  "streamingBehavior": "followUp"
}
```

**Поля:**
- `task` — трассируемая тема задачи (уникальная в рамках миссии)
- `correlationId` — сквозной ID для трассировки по дереву
- `depth` — текущая глубина (guard: `depth < maxDepth`, жёсткий предел 12)
- `spawnBudget` — максимум дочерних узлов, которые L1 может породить
- `tokenBudget` — лимит токенов на узел (рекомендация: ≤30k на прыжок)
- `costBudgetUsd` — лимит стоимости
- `toolManifest` — декларативный манифест разрешённых инструментов
- `deadline` — ISO-8601 дедлайн
- `verificationCommand` — команда верификации результата
- `context` — избирательная передача контекста (экономия 30–50% токенов)

**Передача глубины:** При запуске дочернего `fan server` depth передаётся через env `FAN_ORCHESTRATOR_DEPTH=<N>`. Guard в `subagent-runner.js` проверяет `depth < maxDepth` (12).

**Критерии приёмки:**
- Дочерний узел получает задачу и начинает выполнение за <30 секунд
- `depth ≥ 12` → запуск блокируется, ошибка возвращается родителю
- `spawnBudget` проверяется до запуска каждого дочернего узла
- Узел не использует инструменты вне `toolManifest` (обеспечивается флагом `--tools` при запуске дочернего `fan server`, аналогично `subagent-runner.js:245`)

#### 2.3.3 Протокол «отчёт узла» (L1 → L0)

**Что делается:** Результат работы узла, возвращаемый родителю.

**Механизм:** Родитель подписывается на WS `/api/ws/:sessionId` дочернего узла, ждёт событие `agent_end`. Извлекает финальный результат из последнего assistant message.

**Формат отчёта (структура в памяти родителя):**
```json
{
  "nodeId": "L1/node-3",
  "correlationId": "mission-uuid/L1/node-3",
  "status": "completed | failed | aborted | timeout",
  "verdict": "PASS | FAIL | PARTIAL",
  "result": {
    "text": "финальный текст ответа",
    "filesModified": ["src/module.ts"],
    "filesCreated": ["tests/module.test.ts"],
    "commitsMade": ["abc1234"]
  },
  "usage": {
    "inputTokens": 15000,
    "outputTokens": 8000,
    "costUsd": 0.45,
    "turns": 12,
    "durationMs": 180000
  },
  "children": [
    {"nodeId": "L2/node-3.1", "usage": {"costUsd": 0.12}, "status": "completed"}
  ],
  "completionReason": "task_completed | budget_exhausted | deadline_reached | aborted"
}
```

**Критерии приёмки:**
- Родитель получает отчёт в течение 5 секунд после `agent_end` дочернего
- `usage` агрегируется рекурсивно (включая детей детей)
- `verdict` парсится по маркеру `VERDICT: PASS|FAIL|PARTIAL` (расширение на межпроцессный протокол)
- При таймауте (deadline) узел останавливается, отчёт помечается `status: timeout`

#### 2.3.4 Агрегация бюджета

**Что делается:** Глобальный учёт расхода по дереву с потолком миссии.

**Где:** `extensions/fan-super-orchestrator/budget-aggregator.ts` + `packages/model-manager/src/budget.ts` (модификация).

**Модель:** «Родитель выделяет детям» — L0 имеет общий бюджет миссии, при порождении L1 выделяет долю. Доля = `tokenBudget` из пакета работ.

**Алгоритм:**
1. L0 знает `budget_total` (из `MISSION.md` frontmatter)
2. При порождении L1: `budget_allocated += L1.tokenBudget`. Если `budget_allocated > budget_total` → отказ в порождении
3. L1 отчитывается: при `agent_end` → `usage` добавляется в `budget_consumed`
4. L0 проверяет: `budget_consumed / budget_total > 0.8` → alert (I2 steer); `> 1.0` → останов новых порождений (I1 drain)
5. Агрегация рекурсивна: L1 отчитывается за своих детей

**Освобождение доли:**
- При завершении узла (`node_completed` / `node_failed`): `budget_allocated -= L1.tokenBudget` — аллокация возвращается в доступный бюджет миссии.
- Инвариант: `budget_allocated` = сумма долей всех **активных** (не завершённых) узлов.
- `budget_consumed` обновляется только при фактическом отчёте узла (не при аллокации).

**Контрольный слой — Global Budget Coordinator:**
- Хранится в `~/.fan/agent/mission-budget.json` (общий файл, блокировка через lockfile-паттерн: запись во временный файл → атомарный `rename` с `O_EXCL`)
- Ключи: `mission_id`, `allocated`, `consumed`, `peak`, `by_branch` (расход по веткам дерева)
- Обновляется атомарно (write-to-temp + rename)

**Критерии приёмки:**
- Сумма `allocated` по всем активным узлам ≤ `budget_total` (инвариант)
- При завершении узла его доля немедленно освобождается (decorated `budget_allocated`)
- Расход не превышает `budget_total` более чем на 10% (buffer на in-flight)
- Атрибуция по веткам: видно, какая ветка L1/L2 сколько потратила
- Alert при 80% бюджета

#### 2.3.5 Журнал дерева

**Что делается:** Сквозная трассировка порождений — кто кого породил, с какой задачей, сколько потратил.

**Где:** `extensions/fan-super-orchestrator/tree-journal.ts`

**Формат:** JSONL-файл `docs/missions/<slug>/tree-journal.jsonl`. Каждая запись:
```json
{
  "timestamp": "2026-08-09T10:15:30Z",
  "event": "spawn | complete | fail | abort",
  "nodeId": "L1/node-3",
  "parentId": "L0",
  "correlationId": "mission-uuid/L1/node-3",
  "task": "краткое описание задачи",
  "depth": 1,
  "port": 7003,
  "usage": {"inputTokens": 15000, "outputTokens": 8000, "costUsd": 0.45}
}
```

**Визуализация:** Дерево доступно через CLI (`fan mission tree <slug>`) и Dashboard (компонент `MissionTreeView`).

**Критерии приёмки:**
- Каждое порождение и завершение записано
- По журналу можно восстановить полную топологию дерева
- Журнал не теряет записи при crash (append-only, fsync)
- CLI выводит дерево в читаемом формате (indent по depth)

#### 2.3.6 Startup-reconciliation (очистка сиротских процессов)

**Что делается:** При запуске контура миссии проверить `child-ports.json` и найти orphaned процессы — записи, PID которых не принадлежит текущему родительскому процессу (например, после crash родителя).

**Алгоритм:**
1. При старте `fan mission start` прочитать `~/.fan/agent/child-ports.json`
2. Для каждой записи проверить: `process.kill(pid, 0)` — если PID существует, но не является дочерним текущему процессу (проверка через `process.ppid` или таблицу процессов) → orphan
3. Orphan: `SIGTERM` → ожидание 5 сек → `SIGKILL`
4. Очистить записи orphaned узлов из `child-ports.json`, освободить порты
5. Записать в `tree-journal.jsonl`: `{"event": "orphan_cleanup", ...}`

**Критерии приёмки:**
- При запуске контура все сиротские процессы обнаружены и остановлены за <10 секунд
- Порты сиротских узлов освобождены
- Очистка залогирована в tree-journal

## 3. Пользовательские сценарии

### Сценарий 1: Инициализация миссии

**Актор:** Оператор (разработчик)

1. Оператор выполняет `fan mission init auth-refactor --template refactor`
2. Создаётся `docs/missions/auth-refactor/` с 5 файлами-шаблонами
3. Оператор редактирует `MISSION.md`: указывает цель, метрику (`npm run test:integration`), бюджет (500k токенов, $10)
4. Оператор редактирует `ROADMAP.md`: добавляет 4 этапа с критериями приёмки
5. Оператор запускает `fan mission start --dir docs/missions/auth-refactor`
6. Контур валидирует файлы, создаёт сессию, начинает первую итерацию

**Результат:** Миссия запущена, виджет отображает статус.

### Сценарий 2: Работа оператора — наблюдение и коррекция

**Актор:** Оператор

1. Миссия на 5-й итерации, этап «Написание тестов»
2. Оператор нажимает Alt+M — виджет показывает: 5/8 итераций, $3.45/$10, 3 L1-узла активны
3. Оператор замечает, что агент идёт не туда → `/mission:steer "Сфокусируйся на auth middleware, не на UI"`
4. Прерывание I2 доставляется в steering-очередь, агент учитывает между tool calls
5. Миссия продолжает работу с учётом коррекции

**Результат:** Коррекция доставлена без остановки миссии.

### Сценарий 3: DECIDE-прерывание — генерация идей

**Актор:** Контур → Оператор

1. Контур завершает этап, генератор идей предлагает 3 кандидата
2. Кандидат A (скор 0.85) → автоматически в ROADMAP
3. Кандидат B (скор 0.62) → DECIDE-прерывание: «Добавить рефакторинг database layer? Скор 0.62, риск средний»
4. Контур встаёт (I3), виджет показывает «Ожидает решения оператора»
5. Оператор: `/mission:decide "Да, но только миграции, без изменения схемы"`
6. Контур возобновляет работу, идея записана в ROADMAP с пометкой оператора

**Результат:** Спорное решение передано оператору, ответ зафиксирован.

### Сценарий 4: Прерывание I0 — аварийная остановка

**Актор:** Оператор

1. Миссия работает, L1-узел на порту 7003 зациклился (детектор циклов обнаружил)
2. Детектор генерирует I1 → drain узла 7003
3. Одновременно оператор видит аномальный расход → `/mission:stop`
4. I0: немедленный abort всех узлов, kill дочерних процессов
5. `STATE.md` записывает status: aborted, последняя рабочая точка сохранена
6. Все порты освобождены, процессы остановлены

**Результат:** Миссия остановлена за <10 секунд, состояние сохранено.

### Сценарий 5: Сбой дочернего узла и восстановление

**Актор:** Система (автоматически)

1. L1-узел на порту 7002 crash (OOM)
2. Health-check обнаруживает (3 провала за 15 секунд)
3. Менеджер процессов: рестарт (1 попытка) → health-check → повторный crash
4. Менеджер эскалирует родителю: `node_failed` с диагностикой
5. L0 (контур): помечает задачу узла как «не завершена», анализирует
6. Контур перезапускает задачу на новом узле (порт 7004) с тем же пакетом работ
7. Идемпотентность: ключ идемпотентности = `mission_id + step_number` — дублирование побочных эффектов исключено

**Результат:** Сбой изолирован, задача перезапущена без потери прогресса миссии.

### Сценарий 6: Масштабирование дерева

**Актор:** Контур (автоматически)

1. ROADMAP содержит крупный этап «Миграция базы данных» — контур решает, что нужен суб-дерево
2. L0 порождает L1-координатор (порт 7001) с `spawnBudget: 3`, `tokenBudget: 100000`
3. L1-координатор внутри себя использует плоский оркестратор FAN: порождает RPC-воркеров для параллельных задач
4. L1 отчитывается: `usage` агрегируется включая воркеров
5. L0 получает отчёт L1: «Миграция завершена, 3 файла изменены, 15 тестов пройдено, расход $1.23»

**Результат:** Крупная задача декомпозирована и исполнена деревом.

### Сценарий 7: Бюджетное ограничение

**Актор:** Система (автоматически)

1. Миссия: бюджет $10, потрачено $7.85 (78.5%)
2. Budget aggregator генерирует alert (I2 steer): «Бюджет на 78%, сократите scope»
3. Контур получает steer, корректирует стратегию: отказывается от генерации идей, фокус на завершение
4. При $9.50 (95%): I1 drain — контур завершает текущую итерацию и останавливается
5. `STATE.md`: status: budget_exhausted, описание оставшейся работы
6. Оператор может увеличить бюджет в `MISSION.md` и `/mission:resume`

**Результат:** Бюджет не превышен, состояние сохранено для продолжения.

## 4. Нефункциональные требования

### 4.1 Производительность

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Запуск дочернего узла | <10 сек | `fan server start` + health-check |
| Доставка steer (I2) | <500 мс | Очередь в памяти, без network round-trip для локального |
| Health-check интервал | 5 сек | Баланс между скоростью детекции и нагрузкой |
| WS-задержка визуализации | <5 сек | Приемлемо для оператора |
| Чтение STATE.md | <30 сек | Ограничение на размер файла (~5KB) |
| Предохранитель глубины | 12 | Жёсткий лимит, env `FAN_MAX_DEPTH` |
| Рабочая глубина | 3–4 | DeepMind: плато после ~4 агентов |
| Ширина на родителя | 3–4 | Настраивается, env `FAN_MAX_WIDTH` |
| Максимум одновременных процессов | 16 | L0 + до 4×L1 + до 11 воркеров |
| Пул портов | 7001–7099 | 99 портов, настраивается |

### 4.2 Надёжность

**Crash recovery:**
- Состояние миссии — в файлах (MISSION.md, STATE.md, ROADMAP.md), переживает crash процесса
- JSONL-сессии восстанавливаются через `continueRecent()` (`session-manager.ts:1337`)
- tree-journal.jsonl — append-only с fsync, не теряет записи
- Дочерние процессы перезапускаются менеджером (1 попытка), затем эскалация

**Идемпотентность:**
- Ключ идемпотентности: `mission_id + step_number` (детерминированный, не зависит от переформулировки модели)
- Каждое внешнее действие (коммит, вызов API) помечается: обратимое (с компенсацией — паттерн саг) или необратимое (требует подтверждения)
- Git-коммит после каждой задачи = durable-журнал: новая сессия читает историю

**Защита от зацикливания:**
- Детектор циклов: тот же инструмент + те же параметры + та же ошибка дважды → стоп + запрет подхода
- Бюджет итерации: при исчерпании — запись состояния, пометка «не завершено», эскалация
- Circuit breaker: 3 провала на одном этапе → останов миссии с диагностикой

### 4.3 Безопасность

**Прерывания:**
- REST abort требует аутентификации (ClientToken, как все эндпоинты API Gateway)
- steer/followUp через API — только для авторизованных клиентов
- Внутренние прерывания (детектор циклов, watchdog) не требуют авторизации

**Инъекции:**
- Все межагентные сообщения санитизируются как недоверенный ввод
- `toolManifest` ограничивает инструменты на узле (минимальные привилегии)
- Prompt injection между уровнями: входные данные от дочерних узлов не включаются в системный промпт родителя напрямую — только через структурированный отчёт

**Изоляция:**
- Каждый узел — отдельный процесс с отдельной сессией
- Дочерний `fan server` слушает только на `127.0.0.1` (не на 0.0.0.0)
- PID-файлы и port-registry очищаются при остановке

### 4.4 Масштабируемость

**Лимиты:**
- Глубина: рабочая 3–4, предохранитель 12 (env `FAN_MAX_DEPTH`)
- Ширина: 3–4 на родителя (настраивается), предохранитель 12 (env `FAN_MAX_WIDTH`)
- Бюджет токенов на прыжок: ≤30k (рекомендация, настраивается)
- Общий бюджет миссии: определяется оператором в `MISSION.md`
- **Одна активная миссия на машину** — контур миссии эксклюзивен, параллельные миссии не поддерживаются (конфликт портов, бюджета, файлов состояния)

**Ресурсы:**
- Порт на узел: пул 7001–7099 (99 портов, настраивается)
- Память: ~100MB на `fan server` процесс → 16 процессов = ~1.6GB (реалистичный предел)
- Дескрипторы файлов: ~50 на процесс → 16 × 50 = 800 (в пределах `ulimit -n` default 1024–65536)

### 5.3 API контракты

#### Протокол «пакет работ» (L0 → L1)

**HTTP:** `POST /api/sessions/:id/messages`

Используется существующий `SendMessageRequest` (`packages/api-gateway/src/types.ts:82-85`):

```json
{
  "message": "{\"work_package\":{\"task\":\"Реализовать middleware авторизации\",\"correlationId\":\"mission-abc/L1/node-3\",\"depth\":1,\"spawnBudget\":4,\"tokenBudget\":50000,\"costBudgetUsd\":2.00,\"toolManifest\":[\"read\",\"write\",\"edit\",\"bash\",\"grep\",\"find\",\"ls\"],\"deadline\":\"2026-08-09T14:00:00Z\",\"verificationCommand\":\"npm run test:unit\",\"context\":{\"parentSummary\":\"Миссия рефакторинга auth, этап 2 из 4\",\"relevantFiles\":[\"src/middleware/auth.ts\",\"tests/auth.test.ts\"],\"constraints\":[\"не менять public API\"]}}}",
  "streamingBehavior": "followUp"
}
```

Поле `message` содержит JSON-строку с структурированным описанием задачи. Поле `streamingBehavior` определяет режим доставки: `"followUp"` — задача после завершения текущего цикла, `"steer"` — инъекция между вызовами инструментов (I2).

#### Протокол «отчёт узла» (L1 → L0)

Извлекается родителем из WS-события `agent_end` + последний assistant message. Структура в памяти родителя описана в §2.3.3 (JSON-формат). Дочерний узел возвращает результат через стандартный ответ агента; род парсит финальный assistant message на маркеры `VERDICT: PASS|FAIL|PARTIAL` и извлекает метаданные (изменённые файлы, коммиты, usage).

## 7. Риски и митигация

| # | Риск | Вероятность | Влияние | Митигация |
|---|------|-------------|---------|-----------|
| 1 | Убегающая стоимость токенов при веерном порождении | Высокая | Критичное | Бюджет порождения на запрос + модель «родитель выделяет детям» + предел 30k токенов на прыжок + потолок миссии в `MISSION.md` |
| 2 | Усиление ошибок по дереву (до 17.2×, DeepMind) | Средняя | Критичное | Структурированная топология с явными handoff-схемами; верификация на каждом уровне; порог уверенности >0.7 на передачу вверх |
| 3 | Рекурсивные петли (ребёнок ретраит через порождение) | Средняя | Критичное | Предел глубины на уровне инфраструктуры (env + guard), circuit breaker на ретраи, stall timer на каждом узле |
| 4 | Каскад prompt injection между уровнями | Средняя | Высокое | Санитизация межагентных сообщений; минимальные манифесты инструментов; входные данные от детей не в системном промпте |
| 5 | Исчерпание ресурсов хоста | Высокая (при ширине 12) | Среднее | Реальная ширина 3–4; лимит 12 — предохранитель; пул портов с возвратом; kill-switch по idle-таймауту |
| 6 | Неотлаживаемость недетерминированного дерева | Высокая | Высокое | Сквозной correlation_id, tree-journal, дерево доступно через API и CLI, LLM-as-Judge по итогам веток |
| 7 | Over-engineering | Средняя | Среднее | Поэтапный план (этап 0 → 1 → 2 → 3); валидация на реальных эпиках перед расширением |
| 8 | Контекстная гниль на длинных миссиях | Средняя | Высокое | Короткие сессии (не накапливающие контекст); STATE.md <30 сек; автокомпактификация; сброс контекста между итерациями |
| 9 | Потеря in-flight состояния при crash | Средняя | Среднее | Git-коммит после каждой задачи; checkpoint через fork(); идемпотентность шагов |
| 10 | MAST-отказы: сбои координации (36.9%) | Средняя | Высокое | Явные handoff-схемы, верификация на каждом уровне, трассировка в tree-journal |

## 8. Компромиссы

| Компромисс | Решение | Обоснование |
|------------|---------|-------------|
| Глубина 12 vs рабочая 3–4 | Лимит 12 — предохранитель, рабочая — 3–4 | DeepMind: плато после ~4 агентов; усиление ошибок в глубоких деревьях. Логическая глубина достигается декомпозицией задач, не вложенностью процессов |
| Файловое состояние vs БД | Файлы (Markdown) — основной источник | Соответствует принципу FAN «диск — единственный источник правды»; человекочитаемость; git-совместимость |
| RPC-рекурсия vs HTTP-иерархия | HTTP-иерархия (отдельные `fan server`) | Полная изоляция, наблюдаемость, соответствие задумке «полноценных агентов» |
| Синхронный vs асинхронный вызов | Асинхронный (WS `agent_end`) | Соответствует архитектуре API Gateway; синхронный клиент — обёртка над WS |
| Temporal/durable execution vs git+JSONL | git+JSONL+fork() | Локальный рантайм, не нужен кластер; облегчённый вариант покрывает потребности |
| Генерация идей: авто vs оператор | Гибрид: контур генерирует, оператор подтверждает спорные | Баланс автономности и контроля; DECIDE-прерывание для спорных (скор 0.5–0.7) |
| Один процесс — много сессий vs отдельные процессы | Отдельные процессы | Runtime держит 1 сессию на процесс; изоляция и надёжность |
| Одна миссия на машину vs параллельные миссии | Одна активная миссия | Конфликт портов, бюджета, файлов состояния; упрощение контрольного слоя |
| Graceful pause/resume vs abort+checkpoint | Abort + checkpoint (P3 отложен) | Дешевле в реализации; покрывает сценарии; полное pause/resume — высокая сложность |

### 11.1 Стратегия отката

Система спроектирована для безопасного отката на любом этапе:

| Компонент | Механизм отката |
|-----------|------------------|
| Расширения FAN Store (`fan-mission`, `fan-super-orchestrator`, `fan-scheduler`, `fan-webhook`) | Удаление через `fan store remove <name>` — расширения изолированы и не влияют на ядро |
| Изменения ядра (REST abort, drain, watchdog, детектор циклов) | Feature-flag: env `FAN_MISSION_ENABLED=1` (default: выключено). Без флага новые эндпоинты и режимы не активируются |
| CLI-команды `fan mission *` | Регистрация команды условна: проверяет наличие расширения `fan-mission` |
| Файлы миссии (`docs/missions/`) | Не влияют на работу FAN при отсутствии активного контура |

**Порядок отката:**
1. Остановить активную миссию: `fan mission stop`
2. Удалить расширения: `fan store remove fan-super-orchestrator && fan store remove fan-mission`
3. Убрать `FAN_MISSION_ENABLED` из `.env` (если устанавливался)
4. Перезапустить `fan server`

## Приложение A: Глоссарий

| Термин | Определение |
|--------|------------|
| Сверх-оркестратор | Координатор верхнего уровня, порождающий полноценные инстансы FAN, а не обрезанных воркеров |
| Миссионный контур (mission loop) | Детерминированный внешний цикл, владеющий состоянием миссии через файлы |
| Узел дерева | Отдельный процесс `fan server` со своими сессиями, портом и внутренним плоским оркестратором |
| Бюджет порождения | Жёсткий потолок на число дочерних узлов, проверяемый до запуска |
| Контрольный слой | Инфраструктурные принуждения (лимиты, бюджеты, трассировка), действующие независимо от агентов |
| Прыжок (hop) | Одна передача задачи/результата между агентами; единица учёта расхода |
| correlation_id | Сквозной идентификатор, связывающий все порождения одной миссии |
| Плато координации | Точка (~4 агента), после которой добавление агентов не даёт выигрыш (DeepMind) |
| Тег обещания | Структурированный маркер терминального состояния: `<promise>COMPLETE/BLOCKED/DECIDE/FAILED` |
| Непробиваемая метрика | Метрика успеха, вычисляемая кодом, который агент не может изменить |
| DECIDE-прерывание | Прерывание I3: контур задаёт вопрос оператору и ждёт ответа |
| Drain (осушение) | Прерывание I1: закончить текущий ход и встать |
