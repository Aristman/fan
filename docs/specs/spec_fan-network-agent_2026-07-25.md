## 1. Обзор

### 1.1 Цель

Превратить FAN из локального инструмента в сетевой агент — «agent-native personal cloud». Агент работает на VPS, доступен из любой точки через Web UI, оперирует несколькими проектами (workspaces), решает не только кодовые, но и исследовательские и автоматизационные задачи.

**Сдвиг рамки относительно v1 (FAN Remote):**

| Аспект | v1 (FAN Remote) | v2 (FAN Network Agent) |
|--------|-----------------|------------------------|
| Категория | GitHub-автоматизация | Персональный облачный агент |
| Главный сценарий | Автономные задачи по расписанию → PR | Живая работа из любой точки с любого устройства |
| Проекты | Несколько репо на инстансе | Полноценные workspaces с переключением |
| Задачи | Код → ветки → PR | Код + исследования + документы + автоматизация — всё |
| Аналоги | code-automator, OpenHands | code-server, Coder, Gitpod, Replit Agent, Devin |

### 1.2 Контекст

Аудит кода (code-research, `.fan/reports/research-fan-workspace-mode.md`) показал: workspace-модель уже наполовину заложена в код — сессии группируются по cwd, ресурсы загружаются двухуровнево (глобально + `<cwd>/.fan/`), `SessionManager.listAll()` сканирует все проекты. Блокеры мультипроектности — одна активная ссессия на процесс (`AgentSessionRuntime`), отсутствие `cwd` в Prisma `Session`, project-agnostic API, плоский dashboard без переключателя проектов.

Аудит server mode (`.fan/reports/explore-fan-server-vps-audit.md`) показал: REST API готов (16 endpoints), WebSocket с broadcast, токены готовы. Критические пробелы для публичного доступа: TLS отсутствует, auth авто-отключается в server mode (`main.ts:1138-1143`), `PORT`/`HOST` не читаются из env.

### 1.3 Описание решения: Вариант A

**Workspace-режим в одном процессе FAN.** Один инстанс обслуживает N проектов. API становится workspace-aware, dashboard получает переключатель проектов, runtime — кеш сервисов по cwd. Деплой — существующий VPS (185.219.41.46), на котором уже запущен FAN Store + nginx. FAN соседствует с FAN Store; предлагается отдельный поддомен `agent.sea-agents.ru`. Порт 3456 не конфликтует — FAN Store раздает статику через nginx.

**Почему не вариант B (инстанс на проект):** вариант B даёт изоляцию, но фрагментирует сессии, бюджеты и настройки между инстансами. Нет единой картины — это противоположность цели «сеть». workspace-режим полезен и локально (TUI, dashboard).

## 3. Модель данных верхнего уровня

| Сущность | Описание | Ключевые поля |
|----------|----------|---------------|
| Workspace (проект) | Директория на VPS + конфигурация `.fan/` | путь (cwd), имя, тип (код/ресёрч/автоматизация), реестр в `~/.fan/agent/projects.json` |
| Session | JSONL-файл с историей сессии | id, cwd (поле Prisma, фаза 1), статус, createdAt |
| Project Registry | Реестр известных проектов | массив `{path, name, type}` в `~/.fan/agent/projects.json` |
| Service Cache | Кеш сервисов по cwd (фаза 2) | `Map<cwd, AgentSessionServices>` с LRU |
| Message Queue | Очередь сообщений в sendMessage (фаза 2, перенесена из фазы 5) | FIFO-буфер + мьютекс per-session |

## 4. Нефункциональные требования

### 4.1 Безопасность публичного агента

- TLS обязателен — только через reverse proxy (nginx + certbot на VPS)
- Auth **не может быть отключён** на публичном экземпляре — патч ядра запрещает авто-выставление `FAN_NO_AUTH=1`; env `FAN_PUBLIC=1` принудительно включает auth
- Whitelist-валидация `cwd` против workspace root (фаза 1) — защита от path traversal
- Bot-identity для git: отдельный аккаунт GitHub, push только в feature-ветки, branch protection на main, PR-only политика
- Budget cap для всех задач (общий или per-project)

### 4.2 Надёжность

- Одна активная сессия на процесс — допустимый компромисс для MVP (фаза 2): очередь сообщений предотвращает потерю запросов
- Персистентная очередь задач — фаза 4 вместе с scheduler
- Бэкапы `~/.fan/agent` + репозитории всегда на GitHub

### 4.3 Ресурсы VPS

- Проверка доступных ресурсов (CPU, RAM, диск) перед деплоем — VPS уже содержит FAN Store
- Отдельный поддомен `agent.sea-agents.ru`
- Порт 3456 не конфликтует — FAN Store раздается как статика через nginx
- Docker-compose: один контейнер FAN + nginx/certbot (или nginx уже есть — добавить правило)

## 5. Общие риски и компромиссы

### 5.1 Риски

| Риск | Вероятность | Влияние | Митигация | Фаза закрытия |
|------|-------------|---------|-----------|---------------|
| Удаление `process.chdir()` сломает расширения/MCP-серверы | Средняя | Среднее | Сохранить chdir до фазы 5; регрессионные тесты; аудит потребителей `process.cwd()` | Фаза 5 |
| Публичный агент с shell скомпрометирован | Средняя | Критичное | Auth обязательна, nginx, TLS, whitelist cwd, budget caps | Фаза 0–1 |
| Path traversal через cwd-параметр API | Высокая | Критичное | Whitelist-валидация cwd относительно workspace root; каноникализация путей; отказ на symlink-выход | Фаза 1 (обязательно до публичного доступа) |
| Scope creep «инструмент для всего» | Высокая | Критичное | Жёсткие фазы; каждая фаза = рабочий результат | На всем протяжении |
| Медленное переключение без кеша сервисов | Высокая без кеша | Низкое | ServiceRegistry с LRU (3–5 проектов) | Фаза 2 |
| Потеря задач из очереди при рестарте | Средняя (in-memory) | Среднее | In-memory очередь → фаза 2 с уведомлением клиента; персистентная — фаза 4 | Фаза 2 → фаза 4 |
| Глобальный бюджет: один проект сожжет всё | Низкая | Среднее | Общий cap + алерты; per-project — позже | Фаза 4+ |

### 5.2 Принятые компромиссы

- **Одна активная сессия на инстанс** — допустимо для личного инструмента. Каждая задача имеет свою сессию, но движок исполняет одну за раз. Параллельное исполнение — фаза 5.
- **Autonomy lives outside execution engine** — scheduler отдельный сервис (паттерн code-automator). Ядро FAN остаётся чистым рантаймом.
- **workspace = директория, git опционален** — естественно покрывает кодовые репозитории, исследовательские workspaces, рабочие директории автоматизации. Без архитектурного усложнения.
- **In-memory очередь в фазе 2** — потеря задач при рестарте сервера. Персистентная очередь — фаза 4. Для личного инструмента приемлемо: уведомление клиенту при рестарте.

## 7. Критерии приёмки каждой фазы

### Фаза 0 — Сетевой контур
- [ ] `PORT`/`HOST` читаются из переменных окружения
- [ ] `FAN_PUBLIC=1` блокирует авто-отключение auth (`FAN_NO_AUTH` не перебивается)
- [ ] Dockerfile + docker-compose существуют и собираются локально
- [ ] nginx проксирует `agent.sea-agents.ru` на порт FAN + TLS через certbot
- [ ] Smoke-тест: curl health endpoint, подключение по WS, отправка сообщения через API с токеном
- [ ] Регрессия локального TUI: `npm run build` — 0 ошибок

### Фаза 1 — Workspace-aware API
- [ ] Prisma `Session` имеет поле `cwd` (nullable, миграция назад совместима)
- [ ] Все session endpoints принимают query-параметр `?project=`
- [ ] `POST /api/sessions` принимает `cwd` в теле запроса
- [ ] `GET /api/projects` возвращает реестр проектов
- [ ] `SessionAdapter` — project-aware операции
- [ ] `SessionManager.listAll()` пробрасывает `cwd` в ответы API
- [ ] Реестр проектов `~/.fan/agent/projects.json` существует
- [ ] Стартовый `cwd` сервера = default workspace root (`~/projects`)
- [ ] **Whitelist-валидация cwd** — публичные эндпоинты отвергают пути вне whitelist
- [ ] Регрессия: сборка без ошибок, тесты green, локальный flow не сломан

### Фаза 2 — Workspace UX
- [ ] Service Registry: кеш `Map<cwd, services>` с LRU (лимит 3–5)
- [ ] Инвалидация кеша при изменении `.fan/settings.json` проекта (mtime)
- [ ] Dashboard: переключатель проектов в навигации
- [ ] Dashboard: группировка сессий по проекту (tree view)
- [ ] Settings reload при смене проекта в dashboard
- [ ] MCP reconnect при смене проекта
- [ ] FIFO-очередь + мьютекс на `sendMessage` — задачи не теряются при занятости движка
- [ ] Регрессия: TUI продолжает работать в однопроектовом режиме

### Фаза 3 — Универсальные задачи
- [ ] Типы workspaces: код / ресёрч / автоматизация
- [ ] Шаблоны workspaces (предопределённые структуры директорий)
- [ ] Не-код задачи как первоклассный сценарий: idea-lab, research-spec-generator работают в любых workspaces

### Фаза 4 — Автономность
- [ ] Scheduler-сервис: cron → FAN API, очередь из одной задачи
- [ ] Git/PR-политика: bot-identity, feature-ветки, `gh` CLI
- [ ] Budget caps для автономных задач

### Фаза 5 — Конкурентность (опционально)

- [ ] Персистентная очередь сообщений
