# Spec: feature-pipeline

## Метаданные
- **Дата**: 2026-05-29
- **Автор**: fan-forge
- **Статус**: Утверждена
- **Тип**: Skill (SKILL.md)

## 1. Обзор

### 1.1 Цель
Создать скилл-оркестратор, который автоматизирует полный цикл разработки фичи от roadmap до готового, закоммиченного, протестированного и задокументированного результата.

### 1.2 Описание решения
Скилл `feature-pipeline` принимает roadmap (из `docs/features/<slug>/roadmap.md`), проходит по всем этапам и функциям последовательно, для каждой функции запуская полный TDD-цикл: план → реализация → верификация (цикл до чистого вердикта) → коммит → тестирование. В конце — полная верификация фичи, обновление документации, финальный коммит и отчёт.

## 2. Входные данные

### 2.1 Аргументы
- `/skill:feature-pipeline <slug>` — slug фичи, ищем roadmap в `docs/features/<slug>/roadmap.md`
- `/skill:feature-pipeline <path>` — прямой путь к roadmap.md
- `/skill:feature-pipeline` — интерактивный выбор

### 2.2 Формат roadmap
Ожидается Markdown-файл, сгенерированный `feature-roadmap` с чеклистом функций, разбитых по этапам, где каждая функция имеет:
- ID (F-<этап>.<номер>)
- Название
- Приоритет (P0-P3)
- Описание
- TDD-тесты (TC-<ID>-1,2,3)
- Критерии приёмки
- Зависимости
- Ожидаемый результат
- Чекбокс статуса: ☐ (не начато) / ⏳ (в работе) / ✅ (готово) / ❌ (провалено)

## 3. Выходные данные

### 3.1 Результаты
- Изменённый код фичи (закоммиченный)
- Юнит-тесты, интеграционные тесты, smoke-тесты
- Обновлённая документация (README, API docs, inline)
- Отчёт о выполнении: `docs/features/<slug>/pipeline-report.md`

### 3.2 Структура отчёта
```markdown

> Дата: YYYY-MM-DD HH:MM
> Ветка: feature/<slug>
```

## 4. Процесс работы скилла

### Фаза 0: Инициализация
1. Получить и распарсить roadmap
2. Создать feature-ветку от master/develop
3. Определить slug фичи, рабочую директорию
4. Создать `docs/features/<slug>/pipeline-report.md` (начало)

### Фаза 1..N: Для каждого этапа roadmap
Для каждой функции в этапе (по порядку приоритета, с учётом зависимостей):

#### Шаг A: План
1. Прочитать TDD-тесты для функции из roadmap
2. Определить, какие файлы нужно создать/изменить
3. Спроектировать архитектуру реализации
4. Записать план в `docs/features/<slug>/plans/<function-id>.md`

#### Шаг B: Реализация
1. Создать/модифицировать файлы согласно плану
2. Написать код, проходящий TDD-тесты

#### Шаг C: Верификация (цикл)
1. Запустить `delegate_task(verify, ...)` для проверки реализации
2. Если **PASS** → переход к шагу D
3. Если **FAIL** → исправить замечания, перейти к шагу B
4. Если 3+ итерации и всё FAIL → пометить ❌, спросить пользователя
5. Обновить статус в roadmap (⏳ → ✅ или ❌)

#### Шаг D: Тестирование
1. Написать/обновить юнит-тесты для функции
2. Запустить тесты — все должны проходить
3. Написать/обновить интеграционные тесты (между реализованными функциями)
4. Запустить интеграционные тесты

#### Шаг E: Коммит
```bash
git add -A
git commit -m "feat(<slug>): implement <function-id> - <description>"
```

#### Шаг F: Обновление отчёта
Добавить запись о функции в pipeline-report.md

### Финальная фаза: Завершение
1. **Полная верификация фичи** — `delegate_task(verify, ...)` всей фичи целиком
2. **Smoke-тестирование** — запустить smoke-тесты, проверяющие основной сценарий
3. **E2E-тестирование** — если применимо
4. **Обновление документации проекта** — README, CHANGELOG, API docs, inline docs
5. **Финальный коммит** — `git commit -m "feat(<slug>): finalize <slug> — documentation, tests, verification"`
6. **Финальный отчёт** — завершить pipeline-report.md, представить пользователю

## 5. API Requirements

### 5.1 Tools (внутренние, через delegate_task)
- `explore` — для исследования кодовой базы на фазе плана
- `plan` — для проектирования реализации каждой функции
- `implement` — для реализации кода
- `verify` — для верификации реализации
- `tests-impl` — для написания тестов
- `docs-impl` — для обновления документации

### 5.2 Внешние инструменты (доступны напрямую)
- `read` — чтение roadmap, существующего кода
- `write` — создание план-файлов и отчёта
- `edit` — изменение roadmap (статусы функций)
- `bash` — git-команды, запуск тестов
- `question` — уточнения у пользователя при критических ошибках
- `questionnaire` — множественные вопросы при инициализации

## 6. План расположения

```
~/.fan/agent/skills/feature-pipeline/
├── SKILL.md           # Главный файл скилла с инструкциями
└── README.md          # Документация скилла
```

## 7. Критерии тестирования

- [ ] Скилл загружается через `fan` без ошибок
- [ ] `/skill:feature-pipeline <slug>` корректно парсит roadmap
- [ ] Создаётся feature-ветка
- [ ] Для каждой функции проходятся все шаги (A-F)
- [ ] Цикл верификации работает (FAIL → исправление → повтор)
- [ ] При 3+ фейлах спрашивает пользователя
- [ ] Коммиты создаются с правильными сообщениями
- [ ] Финальная верификация запускается
- [ ] Smoke-тесты запускаются
- [ ] Документация обновляется
- [ ] Отчёт создаётся в `docs/features/<slug>/pipeline-report.md`
- [ ] roadmap.md статусы синхронизированы с реальностью

## 8. Риски

- Огромные roadmap с 20+ функциями — разбивать на сессии, использовать continue
- Ошибки реализации, которые 3+ итерации не исправляются — нужна точка остановки
- Изменения в кодовой базе во время работы скилла — конфликты мержа
- Долгие операции (много функций) — нужны чекпоинты
