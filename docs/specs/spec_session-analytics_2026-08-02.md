# Спецификация: Session Analytics — расширение анализа истории сессий FAN

## Метаданные
- **Дата**: 2026-08-02
- **Автор**: Specification Generator (по результатам idea-lab)
- **Статус**: Черновик
- **Версия**: 1.0
- **Тип**: Новая фича (standalone-расширение FAN)
- **Предшествующее исследование**: `docs/research/idea-lab/session-analytics/Session Analytics — расширение анализа истории сессий.md`

## 1. Обзор

### 1.1 Цель
Расширение FAN, которое читает историю завершённых сессий (JSONL, целиком или батчами), оценивает правильность и чёткость использования скилов и расширений, измеряет скорость, полноту и правильность флоу сессии — и выдаёт отчёт с находками и рекомендациями по улучшению промптов, скилов и конфигурации агента.

### 1.2 Контекст
FAN хранит полную историю сессий локально (`~/.fan/agent/sessions/<cwd>/<timestamp>_<uuid>.jsonl`), но использует её только для продолжения сессий. Ошибки флоу (неверный выбор скилла, отсутствие верификации после реализации, петли, перерасход токенов) обнаруживаются только вручную. Исследование idea-lab подтвердило: все необходимые данные уже присутствуют в JSONL и Prisma, изменений в ядре FAN не требуется. Главная цель — самоулучшение агента (выбрано пользователем при исследовании). Отдельный фокус — **пропорциональность флоу**: тяжёлые скиллы-пайплайны (`feature-pipeline`, `feature-roadmap`, `dev-docs-pack`) на мелких задачах дают длинный и затратный цикл разработки (десятки координационных вызовов на правку в два файла) — это должно детектироваться автоматически. Второй фокус — **аудит работы оркестратора**: выбор типов воркеров, качество их промптов, обработка результатов и выявление повторяющихся паттернов делегирования как кандидатов на новые типы воркеров и скилы.

### 1.3 Описание решения
Standalone-расширение `session-analytics` (по образцу оркестратора, фаза 7.1, распространение через FAN Store) с двухслойной архитектурой анализа:

1. **Детерминированный слой** — потоковый read-only парсер JSONL строит траекторию сессии; детекторы считают метрики и находят нарушения без расхода токенов.
2. **LLM-судья** — получает сжатую траекторию батчами и оценивает семантические рубрики (уместность скилла, полнота результата, качество декомпозиции) по шкале 0–3 с обоснованием.

Триггеры анализа: вручную (инструмент `session_analyze` + slash-команда), автоматически при завершении сессии (только детерминированные метрики), по расписанию (еженедельный пакетный анализ). Отчёты — markdown в `.fan/reports/session-analytics/`. Отдельная вкладка в дашборде для визуализации.

Реализация поэтапная: **Этап A** — детерминированный MVP, **Этап B** — LLM-судья, **Этап C** — дашборд, расписание, золотые траектории.

## 2. Функциональные требования

### 2.1 Основные функции

**Этап A (MVP):**
- **F1. Парсер сессий**: потоковое read-only чтение JSONL через `parseSessionEntries()` из `@seaagents/fan-coding-agent`; поддержка файлов до 10 МБ; фильтрация мусорных сессий (путь содержит `Temp`/`.tmp`, менее 5 записей, только user-сообщения).
- **F2. Нормализатор траекторий**: преобразование записей `SessionEntry` в упорядоченный список шагов `TrajectoryStep` (см. 6.1) по дереву `id`/`parentId` (основная ветка — от корня к последнему листу); обогащение из Prisma `Message` (токены, стоимость, модель) при доступности.
- **F3. Детекторы и метрики** (детерминированные, см. 2.4).
- **F4. Отчёт**: markdown-файл по шаблону (см. 6.2) в `.fan/reports/session-analytics/<session-slug>_<date>.md`; сводный отчёт при пакетном анализе.
- **F5. Инструмент `session_analyze`**: параметры `target: "last" | "<path>" | "dir"`, `mode: "metrics" | "full"`, `batchSize?: number`, `since?: ISO-date`. Возвращает сводку в сессию + путь к отчёту.
- **F6. Slash-команда `/session-analytics [last|dir|path]`**: тонкая обёртка над F5.

**Этап B:**
- **F7. LLM-судья**: рубрики (см. 2.5), батчинг сжатой траектории (аргументы/результаты обрезаются до 500 символов, лимит батча — 30 шагов или 60k символов), агрегация оценок. Модель — через `ModelManager`/`ProviderRouter`, настраивается в конфиге, по умолчанию самая дешёвая доступная.
- **F8. Рекомендации**: секция отчёта с конкретными предлагаемыми правками (промпт, скилл, конфиг) по каждой находке с severity `high`.

**Этап C:**
- **F9. Авто-анализ при завершении сессии**: подписка на событие `session_shutdown`; запуск только детерминированного слоя (режим `metrics`); результат — краткая сводка + путь к отчёту. Отключается в конфиге.
- **F10. Еженедельный пакетный анализ**: при `session_start` проверяется `lastBatchRun` в состоянии расширения; если прошло ≥ 7 дней — пакетный анализ всех сессий, изменённых за неделю, с тренд-сводкой (сравнение с предыдущим периодом).
- **F11. Вкладка в дашборде**: список проанализированных сессий, граф вызовов инструментов, таблица метрик и находок, тренды по неделям. Источник данных — новый endpoint `GET /api/analytics/sessions` (пакет `api-gateway`) или чтение отчётов с диска через существующий файловый доступ дашборда.
- **F12. Золотые траектории**: пометка сессии как эталонной (`/session-analytics mark-golden`); при анализе новых сессий — семантическое сравнение траектории с ближайшей эталонной (через судью).
- **F13. Майнинг паттернов и синтез воркеров**: в пакетном анализе — кластеризация повторяющихся последовательностей tool calls и цепочек типов воркеров (например, `explore → implement → verify`), повторяющихся ad-hoc инструкций в промптах воркеров. Результат — секция сводного отчёта «Рекомендации по синтезу»: кандидаты на новый тип воркера (`.fan/agents/`), новый скилл (через `fan-forge`) или новое правило в CLAUDE.md/SOUL.md, с частотой паттерна и примерами сессий.

### 2.2 Пользовательские сценарии

#### Сценарий 1: Ручной анализ последней сессии
**Предусловия:** есть хотя бы одна завершённая сессия.
**Шаги:**
1. Пользователь вводит `/session-analytics last`.
2. Расширение находит последний JSONL в каталоге текущего cwd, парсит, строит траекторию.
3. Детекторы считают метрики, находят нарушения.
4. В режиме `full` — сжатая траектория батчами уходит судье.
5. Отчёт сохраняется в `.fan/reports/session-analytics/`, в чат выводится сводка: оценки по рубрикам, топ-3 находки, путь к файлу.
**Ожидаемый результат:** пользователь за < 1 минуты (режим `metrics`) получает объективную картину сессии и конкретные рекомендации.

#### Сценарий 2: Автоматические метрики после каждой сессии
**Предусловия:** `autoAnalyze.enabled: true` в конфиге.
**Шаги:**
1. Сессия завершается → событие `session_shutdown`.
2. Расширение запускает детерминированный анализ в фоне.
3. При старте следующей сессии пользователю показывается однострочная сводка («петель: 0, ошибок инструментов: 2, флоу: OK»).
**Ожидаемый результат:** непрерывная обратная связь без действий пользователя и без расхода токенов.

#### Сценарий 3: Еженедельный тренд
**Предусловия:** `weeklyBatch.enabled: true`.
**Шаги:**
1. При старте сессии расширение видит, что последний пакетный анализ был > 7 дней назад.
2. Спрашивает пользователя (или молча, если `weeklyBatch.silent: true`) и анализирует все сессии за неделю в режиме `metrics`.
3. Формирует сводный отчёт: динамика метрик против прошлой недели, рейтинг повторяющихся проблем.
**Ожидаемый результат:** видна динамика качества работы агента во времени.

#### Сценарий 4: Улучшение скилла по находкам
**Предусловия:** в нескольких отчётах повторяется находка «скилл X активирован, но не применён».
**Шаги:**
1. Пользователь открывает сводный отчёт, видит системную проблему.
2. Рекомендация указывает конкретный файл скилла и предлагаемую правку.
3. Пользователь подтверждает и применяет правку вручную или отдельной сессией.
**Ожидаемый результат:** замкнутая петля самоулучшения, контролируемая человеком.

#### Сценарий 5: Синтез нового воркера из паттернов
**Предусловия:** накоплено ≥ 20 проанализированных сессий.
**Шаги:**
1. Еженедельный пакетный анализ обнаруживает: в 6 из 20 сессий повторяется цепочка `explore → implement → verify` со структурно одинаковыми промптами (например, «исследуй модуль X, добавь поле Y, проверь»).
2. Сводный отчёт предлагает: создать тип воркера `schema-migrator` или скилл с готовым флоу, прикладывает 3 примера промптов.
3. Пользователь подтверждает → создаёт агента/скилл отдельной сессией (вручную или через `fan-forge`).
**Ожидаемый результат:** повторяющаяся ручная оркестрация превращается в переиспользуемые артефакты; координационные расходы падают.

### 2.3 Бизнес-правила
- **BR1.** Расширение НИКОГДА не изменяет файлы сессий, скилы, промпты и конфиги. Только чтение + запись отчётов. Исключение: собственное состояние (`lastBatchRun`, реестр золотых траекторий) в `.fan/session-analytics/state.json`.
- **BR2.** Парсинг чужих сессий — только через `parseSessionEntries()`; `SessionManager.open()` запрещён (может перезаписать файл при миграции).
- **BR3.** Сессии самого расширения (содержат вызовы `session_analyze` к анализируемой сессии) исключаются из анализа.
- **BR4.** Рекомендации (включая предложения по синтезу новых типов воркеров и скилов из F13) применяются только человеком. Автоприменение и автоматическое создание агентов/скилов запрещены.
- **BR5.** Мусорные сессии (Temp-каталоги, < 5 записей) исключаются из статистики, но доступны по явному пути.
- **BR6.** REST API сессий (`GET /api/sessions/:id`) не используется как источник данных — теряет аргументы инструментов и служебные записи.

### 2.4 Детерминированные детекторы

D1–D11 и D13 — Этап A; D12 — Этап B (эвристика средней уверенности, требует калибровки).

| # | Детектор | Алгоритм | Источник в JSONL |
|---|----------|----------|------------------|
| D1 | Ошибки инструментов | Доля `toolResult.isError == true`; группировка по `toolName` | `toolResult` |
| D2 | Петли | ≥ 3 повторов `toolCall` с одинаковыми `name` + canonical `arguments` подряд или в окне 10 шагов | `toolCall` |
| D3 | Длительность шагов | Δ`timestamp` между соседними записями; p50/p95 на шаг, на сессию | `timestamp` |
| D4 | Эффективность пути | Число шагов против эвристического минимума (1 user → N toolCalls → финальный text); шаги без продвижения (повторные `read` одного файла) | вся траектория |
| D5 | Флоу оркестратора | Последовательности: `implement`/`bug-fix` воркер без последующего `verify`; `TaskUpdate` без `status`; > 3 попыток реализации одной задачи; повторный `TaskUpdate` с тем же статусом | `delegate_task`, `TaskCreate`, `TaskUpdate` |
| D6 | Использование скилов | Активации по блоку `<skill name="...">` в user-сообщениях + `read` файлов `SKILL.md`; факт применения (следование инструкциям скилла — эвристика по последующим tool calls) | user-сообщения, `read` |
| D7 | Использование расширений | Частота вызовов по `toolName` из реестра расширений (реестр = манифесты установленных расширений + известные встроенные имена) | `toolCall.name` |
| D8 | Уплотнения контекста | Число и позиции записей `compaction`; `tokensBefore` | `compaction` |
| D9 | Стоимость и токены | Сумма по Prisma `Message.tokens/cost` для сессии; на шаг при наличии `usage` в assistant-записях | Prisma + JSONL |
| D10 | Брошенные вызовы | `toolCall` без парного `toolResult` по `toolCallId` | пары call/result |
| D11 | Пропорциональность флоу | Доля координационных вызовов (`assess_task`, `classify_task`, `TaskCreate`, `TaskUpdate`, `list_tasks`, `question`, `questionnaire`, `delegate_task`) среди всех tool calls и доля времени/токенов на координацию против продуктивной работы; флаг «тяжёлый флоу на мелкой задаче»: скилл-пайплайн (список в конфиге) при итоговом diff < `smallChangeLines` строк в < `smallChangeFiles` файлах (объём — из результатов `edit`/`write`) | tool calls, `model_change`, результаты `edit`/`write` |
| D12 | Маршрутизация воркеров | Соответствие типа воркера задаче по регламенту (`bug-fix` для исправлений, `implement` для новых фич, `explore` для поиска): эвристика по ключевым словам описания задачи и фактическим действиям воркера (implement-воркер, чинящий failing-тесты → кандидат на `bug-fix`) | `delegate_task` (agent + task), toolResult воркеров |
| D13 | Пустые ретраи | Повторный `delegate_task` после FAIL с почти идентичным промптом (порог схожести в конфиге) — симптом цикла без изменения стратегии | последовательные `delegate_task` |

Каждая находка: `{ detectorId, severity: "high"|"medium"|"low", title, evidence: {entryIds, excerpt}, recommendation? }`.

### 2.5 Рубрики LLM-судьи (Этап B)

Шкала 0–3 на рубрику + обязательное обоснование со ссылкой на шаги траектории:

| Рубрика | Что оценивает |
|---------|---------------|
| Уместность скилла | Соответствовал ли выбранный скилл задаче; был ли нужен скилл там, где его не вызвали |
| Полнота результата | Закрыт ли исходный запрос пользователя; не осталось ли заявленного несделанным |
| Качество декомпозиции | (Оркестратор) разумность разбивки на задачи, гранулярность, зависимости |
| Экономность | Не было ли заведомо лишних шагов/повторных исследований; пропорционален ли выбранный флоу (скилл, число воркеров) размеру задачи — семантическая проверка D4 и D11 |
| Соответствие регламенту | Соблюдены ли инструкции из SOUL/CLAUDE.md/скилла (например, формат отчётов, verify после implement) |
| Качество оркестрации | Промпты воркеров самодостаточны (контекст, пути файлов, taskId); координатор синтезирует результаты, а не транслирует их дальше без анализа; вердикты verify обрабатываются действием (PASS → движение дальше, FAIL → изменённый промпт, а не копия) |

Общий балл сессии = среднее по рубрикам × вес детерминированного слоя (штраф за находки `high`).

## 3. UI/UX требования

### 3.1 Экраны и компоненты
- **TUI**: вывод сводки инструментом — компактная таблица рубрик + список находок с severity-индикаторами; slash-команда с автодополнением аргументов (`last`, `dir`, путь).
- **Дашборд (Этап C)**: вкладка «Аналитика» — список сессий с баллами; карточка сессии: граф инструментов (временная шкала), таблица метрик (D1–D10), находки, тренд-график по неделям. Визуальный стиль — существующая тема FAN (oklch hue 260°).

### 3.2 Взаимодействие
- Анализ не блокирует сессию: детерминированный — фон, судья — с прогрессом по батчам (`N/M`).
- Каждая находка кликабельна до фрагмента отчёта (в дашборде — до шага траектории).

### 3.3 Обработка ошибок
- Битый/обрезанный JSONL: парсить до первой невалидной строки, отметить в отчёте `truncated: true`.
- Недоступность Prisma: деградация — D9 считается только по `usage` в JSONL, в отчёте пометка об источнике.
- Недоступность судьи (провайдер упал): отчёт сохраняется в режиме `metrics`, рубрики помечаются `n/a`, fallback-модель через `FallbackChain`.
- Сессия не найдена / пустая: понятное сообщение, без стектрейса.

## 4. Нефункциональные требования

### 4.1 Производительность
- Детерминированный анализ сессии 1 МБ — < 3 сек; 8 МБ — < 15 сек (потоковый парсинг, без загрузки файла целиком в память).
- Пакетный анализ 50 сессий (режим `metrics`) — < 3 мин.
- Судья: не более 1 батча в полёте; общий лимит расхода на один анализ — контролируется `BudgetTracker`.

### 4.2 Безопасность
- Только чтение пользовательских данных; отчёты могут содержать фрагменты сессий — хранятся локально, наружу не отправляются (кроме передачи сжатой траектории судье — тот же провайдер, что и у сессии).
- Состояние расширения — только в `.fan/session-analytics/`.

### 4.3 Надёжность
- Падение анализа одной сессии не прерывает пакетный режим (try/catch на сессию, итоговая статистика ошибок в сводном отчёте).
- Отчёты атомарны: запись через временный файл + rename.

### 4.4 Масштабируемость
- Архивы сессий растут неограниченно — фильтры и инкрементальность (анализ только новых/изменённых файлов по mtime).
- Формат JSONL версионируется (`version: 3`) — парсер проверяет версию заголовка, при несовпадении: предупреждение + попытка best-effort.

## 5. Технические требования

### 5.1 Стек технологий
- **Runtime/язык**: Bun + TypeScript (strict), конвенции монорепозитория FAN
- **Форма поставки**: standalone-расширение FAN Store (манифест, автообнаружение — по образцу оркестратора)
- **Данные**: JSONL-файлы сессий, Prisma/SQLite (`filin.db`) через `@fan/db`
- **Судья**: `ModelManager`/`ProviderRouter`/`FallbackChain` (пакет `model-manager`)
- **Дашборд (Этап C)**: Lit + Tailwind, существующий стек `packages/dashboard`

## 6. Данные

### 6.1 Сущности

- **TrajectoryStep**: `{ entryId, ts, kind: "user"|"assistant_text"|"thinking"|"tool_call"|"tool_result"|"system", toolName?, toolCallId?, args?, isError?, model?, tokens?, cost?, durationMs? }`
- **Trajectory**: `{ sessionId, path, cwd, startedAt, endedAt, steps: TrajectoryStep[], skillsActivated: string[], workersSpawned: {type, verdict?}[], compactions: number }`
- **Finding**: `{ detectorId, severity, title, evidence: { entryIds, excerpt }, recommendation? }`
- **SessionScore**: `{ metrics: Record<string, number>, rubrics?: Record<string, 0|1|2|3>, total: number, truncated: boolean }`
- **PatternCandidate** (Этап C): `{ kind: "worker_chain"|"tool_sequence"|"prompt_template", signature, sessionsCount, exampleSessionIds, suggestedArtifact: "worker"|"skill"|"rule", draftProposal }`
- **State** (`.fan/session-analytics/state.json`): `{ lastBatchRun: ISO, golden: [{ sessionId, path, label }], analyzedMtimes: Record<path, mtime> }`

### 6.2 Формат отчёта
Заголовок (сессия, дата, длительность, модели, стоимость) → общий балл → таблица метрик D1–D10 → рубрики судьи (если есть) → находки по severity (с фрагментами-доказательствами) → рекомендации → приложение (граф инструментов текстом/таблицей).

### 6.3 Валидация
- Каждая строка JSONL парсится независимо; невалидная строка — warning, не fatal.
- `arguments` инструментов — `Record<string, any>` без схемной валидации (толерантность к неизвестным полям, включая встречающееся в реальных данных `partialArgs`).
- Рубрики судьи валидируются: только целые 0–3; невалидный ответ судьи — повтор запроса один раз, затем `n/a`.

## 7. Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Шумные/неверные оценки судьи → вредные рекомендации | Средняя | Критичное | Жёсткие рубрики 0–3 с критериями; детерминированные метрики как якорь; BR4 — применение только человеком; калибровка на 10–15 вручную размеченных сессиях |
| `usage` в JSONL не всегда заполнено | Средняя | Среднее | Основной источник D9 — Prisma; расхождения логировать |
| Дорогой анализ больших сессий | Высокая | Среднее | Сжатие (excerptLimit), лимиты батчей, BudgetTracker, режим `metrics` по умолчанию в авто-триггерах |
| Изменение формата JSONL | Низкая | Среднее | Проверка версии заголовка; парсинг через официальный экспорт; тесты на реальных архивных сессиях |
| Хрупкость эвристик детекции скилов | Средняя | Низкое | Два независимых сигнала (D6); юнит-тесты на реальных сессиях; версионирование детекторов |
| Ложные кандидаты при майнинге паттернов (F13) | Средняя | Низкое | Минимальный порог `patternMinSessions`; рекомендации всегда с примерами сессий и частотой; применение только человеком (BR4) |
| Рекурсивный шум (анализ сессий анализатора) | Средняя | Низкое | BR3 |

## 8. Компромиссы (Tradeoffs)

### 8.1 Принятые решения
- **Решение**: собственное расширение вместо экспорта в Phoenix/Langfuse/OTel.
- **Альтернатива**: внешний стек обсервабилити.
- **Обоснование**: внешний стек не знает семантику FAN (скилы, оркестратор, регламенты), требует серверной инфраструктуры; исследование idea-lab оценило его как переинжиниринг для однопользовательского локального рантайма.

- **Решение**: два слоя (детерминированный + судья), а не чистый LLM-анализ.
- **Альтернатива**: только судья / только метрики.
- **Обоснование**: детерминированный слой бесплатен и объективен, но не измеряет «правильность»; судья измеряет, но шумит и стоит токенов. Гибрид снимает ограничения обоих.

- **Решение**: чтение JSONL напрямую, а не через REST API.
- **Альтернатива**: `GET /api/sessions/:id`.
- **Обоснование**: REST отдаёт упрощённые сообщения — теряются аргументы инструментов, `details`, служебные записи, ветки (разведка, п. 5).

- **Решение**: авто-анализ на `session_shutdown` только в режиме `metrics`.
- **Альтернатива**: полный анализ с судьёй после каждой сессии.
- **Обоснование**: стоимость и шум; судья — по осознанному запросу пользователя.
