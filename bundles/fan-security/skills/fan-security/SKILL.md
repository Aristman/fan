# fan-security — методология аудита безопасности

> **Где находятся сканеры:** CLI-сканеры лежат в корне установленного расширения
> fan-security (обычно `~/.fan/agent/extensions/fan-security/`) — команды ниже
> выполняются оттуда. Сам skill устанавливается в `~/.fan/agent/skills/fan-security/`.

Практичный чеклист для агента в обычной сессии. Проходи разделы по порядку, где
возможно — запускай CLI-сканеры пакета, остальное проверяй чтением кода. Всё, что не
подтверждено автоматикой, помечай в отчёте как needs-verification (см. раздел
«Формат отчёта»).

## Когда применять

- Пользователь просит проверить безопасность кода, секретов, зависимостей или конфигов
- Перед коммитом: в диффе появились auth, файлы конфигурации, работа с сетью, `.env`
- Перед релизом: полный проход по всем шести разделам и сводный отчёт

---

## 1. OWASP Top 10 / CWE-чеклист кода

Ручной проход по горячим точкам + автоматика по CWE-сигнатурам:

- Инъекции: SQL (CWE-89), OS-команды (CWE-78), path traversal (CWE-22)
- XSS (CWE-79), CSRF (CWE-352), SSRF (CWE-918), open redirect (CWE-601)
- Жёстко зашитые креды и ключи в коде (CWE-798, CWE-259)
- Слабая криптография: md5/sha1 для паролей, предсказуемая генерация токенов
  (CWE-327, CWE-338)
- Небезопасная десериализация (CWE-502), XXE (CWE-611), prototype pollution
- Бизнес-логика, которую не покрывают сигнатуры: IDOR (CWE-639), broken auth
  (CWE-287), отсутствующие проверки прав

Автоматическая часть: `bun cli/scan-patterns.ts` ищет CWE-сигнатуры в коде; найденное
сверь с ручным проходом и отсей ложные срабатывания.

## 2. Secret scanning

Что ищем: API-ключи, токены, приватные ключи, пароли, connection strings — в коде,
конфигах, тестах, логах и скриптах. Метод: сигнатуры по префиксам известных
провайдеров + entropy-анализ длинных случайных строк.

- Запуск: `bun cli/scan-secrets.ts <путь>` (можно задать директорию или файл)
- Каждое попадание — CRITICAL: секрет считать скомпрометированным, ротация обязательна
- Ротация важнее удаления: убранный из кода секрет остаётся в истории git

## 3. Dependency audit (зависимости)

Проверяй манифесты и lock-файлы всех экосистем проекта: npm, pip, cargo.

- Нативные аудиты: `npm audit`, `pip-audit`, `cargo audit`
- Сводка в единый отчёт: `bun cli/dep-audit.ts` (можно запускать через bun из корня
  проверяемого проекта)
- Смотри не только на версию, но и на применимость: direct или transitive
  зависимость, есть ли работающий exploit, указана ли fix-версия
- Итог: список пакетов с severity и минимальной fix-версией, а не сырой вывод тулзы

## 4. IaC: Dockerfile / compose / k8s

Чеклист по манифестам инфраструктуры:

- Базовый образ зафиксирован тегом или digest, не latest; образ из доверенного реестра
- Контейнер не под root: указан USER; в k8s — readOnlyRootFilesystem, drop capabilities
- Нет `--privileged`, hostNetwork, hostPid; не смонтирован docker.sock
- Секреты не передаются через ENV в открытом виде и не лежат в манифесте plaintext
- compose: пароли не в файле, к порту хоста привязан только необходимый минимум
- k8s: заданы requests/limits, нет автоматического проброса service account token,
  если он не нужен

`cli/scan-patterns.ts` покрывает CWE-сигнатуры кода; манифесты IaC проверяй вручную
по этому чеклисту и помечай спорные пункты как needs-verification.

## 5. Configuration audit

Аудит файлов конфигурации и security-заголовков приложения. Обязательные зоны:

- CORS: нет сочетания `Access-Control-Allow-Origin: *` с credentials; origin из
  allowlist, а не эхо заголовка запроса
- CSP: заголовок Content-Security-Policy задан и не содержит unsafe-inline и
  unsafe-eval для скриптов
- debug: выключен в prod-окружении, verbose-логирование не пишет секреты и токены
- TLS: минимальная версия 1.2, проверка сертификатов не отключена
  (rejectUnauthorized не выставлен в false)
- Cookie: флаги Secure, HttpOnly, SameSite у всех сессионных cookie

Типовой вид проверяемых настроек (что именно смотреть в конфиге):

```yaml
cors:
  origin: "*.example.com"   # не "*"
  credentials: true
csp: "default-src 'self'; script-src 'self'"
debug: false
tls:
  min-version: "1.2"
cookies:
  secure: true
  httpOnly: true
  sameSite: "strict"
```

## 6. Формат отчёта

Итог аудита — единый отчёт. Каждая находка содержит обязательные поля:

- severity — уровень из пяти значений, см. таблицу ниже
- file:line — точное место в коде (для зависимостей — пакет и версия)
- CWE — идентификатор, если применим
- exploit — вектор эксплуатации: как именно это используют злоумышленник или атака
- remediation — конкретный шаг исправления, а не общие слова
- confidence — confirmed (подтверждено чтением кода или сканером) либо
  needs-verification (гипотеза, требующая ручной проверки)

Таблица severity:

| Уровень | Когда ставить |
|---------|---------------|
| CRITICAL | Секрет в коде, RCE, SQL-инъекция, зависимость с работающим exploit |
| HIGH | XSS без санитизации, слабая криптография, открытый CORS с credentials |
| MEDIUM | Отсутствующие security-заголовки, cookie без SameSite, устаревшая зависимость с fix-версией |
| LOW | Отсутствие rate limit, избыточные логи, мелкие отклонения от практик |
| INFO | Замечания по гигиене кода, кандидаты на рефакторинг без прямого риска |

Правило приоритизации: сначала всё CRITICAL и HIGH, потом MEDIUM; LOW и INFO можно
свести в приложение к отчёту.

## Маскирование секретов

Ни один секрет не попадает в отчёт и в чат в открытом виде. Правило 4+4: показывай
первые 4 и последние 4 символа, середину заменяй многоточием
(пример: `sk_live_abcd…wxyz`). Значения короче 9 символов маскируй целиком. Требование
действует везде: evidence в находках, цитаты кода в ответе, примеры фиксов. Сканеры
пакета маскируют находки сами — но при ручном цитировании применяй правило 4+4
самостоятельно.

## CLI-сканеры пакета

Все три сканера находятся в корне установленного расширения fan-security
(обычно `~/.fan/agent/extensions/fan-security/`, см. примечание в начале) и
запускаются через bun:

- `cli/scan-secrets.ts` — secret scanning: паттерны + entropy, маскирование в evidence
- `cli/scan-patterns.ts` — CWE-сигнатуры для кода
- `cli/dep-audit.ts` — dependency audit, сводит нативные аудиты в единый отчёт

Порядок работы: код-чеклист → секреты → зависимости → IaC → конфигурации → отчёт.
