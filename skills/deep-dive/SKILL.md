# Deep Dive — углублённый анализ репозитория

Берёт отчёт `repo-explorer`, извлекает пункты «Следующие шаги» и для
каждого выбранного пункта проводит глубокое исследование исходного кода.
Каждый пункт — отдельный отчёт в той же директории.

---

## Доступные инструменты

При выполнении deep-dive используй следующие инструменты fan. Они доступны
через расширения (zai-tools и другие) и через встроенные возможности fan.

| Инструмент | Описание | Когда использовать |
|-----------|----------|-------------------|
| `read` | Чтение файлов и изображений. Для текстовых файлов — с поддержкой offset/limit для больших файлов. | Чтение исходного кода, конфигов, отчётов |
| `bash` | Выполнение shell-команд. Вывод обрезается до 2000 строк или 50 КБ. | Поиск по коду (`rg`, `grep`, `find`), сборка, тесты |
| `web_search` | Поиск в интернете. Поддерживает фильтры по дате, домену. Ищет через Z.AI MCP или SearXNG. | Поиск документации, issue, PR, статей по теме исследования |
| `web_reader` | Чтение и парсинг веб-страниц по URL. Возвращает markdown или текст. | Чтение найденных страниц, документации, GitHub raw-файлов |
| `memory_search` | Поиск в постоянной памяти (прошлые сессии, решения, знания проекта). | Поиск релевантного контекста из прошлых исследований |
| `question` | Интерактивный вопрос пользователю с вариантами ответа. | Выбор пунктов, уточнение, подтверждение |
| `questionnaire` | Серия вопросов с таб-навигацией. | Множественный выбор пунктов для deep dive |

---

## Когда использовать

- Пользователь передаёт путь к отчёту `repo-explorer` и просит «разобраться
  глубже», «исследовать по пунктам», «deep dive»
- Пользователь запускает скилл явно: `/deep-dive <path-to-report>`
- После `repo-explorer` пользователь хочет углубиться в конкретные модули

---

## Парсинг входных данных

### Формат вызова

```
/deep-dive <путь-к-отчёту> [номера-через-пробел]
```

Примеры:
```
/deep-dive docs/repo-research/NousResearch-hermes-agent/Hermes Agent исследование.md
/deep-dive docs/repo-research/NousResearch-hermes-agent/Hermes Agent исследование.md 1 3 5
```

Если путь не указан — спроси через `question`.

Если номера не указаны — предложи выбрать через `questionnaire`.

### Извлечение данных из отчёта

Прочитай отчёт и извлеки:

1. **Директория сохранения** — `dirname(path)` от файла отчёта. Все deep-dive
   отчёты сохраняются туда же.
2. **Метаданные репозитория:**
   - Название: из `# Исследование: ...`
   - Платформа: из `**Платформа:** ...` (GitHub / Local)
   - Источник: из `*Источник:* ...` в конце файла
3. **Список пунктов:** из секции `## Следующие шаги`. Каждый элемент
   `- [ ] текст` — один пункт. Если пунктов нет — сообщи и остановись.
4. **Уже выполненные пункты:** `- [x]` — уже исследованы, пропусти
   (но покажи пользователю при выборе).

---

## Определение источника кода

Для глубокого анализа нужен доступ к исходному коду. Порядок:

1. **Локальный клон.** Проверь, есть ли директория репозитория локально:
   - Для GitHub: ищи в `cwd` поддиректорию с именем `repo` из URL
   - Для Local: используй путь из `*Источник:*`
2. **GitHub raw.** Если локального клона нет и платформа — GitHub,
   читай файлы через `web_reader` с URL
   `https://raw.githubusercontent.com/{owner}/{repo}/{branch}/{path}`.
   Определи branch из отчёта (или используй `main`).
3. **Спросить.** Если оба варианта не сработали — спроси через `question`,
   где лежит локальная копия репозитория.

## Процесс (для каждого пункта)

### Фаза 1: Скоупинг

**1.1 Маппинг пункта на код**

На основе информации из родительского отчёта (структура, ключевые модули,
архитектура) определи:
- Какие файлы и директории релевантны этому пункту
- Какой язык и какие паттерны ожидать
- Какие зависимости трассировать

**1.2 Составление списка файлов для чтения**

Начни с файлов, упомянутых в пункте или прямо связанных с ним.
Расширь через:
- Импорты/зависимости найденных файлов
- Ключевые модули из отчёта, связанные с темой
- Entry points, упомянутые в отчёте

Максимум **30 файлов** для одного deep dive. Приоритизируй:
- Файлы, напрямую упомянутые в пункте
- Core-файлы модуля (entry points, main classes)
- Конфигурационные файлы

**1.3 Оценка полноты скоупа (0–1)**

- `1.0` — точное соответствие: пункт прямо называет файлы/модули
- `0.7–0.9` — соответствует, но нужны дополнительные файлы
- `0.4–0.6` — Theme ясна, но конкретные файлы не определены
- `0.0–0.3` — непонятно, что читать

Если `<= 0.6` — уточни у пользователя через `question`.

---

### Фаза 2: Чтение и анализ (циклическая)

Повторяй пока средний балл качества < 0.8.

#### 2.1 Чтение исходного кода

Для каждого файла из списка:
1. Прочитай файл полностью (если `<= 500 строк`) или ключевые фрагменты
   (если больше — entry point, публичные функции/классы, константы)
2. Извлеки: публичные символы, их сигнатуры, краткие описания
3. Запомни: импорты (внутренние и внешние), зависимости, паттерны

**Инструменты:**
- `read` — чтение файлов
- `bash` (rg, grep, find) — поиск по коду, трассировка импортов
- `web_reader` — чтение файлов с GitHub (если нет локального клона)

#### 2.2 Трассировка зависимостей

Для ключевых символов:
- Откуда вызываются? (`rg` по вызывающим паттернам)
- Что вызывают внутри? (следования по импортам)
- Какие конфиги используются?

Не углубляйся глубже 2 уровней от основного модуля.

#### 2.3 Дополнительные источники (если нужно)

Если кода недостаточно для полного понимания:
- `web_search` — поиск документации, issue, PR по теме пункта
- `web_reader` — чтение найденных страниц
- `memory_search` — поиск в памяти прошлых сессий по теме
- GitHub: README секций, AGENTS.md, CONTRIBUTING.md

Все инструменты описаны в таблице «Доступные инструменты» выше.

#### 2.4 Оценка качества анализа

После каждого раунда оцени:

| Критерий | Оценка (0–1) |
|----------|-------------|
| Полнота: все ли ключевые файлы прочитаны | |
| Глубина: понятен ли internal flow | |
| Связность: понятны ли связи с другими модулями | |
| Практичность: есть ли конкретные выводы | |

**Средний балл >= 0.8** — переходи к Фазе 3.
**Средний балл < 0.8** — найди слабое место, дочитай файлы, повтори.

---

### Фаза 3: Синтез

#### 3.1 Структурирование

Организуй найденное по разделам:

1. **Обзор** — что это за модуль/система, зачем существует, high-level flow
2. **Ключевые файлы** — таблица: файл, назначение, размер, роль
3. **Архитектура и поток данных** — как работает, диаграмма если нужно
4. **Ключевые решения и паттерны** — design choices, tradeoffs, почему так
5. **Код walkthrough** — step-by-step по основному пути
6. **Зависимости** — internal + external
7. **Выводы** — ключевые находки, takeaways
8. **Дальнейшие вопросы** — что осталось непонятным

#### 3.2 Проверка на полноту

Ответь себе:
- Могу ли я объяснить как это работает за 3 предложения?
- Понятно ли, какие альтернативы были и почему выбрана именно эта?
- Есть ли конкретные рекомендации/выводы?

Если на любой вопрос «нет» — вернись к Фазе 2.

---

### Фаза 4: Генерация отчёта

#### 4.1 Именование файла

**Путь:** та же директория, что и родительский отчёт.

**Имя файла:** `Deep Dive — <текст пункта>.md`

Используй текст пункта для имени, но:
- Обрезай до ~60 символов
- Убирай технические символы (`:`, `—`, кавычки, markdown-разметку)
- Сохраняй суть пункта

Примеры:
```
Deep Dive — Agent loop run_agent.py.md
Deep Dive — Tool lifecycle и orchestration.md
Deep Dive — Terminal backend abstraction.md
Deep Dive — Memory flow builtin vs Honcho vs plugins.md
```

## Финализация: обновление родительского отчёта

После обработки всех выбранных пунктов обнови родительский отчёт:

1. Замени `- [ ] текст пункта` на `- [x] текст пункта → [Deep Dive — ...](./filename.md)`
2. Если все пункты выполнены — добавь секцию `## Deep Dive отчёты`
   с таблицей всех созданных отчётов

---

## Обработка ошибок

| Ситуация | Действие |
|----------|----------|
| Нет секции «Следующие шаги» | «В отчёте нет пунктов для deep dive. Добавьте секцию `## Следующие шаги` с `- [ ]` элементами.» |
| Все пункты уже выполнены | «Все пункты уже исследованы. Хотите пересмотреть какой-то?» |
| Файл отчёта не найден | «Файл не найден: {path}. Укажите корректный путь.» |
| Нет доступа к исходникам | «Не удалось найти исходный код. Укажите путь к локальному клону.» |
| Файл слишком большой (>5000 строк) | Анализируй только ключевые фрагменты, предупреди пользователя |
| GitHub rate limit | Предложи пользователю клонировать репо локально |

## Правила

1. **Код — primary source.** Всё начинается с чтения исходного кода.
   Web-поиск — только для дополнения, не замена.
2. **Конкретность.** Каждый вывод должен быть подкреплён ссылками на
   конкретные файлы, функции, строки. Не «используется кеширование»,
   а «кеширование через `ContextCompressor.maybe_compact()` в
   `agent/context_compressor.py:45`».
3. **Один отчёт — один пункт.** Не смешивай разные пункты в одном отчёте.
4. **Связность с родительским отчётом.** Используй информацию из него
   (архитектура, ключевые модули, зависимсоти) как стартовый контекст.
5. **Не повторяй.** Не дублируй информацию из родительского отчёта.
   Deep dive — углубление, не пересказ.
6. **Оценка качества.** На каждой фазе оценивай результат. Не переходи
   к следующей, пока текущая не >= 0.8.
7. **Лимит файлов.** Максимум 30 файлов на один deep dive. Приоритизируй.
8. **Глубина трассировки.** Максимум 2 уровня зависимостей от основного
   модуля. Не уходи в кроличью нору.
9. **Практические выводы.** Каждый отчёт должен содержать конкретные
   находки и takeaways, а не просто пересказ кода.
