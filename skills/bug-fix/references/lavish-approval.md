# Lavish-аппрув документа решения (Стадия 2)

> Детализация интерактивного цикла аппрува — единственной интерактивности скилла bug-fix
> ПОСЛЕ intake (вопрос пользователю возможен только в исключениях `not_reproducible` /
> неоднозначный Red; здесь вопрос не задаётся — артефакт утверждается). База: скилл lavish
> (`~/.fan/agent/skills/lavish/SKILL.md`, расширение lavish). Применяется к **одному**
> артефакту: **документ решения** — Стадия 2: `docs/bugs/<slug>/bug.md` (шаблон:
> [solution-doc-template.md](solution-doc-template.md)) → HTML-превью
> `.fan/bug-fix/<slug>/bug-preview.html`.

## Когда запускать

Аппрув **обязателен всегда** — конфига «вкл/выкл» у скилла нет. **Продолжение без аппрува
запрещено** (жёсткое правило 1 SKILL.md). Единственное исключение — явный `--hotfix`:
документ создаётся с пометкой `HOTFIX — аппрув post-hoc`, цикл пропускается, в state пишется
`approval.method = "hotfix-bypass"`, в финале — просьба ретроспективного ревью.

## Точный цикл (порядок нарушать запрещено)

### Шаг A: Playbook ДО HTML

```
lavish({ command: "playbook", playbook_id: "plan" })
```

Вызов обязателен **до** написания HTML — он возвращает guidance по структуре и дизайну.
**Пропуск playbook перед HTML запрещён.**

### Шаг B: Рендер HTML

1. Взять содержимое `docs/bugs/<slug>/bug.md` (markdown — источник истины).
2. Отрендерить в HTML-превью `.fan/bug-fix/<slug>/bug-preview.html` (`mkdir -p` при
   необходимости). Требования к HTML:
   - **inline CSS** (`<style>` в файле), без внешних CDN и внешних stylesheets;
   - **relative paths** для любых локальных ассетов (file:// абсолютные пути не резолвятся
     через Lavish-сервер); лучше — без внешних ассетов вообще;
   - семантическая разметка (`<table>`, `<details>`, `<ol>/<ul>`) — аннотации Lavish
     работают лучше на семантике; таблица «Затронутые файлы» и тест-план — обязательно таблицами;
   - статус документа (Proposed) и метаданные шапки — в видимой шапке превью.

### Шаг C: Open → Poll

```
lavish({ command: "open", file: "<path_to_html>" })
lavish({ command: "poll", file: "<path_to_html>" })
```

**Poll после open обязателен.** Возврат к пользователю в чат без сбора фидбека запрещён.

### Шаг D: Обработка ответа poll

| Ответ poll | Значение | Действие |
|------------|----------|----------|
| `layout_warnings` | доказанные серьёзные поломки вёрстки | Исправить HTML (не содержимое!) → повторный `poll`. Не считать итерацией правок. Не спрашивать пользователя, пока вёрстка сломана |
| `prompts` | аннотации/сообщения пользователя | Для каждого prompt: распознать approve-keyword **ИЛИ** трактовать как содержательную правку (см. Шаг E) |
| `status: "ended"` | пользователь закрыл сессию | См. «Завершение после ended» |

### Шаг E: Разбор prompts

Для каждого prompt из `prompts`:

1. **Сравнить с approve-keywords** (фиксированный список: `approve`, `аппрув`, `ок`,
   `согласовано`).
   - Сопоставление: нормализуй регистр и trim; keyword совпадает, если он равен prompt
     целиком или является его однозначным подтверждением в начале/конце короткого prompt
     (≤ 3 слов). Prompt «ок, но добавь кейс про reconnect» — НЕ аппрув: содержит правку.
2. **Если prompt = правка** (всё, что не распознано как approve-keyword): это фидбек к
   документу. Обязательно:
   - внести правку в **markdown** `docs/bugs/<slug>/bug.md` — правка только HTML-превью
     запрещена (markdown — источник истины);
   - перерендерить HTML из обновлённого markdown (тот же файл превью);
   - вызвать `poll` снова, передав `agent_reply` с описанием того, что изменено.
3. **Если все prompts = approve-keywords** (и правок нет) — аппрув зафиксирован.

### Шаг F: Итерации и лимит

- Максимум **5 итераций доработки** (итерация = цикл «правки → перерендер → poll с
  agent_reply»). Лимит фиксированный, не настраивается.
- Лимит исчерпан → **остановка с отчётом** (валидный исход): что утверждено, какие правки
  вносились, путь к `bug.md` и state.json, как продолжить
  (`/skill:bug-fix docs/bugs/<slug>/bug.md` — resume со стадии approval).
- `layout_warnings` не считаются итерациями доработки (это ремонт вёрстки), но бесконечный
  цикл warnings (≥ 5 подряд без прогресса) также ведёт к остановке с отчётом.

## Что считается зафиксированным аппрувом

Аппрув зафиксирован, когда выполнено **одно** из:

1. Все `prompts` в цикле содержат только approve-keywords (ни одной содержательной правки
   в последнем раунде), ИЛИ
2. Последний `poll` вернул approve-keyword, после чего `status: "ended"` (пользователь
   утвердил и закрыл превью).

## Завершение после ended без аппрува

`status: "ended"` и явный аппрув не зафиксирован → **нейтральное уведомление в чат** и
остановка запуска с отчётом (путь к `bug.md`, статус стадии, как продолжить — resume по
state.json или повторный запуск с путём к документу). Запуск не продолжается вглубь без
аппрува; переоткрывать сессию без явной просьбы пользователя запрещено.

## После аппрува

1. Обнови шапку `bug.md`: `**Статус**: Approved (Lavish-аппрув YYYY-MM-DD)`.
2. Запиши в state: `approval.method = "lavish"`, `approval.approvedAt = <ISO>`,
   `approval.iterations = <N>`, `state.stage = "red"`.
3. Уведомление в чат: «Документ решения утверждён, итераций: N».
4. Переход к Стадии 3 (Red) SKILL.md.

## Фолбэк: question (lavish недоступен)

Если lavish-цикл невозможен (расширение не установлено / команда вернула ошибку
доступности) — используй инструмент `question` с **компактным summary** документа:
slug, symptom, найденная причина (1–2 предложения), решение (1–2 предложения), число
тест-кейсов, путь к полному `bug.md`.

Варианты ответа: **approve / внести правки (текстом) / abort**.

- **Правки текстом** → внести в `bug.md` → показать обновлённое summary → снова `question`.
  Те же **5 итераций**; исчерпание → стоп с отчётом.
- **approve** → state: `approval.method = "question"`, `approvedAt`, `iterations`;
  статус `bug.md` → Approved; переход к Стадии 3.
- **abort** → стоп с отчётом, `state.stage = "stopped"`.

## Оба инструмента недоступны (headless)

Если недоступны И lavish, И question → **стоп с отчётом** (документ создан, статус
Proposed, пути к артефактам, инструкция resume). Исключение — **hotfix**: продолжить без
аппрува с пометкой `HOTFIX — аппрув post-hoc` (см. «Когда запускать»).
