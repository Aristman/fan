## Root Cause Analysis

**Причина:** сформулированной причиной, с evidence — файл:строка, трассировка от места
ошибки вверх по стеку.

**Альтернативные гипотезы:** 2–3 кандидата из RCA, почему отклонены.

**Confidence:** высокий | средний | низкий + обоснование.

## Решение

**Отклонённые альтернативы:** варианты фикса, которые рассматривались и отклонены, почему.

## Риски

- **Регрессия:** какие существующие сценарии может задеть фикс.
- **Edge cases:** что может пойти не так на границах.
- **Performance:** влияние на производительность, если релевантно.

## Решения по edge cases

- **Test-infra стратегия:** `auto` (инфраструктура есть) | `manual-scenario` (дефолт при
  отсутствии: ручной сценарий проверки) | `none` (только build) | создать инфраструктуру
  (только по явному аппруву оператора).
- **Режим верификации при невоспроизводимости:** если баг `not_reproducible` (best-effort —
  по умолчанию) — Red заменяется manual-сценарием по описанным шагам, Verify — build +
  manual-сценарий; иначе `N/A`.

## Правила заполнения

1. **Статусы меняются строго по стадиям:** `Proposed` при создании → `Approved` после
   аппрува (с датой и способом: `Approved (Lavish-аппрув YYYY-MM-DD)` /
   `Approved (question YYYY-MM-DD)`) → `Fixed` на Стадии 6. Других переходов нет.
2. **Hotfix:** шапка `**Hotfix:** да (HOTFIX — аппрув post-hoc)`; в финале — просьба
   ретроспективного ревью.
3. **Баг не воспроизведён локально:** в «Проблеме» шаги repro и целевое окружение заполняются
   в любом случае, пометка «воспроизведение — на окружении X по шагам 1–N»; Red-стадия
   заменена manual-сценарием — отразить в «Решениях по edge cases».
4. **Подсекция «Заявленная причина vs найденная»** — только при расхождении RCA с
   `claimedRootCause`; при совпадении — не создавать.
5. **Секция «Результат»** заполняется только после PASS verify; при остановке с отчётом
   (FAIL после 3 циклов) — краткий статус вместо финального заполнения.
