# bug-fix — конвейер исправления багов (v2)

Координаторский скилл-оркестратор. Получает описание бага в любом виде → выясняет корневую
причину → оформляет документ решения → получает аппрув оператора → пишет красные тесты →
чинит код минимальным диффом → верифицирует независимо.

**Главное отличие от v1:** фикс без утверждённого документа не выполняется. Сначала причина
и план, потом тесты, потом код.

## Контекст запуска

Скилл исполняет **координатор**. Координатор НЕ пишет код и тесты сам — каждая исполнительная
стадия делегируется воркеру через `delegate_task`.

| Запрещено | Обязательно |
|---|---|
| Писать/править код руками координатора | TaskCreate на каждую воркерскую стадию |
| Отдавать документ на аппрув воркеру | Отдельный `delegate_task` на каждый шаг |
| Продолжать без аппрува (искл.: hotfix) | verify-воркер ≠ bug-fix-воркер (независимость) |
| «Спроси пользователя» внутри воркера | Воркер возвращает статус координатору |

Типы воркеров: `code-research` (RCA), `tests-impl` (Red), `bug-fix` (Green), `verify` (проверка).

## Точка входа и resume

| Аргумент | Старт |
|---|---|
| Свободное описание / stack trace | Стадия 0 (Intake) |
| Путь к тикету/доке/спеке (`docs/tickets/TICKET-42.md`) | Стадия 0, читать файл |
| Slug или путь `docs/bugs/<slug>/bug.md` | Resume по `.fan/bug-fix/<slug>/state.json` |
| Без аргумента | Найти свежий прогон: один → resume, несколько → самый свежий + уведомить, ноль → стоп с отчётом |

## Стадия 0: Intake (координатор)

Нормализовать вход в карточку бага `.fan/bug-fix/<slug>/intake.md`:

1. **Путь к файлу** → прочитать, извлечь поля из структуры документа.
2. **Stack trace** (эвристика: `at `, `Error:`, `Exception`, `Traceback`) → топ-фреймы + `файл:строка`.
3. **Свободный текст** → извлечь: symptom, expected vs actual, контекст (модуль/файл/фича),
   шаги воспроизведения, error output, **заявленная причина** (`claimedRootCause`),
   severity (опционально: critical|major|minor|trivial).
4. Флаг `--hotfix` в аргументе или явное «hotfix» → `input.hotfix=true`.
5. Slug = `bug-<kebab-symptom>`. Проверить `git status` (незакоммиченные изменения — отметить).
6. Инициализировать `.fan/bug-fix/<slug>/state.json` (схема ниже).
7. Шагов воспроизведения нет во входе → `question` оператору: запросить описание шагов
   repro (законный вопрос вне аппрува).

Несколько багов во входе → один прогон = один баг, остальные зафиксировать и предложить
отдельные запуски.

## Стадия 1: RCA (воркер code-research)

`delegate_task(agent="code-research")` — read-only, но bash доступен для запуска сборки/тестов.

Задача воркера:
1. **Воспроизвести — best effort на текущем окружении**: определить команду (build /
   конкретный тест / сценарий), запустить, сохранить вывод как baseline. Баг может
   воспроизводиться только на ином окружении (OS, устройство, данные, конфиг) — неудача
   локального repro НЕ блокирует пайплайн.
2. **Трассировать причину**: от места ошибки вверх по стеку, проверить типы, зависимости,
   конфиги; прочитать CLAUDE.md проекта (нарушение правил — частая причина).
3. **Гипотезы**: 2–3 альтернативы, приоритизация, why-обоснование выбранной.

**Fast-path:** если `claimedRootCause` задан — воркер НЕ проводит полный поиск, только
подтверждает или опровергает заявку (сокращённая проверка + evidence).

Критерий выхода: RCA с обоснованием `файл:строка` + задокументированные шаги воспроизведения
(команда или manual-сценарий на указанном окружении). Само воспроизведение не обязательно —
описание шагов обязательно. Статус: `confirmed` / `refuted` / `not_reproducible`.

`not_reproducible` — **не стоп**: шаги repro и целевое окружение фиксируются в bug.md с
пометкой «воспроизведение — на окружении X по шагам 1–N», трассировка ведётся по коду и
логам. Red-стадия — manual-сценарий по описанным шагам, Verify — build + manual-сценарий.
Если шаги отсутствуют во входе — их запрашивает координатор на стадии 0.

## Стадия 2: Документ решения + аппрув оператора (координатор)

Создать `docs/bugs/<slug>/bug.md`:

```markdown
# bug: <slug>
slug / дата / severity / статус (Proposed → Approved → Fixed) / source входа

## Проблема
symptom, expected vs actual, шаги воспроизведения, команда + observed output

## Root Cause Analysis
причина с evidence (файл:строка, трассировка), альтернативные гипотезы, confidence.
Подсекция «Заявленная причина vs найденная» — при расхождении. Молчаливо переопределять
причину оператора запрещено.

## Решение
планируемый минимальный дифф (по файлам), почему чинит причину, а не симптом,
отклонённые альтернативы

## Затронутые файлы
таблица: файл → характер изменения

## Тест-план
TC-BUG-<slug>-1..N: условие / шаги / ожидание; пометки о переиспользовании существующих тестов

## Риски
регрессия, edge cases, performance

## Решения по edge cases
test-infra стратегия; режим верификации при невоспроизводимости
```

Детальный цикл аппрува — `references/lavish-approval.md`; структура и правила заполнения документа — `references/solution-doc-template.md`.

### Аппрув через Lavish (основной путь)

1. `lavish({ command: "playbook", playbook_id: "plan" })` — ДО написания HTML.
2. Рендер `bug.md` → `.fan/bug-fix/<slug>/bug-preview.html` (inline CSS, relative paths).
3. `lavish({ command: "open", file: ... })` → `lavish({ command: "poll", file: ... })`.
4. `layout_warnings` → чинить вёрстку → re-poll (не считается итерацией правок).
5. Feedback с правками → вносить в **markdown** `bug.md` (источник истины) → перерендер →
   re-poll с `agent_reply`. Лимит **5 итераций** → стоп с отчётом.
6. Approve-keywords (`approve`, `аппрув`, `ок`, `согласовано`) → записать в state
   (`approval.method="lavish"`, `approvedAt`), статус документа → `Approved`.
7. `poll` → `status: "ended"` без аппрува → нейтральное уведомление, стоп.

### Фолбэк question (lavish недоступен)

`question` с компактным summary документа: `approve / внести правки (текстом) / abort`.
Те же 5 итераций.

Если недоступны И lavish, И question (headless) → стоп с отчётом (кроме hotfix).

**Продолжение без аппрува запрещено.**

## Стадия 3: Red — тесты на все кейсы (воркер tests-impl)

`delegate_task(agent="tests-impl")` с тест-планом из утверждённого документа.

Требования:
- **Каждый TC тест-плана покрыт тестом.** Существующие тесты, уже покрывающие часть кейсов —
  переиспользовать, не дублировать.
- Запустить новые тесты на текущем (незафиксенном) коде → **обязательный FAIL**.
- **Red-критерий:** каждый тест падает по правильной причине — assertion mismatch / ожидаемое
  исключение, а НЕ ошибка импорта/синтаксиса/setup. Воркер возвращает per-TC цитату failure.

Анти-паттерны: `skip`, тесты-заглушки, ослабленные ассерты.

**Тесты зелёные до фикса → стоп:** либо баг уже починен (быстрая проверка RCA → отчёт
«already fixed» с evidence, state → done), либо тесты неверны (возврат на стадию 3 с правками).
Неоднозначность → вопрос оператору (разрешённое исключение).

---

## Стадия 4: Green — минимальный фикс (воркер bug-fix)

`delegate_task(agent="bug-fix")`. В task передать: RCA-резюме, affected-файлы, список
red-тестов с командами запуска. Worker-инструкция — секция «Worker-инструкция» ниже в этом
файле (координатор вкладывает её в контекст).

Критерий выхода: все red-тесты зелёные, воркер вернул diff-summary.

---

## Стадия 5: Verify (воркер verify)

`delegate_task(agent="verify")` — независимая adversarial-проверка:
build всего проекта + полный test suite + red-тесты зелёные + нет новых
ошибок/предупреждений + «чинит ли фикс причину, а не симптом».

Вердикт `FAIL` → возврат на стадию 4. Счётчик попыток общий: **максимум 3 цикла Green↔Verify**.
Исчерпание → стоп с отчётом: что сделано, diff, причины FAIL, рекомендация. Без автопродолжений.

---

## Стадия 6: Финал (координатор)

1. Статус `bug.md` → `Fixed`, секция «Результат»: diff-summary, вердикт verify, commit-SHA.
2. Коммит по политике из state (`commitPolicy`): `fix(<scope>): <summary>`, conventional.
3. Финальный отчёт в чат. `state.stage = "done"`. `TaskClear`.

## Состояние и resume

Полная схема и правила resume — `references/state-schema.md`.

При resume перед TaskCreate проверить существующие задачи через `list_tasks` — идемпотентность.

`.fan/bug-fix/<slug>/state.json`:

```json
{
  "slug": "bug-session-switch-crash",
  "createdAt": "<ISO>", "updatedAt": "<ISO>",
  "input": { "type": "text|file|stacktrace", "source": null,
             "claimedRootCause": null, "severity": "major", "hotfix": false },
  "stage": "intake|rca|approval|red|green|verify|done|stopped",
  "rca": { "status": "confirmed", "summaryRef": "docs/bugs/<slug>/bug.md#rca", "attempt": 1 },
  "approval": { "method": "lavish|question|hotfix-bypass", "approvedAt": "<ISO>", "iterations": 2 },
  "red": { "tests": [{ "id": "TC-BUG-...-1", "file": "...", "failReason": "..." }], "confirmed": true },
  "green": { "attempts": 1, "maxAttempts": 3, "diffFiles": ["..."] },
  "verify": { "verdict": "PASS", "runs": 1 },
  "decisions": { "commitPolicy": "auto|manual|none",
                 "testInfra": "auto|manual-scenario|none",
                 "docPath": "docs/bugs/<slug>/bug.md" },
  "commits": []
}
```

Resume: чтение state → продолжение с `state.stage`. Отсутствующие ключи → безопасные дефолты
+ запись в отчёт, НЕ вопрос. Стадия считается выполненной, если её артефакты существуют.
Повреждённый state.json → стоп + инструкция пересоздания.

## Edge cases

| Ситуация | Поведение |
|---|---|
| Баг не воспроизводится локально | Не стоп: шаги repro и окружение фиксируются в bug.md, трассировка по коду/логам, пометка в документе; Red → manual-сценарий. Шагов нет во входе → запросить у оператора на Intake |
| Нет тестовой инфраструктуры | Решается на аппруве через секцию «Решения по edge cases»: `manual-scenario` (дефолт) / `none` (только build) / создать инфраструктуру (только по явному аппруву) |
| RCA противоречит заявленной причине | Подсекция «Заявленная vs найденная» + заметка в чат; решение — аппрув документа |
| Hotfix | Только по явному флагу. Документ пишется, помечается `HOTFIX — аппрув post-hoc`, в финале — просьба ретроспективного ревью. Дефолтом НЕ является |
| Баг уже починен | Red-тесты зелёные → проверка → отчёт «already fixed» с evidence, без коммита |
| Несколько багов | Один прогон = один баг; остальные — отдельные запуски |

---

## Жёсткие правила

1. **Аппрув обязателен** (исключение — явный hotfix). Нет аппрува — нет фикса.
2. **Ноль вопросов после intake** (исключения: отсутствие шагов repro, неоднозначный Red).
   Все развилки решаются документом и его аппрувом.
3. **«Спроси пользователя» в воркере запрещено** — воркер возвращает статус координатору.
4. **Минимальный дифф.** Refactor-стадии НЕТ сознательно — рефакторинг ≠ фикс.
5. **1 стадия = 1 воркер = 1 задача.** Координатор код не пишет.
6. **Markdown — источник истины.** HTML — превью для аппрува, правки вносятся в `bug.md`.
7. **Red обязателен.** Тест, который зелёный до фикса, не доказывает ничего.
8. **Максимум 3 цикла Green↔Verify.** Исчерпание → честный стоп с отчётом.

## Артефакты

| Артефакт | Путь | Коммитится |
|---|---|---|
| Документ решения | `docs/bugs/<slug>/bug.md` | да (вместе с фиксом) |
| Intake-карточка | `.fan/bug-fix/<slug>/intake.md` | нет |
| State/resume | `.fan/bug-fix/<slug>/state.json` | нет |
| HTML-превью | `.fan/bug-fix/<slug>/bug-preview.html` | нет |

## Worker-инструкция: стадия Green (bug-fix-воркер)

Ты — Bug Fix Worker. RCA уже выполнена, документ решения утверждён, красные тесты написаны.
Твоя задача: минимальным изменением сделать их зелёными.

**Интерактив недоступен:** инструментов `question`/`lavish` у тебя нет. При блокере — верни
статус `FAILED` + причину координатору, не зависай.

### Принципы фикса

- **Минимальный дифф** — только то, что нужно для исправления.
- **Один фикс на один баг** — не чини несколько багов сразу.
- **Следуй стилю проекта** и правилам CLAUDE.md.
- **Не ослабляй тесты.** Тест кажется неверным → репорт координатору, а не хак.

### Чеклист перед фиксом

- [ ] Понимаю почему этот код вызывает баг (RCA из задачи)
- [ ] Фикс решает корневую причину, а не симптом
- [ ] Фикс не меняет логику в других местах
- [ ] Фикс следует стилю проекта и CLAUDE.md

### Применение

Используй `edit` для точечных изменений. Не переписывай файл целиком.
Новый файл — только если без него никак (`write`).

### Верификация (обязательна)

1. Целевые red-тесты:
```bash
./gradlew :module:test --tests "ClassName.testName"   # Gradle/Kotlin
npx vitest run path/to/test                            # JS/TS
```
2. Полная сборка: `./gradlew build` / `npm run build`.
3. Полный test suite. Убедись: сборка проходит, существующие тесты зелёные (кроме сломанных
   до фикса), новых предупреждений компилятора нет.

Если верификация не прошла: ошибка в твоём фиксе → исправь и повтори (максимум 3 попытки).
Ошибка была до фикса → зафиксируй в отчёте отдельно, не трогай.

### Формат ответа

```markdown
## Green Report

### Фикс
- **Файл:** {path}
- **Изменение:**
```diff
- старая строка
+ новая строка
```

### Red → Green
- {test name}: 🔴 {fail reason} → 🟢 PASSED

### Верификация
- Build: ✅ / ❌ {details}
- Full suite: ✅ / ❌ {details}
- Регрессия: ✅ нет новых ошибок / ⚠️ {description}

### Файлы изменены
| Файл | Изменение |
|------|-----------|
| `{path}` | {краткое описание} |

---
*Green Report от bug-fix worker (v2)*
```

## Правила (наследие v1, остаются в силе)

1. **Задокументируй repro раньше чем чинишь.** Шаги воспроизведения обязательны; локальное
   воспроизведение — best effort (баг может воспроизводиться только на ином окружении).
2. **Минимальный дифф.** Один баг — одно изменение.
3. **Верифицируй всё.** Build + test после каждого фикса.
4. **Не угадывай.** Каждое утверждение подкрепляй чтением кода.
5. **Пиши отчёт.** Каждый фикс завершается структурированным отчётом.
6. **Нет аппрува — нет фикса.** v2.
