# Stage Decomposition Guide — Гид по декомпозиции на этапы

## Принципы

1. **Каждый этап должен быть независимо smoke-тестируем** — после завершения этапа N можно запустить всю систему и проверить работу этапа N.
2. **Границы этапов на естественных точках интеграции** — не произвольные.
3. **Data layer first** — этапы обычно следуют: данные → логика → API → UI.
4. **Risk-early** — неопределённые/рисковые задачи — в ранние этапы.
5. **Инкрементальная ценность** — каждый этап доставляет наблюдаемую ценность.

---

## Алгоритм декомпозиции

### Шаг 1: Извлечь функциональные блоки из спеки

Прочитать спеку и выделить:
- Модели данных / схемы
- Бизнес-логику / правила
- Внутренние API / сервисы
- Внешние API / эндпоинты
- UI-компоненты / экраны
- Инфраструктура / конфигурация
- Миграция / совместимость

### Шаг 2: Определить dependency chains

```
Data Models → Business Logic → Internal API → External API → UI
     ↓              ↓               ↓              ↓
  Migration   Validation      Auth/RateLimit   Error Pages
```

### Шаг 3: Определить cross-cutting concerns

- Аутентификация / авторизация
- Обработка ошибок
- Логирование / observability
- Управление конфигурацией

### Шаг 4: Подсчитать complexity score

```
Complexity = N (функциональные блоки) + I (точки интеграции) + S (UI-экраны) + E (API-эндпоинты)
```

### Шаг 5: Определить количество этапов

| Complexity | Этапов | Подход |
|-----------|--------|--------|
| < 5 | 1–2 | Small feature — всё в одном или двух этапах |
| 5–10 | 3–4 | Medium feature — data/logic → API → UI → polish |
| 11–20 | 4–6 | Large feature — data → logic → API → UI → integration → polish |
| > 20 | 6–10 | Epic — вертикальные слайсы по функциональности |

## Шаблоны декомпозиции

### Small (1–2 этапа)

**Этап 1: Полная реализация**
- Data model + Business logic + API + UI в одном проходе
- TDD: Red → Green → Refactor для всего
- Smoke-тест: полный пользовательский сценарий

**Этап 2 (опционально): Полировка**
- Edge cases, performance, UX-улучшения
- Дополнительные тесты

### Medium (3–4 этапа)

**Этап 1: Data model + Core logic**
- Модели данных, репозитории, базовые сервисы
- Unit-тесты для бизнес-логики

**Этап 2: API layer + Integration**
- REST/GraphQL эндпоинты, валидация, обработка ошибок
- Интеграционные тесты

**Этап 3: UI layer + User flows**
- Компоненты, экраны, маршрутизация
- E2E-тесты основных потоков

**Этап 4 (опционально): Integration + Polish**
- Кросс-модульные тесты
- Performance tuning
- Documentation

### Large (4–6 этапов)

**Этап 1: Data model + Basic CRUD**
- Схемы, миграции, репозитории, CRUD-операции
- Unit-тесты

**Этап 2: Core business logic + Validation**
- Сервисы, правила, валидация, edge cases
- Unit + интеграционные тесты

**Этап 3: API endpoints + Documentation**
- REST/GraphQL, auth, rate limiting
- API-тесты + документация

**Этап 4: UI + User flows**
- Компоненты, экраны, маршрутизация, состояния
- E2E-тесты

**Этап 5: Integration + E2E**
- Кросс-модульные сценарии
- Performance тесты
- Smoke-тесты всей системы

**Этап 6 (опционально): Polish + Release prep**
- UX-улучшения, a11y, responsive
- Release notes, deployment guide

### Epic (6–10 этапов)

Для эпиков — декомпозиция по вертикальным слайсам, а не по техническим слоям.

Каждый слайс — полноценная вертикальная фича (data + logic + API + UI).

Инфраструктурные этапы — отдельные.

## Правила именования этапов

Формат: `stage-N-<kebab-name>`

Примеры:
- `stage-1-data-model`
- `stage-2-core-service`
- `stage-3-api-endpoints`
- `stage-4-ui-components`
- `stage-5-e2e-polish`

## Git-бранчи

**Основная фичевая ветка:** `feature/<feature>`

Создаётся перед началом разработки от `develop`. Все подветки этапов мерджатся в неё.
После завершения всех этапов основная ветка мерджится в `develop`.

**Подветки этапов:** `feature/<feature>/stage-N-<name>`

Создаются от основной фичевой ветки. После завершения этапа мерджатся обратно в основную.

Примеры:
```
feature/notification-system                          ← основная ветка
  ├── feature/notification-system/stage-1-data-model     ← подветка этапа 1
  ├── feature/notification-system/stage-2-core-service   ← подветка этапа 2
  ├── feature/notification-system/stage-3-api-endpoints  ← подветка этапа 3
  └── feature/notification-system/stage-4-ui-components  ← подветка этапа 4
```

**Порядок работы:**
1. `git checkout develop && git checkout -b feature/<feature>`
2. Для каждого этапа: `git checkout feature/<feature> && git checkout -b feature/<feature>/stage-N-<name>`
3. После этапа: `git checkout feature/<feature> && git merge --no-ff feature/<feature>/stage-N-<name>`
4. После всех этапов: `git checkout develop && git merge --no-ff feature/<feature>`

## Валидация этапов

Для каждого кандидат-этапа проверить:
- [ ] Можно ли завершить этап независимо?
- [ ] Можно ли smoke-протестировать после этапа?
- [ ] Зависимости ясны (что входит, что выходит)?
- [ ] Объём разумный (1–3 дня работы)?
- [ ] Понятна стратегия ветвления?
- [ ] Есть ли конкретные файлы для создания/изменения?
- [ ] Определены тесты (unit, integration, smoke)?

## Ошибки декомпозиции

| Ошибка | Признак | Решение |
|--------|---------|---------|
| Этап слишком большой | >5 дней, множество разнородных задач | Разделить на подэтапы |
| Этап слишком маленький | <0.5 дня, тривиальные изменения | Объединить с соседним |
| Циклические зависимости | Этап A зависит от B, B от A | Пересмотреть границы, выделить общую часть |
| Нет smoke-теста | Нельзя проверить результат этапа | Добавить проверяемый результат |
| Неинкрементально | Ценность появляется только в последнем этапе | Переструктурировать для ранней доставки ценности
