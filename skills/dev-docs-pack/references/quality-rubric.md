# Quality Rubric — Критерии оценки входных данных

## Шкала оценок (per dimension)

| Уровень | Диапазон | Описание |
|---------|----------|----------|
| Отлично | 0.9–1.0 | Чётко определено, с примерами, можно сразу использовать |
| Хорошо | 0.7–0.8 | Понятно, но есть 1–2 уточнения |
| Удовлетворительно | 0.4–0.6 | Направление ясно, детали размыты |
| Плохо | 0.0–0.3 | Существенные пробелы, требуется глубокое уточнение |

---

## Измерение 1: Цели и задачи (вес: 0.15)

**Что проверяем:** Понимание проблемы, целевой аудитории, ценности и метрик успеха.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет описания цели |
| 0.3 | Общая идея без конкретики («сделать систему уведомлений») |
| 0.5 | Цель описана, но не ясно для кого и зачем |
| 0.7 | Цель + целевая аудитория + основная ценность |
| 0.9 | Цель + аудитория + метрики успеха + что произойдёт если НЕ делать |

**Красные флаги** (автоматический 0.0):
- Нет ответа на вопрос «Зачем это нужно?»

---

## Измерение 2: Функциональный охват (вес: 0.20)

**Что проверяем:** Полноту описания функциональности, граничных случаев и ограничений.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет описания функциональности |
| 0.3 | Список фич без деталей |
| 0.5 | Основные функции описаны, но edge cases не продуманы |
| 0.7 | Функции + входные/выходные данные + основные сценарии |
| 0.9 | Полное описание + edge cases + ограничения + обратная совместимость |

**Красные флаги:**
- Нет ни одного пользовательского сценария
- Нет описания что система НЕ должна делать

---

## Измерение 3: Техническая архитектура (вес: 0.15)

**Что проверяем:** Стек, архитектурные решения, интеграции, data flow.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет технического описания |
| 0.3 | Упомянут стек, но без деталей |
| 0.5 | Стек + общая архитектура, но без интеграций |
| 0.7 | Стек + архитектура + интеграции + data flow |
| 0.9 | Стек + архитектура + интеграции + data flow + миграция + rollback |

**Красные флаги:**
- Неясно как новая фича интегрируется с существующим кодом

---

## Измерение 4: UI/UX определение (вес: 0.10)

**Что проверяем:** Экраны, состояния, user flows, обработка ошибок.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет UI/UX упоминания |
| 0.3 | Есть упоминание UI но без деталей |
| 0.5 | Описаны экраны, но нет user flows |
| 0.7 | Экраны + user flows + error states |
| 0.9 | Полный UX: экраны + flows + states + a11y + responsive |

**Примечание:** Если фича не имеет UI — выставить **1.0** (not applicable = perfect).

---

## Измерение 5: API / интерфейсы (вес: 0.10)

**Что проверяем:** Внешние API, контракты данных, события, версионирование.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет описания API |
| 0.3 | Упомянуты endpoints но без контрактов |
| 0.5 | Endpoints + request/response форматы |
| 0.7 | Full API: endpoints + контракты + ошибки + auth |
| 0.9 | Full API + версионирование + обратная совместимость + rate limiting |

**Примечание:** Если фича не имеет внешнего API — выставить **1.0** (not applicable = perfect).

---

## Измерение 6: Требования к тестированию (вес: 0.10)

**Что проверяем:** Acceptance criteria, smoke-тесты, E2E-сценарии.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет упоминания тестирования |
| 0.3 | «Нужны тесты» без деталей |
| 0.5 | Типы тестов упомянуты, но нет acceptance criteria |
| 0.7 | Типы тестов + acceptance criteria + smoke tests |
| 0.9 | Полная стратегия: unit + integration + E2E + smoke + coverage targets |

---

## Измерение 7: Нефункциональные требования (вес: 0.05)

**Что проверяем:** Производительность, безопасность, масштабируемость.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет NFR |
| 0.5 | Упомянуты 1–2 NFR |
| 0.7 | Performance + security базово |
| 0.9 | Performance + security + scalability + observability + конкретные метрики |

---

## Измерение 8: Ограничения и риски (вес: 0.05)

**Что проверяем:** Зависимости, таймлайн, известные ограничения.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет упоминания constraints/risks |
| 0.5 | Есть общий список рисков |
| 0.7 | Риски + митигация + зависимости |
| 0.9 | Полный риск-регистр + митигация + timeline + resource constraints |

---

## Измерение 9: Контекст и стейкхолдеры (вес: 0.05)

**Что проверяем:** Кто использует, кто ревьюит, кто деплоит, влияние на другие фичи.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет контекста |
| 0.5 | Упомянут контекст проекта |
| 0.7 | Контекст + стейкхолдеры + downstream impact |
| 0.9 | Полный контекст + кто ревьюит + кто деплоит + как влияет на другие фичи |

---

## Измерение 10: Критерии приёмки (вес: 0.05)

**Что проверяем:** Как понять что фича готова, измеримые критерии.

| Оценка | Критерий |
|--------|----------|
| 0.0 | Нет критериев приёмки |
| 0.5 | Общие критерии («должно работать») |
| 0.7 | Конкретные проверки для основной функциональности |
| 0.9 | Измеримые критерии + критерии отказа + rollback критерии |

---

## Формула расчёта

```
Score = Σ(score_i × weight_i), где i = 1..10
```

| Измерение | Вес |
|-----------|------|
| 1. Цели и задачи | 0.15 |
| 2. Функциональный охват | 0.20 |
| 3. Техническая архитектура | 0.15 |
| 4. UI/UX определение | 0.10 |
| 5. API / интерфейсы | 0.10 |
| 6. Требования к тестированию | 0.10 |
| 7. Нефункциональные требования | 0.05 |
| 8. Ограничения и риски | 0.05 |
| 9. Контекст и стейкхолдеры | 0.05 |
| 10. Критерии приёмки | 0.05 |
| **Итого** | **1.00** |

**Целевой порог:** ≥ 0.95
