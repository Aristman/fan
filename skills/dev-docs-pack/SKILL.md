# dev-docs-pack — Генератор пакета разработки

Создаёт полный комплект документации для разработки фичи на основе спецификации: roadmaps, UI/UX, API, тестирование, релиз.

---

<!-- worker:exclude-start -->
## Когда использовать
- Есть спецификация фичи (или детальное описание) и нужен полный пакет документов для разработки
- Нужно декомпозировать фичу на этапы с TDD-подходом и smoke-тестами
- Требуется подготовить roadmap, UI/UX, API и релизные документы

## Когда НЕ использовать
- Нужно только исследовать тему (используйте research-spec-generator)
- Нужно оценить идею (используйте idea-lab)
- Нет никакого описания фичи и нужно сначала создать спецификацию (сначала research-spec-generator, потом dev-docs-pack)
<!-- worker:exclude-end -->

## Доступные инструменты

| Инструмент | Для чего |
|-----------|----------|
| `read` | Чтение исходной спеки, проекта контекста, reference-файлов |
| `write` | Создание всех документов пакета |
| `bash` | Создание директорий, поиск файлов |
| `question` | Единичный выбор пользователем |
| `questionnaire` | Набор вопросов на вкладках |
| `memory_search` | Поиск контекста о проекте из предыдущих сессий |

## Парсинг входных данных

Скилл принимает:
- Путь к файлу спецификации: `/skill:dev-docs-pack docs/specs/spec_my-feature_2026-05-06.md`
- Имя фичи: `/skill:dev-docs-pack notification-system`
- Описание фичи в свободной форме: `/skill:dev-docs-pack Нужно сделать систему уведомлений с...`

Если указан путь — читать файл напрямую. Если имя — искать в `docs/specs/` и `docs/roadmaps/`. Если описание — использовать как есть.

## Процесс

### Фаза 1: Инициализация

**1.1 Определить входные данные**
- Извлечь из аргументов: путь к спеке / имя фичи / описание
- Если путь — `read()` файл
- Если имя — `bash("find docs/specs/ -name '*<name>*' -type f")` и `bash("find docs/roadmaps/ -name '*<name>*' -type f")`
- Если описание — использовать как есть

**1.2 Определить имя фичи (feature slug)**
- Извлечь из заголовка спеки или из описания
- Формат: kebab-case (например, `notification-system`)
- Использовать для директории `docs/features/<slug>/`

**1.3 Проверить существующий output**
- Если `docs/features/<slug>/` уже существует:
```
question({
  question: "Документация для «<slug>» уже существует. Что делаем?",
  options: [
    { label: "Перезаписать", description: "Удалить существующее и создать заново" },
    { label: "Обновить", description: "Добавить недостающие, обновить существующие" },
    { label: "Отмена" }
  ]
})
```

**1.4 Загрузить контекст проекта**
```
read("ARCHITECTURE.md") — стек, архитектура
read("CLAUDE.md") — конвенции, git-правила
read("docs/MANIFEST.md") — существующие документы
bash("ls docs/specs/") — существующие спеки
bash("ls packages/") — структура проекта
```

**Критерий завершения фазы 1:** Имя фичи определено, исходный материал загружен, контекст проекта понятен.

### Фаза 2: Оценка качества входных данных

**2.1 Загрузить рубрику**
```
read("skills/dev-docs-pack/references/quality-rubric.md")
```

**2.2 Оценить каждое измерение (0–1)**

| # | Измерение | Вес | Что проверяем |
|---|-----------|------|---------------|
| 1 | Цели и задачи | 0.15 | Какую проблему решает? Для кого? Метрики успеха? |
| 2 | Функциональный охват | 0.20 | Что должна делать фича? Edge cases? Ограничения? |
| 3 | Техническая архитектура | 0.15 | Как будет построена? Интеграции? Data flow? |
| 4 | UI/UX определение | 0.10 | Экраны? User flows? Состояния ошибок? |
| 5 | API / интерфейсы | 0.10 | Внешние API? Контракты? События? |
| 6 | Требования к тестированию | 0.10 | Acceptance criteria? Smoke-тесты? E2E? |
| 7 | Нефункциональные требования | 0.05 | Производительность? Безопасность? Масштабируемость? |
| 8 | Ограничения и риски | 0.05 | Зависимости? Таймлайн? Ограничения? |
| 9 | Контекст и стейкхолдеры | 0.05 | Кто использует? Кто ревьюит? Влияние? |
| 10 | Критерии приёмки | 0.05 | Как понять что готово? Измеримые критерии? |

**2.3 Вычислить взвешенную оценку**
```
Score = Σ(score_i × weight_i)
```

**Важно:** Если фича не имеет UI — измерение 4 = 1.0 (not applicable = perfect). Если нет внешнего API — измерение 5 = 1.0.

**2.4 Идентифицировать пробелы**
Для каждого измерения с оценкой < 0.8:
- Что не хватает
- Почему это важно
- Категория: 🔴 Блокирующее / 🟡 Важное / 🟢 Рекомендательное

**2.5 Представить результат пользователю**
```
## Оценка входных данных

| Измерение | Оценка | Статус |
|-----------|--------|--------|
| Цели и задачи | 0.9 | ✅ |
| Функциональный охват | 0.5 | 🔴 Не хватает деталей |
| Техническая архитектура | 0.7 | 🟡 Требуется уточнение |
| ... | ... | ... |

**Общая оценка:** 0.68 / 1.0
**Целевой порог:** 0.95
```

**Критерий завершения фазы 2:** Оценка вычислена, пробелы категоризированы.

**Переход:**
- Score ≥ 0.95 → Фаза 4 (пропустить интервью, но спросить подтверждение)
- Score < 0.95 → Фаза 3 (интервью)

### Фаза 3: Цикл интервью

**Вход:** Оценка < 0.95, есть список пробелов.

**Эта фаза ЦИКЛИЧЕСКАЯ.** Повторять пока score ≥ 0.95.

**3.1 Приоритизировать пробелы**
Сортировка: 🔴 → 🟡 → 🟢, внутри — по весу измерения (от большего к меньшему).

**3.2 Сформулировать вопросы**
- Загрузить банк вопросов: `read("skills/dev-docs-pack/references/interview-questions.md")`
- Адаптировать к контексту фичи
- Группировать в раунды по 3–5 вопросов

**3.3 Задать вопросы через questionnaire**
```
questionnaire({
  questions: [
    {
      id: "functional_core",
      label: "Ядро фичи",
      prompt: "Какие именно операции должен поддерживать <feature>?",
      options: [
        { value: "crud", label: "CRUD (создание, чтение, обновление, удаление)" },
        { value: "read_only", label: "Только чтение/просмотр" },
        { value: "complex_workflow", label: "Многошаговый бизнес-процесс" }
      ],
      allowOther: true
    },
    {
      id: "api_type",
      label: "Тип API",
      prompt: "Фича предоставляет внешний API?",
      options: [
        { value: "rest", label: "Да, REST API" },
        { value: "graphql", label: "Да, GraphQL" },
        { value: "ws", label: "Да, WebSocket" },
        { value: "none", label: "Нет внешнего API" }
      ],
      allowOther: true
    },
    // ... остальные вопросы по пробелам
  ]
})
```

**3.4 Обработать ответы**
- Интегрировать в понимание фичи
- Пересчитать затронутые измерения
- Определить новые пробелы (если ответы открыли новые вопросы)

**3.5 Итерация**
```
Вопросы → Ответы → Интеграция → Пересчёт
  ↑                                    ↓
  └──── если < 0.95, новые вопросы ←───┘
```

**3.6 Лимит раундов:** 5 максимум. Если после 5 раундов < 0.95:
```
question({
  question: "После 5 раундов уточнений оценка < 0.95. Как поступаем?",
  options: [
    { label: "Продолжить с тем что есть" },
    { label: "Ещё один раунд" },
    { label: "Отмена" }
  ]
})
```

**3.7 Когда ≥ 0.95:**
```
question({
  question: "Оценка входных данных достигла 0.95+. Готовы генерировать пакет?",
  options: [
    { label: "Да, генерировать" },
    { label: "Дополнить ещё" },
    { label: "Отмена" }
  ]
})
```

**Критерий завершения фазы 3:** Score ≥ 0.95 И пользователь подтвердил готовность.

### Фаза 4: Подготовка и декомпозиция

**4.1 Загрузить гид по декомпозиции**
```
read("skills/dev-docs-pack/references/stage-decomposition-guide.md")
```

**4.2 Определить количество этапов**

Анализ спеки:
- Выделить функциональные блоки (N)
- Подсчитать точки интеграции (I)
- Подсчитать UI-экраны (S)
- Подсчитать API-эндпоинты (E)
- Complexity = N + I + S + E

| Complexity | Этапы |
|-----------|--------|
| < 5 | 1–2 |
| 5–10 | 3–4 |
| 11–20 | 4–6 |
| > 20 | 6–10 |

**4.3 Именовать этапы**
Формат: `stage-N-<kebab-name>` (например, `stage-1-data-model`).

**4.4 Определить границы этапов**
Для каждого этапа:
- Что входит (от предыдущего)
- Что производит (для следующего)
- Что можно smoke-протестировать
- Зависимости от предыдущих этапов

**4.5 Создать блочные диаграммы**
Загрузить конвенции: `read("skills/dev-docs-pack/references/block-diagram-patterns.md")`

Создать:
- Общую архитектурную диаграмму (для main roadmap)
- Диаграмму компонентов на этап (для stage roadmaps)
- Диаграмму data flow (если применимо)

**4.6 Определить область документов**
Использовать decision tree:

```
Есть UI? → Да: генерировать ui-ux/ → Нет: пропустить
Есть внешний API? → Да: генерировать api/ → Нет: пропустить
Несколько этапов? → Да: полный testing/ → Нет: минимальный testing/
```

**4.7 Определить основную фичевую ветку**

Основная ветка для разработки: `feature/<feature>`
Все подветки этапов мерджатся в неё. После завершения всех этапов основная ветка мерджится в `develop`.

**4.8 Предложить пользователю выбор:**
```
questionnaire({
  questions: [
    {
      id: "doc_scope",
      label: "Объём документов",
      prompt: "Какие документы генерируем?",
      options: [
        { value: "full", label: "Полный пакет (все по decision tree)" },
        { value: "roadmaps_only", label: "Только roadmaps" },
        { value: "roadmaps_testing", label: "Roadmaps + тестирование" },
        { value: "roadmaps_uiux", label: "Roadmaps + UI/UX" },
        { value: "roadmaps_api", label: "Roadmaps + API" },
        { value: "custom", label: "Выборочно" }
      ],
      allowOther: false
    },
    {
      id: "confirm_stages",
      label: "Этапы",
      prompt: "Предложено N этапов: [список]. Подтверждаете?",
      options: [
        { value: "yes", label: "Да, продолжить" },
        { value: "modify", label: "Изменить этапы" },
        { value: "merge", label: "Объединить этапы" },
        { value: "split", label: "Разделить подробнее" }
      ],
      allowOther: true
    }
  ]
})
```

Если пользователь выбрал «Изменить/Объединить/Разделить» — пересчитать и повторить.

**Критерий завершения фазы 4:** Этапы определены, основная фичевая ветка `feature/<feature>` определена, область документов установлена, пользователь утвердил.

### Фаза 5: Основной roadmap

**5.1 Создать структуру директорий**
```bash
mkdir -p docs/features/<feature>/
mkdir -p docs/features/<feature>/roadmaps/
# + другие директории по decision tree
```

**5.2 Создать основную фичевую ветку**
```bash
git checkout develop
git checkout -b feature/<feature>
```

**5.3 Загрузить шаблон**
```
read("skills/dev-docs-pack/references/template-roadmap-main.md")
```

**5.4 Сгенерировать основной roadmap**
Записать в `docs/features/<feature>/roadmaps/roadmap-main.md`:

**Обязательные разделы:**
- Метаданные (дата, автор, статус, ссылка на спеку, основная ветка `feature/<feature>`)
- Обзор фичи (2–3 абзаца)
- Инструкция по началу работы (создание основной ветки, подготовка)
- Архитектурная блочная диаграмма (ASCII)
- Таблица этапов (N строк, по одному на этап, с бранчами `feature/<feature>/stage-N-<name>`)
- Детали каждого этапа: название, цель, ключевые результаты, smoke-тест
- Карта зависимостей между этапами
- Риск-регистр
- Классификация приоритетов (MoSCoW)
- Критерии успеха всей фичи
- Прогресс-трекинг (таблица со статусами)

**5.5 Записать файл через `write()`**

**Критерий завершения фазы 5:** `roadmap-main.md` существует и содержит все обязательные разделы.

### Фаза 6: Детальные roadmap-и этапов

**6.1 Загрузить шаблон**
```
read("skills/dev-docs-pack/references/template-roadmap-stage.md")
```

**6.2 Для каждого этапа сгенерировать TDD-roadmap**
Записать в `docs/features/<feature>/roadmaps/roadmap-stage-N-<name>.md`:

**Обязательные разделы:**
- Метаданные (номер этапа, подветка `feature/<feature>/stage-N-<name>`, основная ветка `feature/<feature>`, зависимости)
- Цель этапа (1–2 предложения)
- Блочная диаграмма этапа (ASCII, компоненты этого этапа)
- TDD-подход в формате **чекбокс-листа** (отмечать по мере разработки):
  - **Red** — определяем тесты (unit, integration, smoke)
  - **Green** — реализация (файлы, ключевые решения)
  - **Refactor** — улучшение
- Ветвление и слияние (пошаговый процесс: подветка → merge в `feature/<feature>`)
- **Smoke-тесты этапа (ОБЯЗАТЕЛЬНЫЙ раздел)** — таблица: проверка / команда / ожидаемый результат
- Критерии завершения этапа (чеклист)
- **Инструкция по обновлению roadmap-stage** — отмечать выполненные пункты чеклиста прямо в файле roadmap по мере разработки
- Инструкция по обновлению roadmap-main

**6.3 Записать каждый файл через `write()`**

**Критерий завершения фазы 6:** Все `roadmap-stage-N-*.md` существуют с полной TDD-структурой.

### Фаза 7: Дополнительные документы

Для каждого типа документа — загрузить шаблон из `references/` и заполнить.

**7a. UI/UX документы** (если есть UI у фичи):
- Загрузить: `references/template-user-flows.md`, `references/template-scenarios.md`, `references/template-wireframes.md`
- Генерировать:
  - `docs/features/<feature>/ui-ux/user-flows.md` — пользовательские потоки по ролям
  - `docs/features/<feature>/ui-ux/scenarios.md` — сценарии использования (happy path, edge cases, ошибки)
  - `docs/features/<feature>/ui-ux/wireframes.md` — ASCII-описания макетов экранов

**7b. API документы** (если есть внешний API):
- Загрузить: `references/template-api-reference.md`, `references/template-api-changelog.md`
- Генерировать:
  - `docs/features/<feature>/api/api-reference.md` — спецификация эндпоинтов, моделей, событий
  - `docs/features/<feature>/api/api-changelog.md` — история изменений API

**7c. Тестовые документы** (всегда):
- Загрузить: `references/template-test-strategy.md`, `references/template-smoke-tests.md`, `references/template-e2e-tests.md`
- Генерировать:
  - `docs/features/<feature>/testing/test-strategy.md` — стратегия тестирования (пирамида, инструменты, покрытие)
  - `docs/features/<feature>/testing/smoke-tests.md` — smoke-тесты (по этапам + финальные + регрессия)
  - `docs/features/<feature>/testing/e2e-tests.md` — E2E-сценарии (если >2 этапов)

**7d. Релизные документы** (всегда):
- Загрузить: `references/template-release-notes.md`, `references/template-deployment-guide.md`
- Генерировать:
  - `docs/features/<feature>/release/release-notes.md` — release notes (changelog-формат)
  - `docs/features/<feature>/release/deployment-guide.md` — инструкция по деплою, rollback, мониторинг

**Критерий завершения фазы 7:** Все применимые дополнительные документы сгенерированы.

### Фаза 8: Верификация

**Эта фаза ЦИКЛИЧЕСКАЯ.** Повторять пока все проверки не пройдут. Максимум 3 цикла.

**8.1 Проверка структуры**
- Все ожидаемые файлы существуют
- Директории на месте
- Имена файлов соответствуют конвенции

**8.2 Проверка содержимого**
Для каждого файла:
- Блок метаданных присутствует (дата, автор, статус)
- Кросс-ссылки валидны (связанные файлы существуют)
- Нет плейсхолдеров ("TODO", "TBD", "...")
- ASCII-диаграммы корректны (сбалансированные скобки/рамки)
- Таблицы хорошо сформированы

**8.3 Проверка согласованности**
- Количество этапов в roadmap-main совпадает с количеством файлов stage-*
- Smoke-тесты в stage roadmaps соответствуют smoke-tests.md
- API reference соответствует функциональным требованиям спеки
- User flows ссылаются на правильные экраны/состояния

**8.4 Проверка качества**
- Русский язык (без непереведённых английских фраз в прозе)
- Конкретное, применимое содержание (не размытое)
- Конкретные пути файлов и команды
- Тестовые команды реально выполнимы

**8.5 Исправление** — если найдены проблемы, исправить и повторить.

**Критерий завершения фазы 8:** Все проверки структуры, содержимого, согласованности и качества пройдены.

## Правила

1. **Не выдумывай** — если в спеке нет информации, спрашивай. Не заполняй пробелы догадками.
2. **Конкретика** — каждый пункт roadmap должен содержать конкретные файлы, команды, критерии.
3. **Smoke-тесты обязательны** — каждый этап ДОЛЖЕН иметь хотя бы 1 smoke-тест в таблице.
4. **TDD-подход** — каждый этап следует Red → Green → Refactor.
5. **Кросс-ссылки** — все документы ссылаются друг на друга через относительные пути.
6. **Русский язык** — все документы на русском (кроме кода, имён файлов, API, git-команд).
7. **No TODO** — каждый документ полностью заполнен. Если данных нет — так и напиши «Данные отсутствуют».
8. **ASCII-диаграммы** — box-drawing characters (┌ ┐ └ ┘ ├ ┤ │ ─), максимум 80 символов шириной.
9. **Адаптивность** — для простых фичей (1–2 этапа) не раздувай документы. Для эпиков — полная глубина.
10. **Проектные конвенции** — проверяй ARCHITECTURE.md и CLAUDE.md для технического контекста.
11. **MANIFEST** — всегда обновляй docs/MANIFEST.md при генерации.
12. **Перезапись** — всегда спрашивай перед перезаписью существующих документов.
13. **Ветвление** — основная фичевая ветка `feature/<feature>`, подветки этапов `feature/<feature>/stage-N-<name>`. Все подветки мерджатся в основную. После завершения всех этапов основная ветка мерджится в `develop`.
14. **Верификация** — Фаза 8 обязательна. Не считай работу завершённой без проверки.
15. **Сохранение контекста** — если сессия прерывается, весь прогресс восстанавливается по записанным файлам.
