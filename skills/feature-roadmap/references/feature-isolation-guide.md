# Руководство по обособленности фич

> Reference-файл скилла feature-roadmap.
> Подробные примеры, таблицы и чеклисты для проверки обособленности фич.

## Типы хороших фич (эталон)

Фича соответствует **одному** из следующих критериев (и только одному):

| Тип фичи | Примеры | Эвристика «золотой середины» |
|----------|---------|------------------------------|
| **API endpoint** | `POST /api/notifications`, `GET /api/users/:id` | Один HTTP-метод + один ресурс |
| **UI-компонент** | `NotificationBell`, `UserProfileCard` | Один переиспользуемый компонент с собственным состоянием |
| **Модель данных** | `Notification`, `UserPreferences` | Одна сущность + её валидации + миграция |
| **Пользовательская история** | «Пользователь видит список уведомлений» | Один user story с 2-3 шагами |
| **Бизнес-правило / процесс** | «Дедупликация уведомлений в течение 1 мин» | Одно правило, проверяемое юнит-тестом |
| **Интеграция с внешним сервисом** | «Отправка email через SendGrid» | Один внешний сервис + один адаптер |
| **Команда / CLI-операция** | `notifications:send-daily-digest` | Одна команда с флагами |

### Числовые характеристики хорошей фичи

- 1-3 TDD-теста
- 2-3 критерия приёмки
- 1-3 файла исходного кода в реализации
- Один слой архитектуры (НЕ смесь API + UI + storage)

## Слишком мелкая фича (объединить)

Фича слишком мелка, если выполняются **≥ 2** из условий:
- 1 TDD-тест
- 1 критерий приёмки
- Нет самостоятельной пользовательской ценности (тривиальный шаг внутри другой фичи)
- Тривиальная обёртка над существующим API (`isEmpty()`, `formatDate()`)
- Только валидация / guard clause без бизнес-логики

**Действие:** объединить с родительской фичей как «подшаг» (в раздел «Ожидаемый результат»).

### Примеры слишком мелких фич

| Плохо (слишком мелко) | Хорошо (объединено) |
|------------------------|---------------------|
| «Валидация email в форме» | «Форма создания уведомления с валидацией» (включает валидацию как подшаг) |
| «Модель Notification» | «Модель Notification с миграцией и валидациями» |
| `isEmpty()` helper | Включить в фичу, которая использует этот helper |

## Слишком крупная фича (разбить)

Фича слишком крупна, если выполняется **≥ 1** из условий:
- **Смешивает слои:** API + UI + storage в одной карточке
- **> 3 TDD-теста** в эскизе (легко генерируется 5-7 — это сигнал разбить)
- **> 3 критериев приёмки** (5+ — перегруз)
- **> 3 подзадач** в логике реализации
- **> 2 файлов ответственности** (например, `controller.ts` + `service.ts` + `repository.ts` + `component.tsx` — это уже 3-4 фичи)
- **Зависит от > 2 других фич** одновременно
- **Длительность реализации** > 1-2 дней для соло-разработчика

**Действие:** разбить на N фич по слоям или по сценариям. Если после разбиения
суммарное число функций в roadmap превышает 15 — делегировать часть в
`/skill:research-spec-generator` (см. `references/delegation-guide.md`).

### Примеры слишком крупных фич

| Плохо (слишком крупно) | Хорошо (разбито) |
|------------------------|-------------------|
| «Управление уведомлениями (API + UI + БД)» | F-a: «Модель Notification + миграция» [DATA], F-b: «POST /api/notifications» [API], F-c: «NotificationBell UI» [UI] |
| «Авторизация (email + OAuth + 2FA)» | F-a: «Авторизация по email» [API], F-b: «OAuth Google» [INTEG], F-c: «2FA TOTP» [BIZ] |
| «Дашборд аналитики» (>300 слов описания) | Разбить по виджетам: F-a: «Виджет активных пользователей» [UI], F-b: «Виджет конверсии» [UI], F-c: «API аналитики» [API] |

## SMART-формулировки

Каждый элемент карточки (название, описание, TDD-тест, критерий приёмки) должен быть:

- **S** (Specific) — Конкретно: что именно, где, для кого. Без абстракций.
- **M** (Measurable) — Измеримо: число, статус-код, состояние UI, процент.
- **A** (Achievable) — Достижимо: реализуемо в рамках одной фичи.
- **R** (Relevant) — Релевантно: связано с пользовательской историей или бизнес-правилом.
- **T** (Testable) — Проверяемо: можно написать автотест или вручную кликнуть.

### Примеры SMART-формулировок

| Плохо (абстрактно) | Хорошо (SMART) |
|---------------------|----------------|
| «Система работает быстро» | «GET /api/notifications возвращает 200 OK и массив за < 100 мс при N=100» |
| «UI выглядит хорошо» | «NotificationBell виден в шапке при непрочитанных > 0» |
| «API надёжный» | «POST /api/notify возвращает 201 и идемпотентен при дублях в течение 60с» |
| «Обработка ошибок» | «При недоступности БД API возвращает 503 в течение 5с и логирует ошибку» |
| «Кэширование» | «Redis-кэш снижает p95 latency GET /api/users с 200мс до 20мс при N=1000» |

### SMART для TDD-тестов

| Поле | Требование | Пример |
|------|-----------|--------|
| Условие | Конкретное предусловие с данными | «В БД 50 уведомлений, пользователь авторизован с ролью admin» |
| Шаги | Точные действия (HTTP-запрос / метод) | `GET /api/notifications?status=unread&limit=10` |
| Ожидаемый результат | Измеримый результат | «200 OK, массив из 10 объектов, каждый с полями id/title/createdAt» |

## Чеклист валидации фичи

Применить к **каждой** карточке перед включением в roadmap:

- [ ] Фича относится ровно к одному слою архитектуры
- [ ] Количество TDD-тестов в эскизе: 1-3
- [ ] Количество критериев приёмки: 2-3
- [ ] Есть самостоятельная пользовательская ценность или чёткая техническая ответственность
- [ ] Название сформулировано как SMART-цель
- [ ] Оценка объёма: S (≤ 4ч) / M (≤ 1 день) / L (≤ 2 дня) — не XL
- [ ] Количество файлов ответственности: ≤ 2
