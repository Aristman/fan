# Шаблон roadmap.md

> Reference-файл скилла feature-roadmap.
> Полный шаблон выходного файла roadmap.md.

```markdown
# Roadmap: <Название фичи>

> **Дата генерации:** YYYY-MM-DD
> **Источник:** <путь к спеке или описание>
> **Версия SKILL:** 1.3.0
> **Функций / Этапов:** N / M (лимит: 15 / 8)

> ⚠️ **Предупреждения** (если есть, иначе удалить блок):
> - Превышен лимит функций (>15) — рекомендуется разбиение
> - Этапов: {N} (>8) — сгенерировано по запросу пользователя «продолжить с предупреждением»
> - Функций с пометкой `too_large_candidate`: {K} (требуется разбиение на слои)

## Сводка

| Метрика | Значение |
|---------|----------|
| Всего функций | N |
| Этапов | M |
| P0 (критические) | K |
| P1 (высокие) | L |
| P2 (средние) | M |
| P3 (низкие) | P |

## Легенда

- ✅ — Реализовано
- ☐ — Запланировано
- ⏳ — В работе
- ❌ — Заблокировано

### Приоритеты
- **P0** — Критично (без этого фича не имеет смысла)
- **P1** — Высокий (важно для большинства пользователей)
- **P2** — Средний (полезно, но не срочно)
- **P3** — Низкий (future enhancement)

### Слои архитектуры
- **[API]** — Backend endpoint / RPC / middleware
- **[UI]** — React-компонент / страница / форма
- **[DATA]** — Модель / миграция / схема
- **[INTEG]** — Интеграция с внешним сервисом
- **[BIZ]** — Бизнес-правило / процесс
- **[CLI]** — Команда / скрипт

---

## <Этап 1: Название>

**Цель:** <SMART-цель этапа — конкретно, измеримо, с критерием завершения>
**Приоритет функций:** <диапазон приоритетов>
**E2E-сценарий этапа:** <1–2 сквозных сценария (от входа пользователя/API до результата), проверяющих работоспособность инкремента целиком. Формат: Условие/Шаги/Ожидаемый результат>
**Smoke-критерий этапа:** <один быстрый сквозной тест, подтверждающий «этап завершён = система работает». Запускается на границе этапа перед переходом к следующему>

#### ☐ <ID>: <Название функции>
- **Приоритет:** P0/P1/P2/P3
- **Слой:** [API]/[UI]/[DATA]/[INTEG]/[BIZ]/[CLI]  ← ровно один
- **Описание:** <SMART-описание: что, для кого, зачем — конкретно>
- **Пользовательская история:** «Как <роль>, я хочу <действие>, чтобы <ценность>» (если применимо)
- **Зависимости:** <ID других функций> или (none)
- **TDD-тесты:**  ← ровно 1-3
  - [ ] **TC-<ID>-1:** <название — конкретное и проверяемое>
    - *Условие:* <предусловие, контекст — SMART>
    - *Шаги:* <что делает тест — конкретные действия>
    - *Ожидаемый результат:* <конкретный, измеримый результат — статус-код, состояние, значение>
- **Red-тест:** <ID тест-кейса, который должен упасть первым, и почему он падает (какой функциональности ещё нет)>
- **Refactor-цели:** <что улучшить после Green: дублирование, именование, структура, coupling; или (none) с обоснованием>
- **Критерии приёмки:**  ← ровно 2-3, SMART
  1. <конкретное, измеримое условие — не «работает хорошо», а «обрабатывает 1000 запросов за < 200 мс»>
  2. <критерий 2>
  3. <критерий 3>
- **Ожидаемый результат:** <конкретный артефакт — файл, endpoint, компонент>
- **Оценка объёма:** S (≤ 4ч) / M (≤ 1 день) / L (≤ 2 дня) / XL (> 2 дней, требует разбиения)

## Делегирование (если применимо)

- Сгенерировано из родительской спецификации: <parent_spec_path> (если применимо)

```

> **Примечание:** E2E-сценарии и Smoke-критерии этапов создаются на этапе планирования (до начала разработки) и исполняются в финале этапа как phase-gate перед переходом к следующему этапу.
