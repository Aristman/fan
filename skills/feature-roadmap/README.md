# feature-roadmap

## Описание

Генерирует TDD-роадмапу в стиле чеклиста на основе спецификации фичи.
Парсит спецификацию, извлекает функции, определяет приоритеты и зависимости,
группирует по этапам разработки и создаёт `docs/features/<slug>/roadmap.md`
с TDD-тестами и критериями приёмки для каждой функции.

Поддерживает цикл **Red-Green-Refactor** (RGR TDD): для каждой функции определяется
Red-тест (первый падающий тест) и Refactor-цели. Каждый этап имеет E2E-сценарий
и Smoke-критерий для phase-gate верификации.

## Установка

Скопировать в глобальную директорию скиллов:

```bash
cp -r ~/.fan/agent/skills/fan-forge/workspace/feature-roadmap/ ~/.fan/agent/skills/feature-roadmap/
```

Или установить через FAN Store (когда будет опубликован).

## Использование

### Через slash command:
```
/skill:feature-roadmap docs/specs/spec_my-feature_2025-06-01.md   # по пути к файлу
/skill:feature-roadmap notification-system                         # по имени фичи
/skill:feature-roadmap                                              # интерактивный режим
```

### Результат

Создаёт `docs/features/<slug>/roadmap.md` с:

- Сводная таблица (всего функций, этапов, по приоритетам)
- Функции, сгруппированные по этапам разработки
- Для каждой функции: **приоритет**, **слой** (ровно один из API/UI/DATA/INTEG/BIZ/CLI), **SMART-описание**, **пользовательская история**, зависимости
- **TDD-тесты** для каждой функции (1-3 на фичу, happy path, edge case, error case)
- **Red-тест** — первый падающий тест с обоснованием
- **Refactor-цели** — что улучшить после Green
- **Критерии приёмки** (2-3 на фичу, измеримые SMART-условия готовности)
- **E2E-сценарий этапа** и **Smoke-критерий этапа** — phase-gate верификация
- **Оценка объёма** (S/M/L/XL) для каждой фичи
- Полный чеклист по приоритетам
- Граф зависимостей
- При превышении лимитов — блок ⚠️ «Предупреждения»

## Пример полного фрагмента roadmap

Ниже — пример одного этапа с карточками функций в формате v1.3 (RGR TDD):

```markdown
## Этап 1: API уведомлений (MVP)

**Цель:** Базовый CRUD API для уведомлений, позволяющий создавать и получать уведомления через REST.
**Приоритет функций:** P0–P1
**E2E-сценарий этапа:**
  - *Условие:* Пользователь авторизован, БД пуста.
  - *Шаги:* POST /api/notifications { title: "Test", body: "Hello" } → GET /api/notifications.
  - *Ожидаемый результат:* 201 Created на POST, массив из 1 элемента на GET с полями id/title/body/createdAt.
**Smoke-критерий этапа:** POST /api/notifications возвращает 201, GET /api/notifications возвращает 200 с массивом.

#### ☐ F-1.1: POST /api/notifications — создание уведомления
- **Приоритет:** P0
- **Слой:** [API]
- **Описание:** Endpoint принимает JSON { title, body }, валидирует, сохраняет в БД, возвращает 201.
- **Пользовательская история:** «Как клиент API, я хочу создавать уведомления через POST, чтобы автоматизировать отправку»
- **Зависимости:** (none)
- **TDD-тесты:**
  - [ ] **TC-F-1.1-1:** Создание уведомления с валидными данными
    - *Условие:* БД пуста, пользователь авторизован
    - *Шаги:* POST /api/notifications { title: "Alert", body: "Server down" }
    - *Ожидаемый результат:* 201 Created, тело ответа содержит id, title="Alert", body="Server down", createdAt (ISO 8601)
  - [ ] **TC-F-1.1-2:** Создание уведомления с пустым title
    - *Условие:* Пользователь авторизован
    - *Шаги:* POST /api/notifications { title: "", body: "Test" }
    - *Ожидаемый результат:* 400 Bad Request, тело ошибки содержит поле "title" с сообщением "required"
- **Red-тест:** TC-F-1.1-1 — падает, потому что endpoint POST /api/notifications ещё не реализован (404 Not Found)
- **Refactor-цели:** Вынести валидацию title/body в отдельный middleware; унифицировать формат ошибок
- **Критерии приёмки:**
  1. POST /api/notifications с валидными данными возвращает 201 и объект уведомления за < 50 мс
  2. POST с пустым title или body возвращает 400 с описанием ошибки
  3. Дубликаты (title+body совпадают в течение 60с) возвращают 200 с существующим объектом (идемпотентность)
- **Ожидаемый результат:** Файл `src/api/notifications.controller.ts` + маршрутизация
- **Оценка объёма:** M (≤ 1 день)

#### ☐ F-1.2: GET /api/notifications — получение списка
- **Приоритет:** P0
- **Слой:** [API]
- **Описание:** Endpoint возвращает пагинированный список уведомлений, сортировка по createdAt DESC.
- **Зависимости:** F-1.1
- **TDD-тесты:**
  - [ ] **TC-F-1.2-1:** Получение списка уведомлений
    - *Условие:* В БД 25 уведомлений, пользователь авторизован
    - *Шаги:* GET /api/notifications?page=1&limit=10
    - *Ожидаемый результат:* 200 OK, массив из 10 элементов, отсортированных по createdAt DESC
- **Red-тест:** TC-F-1.2-1 — падает, потому что GET /api/notifications возвращает 404
- **Refactor-цели:** (none) — простая выборка, рефакторинг не требуется на этом этапе
- **Критерии приёмки:**
  1. GET /api/notifications возвращает 200 и массив уведомлений за < 100 мс при N=100
  2. Пагинация: limit=10 возвращает ровно 10 записей, page=2 — следующие 10
  3. Сортировка: первый элемент имеет максимальный createdAt
- **Ожидаемый результат:** Метод в `src/api/notifications.controller.ts` + query-параметры
- **Оценка объёма:** S (≤ 4ч)
```

## Конфигурация

Не требует конфигурации. Входные данные — спецификация в Markdown.

## Зависимости

Нет внешних зависимостей. Использует только встроенные инструменты агента (read, write, bash, question, questionnaire).

## Структура

```
feature-roadmap/
├── SKILL.md                              # Главный файл скилла с инструкциями
├── README.md                             # Этот файл
├── package.json                          # Метаданные пакета
├── DEPLOY.toml                           # Манифест деплоя
└── references/
    ├── feature-isolation-guide.md        # Подробные правила обособленности фич
    ├── delegation-guide.md               # Полное руководство по делегированию
    └── roadmap-template.md               # Шаблон выходного roadmap.md
```
