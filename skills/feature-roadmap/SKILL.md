# feature-roadmap — TDD-роадмапа по спецификации

Генерирует полный roadmap развития фичи в парадигме TDD. Каждая функция — пункт с чекбоксом,
разбитый по этапам и приоритетам. Для каждой функции перечисляются TDD-тесты,
которые нужно пройти для её реализации.

<!-- worker:exclude-start -->
## Когда использовать

- Есть спецификация фичи (или детальное описание) и нужен план разработки
- Нужно разбить фичу на этапы с чётким TDD-подходом
- Требуется определить приоритеты функций и их зависимости
- Нужен готовый чеклист для отслеживания прогресса разработки

## Когда НЕ использовать

- Нужно создать спецификацию (сначала research-spec-generator)
- Спецификация описывает > 15 функций — сначала разбейте спеку на дочерние через `/skill:research-spec-generator`
- Нужно создать полный пакет документации для разработки (используйте dev-docs-pack)
- Нужно исследовать идею (используйте idea-lab)
- Нет описания фичи (сначала создайте spec, потом возвращайтесь)

## Правила обособленности фич

Каждая фича в roadmap — это **одна логическая единица изменения**, а не описание
куска работы. Гранулярность фич — ключевое свойство roadmap: слишком мелкие
фичи порождают шум в чеклисте, слишком крупные — невозможно оценить и делегировать.

### ✅ Хорошая фича (эталон)

Фича соответствует **одному** из следующих критериев (и только одному):

| Тип фичи | Примеры | Эвристика «золотой середины» |
|----------|---------|------------------------------|
| **API endpoint** | `POST /api/notifications`, `GET /api/users/:id` | Один HTTP-метод + один ресурс |
| **UI-компонент** | `NotificationBell`, `UserProfileCard` | Один переиспользуемый компонент с собственным состоянием |
| **Модель данных** | `Notification`, `UserPreferences` | Одна сущность + её валидации + миграция |
| **Пользовательская история** | «Пользователь видит список уведомлений» | Один user story с 2-3 шагами |
| **Бизнес-правило / процесс** | «Дедупликация уведомлений в течение 1 мин» | Одно правило, проверяемое юнит-тестом |
| **Интеграция с внешним сервисом** | «Отправка email через SendGrid» | Один внешний сервис + один адаптер |
| **Команда / CLI-операция** | `notifications:send-daily-digest` | Одна команда с флагами |

**Числовые характеристики хорошей фичи:**
- 1-3 TDD-теста
- 2-3 критерия приёмки
- 1-3 файла исходного кода в реализации
- Один слой архитектуры (НЕ смесь API + UI + storage)

### ⚠️ Слишком мелкая фича (объединить)

Фича слишком мелка, если выполняются **≥ 2** из условий:
- 1 TDD-тест
- 1 критерий приёмки
- Нет самостоятельной пользовательской ценности (тривиальный шаг внутри другой фичи)
- Тривиальная обёртка над существующим API (`isEmpty()`, `formatDate()`)
- Только валидация / guard clause без бизнес-логики

**Действие:** объединить с родительской фичей как «подшаг» (в раздел «Ожидаемый результат»).

### ⚠️ Слишком крупная фича (разбить)

Фича слишком крупна, если выполняется **≥ 1** из условий:
- **Смешивает слои:** API + UI + storage в одной карточке
- **> 3 TDD-теста** в эскизе (легко генерируется 5-7 — это сигнал разбить)
- **> 3 критериев приёмки** (5+ — перегруз)
- **> 3 подзадач** в логике реализации
- **> 2 файлов ответственности** (например, `controller.ts` + `service.ts` + `repository.ts` + `component.tsx` — это уже 3-4 фичи)
- **Зависит от > 2 других фич** одновременно
- **Длительность реализации** > 1-2 дней для соло-разработчика

**Действие:** разбить на N фич по слоям или по сценариям. Если после разбиения
суммарное число функций в roadmap превышает 15 — делегировать часть в
`/skill:research-spec-generator` (см. секцию «Делегирование в research-spec-generator»).

### Чеклист валидации фичи (применить к каждой карточке)

- [ ] Фича относится ровно к одному слою архитектуры
- [ ] Количество TDD-тестов в эскизе: 1-3
- [ ] Количество критериев приёмки: 2-3
- [ ] Есть самостоятельная пользовательская ценность или чёткая техническая ответственность
- [ ] Название сформулировано как SMART-цель (см. ниже)

### SMART-формулировки в карточке фичи

Каждый элемент карточки (название, описание, TDD-тест, критерий приёмки) должен быть:

- **S** (Specific) — Конкретно: что именно, где, для кого. Без абстракций.
- **M** (Measurable) — Измеримо: число, статус-код, состояние UI, процент.
- **A** (Achievable) — Достижимо: реализуемо в рамках одной фичи.
- **R** (Relevant) — Релевантно: связано с пользовательской историей или бизнес-правилом.
- **T** (Testable) — Проверяемо: можно написать автотест или вручную кликнуть.

**Плохо:** «Система работает быстро», «UI выглядит хорошо», «API надёжный».
**Хорошо:** «GET /api/notifications возвращает 200 OK и массив за < 100 мс при N=100»,
«NotificationBell виден в шапке при непрочитанных > 0», «POST /api/notify возвращает 201 и идемпотентен при дублях в течение 60с».

## Парсинг входных данных

Skill принимает аргументы через `/skill:feature-roadmap <args>`:

1. **Путь к файлу спецификации:**
   ```
   /skill:feature-roadmap docs/specs/spec_notification-system_2026-05-06.md
   ```
   Читать файл напрямую через `read`.

2. **Имя фичи (slug):**
   ```
   /skill:feature-roadmap notification-system
   ```
   Искать файлы через:
   ```bash
   find docs/specs/ -name '*<slug>*' -type f
   find docs/features/ -name '*<slug>*' -type f
   ```
   Если найдено несколько — спросить пользователя через `question`.

3. **Описание фичи (свободный текст):**
   ```
   /skill:feature-roadmap Нужно сделать систему уведомлений с...
   ```
   Использовать описание как есть. Полнота описания будет низкой — сразу запросить детали через questionnaire.

4. **Без аргументов:**
   Запустить интерактивный режим — запросить путь к спеке или описание фичи через `question`.

5. **Если аргумент содержит `/` или `.md`** — считать путём к файлу. Иначе — считать именем фичи.

## Процесс

### Фаза 1: Получение и парсинг входных данных

**1.1 Определить входные данные**

Распарсить аргументы по правилам выше. Если ничего не передано — запросить:

```
question({
  question: "Укажите спецификацию или описание фичи:",
  options: [
    { label: "Путь к файлу спецификации", description: "например docs/specs/spec_...md" },
    { label: "Имя фичи (поиск в docs/)", description: "поищем в docs/specs/ и docs/features/" },
    { label: "Опишу сейчас", description: "введу описание фичи в свободной форме" },
    { label: "Отмена" }
  ]
})
```

Если выбран путь или имя — получить содержимое через `read()`.

**1.2 Определить slug фичи**

- Если указан путь — извлечь имя из названия файла (после `spec_` или первое слово)
- Если указано имя — использовать его
- Если свободное описание — извлечь ключевое слово и предложить пользователю

Формат: kebab-case (например, `notification-system`).

**1.3 Создать директорию для вывода**

```bash
mkdir -p docs/features/<slug>
```

### Фаза 2: Извлечение функций из спецификации

**2.1 Парсинг спецификации**

Прочитать содержимое спецификации полностью. Извлечь:

- **Функции/возможности** — всё, что описывает конкретную функциональность:
  - Заголовки разделов, подразделов, пунктов (##, ###)
  - Списки требований (`- ...`, `1. ...`)
  - API endpoints (POST, GET, PUT, DELETE)
  - Компоненты UI
  - Модели данных и схемы
  - Use cases и user stories
  - Команды и сценарии

- **Описание каждой функции** — текст рядом с упоминанием
- **Связи/зависимости** — если одна функция упоминается в контексте другой
- **Этапы** — если спецификация уже разбита на фазы

**2.2 Структурировать функции**

Для каждой функции записать:
```
- **ID:** F-<этап>.<номер> (автонумерация)
- **Название:** извлечённое из спецификации
- **Описание:** краткое описание что делает
- **Приоритет:** не назначен (будет уточнено на фазе 3)
- **Этап:** не назначен (будет уточнено)
- **Зависимости:** пусто (будет заполнено)
```

**2.2.1 Первичная проверка обособленности (эвристика по сырому списку функций)**

После парсинга спецификации, **до интервью**, применить следующие эвристики
к каждой извлечённой функции:

1. **Слои в одной карточке.** Если функция упоминает и API-эндпоинт,
   и UI-компонент, и модель данных — пометить как `needs_split` и в Фазе 3
   задать вопрос «Разбить на N фич по слоям?».

2. **Размер описания.** Если описание функции в спецификации занимает
   > 300 слов или содержит > 3 пунктов списка — пометить как `too_large_candidate`.

3. **Множественность ресурсов.** Если в одной карточке смешано
   > 1 типа сущности (например, «управление пользователями и ролями»)
   — пометить как `too_large_candidate`.

Зафиксировать список помеченных функций в контексте агента — он понадобится
в Фазе 3 для таргетированных уточнений.

**Пример:**
```
Обнаружено 3 функции, требующих разбиения:
- «F-2.1 Управление уведомлениями (API + UI + БД)» — нужно разбить на F-2.1a, F-2.1b, F-2.1c
- «F-3.1 Авторизация (email + OAuth + 2FA)» — нужно разбить по провайдерам
- «F-4.1 Дашборд аналитики» — описание > 300 слов, разбить по виджетам
```

**2.3 Оценить полноту извлечения**

- Если из спецификации удалось извлечь < 3 функций — полнота низкая
- Если есть явные пробелы (описан API, но не описаны use cases) — полнота средняя
- Если спецификация структурирована и функции чётко выделены — полнота высокая

Если полнота < средней — перейти к Фазе 3 (интервью) для заполнения пробелов.

### Фаза 3: Интервью для уточнения

Использовать `questionnaire` для сбора недостающей информации.

**3.1 Если не определены этапы:**

```
questionnaire({
  questions: [
    {
      id: "phases",
      label: "Этапы",
      prompt: "На какие этапы разбить разработку?",
      options: [
        { value: "mvp-expand-polish", label: "MVP → Расширение → Полировка" },
        { value: "core-integration-advanced", label: "Ядро → Интеграция → Продвинутые" },
        { value: "custom", label: "Свои этапы (введу вручную)" }
      ]
    },
    ...
  ]
})
```

**3.2 Если не определены приоритеты:**

Для каждой функции спросить приоритет. Если функций много — группировать:

```
question({
  question: "Какой приоритет у функции «<название>»?",
  options: [
    { label: "P0 — Критично", description: "Без этого фича не имеет смысла" },
    { label: "P1 — Высокий", description: "Важно для большинства пользователей" },
    { label: "P2 — Средний", description: "Полезно, но не срочно" },
    { label: "P3 — Низкий", description: "Future enhancement" }
  ]
})
```

**3.3 Если есть неясные функции:**

Запросить описание уточняющим вопросом.

**3.4 Проверка лимита этапов (лимит = 8)**

После выбора этапов (п. 3.1) или после ручного ввода (custom) **посчитать
количество этапов**. Если `количество_этапов > 8` — сработал триггер
делегирования. Выполнить следующий поток:

```
// Агент вычисляет автоматически
const phaseCount = phases.length;
if (phaseCount > 8) {
  triggerDelegationFlow();
}
```

**Сообщение пользователю:**
```
Обнаружено {N} этапов (лимит: 8). Фича слишком крупная для одного roadmap.
Рекомендую разбить спецификацию на дочерние через /skill:research-spec-generator,
а затем сгенерировать roadmap для каждой дочерней спеки отдельно.
```

**Варианты действий (через `question`):**
```
question({
  question: "Как поступить с превышением лимита этапов?",
  options: [
    { label: "Делегировать в spec-generator", description: "Разбить спеку на 2-3 дочерние, по каждой сделать roadmap" },
    { label: "Сократить этапы", description: "Помогите сократить до 8 (объединить близкие)" },
    { label: "Продолжить с предупреждением", description: "Сгенерировать roadmap для всех {N} этапов, но пометить как нерекомендуемый" }
  ]
})
```

Если пользователь выбирает «Сократить» — перейти к подразделу 3.5
«Помощь в сокращении этапов» (см. ниже).

Если пользователь выбирает «Делегировать» — перейти к секции
«Делегирование в research-spec-generator» (полная спецификация — в Фазе 4).

Если пользователь выбирает «Продолжить с предупреждением» — зафиксировать
предупреждение в roadmap (в шапке) и продолжить Фазу 4.

**3.5 Помощь в сокращении этапов**

Если выбрано «Сократить» — агент выводит список этапов и предлагает объединить
близкие по содержанию. Например:
```
Сейчас 10 этапов. Вижу кандидатов на объединение:
- «Авторизация через email» + «Авторизация через OAuth» → «Авторизация пользователей»
- «Кэширование запросов» + «Оптимизация индексов» → «Производительность и кэширование»

Объединить эти пары? (Y/n/custom)
```

**Правило «золотой середины» для этапов:**
- **Минимум:** 2 этапа (иначе нет смысла в roadmap — это просто список фич)
- **Оптимум:** 3-5 этапов
- **Допустимо:** 6-8 этапов
- **Превышение (≥ 9):** обязательное делегирование или сокращение

**Критерий завершения фазы 3:** каждая функция имеет приоритет и этап, количество этапов ≤ 8.

---

### Фаза 4: Генерация roadmap

**4.1 Сгенерировать TDD-тесты для каждой функции**

Для каждой функции создать 1-3 TDD-тест-кейса:

```markdown
#### ☐ <ID>: <Название функции>
- **Приоритет:** P0/P1/P2/P3
- **Описание:** <что делает>
- **Зависимости:** <ID других функций> или (none)
- **TDD-тесты:**
  - [ ] **TC-<ID>-1:** <название теста>
    - *Условие:* <предусловие, контекст>
    - *Шаги:* <что делает тест>
    - *Ожидаемый результат:* <что должно произойти>
  - [ ] **TC-<ID>-2:** <название>
    - *Условие:* ...
    - *Шаги:* ...
    - *Ожидаемый результат:* ...
- **Критерии приёмки:**
  1. <критерий 1 — конкретное, измеримое условие>
  2. <критерий 2>
  3. <критерий 3>
- **Ожидаемый результат:** <что получаем на выходе — конкретное описание>
```

**Правила для TDD-тестов:**
- Каждый тест должен быть конкретным и проверяемым
- Тесты покрывают: happy path, edge case, error case
- Предусловия явные и воспроизводимые
- Ожидаемый результат — однозначный

**Правила для критериев приёмки:**
- Каждый критерий измеримый (не "работает хорошо", а "обрабатывает 1000 запросов за < 200ms")
- Покрывают функциональные и нефункциональные требования
- Могут быть автоматизированы

**4.2 Сгруппировать функции по этапам**

Внутри каждого этапа отсортировать по приоритету (P0 → P1 → P2 → P3).

**4.3 Создать roadmap.md**

```markdown
# Roadmap: <Название фичи>

> **Дата генерации:** YYYY-MM-DD
> **Источник:** <путь к спеке или описание>
> **Версия SKILL:** 1.2.0
> **Функций / Этапов:** N / M (лимит: 15 / 8)

> ⚠️ **Предупреждения** (если есть, иначе удалить блок):
> - Превышен лимит функций (>15) — рекомендуется разбиение
> - Этапов: {N} (>8) — сгенерировано по запросу пользователя «продолжить с предупреждением»
> - Функций с пометкой `too_large_candidate`: {K} (требуется разбиение на слои)

### Приоритеты
- **P0** — Критично (без этого фича не имеет смысла)
```

## Делегирование в /skill:research-spec-generator

### Когда срабатывает

Триггеры делегирования (любой из):

1. **Превышение лимита этапов** — `phaseCount > 8` (п. 3.4).
2. **Превышение лимита функций** — после Фазы 2 обнаружено `functionCount > 15`.
3. **Множество «too_large_candidate»** — более 30% функций помечены как
   требующие разбиения (см. п. 2.2.1).
4. **Смешение слоёв в спецификации** — спека описывает одновременно
   > 2 слабо связанных областей (например, «система уведомлений + админка
   + аналитика» в одной спеке).
5. **Явный запрос пользователя** — «разбей на части», «слишком много» и т.п.

### Формат передачи данных

Делегирование выполняется **через инструкцию пользователю** (скиллы в FAN
не вызывают друг друга напрямую):

```
🚨 Рекомендация: делегировать в /skill:research-spec-generator

Текущая спецификация: {source_spec_path или описание}
Обнаружено: {N} функций, {M} этапов (лимит: 15 функций / 8 этапов)

Кандидаты на выделение в дочерние спецификации:
1. «Подсистема X» — {N1} функций: {список через запятую}
2. «Подсистема Y» — {N2} функций: {список через запятую}
3. «Подсистема Z» — {N3} функций: {список через запятую}

Предлагаю запустить:
/skill:research-spec-generator {source_spec_path} — выделить в дочернюю спеку: «Подсистема X» (функции: F-1.1, F-1.2, F-2.3)
/skill:research-spec-generator {source_spec_path} — выделить в дочернюю спеку: «Подсистема Y» (функции: F-2.1, F-2.2)
/skill:research-spec-generator {source_spec_path} — выделить в дочернюю спеку: «Подсистема Z» (функции: F-3.1, F-3.2, F-3.3)

После создания дочерних спек запустите /skill:feature-roadmap для каждой:
/skill:feature-roadmap docs/specs/spec_x_2026-06-02.md
/skill:feature-roadmap docs/specs/spec_y_2026-06-02.md
/skill:feature-roadmap docs/specs/spec_z_2026-06-02.md

Если хотите делегировать автоматически (в одном интерактивном сеансе) — 
подтвердите, и я вызову research-spec-generator последовательно для каждой подсистемы.
```

**Структура аргумента** для `research-spec-generator`:
- Запрос = `<source_spec_path или краткое описание>` + ` — выделить в дочернюю спеку: "<имя_подсистемы>" (функции: <список ID>)`
- Тип запроса: «Новая фича» (уже категоризирован)
- Полнота: ~0.6 (агент знает, что выделять, но требует подтверждения)

### Обработка результата

После делегирования возможны **три сценария**:

**Сценарий A: одна новая спецификация → один новый roadmap.**
- spec-generator создаёт `docs/specs/spec_<subsystem>_<date>.md`
- Запускается `/skill:feature-roadmap <новый_путь>` (в том же сеансе или по запросу)
- Создаётся `docs/features/<subsystem>/roadmap.md`

**Сценарий B: несколько новых спецификаций → несколько roadmap-ов.**
- spec-generator создаёт N файлов в `docs/specs/`
- Агент предлагает пользователю запустить `/skill:feature-roadmap` для каждого
- ИЛИ, при подтверждении, запускает цикл `for spec in spec_*.md: roadmap(spec)`

**Сценарий C: spec-generator не установлен.**
- Агент сообщает: «Скилл /skill:research-spec-generator не обнаружен. Установите его через FAN Store (`fan store install research-spec-generator`) или вручную. Пока продолжим с предупреждением.»
- Спрашивает: «Продолжить генерацию roadmap с превышением лимита (Y/n)?»
- Если «да» — продолжает Фазу 4, ставит в шапке roadmap предупреждение
- Если «нет» — прерывает процесс, рекомендует установить скилл

### Связь с обособленностью фич

Делегирование **не подменяет** разбиение крупных фич на слои (п. 2.2.1).
Это разные механизмы:
- **Разбиение фич** — внутри одного roadmap, для ясности реализации
- **Делегирование в spec-generator** — между roadmap-ами, когда весь объём
  фичи превышает разумные границы (15+ функций, 9+ этапов)

## Правила

### Базовые правила (сохранены из v1.0)

1. **Каждая функция — пункт чеклиста.** Никаких общих описаний без чекбоксов для функций.
2. **TDD-first.** Для каждой функции сначала тесты, потом реализация. Тесты пишутся до кода.
3. **P0 функции в MVP.** Если этап 1 (MVP) не имеет P0 функций — пересмотреть распределение.
4. **Минимум вопросов.** Если спецификация полная — не задавай лишних вопросов.
5. **Документируй решения.** Любые решения пользователя по приоритетам/этапам фиксируй в roadmap.
6. **Чёткие формулировки.** TDD-тесты и критерии приёмки должны быть однозначными и проверяемыми.
7. **Не overwrite без спроса.** Если `docs/features/<slug>/` уже существует — спросить перезаписать, обновить или отменить.
8. **Сохраняй slug в памяти.** После генерации запомни `<slug>` и путь к roadmap для возможных follow-up вопросов.

### Новые правила (v1.1)

9. **Обособленность фич.** Каждая фича = один логический слой + 1-3 TDD-теста + 2-3 критерия приёмки.
   Смешение слоёв (API + UI + storage) в одной карточке — запрещено. Триггер разбиения
   срабатывает на Фазе 2 (п. 2.2.1) и Фазе 4 (п. 4.4).

10. **Лимит этапов = 8.** При `phaseCount > 8` запускается триггер делегирования (п. 3.4).
    Пользователь выбирает: делегировать в spec-generator / сократить этапы / продолжить
    с предупреждением. Продолжение без явного согласия пользователя запрещено.

11. **Лимит функций = 15.** При `functionCount > 15` после Фазы 2 — рекомендация
    делегирования. Мягкий лимит (warning, не блок), но фиксируется в шапке roadmap.

12. **Делегирование в spec-generator.** При срабатывании триггера — сформировать
    чёткую инструкцию пользователю (какие подсистемы выделить, в каком формате
    передать в spec-generator), а не пытаться уместить всё в один roadmap.
    Если spec-generator не установлен — сообщить и предложить пользователю
    выбор «продолжить с предупреждением» или «прервать и установить скилл».

### Правила формулировок (v1.1)

13. **SMART для всего проверяемого.** Название фичи, описание, TDD-тесты,
    критерии приёмки — всё формулируется по SMART (S/M/A/R/T). Абстрактные
    формулировки («работает хорошо», «быстро», «надёжно») запрещены.

14. **Оценка объёма обязательна.** Каждая функция имеет метку S/M/L/XL.
    `XL` (> 2 дней соло) — сигнал разбиения перед коммитом roadmap.
