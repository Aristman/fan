# Lavish-аппрув (Фазы 3 и 5)

> Детализация интерактивного цикла аппрува — единственной интерактивности скилла
> feature-factory ПОСЛЕ kickoff (вопросы пользователю — только в Фазе 1, единый
> kickoff-опрос; здесь вопрос не задаётся — артефакт утверждается). База: скилл lavish
> (`~/.fan/agent/skills/lavish/SKILL.md`, расширение lavish). Применяется к двум артефактам:
> - **спека** — Фаза 3: `config.lavish.specApproval` + `templates/spec-preview.html` → `.fan/feature-factory/<slug>/spec-preview.html`;
> - **роадмапа** — Фаза 5: `config.lavish.roadmapApproval` + `templates/roadmap-preview.html` → `.fan/feature-factory/<slug>/roadmap-preview.html`.

## Когда запускать

- `config.lavish.specApproval.enabled: true` / `config.lavish.roadmapApproval.enabled: true` — цикл обязателен. **Продолжение без аппрува запрещено** (жёсткое правило 3 SKILL.md).
- `enabled: false` — цикл пропускается; в чат выводится уведомление «аппрув отключён конфигом», путь к markdown-артефакту, и запуск продолжается.

## Точный цикл (порядок нарушать запрещено)

### Шаг A: Playbook ДО HTML

```
lavish({ command: "playbook", playbook_id: "<config.lavish.*Approval.playbook>" })
```

`playbook` берётся из конфига (дефолт: `"plan"` — соответствует типу артефакта
«план/спецификация» по роутеру playbook'ов lavish). Вызов обязателен **до** написания HTML —
он возвращает guidance по структуре и дизайну. **Пропуск playbook перед HTML запрещён**
(жёсткое правило 4 SKILL.md).

### Шаг B: Рендер HTML

1. Взять каркас: `templates/spec-preview.html` (Фаза 3) или `templates/roadmap-preview.html` (Фаза 5).
2. Подставить данные из markdown-артефакта вместо плейсхолдеров `{{...}}`.
3. Требования к HTML:
   - **inline CSS** (`<style>` в файле), без внешних CDN и внешних стилейheets. Исключение: явный design guidance от playbook/design-команды lavish;
   - **relative paths** для любых локальных ассетов (file:// абсолютные пути не резолвятся через Lavish-сервер); лучше — без внешних ассетов вообще;
   - семантическая разметка (`<table>`, `<details>`, `<ol>/<ul>`) — аннотации Lavish работают лучше на семантике;
   - каркасы шаблонов уже поддерживают тёмную/светлую тему — не ломай CSS-переменные.

4. Сохранить в `.fan/feature-factory/<slug>/spec-preview.html` или `roadmap-preview.html` (`mkdir -p` при необходимости).

### Шаг C: Open → Poll

```
lavish({ command: "open", file: "<path_to_html>" })
lavish({ command: "poll", file: "<path_to_html>" })
```

**Poll после open обязателен.** Возврат к пользователю в чат без сбора фидбека запрещён.

### Шаг D: Обработка ответа poll

| Ответ poll | Значение | Действие |
|------------|----------|----------|
| `layout_warnings` | доказанные серьёзные поломки вёрстки | Исправить HTML (не содержимое!) → повторный `poll`. Не спрашивать пользователя, пока вёрстка сломана |
| `prompts` | аннотации/сообщения пользователя | Для каждого prompt: распознать по `config.lavish.approveKeywords` **ИЛИ** трактовать как содержательную правку (см. ниже) |
| `status: "ended"` | пользователь закрыл сессию | Стоп polling. Не переоткрывать сессию без явной просьбы пользователя. Если явный аппрув не зафиксирован — см. «Завершение после ended» |

### Шаг E: Разбор prompts

Для каждого prompt из `prompts`:

1. **Сравнить с `config.lavish.approveKeywords`** (дефолт: `approve`, `approved`, `аппрув`, `ок`, `согласовано`, `всё отлично`, `выглядит хорошо`).
   - Сопоставление: нормализуй регистр и(trim); keyword совпадает, если он равен prompt целиком или является его однозначным подтверждением в начале/конце короткого prompt (≤ 3 слов). Prompt «ок, но поправь X» — НЕ аппрув: содержит правку.
2. **Если prompt = правка** (всё, что не распознано как approve-keyword): это фидбек к артефакту. Обязательно:
   - внести правку в **markdown-артефакт** (спеку или roadmap) — правка только HTML-превью запрещена (жёсткое правило 5 SKILL.md: markdown — источник истины);
   - перерендерить HTML из обновлённого markdown (тот же файл превью);
   - вызвать `poll` снова, передав `agent_reply` с описанием того, что изменено.
3. **Если все prompts = approve-keywords** (и правок нет) — аппрув зафиксирован.

### Шаг F: Итерации и лимит

- Максимум **`config.lavish.maxRevisions` итераций доработки на артефакт** (дефолт 5; итерация = цикл «правки → перерендер → poll»).
- Лимит исчерпан → **остановка с отчётом** (валидный исход, жёсткое правило 6 SKILL.md): что утверждено, какие правки вносились, путь к markdown-артефакту, как продолжить (`/skill:feature-factory <путь к артефакту>`).
- `layout_warnings` не считаются итерациями доработки (это ремонт вёрстки), но бесконечный цикл warnings (≥ 5 подряд без прогресса) также ведёт к остановке с отчётом.

## Что считается зафиксированным аппрувом

Аппрув зафиксирован, когда выполнено **одно** из:

1. Все `prompts` в цикле содержат только `approveKeywords` (ни одной содержательной правки в последнем раунде), ИЛИ
2. Пользователь подтвердил в явной форме **после** `status: "ended"` — например, написал в чат «аппрув» / keyword из `approveKeywords` по факту закрытия превью. Инициировать такой запрос в чате можно только когда сессия ended без оценки: выведи нейтральное уведомление «Превью закрыто без явного аппрува. Ответь "аппрув" в чате, чтобы продолжить, или запусти скилл заново с правками» — это единственный случай, когда feature-factory ожидает реплику пользователя вне kickoff-опроса (Фаза 1), и он не является вопросом: вопрос не задаётся, констатируется состояние (жёсткие правила 1–2 SKILL.md не нарушаются).

## Завершение после ended без аппрува

- `status: "ended"` + не было ни одного prompt → нейтральное уведомление в чат (см. выше) и остановка запуска с отчётом (путь к артефакту, статус фаз). Запуск не продолжается вглубь без аппрува.
- `status: "ended"` + последний prompt был approve-keyword → аппрув зафиксирован (случай 2), продолжай следующую фазу.

## После аппрува

1. Обнови метаданные markdown-артефакта: спека `**Статус**: Утверждена (Lavish-аппрув YYYY-MM-DD)`, roadmap — отметка в шапке.
2. Уведомление в чат: «Спека/роадмапа утверждена, итераций: N».
3. Переход к следующей фазе SKILL.md (Фаза 3 → Фаза 4; Фаза 5 → Фаза 6).

Для роадмапы (Фаза 5) переходу к Фазе 6 предшествует baseline-коммит артефактов планирования (точка начала разработки; детали в SKILL.md, Фаза 5, «Baseline-коммит точки начала разработки»).
