# Фаза 5: Pipeline (TDD-реализация)

> Детализация фазы 5 скилла feature-factory. База: скилл feature-pipeline v3.3
> (`skills/feature-pipeline/SKILL.md`) — **первоисточник полной детализации шагов,
> анти-паттернов, commit policy и форматов delegate_task**. Эта фаза исполняема без него,
> но при спорных деталях сверяйся с первоисточником. Все интерактивные точки исходного
> скилла (P-1..P-5) заменены полями `config.pipeline.*` — вопросник Фазы 0 (P-1/P-2)
> исключён полностью.
>
> Координатор НЕ пишет код, НЕ пишет тесты, НЕ коммитит сам. Каждый шаг TDD-цикла —
> отдельный `delegate_task`. Верификация — всегда отдельным воркером, не тем же,
> что implement (adversarial verify).

## Маппинг интерактивных точек feature-pipeline → конфиг

| # | Точка в исходном скилле | Было | Стало в feature-factory |
|---|------------------------|------|------------------------|
| P-1 | Questionnaire перед стартом: стратегия коммитов + scope + репортинг | интерактив | `config.pipeline.commitStrategy`; scope = все функции roadmap (уведомление в чат); репортинг — артефакты на диске |
| P-2 | Контрольные точки (вопросы на границах этапов и после функций) | интерактив | `config.pipeline.controlPoints` — режим уведомлений/остановок без вопросов |
| P-3 | Вопрос после исчерпания попыток verify (пропустить/ещё/отменить) | интерактив | `config.pipeline.maxVerifyRetries` + `config.pipeline.onMaxRetriesExceeded` — автоматическое действие |
| P-4 | Вопрос на phase-gate (сводка этапа, что дальше) | интерактив | `config.pipeline.phaseGate` — gate исполняется автоматически, сводка в чат |
| P-5 | Финальный вопрос «Что дальше?» после отчёта | интерактив | Удалён. Финал — pipeline-report.md + сводка в чат (Фаза 6) |

## Шаг 5.0: Инициализация (Фаза 0 исходного скилла, без вопросника)

1. **Прочитать roadmap** (`docs/features/<slug>/roadmap.md`) и распарсить: этапы (`## Этап X`), функции (`#### ☐ F-X.Y`), TDD-тесты (`TC-F-X.Y-N`), Red-тест, Refactor-цели, критерии приёмки, зависимости, `E2E-сценарий этапа`, `Smoke-критерий этапа`.
2. **Проверить статусы** (resumable): функции со статусом ✅ — пропускаются; ⏳/❌ — возвращаются в работу (❌ только если явно помечены как отказ); roadmap без функций — остановка с отчётом.
3. **Scope-уведомление в чат** (вместо P-1): перечисли найденные функции с приоритетами и стратегию коммитов `config.pipeline.commitStrategy`. Это уведомление, не вопрос.
4. **Создать task list** — `TaskCreate` на каждую функцию `F-X.Y` (subject = `F-X.Y [<слой>]: <название>`, чтобы orchestrator мог инферить phaseId) плюс фиксированные: `Verify final`, `Smoke`, `Docs`. Все в статусе `pending`; зависимости через `blocks[]`.
5. **Создать feature-ветку** (если её ещё нет): `git checkout -b feature/<slug>` (базовая — master или develop по конвенции проекта).
6. **Рабочие артефакты**: если установлен FAN Orchestrator — `/pipeline init` (создаёт `docs/development-plan.md`, `docs/development-log.md`, `.fan/tracking/phase-status.json`); иначе веди `docs/features/<slug>/pipeline-report.md` инкрементально сам.

## Основной цикл (по функциям, Red-Green-Refactor)

Итерация = одна функция (первая ☐ с учётом зависимостей и приоритетов):

1. `TaskUpdate(F-X.Y, in_progress)`.
2. **🔴 Red** — `delegate_task(agent="tests-impl")`: написать failing-тесты по TC-карточкам F-X.Y; запустить, **подтвердить FAIL** (Red не подтверждён — к Green не переходить).
3. **🟢 Green** — `delegate_task(agent="implement")`: минимальная реализация для PASS (без лишней функциональности); подтвердить PASS.
4. **Verify** — `delegate_task(agent="verify")` (независимый, без контекста implement): TDD-тесты + критерии приёмки + сборка + регрессия. VERDICT: PASS / FAIL.
5. **При FAIL** — `delegate_task(agent="bug-fix")` → повторный verify. Лимит попыток: `config.pipeline.maxVerifyRetries` (дефолт 3). После исчерпания — действие `config.pipeline.onMaxRetriesExceeded`:
   - `"abort"` (дефолт) — `TaskUpdate(F-X.Y, failed)`, **остановка всего запуска с отчётом** (см. «Остановка с отчётом» ниже);
   - `"skip"` — `TaskUpdate(F-X.Y, failed)`, пометить ❌ в roadmap, продолжить со следующей функции;
   - `"ask"` — недопустимо в feature-factory (превратился бы в вопрос вне конфига); если в проектном конфиге стоит `"ask"` — веди себя как `"abort"`.
6. **🔵 Refactor** — `delegate_task(agent="implement", phase="refactor")`: выполнить `Refactor-цели` из roadmap; если `(none)` — шаг пропускается. Рефакторинг только при зелёных тестах; после рефакторинга тесты прогоняются повторно (упали — откат/исправление до зелёного).
7. **Commit** — по `config.pipeline.commitStrategy`:

   | Стратегия | Когда | Формат |
   |-----------|-------|--------|
   | `per-function` (дефолт) | после завершения функции | `feat(<slug>/F-X.Y): <summary>` |
   | `per-phase` | на границе завершённого этапа | `feat(<slug>/stage-X): <название этапа> complete` |
   | `manual` | никогда автоматически | — |

   Правила коммита (из первоисточника): `git status` перед коммитом; `git add` явным списком файлов (не `-A`); conventional-commits; без `--no-verify`; один коммит = одна функция/этап; SHA фиксируется в отчёте/артефактах.

8. `TaskUpdate(F-X.Y, completed)`; обновить статус в roadmap.md (☐ → ✅/❌ — единственное допустимое изменение roadmap).
9. **Phase-gate** (граница этапов: следующая функция из нового этапа) — по `config.pipeline.phaseGate`:
   - `"auto"` (дефолт): выполнить `Smoke-критерий этапа` (verify-воркер) + `E2E-сценарий этапа` (tests-impl-воркер) из roadmap; FAIL → bug-fix до зелёного, этап не считается завершённым; PASS → краткая сводка этапа ✅/❌ в чат и переход к следующему этапу. Если этап затрагивал auth/секреты/пользовательский ввод и `config.pipeline.securityAudit` ≠ `"off"` — дополнительный `delegate_task(agent="security")` на код этапа;
   - `"off"`: gate не выполняется (не рекомендуется — теряется гарантия целостности этапа).
10. Есть следующая ☐ функция → шаг 1. Нет → **финальная фаза G**.

### Контрольные точки (P-2 → конфиг)

`config.pipeline.controlPoints` управляет тем, где координатор пишет пользователю (всегда уведомлением, не вопросом):

| Значение | Поведение |
|----------|-----------|
| `"on-error"` (дефолт) | Пишет только при исчерпании попыток (тогда обычно и остановка) и в финале |
| `"per-stage"` | + краткая сводка после каждого phase-gate |
| `"per-function"` | + краткая сводка ✅/❌ после каждой функции |
| `"final"` | Пишет только в финале |

### Принципы (из первоисточника, соблюсти обязательно)

- Запрещена black-box делегация (весь pipeline одному implement-воркеру).
- Запрещён Test-After (код до тестов) — порядок строго Red → Green.
- Запрещён рефакторинг без зелёных тестов.
- Координатор хранит только метаданные: taskIds, статусы, SHA коммитов, вердикты.

## Финальная фаза G

> Выполняется, только когда все функции roadmap обработаны (✅ или ❌).

| Шаг | Что делается | Условие (конфиг) |
|-----|--------------|------------------|
| G.0 | Собрать сводку из артефактов (development-log / pipeline-report) | всегда |
| G.1 | Полная верификация фичи — `delegate_task(agent="verify")` на весь pipeline: все функции, критерии, сборка, регрессия, интеграция. FAIL/PARTIAL → implement-фикс → повтор (max 3 итерации) | всегда |
| G.1.5 | Code-review — `delegate_task(agent="code-review")` на полный дифф фичи (read-only, один раз на фичу): качество, дублирование, обработка ошибок. CHANGES_REQUESTED → implement-фикс → повтор (max 2) | `config.pipeline.codeReview`: `"final"` (дефолт) — выполнять; `"off"` — пропустить |
| G.1.6 | Security-аудит — `delegate_task(agent="security")` (read-only): OWASP/CWE, secret scanning, зависимости, конфигурации; findings с severity. CRITICAL/HIGH → implement-фикс → повтор (max 2) | `config.pipeline.securityAudit`: `"final"` (дефолт) — выполнять; `"off"` — пропустить |
| G.2 | Smoke-тест — `delegate_task(agent="tests-impl")`: один тест через основной сценарий фичи | всегда |
| G.3 | E2E-тест (если применимо: UI/сеть); иначе сообщить и пропустить | всегда (с autodetect применимости) |
| G.4 | Обновление документации — `delegate_task(agent="docs-impl")`: README, CHANGELOG, синхронизация roadmap | `config.pipeline.docsUpdate: true` (дефолт); `false` — пропустить |
| G.5 | Синхронизировать статусы в roadmap.md: ☐ → ✅/❌, ⏳ не остаётся | всегда |
| G.6 | Финальный коммит: `feat(<slug>): finalize <slug>` с явным списком файлов; SHA запомнить | если были незакоммиченные изменения и стратегия ≠ manual |
| G.7 | Сгенерировать `docs/features/<slug>/pipeline-report.md` (структура отчёта — в первоисточнике, шаг G.7: сводка, таблица функций, финальная верификация, проблемы, изменённые файлы, документация, рекомендации) | всегда |
| G.8 | Вывести сводку в чат + `TaskClear()` (очистка завершённых задач). Финального вопроса пользователю нет (P-5 удалён) — за ним следует Фаза 6 SKILL.md | всегда |

## Остановка с отчётом (валидный исход)

Остановка — нормальный результат pipeline, не ошибка агента. Выполняется при:

- `onMaxRetriesExceeded: "abort"` после исчерпания `maxVerifyRetries` на функции;
- `onStageLimitExceeded: "abort"`/`"delegate"` в фазе роадмапы (Фаза 3);
- 5 исчерпанных итераций Lavish-аппрува (Фазы 2/4);
- пустом/некорректном roadmap или конфликте артефактов.

Формат остановки: статус запуска (какая фаза/функция), причина, что уже сделано (коммиты, артефакты), что нужно от пользователя (в свободной форме — это не вопрос с ожиданием ответа в текущем запуске), как возобновить (`/skill:feature-factory <путь к roadmap>`).
