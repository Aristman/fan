# Фаза 1: Спецификация

> Детализация фазы 1 скилла feature-factory. База: скилл research-spec-generator
> (`skills/research-spec-generator/SKILL.md`), переведённый на конфиг-управление:
> все интерактивные точки исходного скилла (R-1..R-3) заменены полями конфига.
> Аргумент фазы — описание фичи свободным текстом (аргумент запуска `/skill:feature-factory`).

## Маппинг интерактивных точек research-spec-generator → конфиг

| # | Точка в исходном скилле | Было | Стало в feature-factory |
|---|------------------------|------|------------------------|
| R-1 | Вопрос «Какой тип запроса?» (`question`, 6 опций) | интерактив | `config.spec.autoDetectType: true` → тип определяется автоматически по описанию из `config.spec.requestTypes`; уведомление в чат |
| R-2 | Раунды уточняющих вопросов (`questionnaire`, импровизированные вопросы) | интерактив | Только вопросы из `config.spec.interview.rounds[]`, ≤ `config.spec.interview.maxQuestionsPerRound` за раунд |
| R-3 | Финальное подтверждение «Готовы создать спецификацию?» (`question`) | интерактив | Удалено. Роль подтверждения выполняет Lavish-аппрув спеки (Фаза 2, `config.lavish.specApproval`) |

## Шаг 1.1: Зафиксировать исходный запрос

Сохрани аргумент запуска как «Ядро идеи» — отправную точку всего процесса. Если запуск
resumable (аргумент = путь к спеке или roadmap), эта фаза пропускается — см. «Обзор» в SKILL.md.

## Шаг 1.2: Категоризация запроса (R-1 → конфиг)

Определи тип запроса из `config.spec.requestTypes`:

| Тип | Признаки |
|-----|----------|
| `feature` | функционал для существующей системы |
| `project` | создание с нуля |
| `modification` | изменение существующего поведения |
| `integration` | соединение систем |
| `optimization` | улучшение характеристик |
| `research` | изучение технологии/подхода |

- Если `config.spec.autoDetectType: true` — определи тип сам по контексту описания и **сообщи его в чат** (не вопросом).
- Если `config.spec.autoDetectType: false` и тип неоднозначен — используй первый подходящий из `requestTypes`, зафиксируй допущение в спеке (метаданные «Тип»). **Вопрос пользователю запрещён.**
- Для `research` спека создаётся по исследовательскому шаблону (см. research-spec-generator, шаблон «Исследование»); роадмапа/pipeline для него обычно не нужны — после Фазы 2 остановись с отчётом, если явно не указано иное.

## Шаг 1.3: Оценка полноты запроса (0–1)

- `1.0` — максимально конкретно
- `0.7–0.9` — понятно, но нужны уточнения
- `0.4–0.6` — тема ясна, цель размыта
- `0.0–0.3` — требуется существенное уточнение

Оценка определяет глубину следующего шага, но НЕ порождает вопросов вне конфига.

## Шаг 1.4: Исследование (циклическое)

Выполняется строго по `config.spec.research`:

| Поле | Дефолт | Что делать |
|------|--------|-----------|
| `research.memory` | `true` | `memory_search` по теме, контексту, решённым проблемам проекта |
| `research.projectFiles` | `true` | `read` + `bash` (grep/find): архитектура, стек, паттерны, смежные модули |
| `research.webSearch` | `true` | `web_search` (доки, best practices) → `web_reader` для глубокого чтения лучших результатов |
| `research.minQuality` | `0.8` | целевой средний балл качества раунда исследования |

Порядок: внутренние источники (memory → project) → внешние (web) → синтез.

**Оценка качества раунда** (по 4 критериям, 0–1 каждый: полнота охвата, актуальность,
разнообразие перспектив, практическая применимость):

- средний балл ≥ `research.minQuality` → переход к интервью;
- средний балл < `research.minQuality` → ещё один раунд по слабым направлениям (максимум 3 раунда; после третьего — продолжай с тем, что есть, зафиксировав пробелы в спеке).

Фиксируй источники: URL для веб-результатов, пути для файлов — они идут в
«Приложение: Источники исследования» (`references/spec-template.md`).

## Шаг 1.5: Интервью — СТРОГО по конфигу (R-2 → конфиг)

Единственный разрешённый источник вопросов — `config.spec.interview`.

### Правила

1. **Динамические (импровизированные) вопросы запрещены.** Нельзя формулировать вопрос, которого нет в активном конфиге — ни через `question`, ни текстом в чате.
2. Раунды запускаются по `trigger`:
   - `"always"` — выполняется всегда;
   - `"on_gaps"` — выполняется **только если** после основного раунда и исследования остались пробелы, влияющие на секции спеки (нет данных для «Функций», NFR, рисков и т.п.). Пробелы сверяются со списком вопросов раунда: если вопрос раунда не закрывает ни один пробел — раунд пропускается целиком.
3. За один вызов `questionnaire` — не более `config.spec.interview.maxQuestionsPerRound` вопросов. Если в раунде вопросов больше — разбей на несколько вызовов в порядке следования.
4. **`required: true`** — вопрос без опции «Пропустить», ответ обязателен. Нельзя перейти к генерации спеки, оставив required-вопрос без ответа (пользователь может дать свободный ответ через `allowOther`).
5. **`required: false`** — к вопросам добавляется опция `{ value: "skip", label: "Пропустить" }`.
6. `allowOther: true` — оставь возможность свободного ввода (questionnaire делает это автоматически опцией «Type something...»).
7. Вопросы подаются через `questionnaire` (серия, таб-навигация) в формате:

```
questionnaire({
  questions: [
    {
      id: "<question.id>",        // как в конфиге
      label: "<question.label>",  // как в конфиге
      prompt: "<question.prompt>",// как в конфиге
      options: <question.options>, // как в конфиге (+ "Пропустить" для required: false)
      allowOther: <question.allowOther>
    }
  ]
})
```

### Цикл после интервью

1. Интегрируй ответы в накопленную информацию.
2. Если ответы открыли новые направления — вернись к Шагу 1.4 (точечное исследование, без повторов).
3. Если после этого остались пробелы — запусти раунды с `trigger: "on_gaps"` (если ещё не запускались).
4. Пробелы, не покрытые ни одним вопросом конфига, **не спрашиваются**: заполни их обоснованными допущениями и явно перечисли в спеке (секция «Компромиссы» или «Примечания» функции).

### Дефолт-конфиг (пример раундов)

- `round-1` «Скоуп» (`trigger: "always"`): target_users (необязательный), success_criteria (**обязательный**), constraints (необязательный).
- `round-2` «Детали» (`trigger: "on_gaps"`): список вопросов пуст в дефолте — раунд пропускается (пустой список = нет вопросов = нет вызова questionnaire).

## Шаг 1.6: Генерация спецификации

1. Определи slug фичи: kebab-case из названия (например, `notification-system`).
2. Сформируй путь: `docs/specs/spec_<slug>_<YYYY-MM-DD>.md`.
3. Создай директорию: `mkdir -p docs/specs/`.
4. Заполни шаблон `references/spec-template.md` на основе исследования и ответов интервью. Критично для фазы роадмапы:
   - секция **«Функции»** — структурированные записи `F-1..F-N` с полями Описание / Приоритет / Слой / Зависимости;
   - приоритеты — `P0-P3` или MoSCoW; MoSCoW при желании можешь сразу записать через маппинг `config.roadmap.priorityMapping` (Must Have → P0, Should Have → P1, Could Have → P2, Won't Have → exclude);
   - слой — ровно один из `API | UI | storage | model | integration | business | cli`;
   - функция не смешивает слои (иначе раздели на две записи).
5. Сохрани файл, сообщи путь в чат.
6. Критерии готовности спеки: нет безответных required-вопросов; исследование ≥ `minQuality` (или исчерпаны 3 раунда); секция «Функции» непустая; все пробелы либо закрыты, либо зафиксированы как допущения.

После генерации → **Фаза 2: Lavish-аппрув спеки** (`references/lavish-approval.md`).
