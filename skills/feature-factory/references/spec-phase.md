# Фаза 2: Спецификация

> Детализация фазы 2 скилла feature-factory. База: скилл research-spec-generator
> (`skills/research-spec-generator/SKILL.md`), переведённый на kickoff-управление:
> интерактивные точки исходного скилла (R-1..R-3) закрыты авто-детекцией, единым
> kickoff-опросом (Фаза 1) и Lavish-аппрувом. Аргумент фазы — описание фичи свободным
> текстом (аргумент запуска `/skill:feature-factory`). Лёгкое исследование уже выполнено
> в Фазе 1 (Kickoff), ответы пользователя — в `decisions.json`.

## Маппинг интерактивных точек research-spec-generator → kickoff/автоматика

| # | Точка в исходном скилле | Было | Стало в feature-factory |
|---|------------------------|------|------------------------|
| R-1 | Вопрос «Какой тип запроса?» (`question`, 6 опций) | интерактив | `config.spec.autoDetectType: true` → тип определяется автоматически по описанию; уведомление в чат. Список типов — фиксированная логика скилла (таблица ниже), не настройка |
| R-2 | Раунды уточняющих вопросов (`questionnaire`, импровизированные вопросы) | интерактив | Единый kickoff-опрос (Фаза 1, таб «Скоуп»): контекстные вопросы генерирует агент ПОСЛЕ исследования; ответы персистятся в `decisions.scope` / `decisions.specAnswers`. Вопросов в этой фазе нет |
| R-3 | Финальное подтверждение «Готовы создать спецификацию?» (`question`) | интерактив | Удалено. Роль подтверждения выполняет Lavish-аппрув спеки (Фаза 3, `config.lavish.specApproval`) |

## Шаг 2.1: Зафиксировать исходный запрос

Сохрани аргумент запуска как «Ядро идеи» — отправную точку всего процесса. Если запуск
resumable (аргумент = путь к спеке или roadmap), эта фаза пропускается — см. «Обзор» в SKILL.md.

## Шаг 2.2: Категоризация запроса (R-1 → авто-детекция)

Тип запроса определяется из фиксированного набора (логика скилла, не конфиг):

| Тип | Признаки |
|-----|----------|
| `feature` | функционал для существующей системы |
| `project` | создание с нуля |
| `modification` | изменение существующего поведения |
| `integration` | соединение систем |
| `optimization` | улучшение характеристик |
| `research` | изучение технологии/подхода |

- Если `config.spec.autoDetectType: true` — определи тип сам по контексту описания и **сообщи его в чат** (не вопросом).
- Если `config.spec.autoDetectType: false` — авто-детекция отключена: используй тип `feature` (безопасный дефолт), зафиксируй допущение в спеке (метаданные «Тип»). **Вопрос пользователю запрещён** — вопросы остались в kickoff (Фаза 1).
- Для `research` спека создаётся по исследовательскому шаблону (см. research-spec-generator, шаблон «Исследование»); роадмапа/pipeline для него обычно не нужны — после Фазы 3 остановись с отчётом, если явно не указано иное.

## Шаг 2.3: Оценка полноты запроса (0–1)

- `1.0` — максимально конкретно
- `0.7–0.9` — понятно, но нужны уточнения
- `0.4–0.6` — тема ясна, цель размыта
- `0.0–0.3` — требуется существенное уточнение

Оценка определяет глубину следующего шага, но НЕ порождает вопросов: уточнения уже собраны
в kickoff (Фаза 1, таб «Скоуп»); что не собрано — закрывается допущениями (Шаг 2.5).

## Шаг 2.4: Исследование (циклическое)

Выполняется строго по `config.spec.research`:

| Поле | Дефолт | Что делать |
|------|--------|-----------|
| `research.memory` | `true` | `memory_search` по теме, контексту, решённым проблемам проекта |
| `research.projectFiles` | `true` | `read` + `bash` (grep/find): архитектура, стек, паттерны, смежные модули |
| `research.webSearch` | `true` | `web_search` (доки, best practices) → `web_reader` для глубокого чтения лучших результатов |
| `research.minQuality` | `0.8` | целевой средний балл качества раунда исследования |

Порядок: внутренние источники (memory → project) → внешние (web) → синтез. Лёгкое
исследование Фазы 1 — база: здесь оно углубляется до генерации спеки, повторы уже
пройденных запросов не нужны.

**Оценка качества раунда** (по 4 критериям, 0–1 каждый: полнота охвата, актуальность,
разнообразие перспектив, практическая применимость):

- средний балл ≥ `research.minQuality` → переход к Шагу 2.5;
- средний балл < `research.minQuality` → ещё один раунд по слабым направлениям (максимум 3 раунда; после третьего — продолжай с тем, что есть, зафиксировав пробелы в спеке).

Фиксируй источники: URL для веб-результатов, пути для файлов — они идут в
«Приложение: Источники исследования» (`references/spec-template.md`).

## Шаг 2.5: Ответы kickoff (R-2 → Фаза 1, таб «Скоуп»)

Вопросов пользователю в этой фазе НЕТ: все контекстные уточнения спеки были собраны
единым kickoff-опросом (Фаза 1) — это единственное место, где допустимы
импровизированные вопросы. Здесь ответы только потребляются:

1. Прочитай `decisions.json` (`.fan/feature-factory/<slug>/decisions.json`; он существует —
   kickoff обязателен перед этой фазой, см. «Обзор» SKILL.md).
2. **`decisions.scope`** — нормализованные решения по скоупу: границы фичи (`boundaries`),
   критерии успеха (`successCriteria`), ограничения/зависимости (`constraints`),
   целевые пользователи (`targetUsers`) → идут в секции «Обзор», «Критерии успеха»,
   «Ограничения» и в критериях приёмки функций.
3. **`decisions.specAnswers`** — сырые ответы на контекстные вопросы (ключи = id вопросов) →
   дополнительный материал для секций спеки.
4. **Пробелы** (что не покрыто вопросами kickoff и исследованием) НЕ спрашиваются:
   заполни обоснованными допущениями и явно перечисли в спеке (секция «Компромиссы»
   или «Примечания» функции).

## Шаг 2.6: Генерация спецификации

1. Определи slug фичи: kebab-case из названия (например, `notification-system`).
2. Сформируй путь: `docs/specs/spec_<slug>_<YYYY-MM-DD>.md`.
3. Создай директорию: `mkdir -p docs/specs/`.
4. Заполни шаблон `references/spec-template.md` на основе исследования и ответов kickoff.
   Критично для фазы роадмапы:
   - секция **«Функции»** — структурированные записи `F-1..F-N` с полями Описание / Приоритет / Слой / Зависимости;
   - приоритеты — `P0-P3` или MoSCoW (записываются как есть; MoSCoW → P0-P3 переводится в Фазе 4 по фиксированному маппингу формата — таблица в `references/roadmap-phase.md`);
   - слой — ровно один из `API | UI | storage | model | integration | business | cli`;
   - функция не смешивает слои (иначе раздели на две записи).
5. Сохрани файл, сообщи путь в чат.
6. Критерии готовности спеки: все поля `decisions.scope` отражены (или помечены как допущения); исследование ≥ `minQuality` (или исчерпаны 3 раунда); секция «Функции» непустая; все пробелы либо закрыты, либо зафиксированы как допущения.

После генерации → **Фаза 3: Lavish-аппрув спеки** (`references/lavish-approval.md`).
