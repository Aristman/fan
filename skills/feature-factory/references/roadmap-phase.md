# Фаза 4: Роадмапа

> Детализация фазы 4 скилла feature-factory. База: скилл feature-roadmap v1.3
> (`skills/feature-roadmap/SKILL.md`), переведённый на kickoff-управление: интерактивные
> точки исходного скилла (M-1..M-6) закрыты аргументом запуска, решениями kickoff
> (`decisions.roadmap.*`) и Lavish-аппрувом.
> Вход: путь к спеке `docs/specs/spec_<slug>_<YYYY-MM-DD>.md` (из Фаз 2–3) или переданный
> пользователем путь/slug (resumable-запуск). Решения по этапам — только из
> `decisions.roadmap` (`.fan/feature-factory/<slug>/decisions.json`, Фаза 1); вопросов нет.

## Маппинг интерактивных точек feature-roadmap → kickoff/автоматика

| # | Точка в исходном скилле | Было | Стало в feature-factory |
|---|------------------------|------|------------------------|
| M-1 | Выбор входа (путь/имя/описание) при неоднозначности (`question`) | интерактив | Аргумент запуска resumable. При неоднозначности (несколько спек по slug) — берётся самая свежая по дате в имени файла, уведомление в чат |
| M-2 | Предложение slug для свободного описания | интерактив | Slug выводится автоматически из названия спеки; уведомление в чат |
| M-3 | Вопрос «На какие этапы разбить?» (mvp-first / core-integration / custom) | интерактив | `decisions.roadmap.stageStrategy` — ответ собран в kickoff (Фаза 1, таб «Роадмапа»); отсутствует → безопасный дефолт `mvp-first` + запись в отчёт |
| M-4 | Вопрос «Какой приоритет у функции?» для каждой функции | интерактив | Приоритеты берутся из секции «Функции» спеки по **фиксированному** маппингу формата (таблица ниже) — это часть формата roadmap, не настройка |
| M-5 | Вопрос при превышении лимита этапов (делегировать/сократить/продолжить) | интерактив | `decisions.roadmap.onStageLimitExceeded` — ответ собран в kickoff (таб «Роадмапа»); отсутствует → безопасный дефолт `delegate` + запись в отчёт |
| M-6 | Финальный вопрос «Roadmap создан. Что дальше?» | интерактив | Удалён. Роль фидбека выполняет Lavish-аппрув роадмапы (Фаза 5, `config.lavish.roadmapApproval`) |

## Шаг 4.1: Получить и распарсить спеку

1. Определи вход:
   - путь к `spec_*.md` из аргумента → читать напрямую;
   - slug → `find docs/specs/ docs/features/ -name '*<slug>*'`; несколько совпадений → самая свежая по дате `YYYY-MM-DD` в имени, уведомление в чат;
   - свободное описание → фаза пропускается (нужны Фазы 1–2): при resumable-запуске по описанию роадмапа не может быть построена без спеки — выполни Фазы 1–3, затем вернись сюда.
2. Прочитай спеку. Извлеки:
   - **slug** — из метаданных или имени файла;
   - **функции** — из структурированной секции «Функции» (`F-1..F-N` с полями Описание/Приоритет/Слой/Зависимости). Спека feature-factory содержит эту секцию обязательно; для внешних спек (созданных не feature-factory) — извлекай функции по заголовкам и спискам, как в исходном feature-roadmap, и применяй правила обособленности ниже;
   - **NFR, риски, сценарии** — для критериев приёмки и E2E;
   - контекст скоупа — `decisions.scope` из `decisions.json` (границы фичи, критерии успеха, ограничения) — для формулировок целей этапов и E2E-сценариев.

## Шаг 4.2: Формализация приоритетов (M-4 → фиксированный маппинг формата)

Переведи приоритеты из спеки в P0–P3 по **фиксированному** маппингу (часть формата
roadmap-файла, в конфиге не настраивается):

| Значение в спеке | Маппинг (фиксированный) |
|------------------|-------------------------|
| `Must Have` | `P0` — критично (без этого фича не имеет смысла) |
| `Should Have` | `P1` — высокий |
| `Could Have` | `P2` — средний |
| `Won't Have` | `exclude` — не попадает в roadmap (остаётся в спеке с обоснованием) |

Приоритет `P0-P3` в спеке маппится сам на себя напрямую. Другие метки (кастомные labels)
— сверь по смыслу с ближайшим уровнем MoSCoW, допущение пометь `<!-- inferred -->` в
блоке «Допущения» шапки roadmap (вопрос пользователю не задаётся).

## Шаг 4.3: Проверка обособленности функций

Каждая функция из спеки проверяется по чеклисту (база: feature-roadmap v1.3, rules обособленности):

- [ ] Ровно один слой (поле «Слой» из спеки; при внешней спеке — определить по содержанию)
- [ ] Помещается в 1–3 TDD-теста
- [ ] Имеет 2–3 критерия приёмки (вывести из описания + NFR + `decisions.scope.successCriteria`)
- [ ] Самостоятельная ценность или чёткая техническая ответственность
- [ ] SMART-формулировка

**Автоматическое разбиение без вопросов** (замена эвристики 2.2.1 исходного скилла):

- Функция смешивает слои (в спеке так быть не должно; во внешней спеке — бывает) → раздели на N записей по слоям, ID получат суффиксы (`F-1` → `F-1a`, `F-1b`, `F-1c`), уведомление в чат.
- Описание > 300 слов или > 3 пунктов → `too_large_candidate`: раздели по смысловым частям (виджеты, провайдеры, подпункты).
- Смешение > 1 типа сущности («управление пользователями и ролями») → раздели по сущностям.

## Шаг 4.4: Этапы (M-3 → decisions.roadmap.stageStrategy)

Стратегия этапов берётся из `decisions.roadmap.stageStrategy` (собрана в kickoff, таб
«Роадмапа»; отсутствует → безопасный дефолт `mvp-first` + запись в отчёт, НЕ вопрос):

| Стратегия | Логика распределения по этапам |
|-----------|-------------------------------|
| `mvp-first` | Этап 1 = MVP (все P0 + минимум зависимостей), Этап 2 = расширение (P1), Этап 3+ = полировка (P2, P3) |
| `core-integration` | Этап 1 = ядро/данные (storage, model, API-базис), Этап 2 = интеграция (API, INTEG, BIZ), Этап 3+ = продвинутые (UI-обвязка, P2/P3, cli) |
| `<кастомная строка>` | Свободный вариант пользователя из kickoff: интерпретируй текст как описание логики распределения; неоднозначная интерпретация → ближайшая встроенная (`mvp-first`), допущение — в отчёт. Вопрос не задаётся |

Правила группировки:

1. Зависимости обязательны к уважению: функция не попадает в этап раньше своих зависимостей.
2. P0-функции должны попасть в этап 1 (иначе пересмотри распределение — правило 4 исходного скилла).
3. Внутри этапа функции сортируются по приоритету (P0 → P1 → P2 → P3).
4. Присвой ID `F-X.Y`: X = номер этапа, Y = порядковый номер в этапе (переприсвоение ID из спеки; в шапке roadmap зафиксируй соответствие исходным ID спеки).

**Минимум 2 этапа, оптимум 3–5, допустимо 6–8.**

## Шаг 4.5: Лимиты

| Лимит | Поле конфига | Дефолт |
|-------|--------------|--------|
| Этапов всего | `config.roadmap.maxStages` | 8 |
| Функций всего | `config.roadmap.maxFunctions` | 15 |
| Функций на этап | `config.roadmap.functionsPerStage` | [3, 30] |

- Этапов > `maxStages` → сработало `decisions.roadmap.onStageLimitExceeded` (см. ниже).
- Функций > `maxFunctions` → фиксируется предупреждение ⚠️ в шапке roadmap (продолжение допустимо, т.к. вопроса пользователю нет; при `onStageLimitExceeded: "delegate"` — действует delegate-сценарий и для этого случая).
- Функций в этапе вне `functionsPerStage` → перебалансируй этапы в пределах стратегии.

### onStageLimitExceeded (M-5 → decisions.roadmap.onStageLimitExceeded)

Собрано в kickoff (таб «Роадмапа»); отсутствует → безопасный дефолт `delegate` + запись в отчёт.

| Значение | Действие |
|----------|----------|
| `"delegate"` (дефолт) | Делегировать разбиение: `delegate_task(agent="plan", task="Разбей спеку <path> на 2–3 дочерних спецификации по подсистемам...")` → план дочерних спек в чат; roadmap для дочерних спек создаётся следующими запусками (`/skill:feature-factory docs/specs/spec_<slug>-part-N_*.md`). Текущий запуск останавливается с отчётом |
| `"truncate"` | Сократить до первых `maxStages` этапов (по приоритетам), остальные функции перечислить в секции «Отложено» roadmap |
| `"warn"` | Продолжить со всеми этапами, блок ⚠️ «Предупреждения» в шапке roadmap |

Все варианты — с уведомлением в чат; **вариант «спросить пользователя» отсутствует намеренно**. Значение вне `{delegate, truncate, warn}` трактуй как `"delegate"`.

## Шаг 4.6: Пробелы в спеке (фиксированное поведение)

Недостающие поля функций (приоритет, слой, зависимости) выводятся из контекста спеки —
вопрос пользователю не задаётся ни при каких условиях:

- каждое выведенное значение пометь в roadmap `<!-- inferred -->`;
- перечисли выведенное в блоке «Допущения» шапки roadmap;
- если обязательные поля секции «Функции» отсутствуют настолько, что функция не восстановима
  по контексту — остановка с отчётом (нужна спека с заполненной секцией).

## Шаг 4.7: Генерация roadmap.md

1. `mkdir -p docs/features/<slug>/`.
2. Если `docs/features/<slug>/roadmap.md` уже существует — **не перезаписывай молча**: если это resumable-запуск и roadmap соответствует текущей спеке (совпадает набор F-X.Y), обнови его; иначе сохрани существующий и остановись с отчётом о конфликте (выбор без вопроса: приоритет у существующего артефакта).
3. Сгенерируй roadmap по структуре ниже (база: `skills/feature-roadmap/references/roadmap-template.md`).

### Обязательные поля карточки функции (нужны pipeline-у в Фазе 6)

```markdown
#### ☐ <F-X.Y>: <Название функции>
- **Приоритет:** P0|P1|P2|P3
- **Слой:** [API]|[UI]|[DATA]|[INTEG]|[BIZ]|[CLI]  ← ровно один (маппинг из спеки: API→[API], UI→[UI], storage/model→[DATA], integration→[INTEG], business→[BIZ], cli→[CLI])
- **Описание:** <SMART-описание из спеки>
- **Зависимости:** <F-ID других функций> или (none)
- **TDD-тесты:**  ← ровно 1-3
  - [ ] **TC-F-X.Y-1:** <название — конкретное и проверяемое>
    - *Условие:* <предусловие>
    - *Шаги:* <что делает тест>
    - *Ожидаемый результат:* <измеримый результат: статус-код, состояние, значение>
- **Red-тест:** <ID TC, который падает первым, и почему>
- **Refactor-цели:** <что улучшить после Green> или (none) с обоснованием
- **Критерии приёмки:**  ← ровно 2-3, SMART
  1. <измеримое условие>
  2. <критерий 2>
- **Ожидаемый результат:** <конкретный артефакт — файл, endpoint, компонент>
- **Оценка объёма:** S / M / L / XL (XL = триггер разбиения до записи roadmap)
```

### Обязательные поля этапа (нужны phase-gate в Фазе 6)

```markdown
## <Этап X: Название>

**Цель:** <SMART-цель этапа>
**Приоритет функций:** <диапазон P>
**E2E-сценарий этапа:** <1–2 сквозных сценария: Условие/Шаги/Ожидаемый результат>
**Smoke-критерий этапа:** <один быстрый тест завершённости этапа>
```

TDD-тесты нумеруются `TC-F-X.Y-N` — pipeline парсит именно этот формат. Тесты покрывают
happy path, edge case, error case.

4. Добавь служебные секции: Сводка (счётчики по приоритетам), Легенда (✅/☐/⏳/❌), Полный чеклист по приоритетам, Граф зависимостей (проверь отсутствие циклов), блок ⚠️ «Предупреждения» (если сработал warn), «Допущения» (если были inferred-поля), «Делегирование» (если применимо).
5. Прочитай результат и проверь: все функции из спеки присутствуют (кроме `exclude`), лимиты соблюдены/подтверждены предупреждениями, обособленность, SMART, Red-тест и Refactor-цели у каждой функции, E2E + Smoke у каждого этапа, нет циклов в зависимостях.

После генерации → **Фаза 5: Lavish-аппрув роадмапы** (`references/lavish-approval.md`).
