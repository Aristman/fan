# feature-pipeline — TDD-пайплайн разработки фичи

Автоматизирует полный цикл разработки фичи от roadmap до закоммиченного,
протестированного и задокументированного кода. Проходит по roadmap этап за этапом,
функция за функцией, для каждой выполняя полный TDD-цикл.

<!-- worker:exclude-start -->
## Когда использовать

- Есть roadmap фичи (docs/features/<slug>/roadmap.md) и нужно реализовать всю фичу
- Нужен автоматизированный TDD-конвейер: план → код → верификация → тесты → коммит
- Требуется гарантированное качество: каждая функция верифицируется перед коммитом
- Нужен финальный отчёт с результатами по каждой функции

## Когда НЕ использовать

- Нет roadmap (сначала используйте feature-roadmap для его создания)
- Нужно реализовать только одну функцию из roadmap (укажите её вручную)
- Есть только идея без спецификации (сначала research-spec-generator, потом feature-roadmap)
- Не нужно ветвление и коммиты (просто правка кода)
- Нужен полный пакет документов разработки (используйте dev-docs-pack)

## Парсинг входных данных

Skill принимает аргументы через `/skill:feature-pipeline <args>`:

1. **Slug фичи:**
   ```
   /skill:feature-pipeline notification-system
   ```
   Искать roadmap: `docs/features/notification-system/roadmap.md`

2. **Путь к roadmap:**
   ```
   /skill:feature-pipeline docs/features/notification-system/roadmap.md
   ```
   Читать прямой путь.

3. **Без аргументов:**
   ```bash
   # Найти все roadmap
   find docs/features/ -name "roadmap.md" -type f 2>/dev/null
   ```
   Если найден 1 — использовать его. Если несколько — спросить через `question`.

4. **Если аргумент содержит `.md`** — считать путём к файлу. Иначе — считать slug.

## Процесс

### Фаза 0: Инициализация

**0.1 Прочитать и распарсить roadmap**

```bash
# Если slug:
read docs/features/<slug>/roadmap.md

# Если путь:
read <path>
```

Распарсить:
- **Название фичи** — из заголовка `# Roadmap: <Название>`
- **Slug** — имя директории (`docs/features/<slug>/`)
- **Этапы** — разделы `## Этап N: <Название>`
- **Функции** — пункты с `#### ☐ <ID>: <Название>` внутри каждого этапа
- **TDD-тесты** — `**TC-<ID>-N:** <название>` с условиями и ожидаемыми результатами
- **Критерии приёмки** — `**Критерии приёмки:**` со списком
- **Зависимости** — `**Зависимости:**` с перечислением ID

Для каждой функции собрать структуру:
```
{
  id: "F-1.1",
  name: "...",
  priority: "P0",
  description: "...",
  stage: 1,
  tests: [ { id: "TC-1.1-1", name: "...", condition: "...", steps: "...", expected: "..." } ],
  criteria: ["...", "..."],
  dependencies: ["F-1.0"],
  status: "☐"  // ☐ ⏳ ✅ ❌
}
```

**0.2 Проверить статусы**

- Если в roadmap есть уже выполненные функции (✅) — спросить, переделать или пропустить
- Если roadmap пустой (нет функций) — сообщить об ошибке

**0.3 Создать feature-ветку**

```bash
# Определить текущую ветку
git branch --show-current

# Если не в master/develop:
git checkout master  # или develop
git pull

# Создать feature-ветку
git checkout -b feature/<slug>
```

**0.4 Установить slug фичи**

Если slug не определён — извлечь из пути к roadmap (директория после `docs/features/`).

**0.5 Создать pipeline-report.md**

```bash
mkdir -p docs/features/<slug>/plans/
```

```markdown
# Pipeline Report: <название фичи>

> **Дата:** YYYY-MM-DD HH:MM
> **Ветка:** feature/<slug>

## Сводка

| Метрика | Значение |
|---------|----------|
| Всего функций | <N> |
| Реализовано | 0 |
| Провалено | 0 |
| Коммитов | 0 |

## Функции

_(будет заполнено по ходу работы)_

## Проблемы

_(пусто)_

## Изменённые файлы

_(пусто)_

## Документация

_(пусто)_
```

---

### Фазы 1..N: Для каждого этапа roadmap

Для каждого этапа по порядку:
- Сортировать функции внутри этапа: сначала P0, потом P1, P2, P3
- Учитывать зависимости: если функция зависит от другой — та должна быть выполнена первой
- Если функция уже выполнена (✅) — пропустить

Для каждой функции выполнить шаги A-F:

---

#### Шаг A: План

**A.1 Прочитать контекст**

```bash
# Прочитать TDD-тесты для функции из roadmap
# Прочитать зависимости (уже реализованные функции)
# Исследовать кодовую базу для понимания архитектуры
```

**A.2 Запустить explore для контекста кодовой базы**

```
delegate_task({
  agent: "explore",
  task: "Исследуй кодовую базу проекта для реализации функции <id>: <name> из roadmap.
         Найди: существующую архитектуру, похожие реализации, файлы, которые нужно
         изменить. Путь к roadmap: docs/features/<slug>/roadmap.md.
         slug: <slug>"
})
```

**A.3 Запустить plan для проектирования**

```
delegate_task({
  agent: "plan",
  task: "Спроектируй реализацию функции <id>: <name>.
         Данные: roadmap в docs/features/<slug>/roadmap.md.
         TDD-тесты: <перечислить TC-<ID>-1,2,3 с условиями и ожидаемыми результатами>
         Slug: <slug>.
         Определи: какие файлы создать, какие изменить, архитектуру, сигнатуры функций.
         Учти зависимости от: <dependencies>"
})
```

**A.4 Записать план**

```bash
mkdir -p docs/features/<slug>/plans/
```

```markdown
# Plan: <ID> — <Name>

## Анализ
<из plan worker'а>

## Файлы для изменения
- <file1>: <что делать>
- <file2>: <что делать>

## Архитектура
<детали>

## Риски
<если есть>
```

**Критерий:** План утверждён и записан в `docs/features/<slug>/plans/<id>.md`.

---

#### Шаг B: Реализация

**B.1 Обновить статус в roadmap**

```markdown
#### ⏳ <ID>: <Name>
```

**B.2 Запустить implement**

```
delegate_task({
  agent: "implement",
  task: "Реализуй функцию <ID>: <Name> согласно плану.
         План: docs/features/<slug>/plans/<id>.md
         Roadmap: docs/features/<slug>/roadmap.md (TDD-тесты и критерии приёмки)
         Slug: <slug>
         Файлы для изменения: <file1>, <file2>
         
         Критерии приёмки:
         - <criteria1>
         - <criteria2>
         
         TDD-тесты:
         - TC-<ID>-1: <name> — условие: ..., ожидаемый результат: ...
         - TC-<ID>-2: ...
         
         Важно: код должен проходить все TDD-тесты при проверке."
})
```

**Критерий:** Код функции реализован и готов к верификации.

---

#### Шаг C: Верификация (цикл)

**C.1 Запустить verify**

```
delegate_task({
  agent: "verify",
  task: "Проверь реализацию функции <ID>: <Name>.
         Roadmap: docs/features/<slug>/roadmap.md (содержит TDD-тесты и критерии приёмки)
         Slug: <slug>
         
         TDD-тесты для проверки:
         - TC-<ID>-1: <name> — условие: ..., шаги: ..., ожидаемый результат: ...
         - TC-<ID>-2: ...
         - TC-<ID>-3: ...
         
         Критерии приёмки:
         - <criteria1>
         - <criteria2>
         
         Проверь:
         1. Код компилируется/парсится без ошибок
         2. Каждый TDD-тест проходится (мысленно или запуском)
         3. Каждый критерий приёмки выполнен
         4. Нет регрессий в существующем коде
         5. Архитектура соответствует плану
         
         Вердикт: PASS — всё ок, или FAIL — с конкретными замечаниями.
         Формат: начинай с VERDICT: PASS или VERDICT: FAIL"
})
```

**C.2 Анализ вердикта**

Из результата verify извлечь строку `VERDICT:`.

- **VERDICT: PASS** → переход к шагу D
- **VERDICT: FAIL** → исправить замечания:
  1. Проанализировать замечания из verify
  2. Запустить implement снова с указанием, что исправить
  3. Перейти к шагу C.1 (новая итерация верификации)
- **Счётчик итераций:** max 3 на функцию
  - Если 3 итерации и всё FAIL → пометить функцию ❌ в roadmap, записать в отчёт, спросить пользователя:
    ```
    question({
      question: "Функция <ID>: <Name> не прошла верификацию за 3 попытки. Что делаем?",
      options: [
        { label: "Пропустить", description: "Отметить ❌ и продолжить со следующей" },
        { label: "Ещё попытка", description: "Попробовать 4-й раз с моими комментариями" },
        { label: "Отмена", description: "Остановить пайплайн" }
      ]
    })
    ```

**C.3 Обновить roadmap**

- ✅ или ❌ в зависимости от результата

**Критерий:** Функция прошла верификацию (PASS) или помечена как ❌ с уведомлением пользователя.

---

#### Шаг D: Тестирование

**D.1 Создать/обновить юнит-тесты**

```
delegate_task({
  agent: "tests-impl",
  task: "Напиши юнит-тесты для функции <ID>: <Name>.
         Roadmap: docs/features/<slug>/roadmap.md (содержит TDD-тесты TC-<ID>-1,2,3)
         Slug: <slug>
         
         TDD-тесты для покрытия:
         - TC-<ID>-1: <условие> → <ожидаемый результат>
         - TC-<ID>-2: <условие> → <ожидаемый результат>
         - TC-<ID>-3: <условие> → <ожидаемый результат>
         
         Напиши тесты в стиле, принятом в проекте.
         Happy path, edge cases, error cases.
         Тесты должны быть запускаемыми."
})
```

**D.2 Запустить юнит-тесты**

```bash
# Команда запуска тестов зависит от проекта.
# Попробовать стандартные:
npm test 2>&1 || npx vitest run 2>&1 || npx jest 2>&1 || pytest 2>&1 || go test ./... 2>&1
```

- Если тесты не проходят: исправить и перезапустить
- Если тесты проходят: перейти к D.3

**D.3 Создать/обновить интеграционные тесты**

```
delegate_task({
  agent: "tests-impl",
  task: "Напиши интеграционные тесты для функции <ID>: <Name> 
         во взаимодействии с уже реализованными функциями: <list_of_implemented_ids>.
         Slug: <slug>.
         Тесты должны проверять, что функции корректно работают вместе.
         Используй стиль тестирования, принятый в проекте."
})
```

**D.4 Запустить интеграционные тесты**

Аналогично D.2. Если не проходят — исправить.

**Критерий:** Все тесты (юнит + интеграционные) проходят.

---

#### Шаг E: Коммит

```bash
git add -A
git commit -m "feat(<slug>): implement <ID> - <name>

- TDD-тесты: TC-<ID>-1, TC-<ID>-2, TC-<ID>-3
- Критерии приёмки: все выполнены
- Верификация: PASS (с N попытки)"
```

Запомнить SHA коммита:
```bash
git rev-parse --short HEAD
```

**Критерий:** Закоммичено с осмысленным сообщением.

---

#### Шаг F: Обновление отчёта

Добавить запись о функции в `pipeline-report.md`:

```markdown
### <ID>: <Name>
- **Статус:** ✅ Выполнуто или ❌ Провалено
- **Коммит:** <sha>
- **Верификация:** PASS (с N попытки)
- **Тесты:** <TC-1> ✅, <TC-2> ✅, <TC-3> ✅
- **Критерии приёмки:** Все выполнены / Частично
```

Обновить сводку в начале отчёта.

---

### Финальная фаза: Завершение

Когда все этапы пройдены (все функции обработаны):

#### Шаг G.1: Полная верификация фичи

```
delegate_task({
  agent: "verify",
  task: "Проведи ПОЛНУЮ верификацию фичи <slug>.
         Roadmap: docs/features/<slug>/roadmap.md
         Отчёт: docs/features/<slug>/pipeline-report.md
         
         Проверь:
         1. Все ли функции из roadmap реализованы (✅)?
         2. Каждая функция проходит свои TDD-тесты
         3. Каждая функция удовлетворяет критериям приёмки
         4. Нет регрессий в смежных модулях
         5. Архитектура целостна и консистентна
         6. Нет дублирования кода
         7. Нет очевидных дыр в безопасности или обработке ошибок
         8. Интеграция между функциями корректна
         
         Отдельно проверь:
         - Проект собирается/компилируется (npm run build, go build, etc.)
         - Все существующие тесты проходят
         
         Вердикт: VERDICT: PASS / FAIL / PARTIAL
         Если PARTIAL — перечисли, что именно не прошло."
})
```

Если FAIL или PARTIAL:
- Исправить проблемы через implement
- Повторить верификацию (max 3 итерации для финала)

#### Шаг G.2: Smoke-тестирование

```
delegate_task({
  agent: "tests-impl",
  task: "Напиши smoke-тест для фичи <slug>.
         Smoke-тест должен проверять основной сценарий использования фичи
         от начала до конца (happy path). 
         Slug: <slug>.
         Название фичи: <name> из roadmap.
         Описание: <description> из roadmap.
         
         Smoke-тест — это один тест, который проходит через все ключевые функции.
         Если проект больше (например, веб-сервер), smoke-тест может быть 
         скриптом, который запускает приложение и делает ключевой запрос."
})
```

#### Шаг G.3: E2E-тестирование (если применимо)

Если фича имеет пользовательский интерфейс или сетевое взаимодействие:

```
delegate_task({
  agent: "tests-impl",
  task: "Напиши e2e-тест для фичи <slug> проверяющий полный пользовательский сценарий.
         Slug: <slug>.
         Название: <name>.
         Если e2e-тесты не применимы к проекту — сообщи и пропусти."
})
```

#### Шаг G.4: Обновление документации

```
delegate_task({
  agent: "docs-impl",
  task: "Обнови документацию для фичи <slug>.
         Что обновить:
         1. README.md проекта — добавь информацию о новой фиче, если нужно
         2. CHANGELOG.md или аналог — добавь запись о новой фиче
         3. docs/features/<slug>/ — обнови roadmap.md (синхронизируй статусы)
         4. Дополни: обнови инлайн-документацию в коде, если были изменения API
         
         Slug: <slug>.
         Название фичи: <name>."
})
```

#### Шаг G.5: Обновить roadmap.md

Синхронизировать статусы в roadmap.md с фактическим состоянием:
- Все ☐ заменить на ✅ (реализованные) или ❌ (проваленные)
- Убедиться, что ⏳ нет (все обработаны)

```bash
# Обновить roadmap
edit docs/features/<slug>/roadmap.md
```

#### Шаг G.6: Финальный коммит

```bash
git add -A
git commit -m "feat(<slug>): finalize <slug>

- Full verification: PASS
- Smoke tests: PASS
- E2E tests: PASS / N/A
- Documentation: updated
- All <N> functions implemented"
```

Запомнить SHA.

#### Шаг G.7: Обновить финальный отчёт

Дополнить `pipeline-report.md`:

1. Обновить сводку
2. Добавить секцию **Финальная верификация**
3. Добавить **Изменённые файлы** (из git log)
4. Добавить **Проблемы** (если были)
5. Добавить **Документация** (какие файлы обновлены)
6. Добавить **Рекомендации** (если есть)

**Финальная структура отчёта:**

```markdown
# Pipeline Report: <Название фичи>

> **Дата:** YYYY-MM-DD HH:MM
> **Ветка:** feature/<slug>

## Сводка

| Метрика | Значение |
```

## Правила

1. **Одна функция за раз.** Не переходи к следующей, пока текущая не завершена (✅ или ❌).
2. **Учитывай зависимости.** Функция, от которой зависят другие, должна быть реализована первой.
3. **Максимум 3 попытки верификации на функцию.** После 3 FAIL — спросить пользователя.
4. **Каждый коммит — только одна функция.** Никогда не коммить несколько функций вместе.
5. **TDD-first.** Код пишется так, чтобы проходить TDD-тесты, указанные в roadmap.
6. **Не ломай существующее.** Перед каждой реализацией проверяй, что старые тесты всё ещё проходят.
7. **Документируй всё.** Каждый шаг (план, верификация) фиксируется в файлах.
8. **Не трогай roadmap пользователя.** Статусы ☐ ✅ ⏳ ❌ — единственное, что меняется в roadmap.md.
9. **Если пайплайн прерван** (crash, ошибка) — при новом запуске проверить статусы в roadmap и продолжить с последней незавершённой функции.
10. **Перед коммитом — git status.** Убедись, что нет неожиданных изменений.
