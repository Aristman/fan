# Research & Specification Generator

## Назначение

Принимает запрос пользователя на естественном языке, исследует тему из
множества источников, проводит итеративное интервьюирование для устранения
неопределённостей и создаёт файл спецификации в `docs/specs/`.

## Когда использовать

- Пользователь просит исследовать тему или технологию
- Пользователь хочет подготовить техническое задание
- Пользователь описывает идею для фичи/проекта и хочет получить спецификацию
- Пользователь хочет изучить предметную область перед разработкой

## Доступные инструменты

Для интерактивного диалога с пользователем используй tools `question` и `questionnaire` (расширение **fan-ask-answer**):

- **`question`** — один вопрос с вариантами. TUI рендерит список со стрелками, Enter для выбора, Esc для отмены. Автоматически добавляется опция "Type something..." для свободного ввода.
- **`questionnaire`** — серия вопросов с таб-навигацией (Tab/←→ между вкладками). Используй для сбора нескольких ответов за один вызов.

**Когда использовать:**
- Категоризация запроса, выбор подхода, подтверждение решения → `question`
- Раунд уточняющих вопросов (3–5 штук) → `questionnaire`
- Финальное подтверждение готовности → `question`

**Когда НЕ использовать:**
- Если вопрос открытый и не имеет очевидных вариантов — спрашивай текстом
- Если можешь решить сам — действуй

## Процесс

### Фаза 1: Инициализация

**1.1 Зафиксируй исходный запрос**

Сохраните запрос пользователя как «Ядро идеи». Это отправная точка всего процесса.

**1.2 Категоризируй запрос**

Используй tool `question` для интерактивного выбора типа:

```
question({
  question: "Какой тип запроса?",
  options: [
    { label: "Исследование", description: "Изучение технологии, подхода, предметной области" },
    { label: "Новая фича", description: "Функционал для существующей системы" },
    { label: "Новый проект", description: "Создание с нуля" },
    { label: "Модификация", description: "Изменение существующего поведения" },
    { label: "Интеграция", description: "Соединение систем" },
    { label: "Оптимизация", description: "Улучшение характеристик" }
  ]
})
```

Если уверен в типе по контексту — не спрашивай, определи сам.

**1.3 Оцени полноту запроса (0–1)**

- `1.0` — максимально конкретно
- `0.7–0.9` — понятно, но нужны уточнения
- `0.4–0.6` — тема ясна, цель размыта
- `0.0–0.3` — требуется существенное уточнение

---

### Фаза 2: Исследование (циклическая)

Повторяй эту фазу до достижения целевого качества.

#### 2.1 Поиск информации

Используй **все доступные инструменты** по приоритету:

1. **`memory_search`** — поиск в персистентной памяти проекта по теме, контексту, решённым проблемам
2. **`read`** + **`bash`** (grep, find) — изучение исходного кода, архитектуры, паттернов, зависимостей проекта
3. **`web_search`** — веб-поиск через Z.AI Search Engine. Используй для поиска документации, статей, best practices, сравнительных обзоров.
   - Параметры: `query` (обязательно), `count` (1-50), `recency_filter` (noLimit/oneDay/oneWeek/oneMonth/oneYear), `domain_filter` (ограничение по домену)
   - Примеры: `web_search({ query: "JWT best practices Spring Boot 2025", recency_filter: "oneYear" })`
   - Для официальной документации: `web_search({ query: "Express.js middleware guide", domain_filter: "expressjs.com" })`
4. **`web_reader`** — чтение и парсинг содержимого веб-страницы по URL. Используй после `web_search` для глубокого изучения конкретных страниц.
   - Параметры: `url` (обязательно), `return_format` (markdown/text), `with_links_summary`, `with_images_summary`, `no_cache`
   - Возвращает контент в markdown или plain text с заголовком, мета-данными и ключевыми словами
   - Пример: `web_reader({ url: "https://expressjs.com/en/guide/routing.html" })`

#### 2.2 Стратегия исследования

Выполняй поиск по этапам:

**Шаг 1 — Внутренние источники:**
1. `memory_search` — есть ли релевантный контекст, предыдущие исследования, решения?
2. Изучение структуры проекта (`read`, `bash`) — текущая архитектура, стек, паттерны

**Шаг 2 — Внешние источники (веб):**
3. `web_search` — официальная документация, статьи, best practices
4. `web_reader` — глубокое чтение релевантных страниц из результатов поиска
5. Повторный `web_search` с уточнёнными запросами при необходимости

**Шаг 3 — Синтез:**
6. Объедини данные из всех источников
7. Выяви противоречия и пробелы
8. Сформируй целостную картину

Для каждого источника записывай:
- Что найдено
- Насколько релевантно
- Какие вопросы вызывает
- URL источника (для веб-результатов)

#### 2.3 Оценка качества исследования

После каждого раунда исследования оцени:

| Критерий | Оценка (0–1) |
|----------|--------------|
| Полнота охвата темы | |
| Актуальность источников | |
| Разнообразие перспектив | |
| Практическая применимость | |

**Средний балл ≥ 0.8** — можно переходить к Фазе 3.
**Средний балл < 0.8** — продолжи исследование по слабым направлениям.

---

### Фаза 3: Анализ и составление уточнений

#### 3.1 Структурирование найденного

Организуй информацию по разделам:
- **Обзор** — ключевые понятия и суть
- **Технические детали** — архитектура, технологии, реализации
- **Преимущества и недостатки** — анализ альтернатив
- **Практические аспекты** — применимость в контексте проекта
- **Открытые вопросы** — что осталось невыясненным
- **Риски** — потенциальные проблемы

#### 3.2 Составление списка уточнений

Проанализируй собранные данные и составь список вопросов,
на которые **нельзя ответить из источников**:

1. **Блокирующие** — без ответа нельзя составить спецификацию
2. **Важные** — влияют на ключевые решения
3. **Рекомендательные** — улучшат качество, но не блокируют

#### 3.3 Представление результатов и уточняющие вопросы

**Сначала выеди пользователю краткое резюме текстом:**

```
## Результаты исследования

[Краткое резюме найденного — 3–5 предложений]

### Что удалось узнать
- [Факт 1]
- [Факт 2]
- [Факт 3]
```

**Затем используй tool `questionnaire` для уточняющих вопросов:**

Для каждого вопроса:
- `id` — уникальный идентификатор (латиница, snake_case)
- `label` — короткий ярлык для таба (1–2 слова)
- `prompt` — полный текст вопроса
- `options` — массив вариантов `{ value, label, description? }`
- Всегда добавляй последний вариант `{ value: "skip", label: "Пропустить" }` для некритичных вопросов
- Для **блокирующих** вопросов НЕ добавляй "Пропустить" — ответ обязателен

Пример:
```
questionnaire({
  questions: [
    {
      id: "notification_types",
      label: "Типы",
      prompt: "Какие типы уведомлений нужны?",
      options: [
        { value: "email+inapp", label: "Email + In-app" },
        { value: "all", label: "Email + Push + In-app" },
        { value: "inapp_only", label: "Только In-app" }
      ],
      allowOther: true
    },
    {
      id: "realtime",
      label: "Realtime",
      prompt: "Уведомления должны быть реального времени?",
      options: [
        { value: "yes", label: "Да, реального времени" },
        { value: "delayed", label: "Допускается задержка до 5 мин" },
        { value: "batch", label: "Пакетная отправка (ежедневно)" }
      ]
    },
    {
      id: "templates",
      label: "Шаблоны",
      prompt: "Нужна ли кастомизация шаблонов через админку?",
      options: [
        { value: "yes", label: "Да, через админку" },
        { value: "code_only", label: "Нет, только через код" }
      ],
      allowOther: true
    },
    {
      id: "analytics",
      label: "Аналитика",
      prompt: "Нужна ли аналитика доставки уведомлений?",
      options: [
        { value: "basic", label: "Базовая (статус доставки)" },
        { value: "detailed", label: "Детальная (открытия, клики)" },
        { value: "skip", label: "Пропустить" }
      ]
    }
  ]
})
```

**Правила:**
- Не более **5 вопросов** за один вызов `questionnaire`
- **Блокирующие** вопросы — без опции "Пропустить", ответ обязателен
- **Важные / Рекомендательные** — с опцией "Пропустить"
- Если вопрос открытый (нет очевидных вариантов) — задавай текстом, не через questionnaire
- Группируй по темам: сначала блокирующие, потом важные, потом рекомендательные

**После получения ответов от `questionnaire`** — обработай их и перейди к Фазе 4.
Не продолжай процесс, если блокирующие вопросы остались без ответа.

---

### Фаза 4: Обработка ответов (циклическая)

#### 4.1 Обработка ответа пользователя

После получения ответа:
1. Интегрируй ответы в накопленную информацию
2. Определи, нужны ли **дополнительные исследования** на основе новых данных

#### 4.2 Дополнительное исследование (если нужно)

Если ответы пользователя открыли новые направления:
- Вернись к **Фазе 2** с обновлённым запросом
- Фокусируйся на новых аспектах
- Не повторяй уже проведённое исследование

#### 4.3 Дополнительные уточнения (если нужно)

Если дополнительное исследование выявило новые неопределённости:
- Составь новый список уточнений
- Представь пользователю
- Повтори цикл

#### 4.4 Подтверждение готовности к спецификации

Перед переходом к Фазе 5 используй `question` для подтверждения:

```
question({
  question: "Все уточнения собраны. Готовы создать спецификацию?",
  options: [
    { label: "Да, создавать" },
    { label: "Ещё есть вопросы", description: "Вернуться к уточнениям" },
    { label: "Нужно больше исследований", description: "Дополнительный поиск по теме" }
  ]
})
```

Если пользователь выбрал дополнительные уточнения или исследования — вернись к соответствующей фазе.

Критерии перехода к Фазе 5:
- ✅ Нет **блокирующих** вопросов
- ✅ Все **важные** вопросы разрешены (или пользователь сознательно пропустил)
- ✅ Исследование покрывает тему на достаточном уровне
- ✅ Понятно **что** делается, **как** и **зачем**
- ✅ Пользователь подтвердил готовность

### Фаза 5: Создание спецификации

#### 5.1 Подготовка

1. Проверь существование директории `docs/specs/`, создай при необходимости:
   ```bash
   mkdir -p docs/specs/
   ```

2. Сформируй имя файла:
   - Префикс: `spec_`
   - Название: английское, слова через дефис
   - Дата: `YYYY-MM-DD`
   - Расширение: `.md`

   Примеры:
   - `docs/specs/spec_notification-system_2026-04-05.md`
   - `docs/specs/spec_jwt-authentication_2026-04-05.md`
   - `docs/specs/spec_migrate-to-postgres_2026-04-05.md`

3. Выбери шаблон спецификации по типу запроса.

#### 5.2 Шаблон: Исследование

Для запросов типа **Исследование** используется шаблон с разделами:
Метаданные, Цель исследования, Обзор (ключевые понятия, текущее состояние),
Детальный анализ, Сравнительный анализ, Выводы и рекомендации,
Риски, Дальнейшие шаги, Источники.

Полный шаблон: [`references/research-report-template.md`](references/research-report-template.md)

#### 5.3 Шаблон: Спецификация

Для запросов типа **Новая фича / Новый проект / Модификация / Интеграция / Оптимизация**
используется шаблон с разделами:
Метаданные, Обзор (цель, контекст, решение), Функциональные требования (функции,
сценарии, бизнес-правила), UI/UX требования, Нефункциональные требования
(производительность, безопасность, надёжность, масштабируемость),
Технические требования (стек, архитектура, интеграции), Данные,
Риски и митигация, Компромиссы, Приоритеты (MoSCoW), Следующие шаги.

Полный шаблон: [`references/spec-template.md`](references/spec-template.md)

#### 5.4 Сохранение

1. Заполни шаблон на основе всех собранных данных и ответов пользователя
2. Сохрани файл по сформированному пути
3. Сообщи пользователю путь к созданному файлу
4. Предложи проверить и внести правки при необходимости

## Правила

### Исследование
1. **Используй все инструменты** — `memory_search`, `read`, `bash`, `web_search`, `web_reader`
2. **Оценивай качество** каждого раунда исследования по 4 критериям
3. **Не повторяй** уже проведённое исследование без причины
4. **Фиксируй источники** — записывай URL для веб-результатов, пути для файлов
5. **`web_search` → `web_reader`** — сначала ищи, потом читай лучшие результаты
6. **Используй фильтры** — `domain_filter` для официальных доков, `recency_filter` для свежести

### Интервьюирование
5. **Не более 5–7 вопросов** за один раунд
6. **Приоритизируй** — сначала блокирующие, потом важные
7. **Давай варианты** ответов там, где это уместно
8. **Всегда ожидай ответа** — не продолжай без ответов на блокирующие вопросы
9. **Резюмируй** промежуточные выводы для проверки понимания
10. **Не делай предположений** — лучше спросить

### Спецификация
11. **Не создавай документ** пока интервью не завершено
12. **Выбирай шаблон** по типу запроса
13. **Адаптируй** — не все разделы нужны для каждого запроса
14. **Будь конкретен** — избегай абстракций без привязки к контексту

### Цикличность
15. **Исследование → Уточнения → Исследование → ...** — повторяй пока есть пробелы
16. **Новые ответы = новые исследования** — ответы могут открыть новые направления
17. **Знай когда остановиться** — нет блокирующих вопросов → создавай спецификацию

## Важные напоминания

1. **Это циклический процесс** — не пытайся завершить за один раунд
2. **Исследование информирует вопросы** — вопросы информируют исследование
3. **Качество важнее скорости** — лучше задать ещё один вопрос, чем написать плохую спецификацию
4. **Адаптируйся** — для исследования нужен другой шаблон, чем для ТЗ фичи
5. **Сохраняй контекст** — пользователь не должен повторять то, что уже сказал
6. **Веб-инструменты всегда доступны** — `web_search` и `web_reader` через Z.AI API
7. **Начинай с внутренних источников** (память, код), затем переходи к внешним (веб)
